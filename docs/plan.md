# Plan de développement — Slipways sur PC (raylib, portage littéral)

Objectif : reproduire *Slipways* (édition PICO-8) en C, jouable sur PC via [raylib](https://www.raylib.com/) en rendu logiciel (raylib sert uniquement de couche fenêtrage/présentation/entrée, aucune primitive raylib n'est utilisée pour dessiner).

Référence de gameplay : [`docs/design/slipways-mechanics.md`](design/slipways-mechanics.md). Idées d'amélioration hors scope : [`docs/after-v1.md`](after-v1.md) (écrit pour l'ancien plan manette PSX — à relire avec un œil critique, certaines idées n'ont plus de sens une fois qu'on porte `btn()`/la souris PICO-8 tels quels).

## Contexte et changement de cap

Le plan précédent (portage direct PSX, réécriture en C à partir de la doc de design, conservé dans l'historique git) s'est heurté à un problème méthodologique de fond : une réécriture complète est très coûteuse à prouver correcte, faute d'oracle de référence pendant tout le développement.

Nouvelle stratégie : **porter `pico8/lua.lua` (le code source réel de la cartouche, pas juste une référence de lecture) fonction par fonction vers le C, en copiant la logique plutôt qu'en réécrivant depuis la doc de design.** Cible : PC, via raylib en rendu logiciel — un environnement de développement et de test immédiat, sans toolchain croisée ni émulateur.

**PSX est mis en pause, pas abandonné** : il ne sera repris qu'une fois obtenue une version PC pleinement jouable en C. Le C porté sur PC devient alors la base du portage PSX (au lieu de repartir d'une réécriture depuis la doc de design). Aucun travail PSX n'est engagé avant ce jalon.

`game/` (prototype Love2D from-scratch : `Spot`/`Camera`/`Panel`/`Probe`) a été supprimé : il incarnait l'ancienne approche « réécriture depuis la doc de design », explicitement abandonnée au profit du portage littéral décrit ici.

## Stratégie de portage : copie fonction par fonction, pas de réécriture

- `pico8/lua.lua` est minifié (noms de fonctions/variables réduits à 1-2 lettres). Chaque fonction portée en C **garde son nom minifié d'origine** (`ft()`, `->ra`, `->qe`, etc.) et est précédée en commentaire du **code Lua source exact** de cette fonction. La comparaison ligne à ligne entre le commentaire et le C juste en dessous est le principal moyen de vérifier la fidélité du portage (cf. Stratégie de test).
- Le mécanisme d'entités/dispatch que `lua.lua` se construit lui-même (`kv:jr` — système de classes par chaîne de prototypes, `hv`/`cv`/`cg` — collections d'entités indexées par tag, `dc()`/`mv()`/`lt()`/`he()` — dispatch par nom de méthode) est **porté littéralement**, pas réécrit en C idiomatique (pas de struct-par-type-d'entité + enum + switch). Les entités C portent un sac de champs optionnels (union/petite table clé-valeur) qui reproduit la forme dynamique des tables Lua ; `dc()`, `mv()`, `lt()`, `he()` sont portées quasi verbatim par-dessus cette structure.
- Renommer en clair est explicitement écarté (perdrait la traçabilité de diff contre la source) — les seuls ajouts sont des commentaires ponctuels quand une signification a été confirmée via `slipways-mechanics.md`.

## Fidélité numérique

Les nombres PICO-8 sont en virgule fixe 16.16, pas en flottant. Le portage C **émule ce type exactement** (dépassement/troncature identiques) ainsi que les algorithmes PICO-8 de `rnd()`, `sin()`, `cos()` (convention « tours » 0-1, signe inversé pour `sin`). Objectif : une graine donnée doit produire exactement la même galaxie/le même déroulé que l'original — pas une approximation en `double`.

## Périmètre de l'API PICO-8 à mimer

Scanné directement dans `lua.lua` (pas deviné, pas construit par anticipation) :

- **Dessin/entrée** : `cls`, `pset`, `spr`, `map`, `mset`, `sget`, `circ`, `circfill`, `rect`, `rectfill`, `line`, `print`, `camera`, `palt`, `fillp`, `btn` (D-pad — utilisé nativement par `qb:ph()` pour le déplacement caméra), `stat` (souris — `stat(32/33/34)`, plus quelques index annexes), `peek`, `poke`, `memcpy` (astuce de palette et décodage `unstash`).
- **Maths/listes/chaînes** (socle de la Phase 2, arithmétique fixe + primitives dynamiques — toutes explicitement affectées à la Phase 2 dans le détail de cette phase ci-dessous) : `sqrt`, `cos`, `sin`, `mid`, `flr`, `abs`, `rnd`, `sgn`, `band`, `bor`, `shl`, `add`, `del`, `all`, `foreach`, `sub`, `tostr`.
- **Explicitement hors périmètre** : `sfx`, `music` (son abandonné entièrement pour ce portage — deviennent des no-op dans la couche de mimétisme) ; tout le reste de l'API PICO-8 non listé ci-dessus n'est tout simplement pas appelé par `lua.lua` (`sspr`, `fget`/`fset`, `mget`, `sset`, `pal`, `cursor`, `color`, `flip`, `btnp`, `peek2/4`, `poke2/4`, `cartdata`, `dget`/`dset`, coroutines, `atan2`…) et n'est donc pas construit.

## Architecture : backend interchangeable sous une API fixe

`main.c` et toutes les fonctions portées n'appellent **jamais** raylib directement — uniquement la couche de mimétisme PICO-8 ci-dessus. Deux implémentations de cette même API existent, choisies au lien/à la compilation, sans toucher au code de jeu :

1. **Backend rendu logiciel + rejeu scripté** (Phases 1 à 4) : framebuffer 128×128/8 couleurs en mémoire, entrée lue depuis un `events.json` (position souris + boutons souris + les 4 booléens `btn()` D-pad, par frame — couvre exactement `stat(32/33/34)` et `btn(0-3)`), sortie dumpée en texte (format proche PPM, pas de PNG) pour être lisible directement par un LLM sans décodage d'image.
2. **Backend raylib interactif** (Phase 5) : fenêtre raylib réelle, entrée souris/clavier live, même framebuffer 128×128 uploadé comme texture et affiché à l'échelle. Inclut un **mode enregistrement** : chaque frame de la session, l'entrée live (souris + D-pad) est écrite dans un `events.json` au même format que celui rejoué par le Backend 1 — ce que l'humain vient de faire redevient un rejeu scripté que l'agent peut réexécuter et inspecter en headless, sans jamais avoir vu la session se dérouler.

## Stratégie de test

Une piste écartée après investigation : faire tourner `lua.lua` lui-même sous un interpréteur Lua standard comme oracle de différence (comparer chaque fonction portée à son original exécuté). Rejetée car :
- La syntaxe PICO-8 (`+=`, littéraux binaires `0b...`, `if (cond) stmt` sans `then`/`end`) est un problème mineur et mécanique (~76 occurrences, préprocesseur trivial à écrire).
- Le vrai problème : `lua.lua` embarque son propre mini-langage de description de données (`ob()`, un parseur caractère par caractère fait main) et un système de classes par chaîne de prototypes (`kv:jr`). Construire une seule entité de test réaliste exige d'avoir cette infrastructure et les singletons globaux (`dk`, `fm`) correctement amorcés — un chantier presque aussi lourd que le portage lui-même, avec le risque que des bugs dans l'oracle Lui-même invalident silencieusement la comparaison.

Stratégie retenue, à trois niveaux, alignée sur les phases :
- **Phase 2 (arithmétique/primitives dynamiques)** : tests unitaires C classiques, valeurs attendues calculées à la main (comportement documenté de PICO-8 pour `rnd`/`sin`/`cos`/débordement fixe). C'est aussi là que vivent les fonctions vraiment pures (opérations vectorielles `km`, géométrie `cl`/`ee`/`be`) — pas d'entité, pas d'état global, donc testables isolément sans le problème ci-dessus.
- **Phase 3 (portage fonction par fonction du reste)** : pas de test automatisé forcé — la comparaison entre le commentaire (source Lua exacte) et le C porté juste en dessous *est* la vérification.
- **Phase 4 (intégration)** : exécution headless pas à pas via le backend rejeu scripté (`events.json` en entrée, dump texte en sortie), lue par l'agent — invariants grossiers (nombre de planètes, crédits, pas de crash), pas de comparaison fine.
- **Phase 5** : test interactif par un humain via le backend raylib — premier moment où le jeu est réellement joué.

**Politique d'exécution** : jamais de fenêtre interactive lancée par l'agent, à aucune phase avant la 5. Seules des vérifications non-interactives sont permises (N frames puis sortie automatique, dump du framebuffer). Voir `CLAUDE.md`.

## Plan d'action

### Phase 1 — Interface PICO-8 minimale + rendu logiciel

Construire en C, sans dépendance raylib, l'interface de dessin/entrée listée ci-dessus (`cls`, `pset`, `spr`, `map`, `mset`, `sget`, `circ`, `circfill`, `rect`, `rectfill`, `line`, `print`, `camera`, `palt`, `fillp`, `btn`, `stat`, `peek`, `poke`, `memcpy`), backée par un framebuffer logiciel 128×128/8 couleurs. `main.c` charge automatiquement `sprite.png` et `map.json` (déjà extraits dans `pico8/`). Lecture d'un `events.json` de rejeu (souris + D-pad par frame). Sortie : dump texte du framebuffer (format simple, pas de PNG). Un petit programme C de démonstration exerce l'interface pour valider la boucle bout en bout avant de commencer le portage réel en Phase 3 : au moins un appel par catégorie (pixel `pset`, forme `line`/`rect`/`circ`, sprite `spr`, carte `map`, texte `print`), une lecture `btn`+`stat`, une frame pilotée par `events.json`, et un dump texte du framebuffer — le tout branché sur la cible `make test` que cette phase ajoute. `make test` fait des assertions précises sur le résultat, pas juste « le programme tourne » : après chaque appel de démonstration, les octets du framebuffer (ou les valeurs lues via `peek`/`memcpy`) attendus à des positions connues sont comparés à des valeurs de référence calculées à la main.

### Phase 2 — Arithmétique fixe & primitives dynamiques

Type fixe 16.16 (`+`, `-`, `*`, `/`, débordement identique à PICO-8), `rnd()`/`sin()`/`cos()`/`sqrt()`/`mid()`/`flr()`/`abs()`/`sgn()`/`band()`/`bor()`/`shl()` reproduisant les algorithmes PICO-8, opérations vectorielles (`km`), géométrie pure (`cl`/`ee`/`be`), primitives de liste (`add`/`del`/`all`/`foreach`) et de chaîne (`sub`/`tostr`), le mini-langage de description de données (`ob()`/`fi()`) et le mécanisme d'entités/dispatch qui en dépend directement (`kv:jr` appelle `ob()` dès sa première ligne — `hv`/`cv`/`cg`, `dc`, `mv`, `lt`, `he`), tous portés littéralement. Tests unitaires C pour les fonctions pures (arithmétique fixe, `rnd`/`sin`/`cos`/`sqrt`/`mid`/`flr`/`abs`/`sgn`/`band`/`bor`/`shl`, `km`, `cl`/`ee`/`be`, `add`/`del`/`all`/`foreach`, `sub`/`tostr`) ; pour `ob()`/`fi()`/`kv:jr`/`hv`/`cv`/`cg`/`dc`/`mv`/`lt`/`he`, pas de test unitaire fonction par fonction — vérifiés par comparaison source/port comme en Phase 3 (cf. Stratégie de test), plus un test de fumée dédié : définir 1-2 types d'entités factices via `ob()`/`kv:jr` et exercer `dc`/`mv`/`lt`/`he` dessus, branché sur la même cible `make test` que la Phase 1. Le test de fumée fait des assertions précises, pas juste « ça tourne » : `dc()`/`mv()` appellent bien la méthode attendue sur l'entité factice, et `lt()`/`he()` l'ajoutent/la retirent effectivement des collections `hv`/`cv`/`cg` concernées. Sortie de phase : ce test de fumée passe (avec ces assertions), en plus des tests unitaires ci-dessus.

### Phase 3 — Portage fonction par fonction

Chaque fonction de `lua.lua` restante est portée en C : nom minifié conservé, code Lua source collé en commentaire juste au-dessus, logique copiée (pas réécrite). Pas d'ordre de portage lié à une « tranche verticale » de fonctionnalités — la notion ne s'applique pas bien à une copie littérale d'un monolithe ; l'ordre suit plutôt les dépendances entre fonctions (ce qui est appelé avant ce qui appelle).

Une liste de suivi (portée / restante), groupée par vague de dépendances, est tenue à jour pendant toute la phase dans [`docs/portage-progress.md`](portage-progress.md) (fichier dédié plutôt qu'une section de ce plan : ~140 fonctions à suivre, ça alourdirait ce document). Checkpoint après chaque lot porté (un lot = une vague de dépendances du tracker ci-dessus) : le projet compile et `make test` passe toujours dans son ensemble (démonstration de la Phase 1, tests unitaires et test de fumée de la Phase 2) — cette phase porte des fonctions qui s'appuient aussi bien sur les primitives de dessin/mémoire de la Phase 1 (`camera`, `spr`, `map`, l'astuce de palette via `memcpy`/`peek`/`poke`...) que sur le mécanisme d'entités/dispatch de la Phase 2, donc la plus susceptible de régresser l'un ou l'autre. Chaque lot inclut trois vérifications bon marché, seuls contrôles intermédiaires de cette phase (pas de test automatisé par fonction, cf. Stratégie de test) :
- **Duplication d'aide interne** : avant d'ajouter une fonction utilitaire privée, grepper les modules `src/` existants pour une équivalente déjà écrite (constat Phase 1 : `read_whole_file` réinventée indépendamment dans deux fichiers, cf. Notes de portage) — *et* vérifier explicitement si le nouveau code réimplémente l'un des deux motifs récurrents déjà constatés en Phase 2 plutôt qu'un nom de fonction : duplication de chaîne (`strdup`-like) et tableau croissant à doublement de capacité avec parcours linéaire (`pico8_value.c`/`pico8_ob.c`/`pico8_class.c`/`pico8_entity.c` réimplémentent chacun ces motifs indépendamment, cf. Notes de portage) — un grep par nom de fonction ne les aurait pas trouvés puisque chaque occurrence est un bloc inline, pas un appel à un nom partagé.
- **Taille de module** : après chaque lot, comparer la taille (nombre de lignes) de chaque module touché à la plage déjà deux fois signalée comme disproportionnée par `warn-review` (~430-540 lignes, `pico8_gfx.c` en Phase 1, `pico8_ob.c`/`pico8_class.c`/`pico8_entity.c` en Phase 2) et noter dans la colonne « module cible » de `docs/portage-progress.md` tout franchissement de ce seuil, pour qu'un découpage soit une décision prise pendant la vague suivante qui dépend de ce module plutôt qu'un constat de fin de phase après coup.
- **Couverture du mécanisme d'entités/dispatch** : si un lot est le premier à exercer `kv:jr`/`hv`/`cv`/`cg`/`dc`/`mv`/`lt`/`he` d'une façon structurellement nouvelle par rapport au test de fumée de la Phase 2 (chaîne d'héritage plus profonde, combinaison de champs `cv`/tags `cg` non couverte, premier usage réel de `dc("kj")`/`mo:md()`...), étendre ce test de fumée avec un cas ciblé pour ce lot plutôt que de compter uniquement sur la comparaison source/port de la fonction qui *appelle* le mécanisme — le test de fumée de la Phase 2 était explicitement scopé à « 1-2 types d'entités factices » et n'est pas dimensionné pour couvrir tous les usages réels que la Phase 3 va lui faire subir ; ce principe reprend celui déjà acté pour la Phase 4→5 (extension du corpus `events.json` quand un cas non couvert est découvert).

Sortie de phase (déclenche la Phase 4) : toute fonction atteignable depuis `_init`, `_update60` ou `_draw` est portée.

### Phase 4 — Vérification de jouabilité en mode headless

**Première tâche de cette phase, avant tout scénario `events.json` ou vérification d'invariant** : câbler `pico8_cart_load()`/`pico8__init()`/`pico8__update60()`/`pico8__draw()` (`src/pico8_cart.c`, Phase 3 chunk 22 — laissés délibérément non branchés à `main.c` par ce chunk, mandat explicite consigné dans `docs/portage-progress.md`) dans une vraie boucle de jeu pilotée par `events.json`, avec un dump texte du framebuffer en sortie — sans cette étape, aucune des vérifications ci-dessous n'est possible (il n'existe aujourd'hui aucun point d'entrée qui appelle le jeu porté). Cette étape implique aussi de décider si `main.c` devient lui-même le pilote de rejeu headless (auquel cas les assertions de démonstration de la Phase 1 — actuellement la totalité de `main.c` — doivent être déplacées vers une cible de test dédiée pour ne pas perdre leur couverture de régression) ou si un binaire de rejeu séparé est ajouté à côté du `main.c` de démonstration de la Phase 1 — décision à trancher et consigner au démarrage de la Phase 4, pas à découvrir en cours de chunk.

Une fois la Phase 3 terminée (toute fonction atteignable depuis `_init`/`_update60`/`_draw` portée), exécution pas à pas via le backend rejeu scripté (`events.json` + dump texte), sans jamais ouvrir de fenêtre. Vérifier que le jeu tourne sans crash et que les mécaniques de base s'enchaînent (sonde → wormhole → colonisation → slipway → commerce → score).

Sortie de phase (déclenche la Phase 5) : un rejeu scripté complet couvrant cette chaîne (sonde → wormhole → colonisation → slipway → commerce → score) tourne sans crash jusqu'au bout, avec à chaque étape : le nombre de planètes qui reste dans une plage plausible (jamais négatif, jamais au-delà de 90 — pas de valeur aberrante signe d'un bug de comptage), et les crédits qui restent dans un ordre de grandeur cohérent avec une partie normale (les crédits peuvent légitimement devenir négatifs en jeu — cf. `hy:hk()`, `self.nz+=self.ge` sans plancher — donc l'invariant n'est pas « jamais négatif » mais l'absence de saut brutal type débordement/valeur aberrante).

### Phase 5 — Intégration raylib interactive

**Avant tout appel à un humain, première tâche de cette phase : audit systématique et ponctuel des sites de désambiguïsation REF non gardés.** Motivation (cf. plan-review post-Phase 4) : le même défaut structurel — une valeur REF de `pico8_value_t` pouvant être soit un `pico8_ob_table_t*` soit un `pico8_instance_t*`/autre struct incompatible en ABI, sans aucun tag de type dans la représentation pour les distinguer — a déjà été trouvé et corrigé au coup par coup à TROIS reprises indépendantes (`pico8_gn`, Phase 3 chunk 1/20 ; `mz:hq`'s `self.et=mz.jj`, Phase 3 chunk 16 ; `pico8_js_pq`, Phase 4, ce dernier confirmé par ASan comme un vrai heap-buffer-overflow), toujours découvert seulement parce qu'un scénario réel (scripté ou humain) finissait par exercer LE site précis en cause — jamais par une revue systématique, puisque le warn-review de chaque phase ne scanne que les fichiers touchés par CETTE phase. Or la Phase 5 est précisément la phase où le clic non scripté d'un humain risque d'atteindre des sites qu'aucun fixture scripté n'a jamais exercés, sur un cycle humain déjà qualifié ailleurs dans ce document de « coûteux et difficile à répéter ». Avant tout appel à un humain, l'agent doit donc : (1) énumérer statiquement (grep, pas d'exécution) tous les sites castant une valeur REF en `(const pico8_ob_table_t *)` ou équivalent (~74 sites recensés sur 30 fichiers au moment de cette note) ; (2) pour chacun, soit appliquer la même désambiguïsation déjà éprouvée au site `pico8_js_pq` (vérifier `->cls` de la REF contre les classes incompatibles réellement atteignables à ce site avant de caster), soit confirmer par le graphe de construction des classes que ce site précis ne peut jamais recevoir une instance d'une classe incompatible (et consigner ce raisonnement, pas juste « semble correct ») ; (3) consigner le résultat de ce balayage en une seule entrée dans le journal « Notes de portage » (nombre de sites audités, sites nécessitant une garde vs. sites confirmés sûrs par construction) — un passage systématique unique, remplaçant désormais la découverte réactive au coup par coup pour ce motif précis. Ce n'est pas la sortie de phase, juste un contrôle préalable bon marché avant d'engager le cycle humain, sur le même principe que le contrôle de compilation/édition de liens raylib ci-dessous.

Basculer vers le backend raylib (fenêtre réelle, entrée souris/clavier live) sans toucher `main.c` ni aucune fonction portée — seul le backend change. Premier moment où un humain joue réellement et donne son retour.

Le backend raylib enregistre toujours la session en `events.json` (mode enregistrement, cf. Architecture ci-dessus) — l'humain n'a rien à activer. Si l'humain rapporte un bug ou un comportement suspect, l'agent n'a pas besoin qu'on le lui décrive : il reprend directement l'`events.json` de la session concernée et le rejoue en headless via le Backend 1 (mêmes outils que la Phase 4) pour reproduire et investiguer, sans jamais avoir besoin d'ouvrir de fenêtre lui-même.

Avant de faire appel à un humain : l'agent compile et lie le backend raylib (compilation/édition de liens uniquement, jamais d'exécution — cf. politique d'exécution) et s'assure que ça réussit. Ce n'est pas la sortie de phase, juste un contrôle préalable bon marché pour ne pas gâcher le cycle humain, coûteux et difficile à répéter, sur une erreur de lien ou une signature incompatible avec l'API de mimétisme.

Juste avant la sortie de phase (l'appel effectif à l'humain), réexécuter une dernière fois le même balayage grep de l'audit REF ci-dessus — pas seulement une fois avant les chunks qui suivent l'audit initial. Motivation (plan-review post-Phase-5) : un chunk ultérieur de cette même phase (`src/main_raylib.c`, Chunk 4) a recréé le motif exact que l'audit venait de balayer (duplication verbatim du cast REF→`pico8_ob_table_t*` de `main.c`, jamais audité puisque écrit après le grep), rendant l'affirmation de complétude de l'audit (« 74 sites, balayage exhaustif ») obsolète dès le commit suivant, sans qu'aucune étape du plan ne le détecte avant le cycle humain. Ce second passage est mécanique et bon marché (un grep, pas une nouvelle analyse complète des 74 sites) — même principe que le contrôle de compilation/édition de liens ci-dessus, à faire immédiatement avant d'engager le cycle humain coûteux, et tout nouveau site trouvé suit le même traitement (garde `->cls` ou preuve par construction) que les 74 premiers.

Sortie de phase (fin du portage) : un humain termine une partie complète de la boucle centrale (sonde → wormhole → colonisation → slipway → commerce → score) via le backend raylib sans crash, et confirme que les mécaniques correspondent à sa compréhension de la cartouche PICO-8 originale.

## Garde-fous

- **Traçabilité** : toute fonction portée garde son nom minifié et son code Lua source en commentaire au-dessus. Une signification de champ/fonction non confirmée par `slipways-mechanics.md` reste documentée comme incertaine plutôt que devinée.
- **Pas de réécriture déguisée** : si une fonction semble « améliorable » en la réécrivant plutôt qu'en la portant, ce n'est pas fait sans discussion explicite — l'objectif du portage littéral est justement d'éviter ce piège.
- **Son hors périmètre** : `sfx`/`music` ne sont pas portés ; ce n'est pas un report à une phase ultérieure, c'est explicitement exclu de ce projet de portage.
- **Jamais de fenêtre interactive lancée par l'agent** avant la Phase 5 (voir `CLAUDE.md`).
- **Constats structurels récurrents consignés en Notes de portage : liste vivante, pas figée par phase** : quand une revue de fin de phase (`warn-review`) ou un audit ponctuel identifie un motif récurrent (duplication d'aide générique, motif de tableau croissant à doublement de capacité, seuil de taille de module, site de cast REF non gardé...), ce motif rejoint une liste vivante à vérifier par CHAQUE phase future lors de ses propres vérifications par lot/chunk — pas seulement la phase qui le découvre en premier ou celle dont le texte de plan a déjà été rédigé avant sa découverte. Motivation (plan-review post-Phase-5) : le motif de tableau croissant à doublement de capacité, déjà flagué à la fin de la Phase 2, a été réimplémenté une nouvelle fois indépendamment en Phase 5 (`pico8_raylib_backend.c`) parce que le texte de plan de la Phase 5 ne l'héritait pas — un point d'autant plus important que ce document prévoit explicitement une reprise PSX future à partir de cette même base C, qui répéterait sinon cette même lacune une troisième fois.
- **PSX en pause, pas abandonné** : aucun travail PSX tant qu'une version PC n'est pas pleinement jouable en C.

## Notes de portage

Journal à compléter au fil des Phases 1 à 5 (contrairement à « Décisions actées » ci-dessous, figée à l'issue du cadrage initial) : chaque résolution d'un cas ambigu rencontré pendant le développement (ex. sémantique exacte d'un index `stat()`, arrondi/débordement d'un cas limite en virgule fixe, ou un chemin insuffisamment exercé par le rejeu scripté de la Phase 4 et découvert seulement pendant le test humain de la Phase 5 — pas seulement les cas rencontrés en Phase 3) est consignée en une ligne — fonction/zone concernée, problème, résolution retenue — pour qu'une décision prise une fois ne soit pas relitigée ou tranchée différemment plus tard sur un cas similaire. Quand un cas est découvert en Phase 5 parce qu'il n'était pas couvert par le rejeu scripté de la Phase 4, le corpus `events.json` de la Phase 4 est étendu pour l'exercer désormais — concrètement, en réutilisant (éventuellement raccourci) l'`events.json` enregistré par le mode enregistrement du backend raylib pendant la session où le cas a été découvert, plutôt qu'en écrivant un nouveau scénario à la main — la consignation dans ce journal documente la décision, mais ne remplace pas la protection par le test de non-régression headless existant.

  **Symptôme 1 — état de transparence dédoublé.** **Hypothèse écartée par la preuve** (consignée ici pour qu'elle ne soit pas refaite) : `gfx->transparent[0] = 1` (`src/pico8_gfx.c:11`, le défaut PICO-8 « couleur 0 transparente ») serait à lui seul la cause — le neutraliser produit un framebuffer strictement identique au bit près, parce que `pico8_planet_display.c:631` réarme ce même drapeau à chaque frame. La cause réelle est structurelle : la transparence vivait dans **deux stores indépendants** combinés par un OU à `src/pico8_gfx.c:254` — le tableau `gfx->transparent[]` écrit par `palt()`, et les 16 octets à `0x5f00` écrits par `cu()`/`dv()` (`src/pico8_hud.c:41-61`). Or sur le vrai PICO-8 `palt()` *est* la palette de dessin : c'est la seule lecture sous laquelle la cartouche est cohérente, puisque `pico8/lua.lua:546` (`dv(self.qw)palt(3,false)palt(0,true)spr(...)dv()`) confie son annulation du `palt(0,true)` au `dv()` nu final, et que `grep -n palt pico8/lua.lua` ne retourne que les lignes 546, 937 et 939 — jamais un `palt(0,false)`. Le `dv()` du port n'écrivant que l'autre store, la couleur 0 restait transparente à vie et mangeait le contour de toutes les icônes du jeu, pas seulement celles des menus. Le même défaut vu par l'autre bout : le `palt(3,false)` de `pico8/lua.lua:937` (porté en `src/pico8_research_icon.c:337`) était structurellement incapable de rendre la couleur 3 opaque, le bit `0x80` posé par `cu()` survivant à tout. **Correctif retenu** : unifier les deux stores — `pico8_palt(mem, col, t)` pose/efface `PICO8_DRAW_PALETTE_TRANSPARENT_BIT` dans `mem[0x5f00+col]`, `pico8_spr` ne consulte plus que cet octet, et `gfx->transparent[]` disparaît de `pico8_gfx_t` ; le défaut PICO-8 à l'allumage (identité, couleur 0 seule transparente) descend dans `pico8_mem_init` (`src/pico8_mem.c:5-26`), seul endroit qui reste pour le porter. Délibérément *non* modifiés : la convention « bit 0x80 = transparent » (`src/pico8_mem.h:20`), déjà établie par le correctif humain `b2fb244`, et le fait que `pico8_spr` n'applique toujours *pas* le remap de couleurs de la palette de dessin (lacune connue et documentée sur place, non atteinte par ce bug). Effet de bord assumé et vérifié : sur 224 frames rejouées, le correctif ajoute exactement 4 pixels de couleur 3 dans l'icône de recherche de la barre du bas — c'est le `palt(3,false)` de `lua.lua:937` qui fonctionne enfin, donc de la fidélité, pas une régression.

  **Symptôme 2 (et 3b) — `print()` Lua coerce les nombres, pas l'adaptateur.** `fm.jk` (le capital technologie, `jk=0` à `pico8/lua.lua:1200`) et `fm.yr` (`yr=3401`, `pico8/lua.lua:1202`) traversent `pj:hb()` en nombres bruts, ce que le port reproduit fidèlement (`src/pico8_score_panel.c:351,380`) ; c'est un cran plus bas que la valeur se perdait — l'adaptateur `fn="qr"` → `io()` substituait `""` à tout argument non-chaîne (`src/pico8_pi.c:110`), alors que le `print()` de Lua convertit un nombre en sa représentation décimale. Les emplacements voisins (`fm.nz.."$"`, `fm.happiness.."%"`) étaient déjà des chaînes côté Lua, d'où deux trous isolés au milieu d'un bandeau par ailleurs correct. **Correctif retenu** : coercition via `pico8_value_tostr` (`src/pico8_value.h`), l'aide de conversion déjà présente dans le port — pas une nouvelle fonction privée, conformément au contrôle de duplication d'aide interne de la Phase 3 ; la chaîne possédée est libérée après le tracé.

Ce qui n'a délibérément pas bougé : l'ordonnancement (`record_frame` reste **avant** `pico8__update60()`, cf. le segfault de playtest documenté en tête de `pico8_raylib_backend.h`), le traitement de l'échec (une écriture ratée perd la frame en silence plutôt que de tuer une session jouée par un humain, et laisse le compteur intact pour que le prochain marqueur désigne toujours la bonne frame), et le format sur disque (chaque frame laisse un `events.json` complet et valide). Le chemin horodaté reste minté dans `pico8_raylib_backend_init()` à partir d'un seul `time(NULL)` : le fichier de marqueurs doit porter le **même** horodatage que l'enregistrement pour s'apparier par le nom, fait qui ne s'exprime que là où les deux noms sont construits côte à côte — et un module qui choisirait son propre chemin dépendrait de l'horloge, donc s'écrirait dans un fichier qu'aucun test ne peut prédire. **Vérification de bout en bout, en headless, comme le PRD la prescrit** : `tests/test_pico8_recording_continuity.c` (nouvelle cible `unit`) pilote le vrai `pico8_replay_source` et le vrai `pico8_session_recorder` exactement comme la boucle de `src/main_raylib.c` les pilote — seul le sondage matériel, la seule partie irréalisable ici, est remplacé par des frames scriptées — puis recharge le fichier produit : il se charge sans erreur, contient N+M frames, et les valeurs de chaque champ sont affirmées une à une, les N premières identiques aux frames rejouées **dans l'ordre**, les M suivantes aux nouvelles (un test qui compterait les frames passerait sur un enregistrement qui a rejoué les mauvaises). Le fichier obtenu est ensuite réinjecté dans une source de rejeu neuve, qui sert bien les N+M frames puis signale l'épuisement : c'est la user story 9, la raison pour laquelle la chaîne ne casse pas à la première reprise. Les valeurs rejouées et vivantes occupent des plages disjointes, et trois mutations (oubli de l'`io_tail_offset`, source resservant toujours la frame 0, boucle n'enregistrant que les frames vivantes) ont été vérifiées comme faisant échouer le test. Prior art du PRD contrôlée et confirmée : `test_append_recording_is_byte_identical_to_save_every_frame` de `tests/test_pico8_input.c` compare bien, **après chaque** frame ajoutée, le fichier écrit incrémentalement à celui qu'aurait écrit `pico8_input_save`. `make test` intégral vert ; `make raylib` toujours inexécutable (raylib non vendorisé ici), `src/main_raylib.c` et `src/pico8_raylib_backend.c` vérifiés par `cc -fsyntax-only` sous les mêmes `-Wall -Wextra -Werror` contre un `raylib.h` factice hors dépôt.

  **Reprise d'une partie depuis un enregistrement (PRD [raylib-replay-then-resume.md](prd/triage/raylib-replay-then-resume.md)), chunk 4 sur 4 — confort de rejeu, et cohérence des marqueurs vérifiée plutôt que supposée.** Le rejeu tourne désormais **plus vite que le jeu par défaut** : échelle de vitesses 1x/2x/4x/8x/sans plafond (multiples du 60 FPS du jeu, jamais des fréquences arbitraires — « deux frames enregistrées par soixantième de seconde réel » est une phrase vérifiable à la montre, « 240 fps » ne l'est pas), défaut à **4x** — une demi-heure d'enregistrement revient en moins de huit minutes tout en restant assez lent pour reconnaître l'instant où quelque chose tourne mal (user story 2), ce que 8x ne permet plus. Touches PAGE UP (plus vite), PAGE DOWN (moins vite), END (plus de plafond du tout, cas « rends-moi ma partie maintenant », user story 7) : ni les quatre flèches (`btn(0..3)`), ni la souris, ni la barre d'espace (déjà le marqueur) ne pouvaient être réutilisées, et ces trois-là sont au même endroit sur tous les agencements de clavier, AZERTY compris. **Arbitrage consigné pour ne pas être relitigé** : le PRD laissait « le comportement par défaut et le mécanisme d'abrègement à arbitrer avec l'utilisateur » ; l'exécution étant non supervisée, l'orchestrateur a tranché (rejeu accéléré par défaut, multiplicateur dans la plage 4x-8x, vitesse réglable en cours de rejeu, touche de déplafonnement, retour à la vitesse normale à l'épuisement) et ces décisions sont celles implémentées. **Abréger ne saute jamais de frame** : chaque frame enregistrée est toujours passée à `pico8__update60()` et toujours dessinée, seul le temps d'attente entre frames change — contrainte dure du PRD (sinon l'état obtenu n'est plus celui de l'enregistrement, le dessin ayant des effets de bord mesurés sur l'état), et `src/pico8_replay_control.{c,h}` est structurellement **incapable** d'exprimer un saut : il ne voit ni frame ni enregistrement, et sa seule sortie est un entier pour `SetTargetFPS` (0 = l'« aucune attente » de raylib lui-même, passé tel quel, pas une sentinelle inventée ici). Le retour aux **60 FPS dès l'épuisement** est une propriété de `pico8_replay_control_target_fps(control, replay_active)` et non une remise à zéro que le pilote pourrait oublier : aucun chemin de code ne rend autre chose qu'un 60 sur une frame vivante, quel que soit le niveau laissé par le rejeu — une partie reprise qui tournerait encore à 8x ressemblerait à un portage cassé, pas à un réglage oublié. **Chemin d'entrée séparé, délibérément étroit** : `pico8_raylib_backend_poll_replay_controls()` lit trois touches et rien d'autre ; il ne reçoit **pas** le backend, donc ne peut atteindre ni l'enregistrement ni le fichier de marqueurs même par accident — `poll_input()` n'est toujours pas appelé tant que le fichier pilote (ce n'est pas une lecture pure : le relâchement de la barre d'espace y écrit un marqueur). **Indication de progression** : `present()` reçoit une chaîne (« replay 1234/9589 (12%) speed x4 », ou « speed max ») ou `NULL`, et `NULL` ne dessine rien — l'overlay ne cesse pas d'exister par un drapeau remis à zéro mais par un argument absent, donc il ne survit pas d'une frame au rejeu. C'est la **seule** exception assumée au « no raylib-native UI/HUD » de `pico8_raylib_backend.h` : le commentaire a été mis à jour pour l'énoncer plutôt que contredit en silence, l'exception étant justifiée par une user story (6) postérieure à la phrase d'origine, et bornée (dessinée **après** le blit de la texture, donc incapable de toucher un pixel PICO-8 ou une frame enregistrée ; chaîne reçue et non composée par le backend). **Cohérence des marqueurs après reprise : déjà correcte, constat vérifié et non corrigé.** L'index écrit par un marqueur est lu dans `pico8_session_recorder_frame_count()`, et le recorder compte **toutes** les frames écrites dans le fichier, rejouées comprises, parce que la boucle les enregistre sans condition depuis le chunk 3 : un marqueur posé sur la première frame réellement jouée d'une session reprise vaut donc N, ce qui est exactement sa position dans le fichier. Rien à corriger, mais rien ne l'affirmait non plus, et c'est précisément le genre de propriété héritée gratuitement qu'une édition locale raisonnable supprime sans le voir — `tests/test_pico8_marker_coherence.c` échoue désormais si quelqu'un cesse d'enregistrer les frames rejouées (ce qui décalerait *tous* les marqueurs de la session de N en silence) ou déplace la lecture du compteur d'une ligne après l'enregistrement de la frame ; les deux mutations ont été vérifiées comme faisant échouer le test. Deux faits d'appui, hors de portée d'un test ici et donc énoncés dans les commentaires : `poll_input()` n'étant pas appelé pendant le rejeu, aucun marqueur ne peut tomber sur une frame seulement regardée ; et raylib recalcule son front « touche relâchée » à partir de l'état des deux dernières frames, donc une barre d'espace relâchée pendant le rejeu est perdue et non mise en file pour la première frame vivante. **Vérification** : deux nouvelles cibles `unit` — `tests/test_pico8_replay_control.c` (valeurs exactes de la table vitesse → plafond, butées aux deux bouts, déplafonnement, 60 FPS en jeu vivant quel que soit le niveau, et texte exact de la ligne de progression, cas dégénérés compris) et `tests/test_pico8_marker_coherence.c` ; trois mutations du module de vitesse (défaut ramené à 1x, suppression du court-circuit `replay_active`, décalage de 1 dans la ligne de progression) vérifiées comme faisant échouer les tests. `tests/test_pico8_replay_source.c` gagne `pico8_replay_source_frames_served()`, accesseur sur le curseur que le module tenait déjà plutôt qu'un second compteur tenu par le pilote — deux compteurs censés s'accorder finissent par diverger, et l'endroit où cela se verrait est justement la ligne que le joueur consulte pour décider s'il attend encore. Propre sous ASan/UBSan avec détection de fuites, `make test` intégral vert. **Ce qui ne peut pas être vérifié ici, et n'est donc pas prétendu** : qu'une pression sur PAGE UP accélère réellement le rejeu, que l'overlay soit lisible et bien placé, et la bascule effective vers l'entrée matérielle en fenêtre réelle — tout cela demande une session humaine. `make raylib` reste inexécutable (raylib non vendorisé ici) : `src/main_raylib.c` et `src/pico8_raylib_backend.c` vérifiés par `cc -fsyntax-only` sous les mêmes `-Wall -Wextra -Werror`, contre un `raylib.h` factice hors dépôt.

  **Prérequis d'en-têtes manquants dans le Makefile (PRD [makefile-header-prerequisites.md](prd/triage/makefile-header-prerequisites.md)) — dépendances générées par le compilateur, objets intermédiaires, et trois arbres d'objets séparés.** Les cibles listaient leurs `.c` exhaustivement mais leurs en-têtes très inégalement : 38 des 66 en-têtes de `src/` n'étaient prérequis d'aucune cible. Mesuré sur le Makefile d'avant : éditer la constante `PICO8_TYPE_TAG_LIST` de `src/pico8_type_tag.h` reconstruisait **1 binaire sur les 30** de `unit` (le seul à nommer cet en-tête), et ajouter une ligne à un en-tête purement déclaratif (`src/pico8_planet.h`) en reconstruisait **0** — soit un `make test` vert obtenu sur des objets périmés, exactement le mode d'échec que ce tag de type existe pour supprimer, puisque cet en-tête compile des constantes magiques et un `static inline` dans *chaque* objet. Chaque `.c` est désormais compilé en objet intermédiaire sous `tmp/` avec `-MMD -MP` : le compilateur écrit lui-même la liste transitive des en-têtes qu'il a réellement ouverts, réincluse par un `-include $(wildcard ...)` tolérant à l'absence (un dépôt frais construit donc sans étape préalable). Après : la même édition reconstruit **14 des 31** binaires, et les 17 autres ont été vérifiés un par un comme n'ayant aucun objet incluant cet en-tête (ce n'est donc pas une omission) ; l'édition déclarative en reconstruit 10, contre 0 avant. La variante minimale — nommer à la main les en-têtes porteurs de sémantique dans les cibles concernées — a été chiffrée puis écartée : une douzaine de lignes, mais c'est la liste manuelle qui a déjà dérivé une fois, et elle rate précisément les cas transitifs (`pico8_type_tag.h` est atteint via `pico8_list.h`/`pico8_ob.h`/`pico8_class.h`, jamais directement, dans toutes les cibles sauf une). Piège principal du changement, et raison des **trois** arbres d'objets (`tmp/obj`, `tmp/obj-asan`, `tmp/obj-ubsan`) : une instrumentation est une propriété de chaque objet, pas du lien — partager un objet non instrumenté avec une cible instrumentée donnerait un binaire qui passe tout en étant aveugle sur la majeure partie de son code, et la cible ASan n'a aucun jumeau non instrumenté dont le crash trahirait ce silence. Vérifié explicitement en retirant temporairement le correctif de `pico8_js_lq_arg_table()` (ASan signale toujours le heap-buffer-overflow, et le signale *dans* `pico8_class_instantiate`, donc depuis un objet moteur bien instrumenté) et en réintroduisant l'UB de débordement signé dans `pico8_fixed_add()` (le binaire simple passe silencieusement, le binaire UBSan sort en erreur). Bénéfice secondaire mesuré : `make test` depuis un état propre passe de 21,9 s à 7,7 s, les sept cibles partageant la fermeture moteur complète ne la recompilant plus chacune de leur côté. `$(TMP_DIR)/main_raylib` est **la seule cible laissée en un seul appel source→exécutable**, délibérément : raylib n'étant pas vendorisé dans l'environnement de vérification, elle n'y est ni constructible ni exécutable, et la convertir à l'aveugle risquerait exactement le partage d'objet que ce découpage interdit ailleurs (trois sources ont besoin de `-I third_party/raylib/src`, les 63 autres non, et `pico8_raylib_backend_coords.c` est aussi lié sans ce drapeau par sa propre cible de test).

  **Audit des casts REF en direction inverse — table ordonnée lue comme liste (PRD [reverse-direction-ref-cast-audit.md](prd/triage/reverse-direction-ref-cast-audit.md)) : 47 sites classés un par un, 1 seul non sûr, 11 non couverts, et une instrumentation rejouable.** Le tag de type avait éteint la direction bruyante (liste lue comme table : pas double, débordement, ASan) ; restait la direction inverse, muette. Les deux structs partagent l'en-tête exacte `{tag ; padding ; pointeur ; count ; capacity}`, si bien que lire une `pico8_ob_table_t` comme une `pico8_list_t` sous-lit toujours — jamais de dépassement, aucun sanitizer — mais rend `items[0]` = la clé de l'entrée 0 réinterprétée en valeur, `items[1]` = sa vraie valeur, `items[2]` = la clé de l'entrée 1, etc. **Conséquence qu'il faut avoir en tête pour lire le résultat de cet audit : `count` est au MÊME offset dans les deux structs, donc pour une table VIDE les deux lectures sont strictement indiscernables.** Un défaut de cette famille ne devient observable qu'à partir de la première entrée — d'où sa discrétion. Le classement détaillé site par site est dans [docs/audit-ref-cast-reverse.md](audit-ref-cast-reverse.md), trop long pour ce journal ; ci-dessous la méthode, les totaux et ce qu'il faut en retenir.

  **Méthode, en deux moitiés, parce que l'échec précédent vient d'en avoir utilisé une seule.** *Statique* : toutes les conversions « valeur REF → `pico8_list_t*` » de `src/` passent désormais par une écriture unique, `PICO8_REF_AS_LIST`/`PICO8_REF_AS_LIST_CONST` (`src/pico8_ref_audit.h`), qui en build ordinaire **est** le cast simple d'avant — l'inventaire devient un `grep` et ne peut plus être incomplet par oubli. Pour chaque site, les producteurs du champ ont été énumérés par trois recherches distinctes : écritures littérales du nom, écritures à nom dynamique (12 dans `src/`, dont la seule générique est `pico8_class_instantiate` recopiant une table d'`overrides` — les tables d'`overrides` du port ont été listées une à une), et **les chaînes de spec de classe**, c'est-à-dire tous les `X=o(...)` que `ob()` parse en `pico8_ob_table_t`. C'est cette troisième recherche qui a trouvé le seul cas non sûr, et c'est exactement celle qui manquait à l'audit de pré-Phase 5 : chercher les écrivains d'un champ par son nom ne trouve pas un producteur qui est une chaîne de données. *Dynamique* : `make ref-audit` compile le moteur dans un quatrième arbre d'objets (`tmp/obj-refaudit`, `-DPICO8_REF_AUDIT`, jamais partagé avec un objet non instrumenté — même raison que pour ASan/UBSan, et ici le silence EST le résultat) et produit huit binaires, avec deux canaux : par site (chaque cast compte les tags réellement reçus, vidés à la sortie du processus) et **à l'entrée des accesseurs** (`pico8_list_add/del/all/foreach/free`, `pico8_ob_table_set_*/get_*/remove_index/free` vérifient le tag de leur argument). Ce second canal existe parce que le premier ne voit que les conversions que l'audit a lui-même trouvées — il attrape un objet mal typé arrivé par n'importe quel chemin, y compris un chemin écrit après cet audit, ce qui est précisément la faille par laquelle `lq` était passé. **Contrôle négatif fait, pour que « 0 table observée » ne soit pas une mesure vide** : un programme jetable qui passe une `pico8_ob_table_t` non vide dans les deux canaux les fait répondre tous les deux (`SITE ... list=0 ob_table=1` d'un côté, `MISMATCH pico8_list_add expected=0x9E5C1157 actual=0x9E5C0B7A` de l'autre). Limite connue et documentée dans l'outil : la vidange passe par `atexit`, qu'`abort()` n'exécute pas — un binaire qui meurt sur un `assert()` raté ne contribue rien et tous ses sites se relisent en NON COUVERT, d'où l'affichage du code de sortie de chaque binaire par le script.

  **Résultat : 47 sites. 45 sûrs par construction, 1 sûr par le tag lui-même, 1 ambigu, 0 réellement faux.** Chaque « sûr » porte sur place un commentaire **nommant son producteur** — pas « semble correct », un nom de fonction et son fichier : `pico8_jo_pq` pour les cinq lectures de `oe`, `pico8_hy_pq` pour les quatre de `invented`, `pico8_jo_lz`/`pico8_jo_cn` pour les six de `jy`, `pico8_trade_kg`/`pico8_jo_ib` pour les cinq de `lp`/`rl` (la classe `trade` est déclarée **sans aucune chaîne de spec**, donc sans défaut concurrent), `pico8_f_` pour `qy`, `pico8_jc_pq` pour `ts`, `pico8_mz_pq` pour `ox`, `pico8_hp_pq` pour `i`, `pico8_lq_pq`/`pico8_jb_pq` pour `fs`/`ls`, `bd_reset_visit` pour `cc`, `pico8_ft_index` pour les buckets de `ic`, `pico8_jo_gh_row` pour le `lq` des lignes de `jo:gh` (la boucle démarre à `i=1` et saute `bs1`, la seule ligne construite à la main dont le `lq` n'est pas une liste — `for i=2,#bs` du vrai Lua). Le 48ᵉ `(pico8_list_t *)` de `src/` a été examiné et laissé en cast explicite : `pico8_la_append` caste le `void *ctx` de `pico8_list_foreach`, qui n'est pas une REF mais le `&t` que `pico8_la` lui passe deux lignes plus bas.

  **Le seul cas ambigu : le champ `by`, six sites, corrigé chez le producteur après chiffrage des deux options.** `by` est lu comme liste par `pico8_jo_ib` (deux fois), `pico8_jo_hb`, `pico8_jo_gh`, `pico8_db` et `pico8_dh`. Cinq de ses producteurs font une vraie liste ; le sixième était la chaîne de spec de la classe `ga` — `by=o(),` — que le repli « identifiant inconnu » d'`ob()` parse en `pico8_ob_table_t`. Les six sites lisaient donc bel et bien une table comme une liste sur toute instance `ga`. **Ce n'était pas un bug visible, et c'est tout l'intérêt de le consigner** : la table que `ob()` construit pour `by=o()` est vide (`count=0`, `capacity=0`, `entries=NULL`, vérifié expérimentalement), et `count` étant au même offset, les six lectures donnaient déjà la bonne réponse — 0 — par le mauvais type. Ce qui restait était une REF dont le tag annonçait OB_TABLE pendant que tout le programme la traitait comme une liste : l'invariant non écrit, exactement la forme qui avait fait classer `lq` sûr. Les deux corrections ont été chiffrées comme le PRD l'exige. Gardes site par site : six `switch` sur le tag à quatre cas, plus un pont table→liste positionnel à écrire ou à promouvoir (il n'en existe aucun de partagé, seulement trois copies privées de `positional_values`), soit 60 à 80 lignes sur cinq fichiers et six occasions de diverger. Correction chez le producteur : **~10 lignes** dans `pico8_planet_family_init()`, calquées mot pour mot sur ce que `pico8_ui_init()` fait déjà pour `le=o()` et `pico8_hy_pq()` pour `invented=o()` — les six sites deviennent sûrs par construction avec un seul producteur à nommer, et le précédent existe déjà deux fois dans ce port. La seconde a été retenue. L'aliasing ne change pas (le défaut de classe reste un objet unique partagé par toutes les instances `ga`, ce que le vrai Lua fait aussi puisque `qj({},X)` copie la référence) et aucun comportement ne change. Recensement exhaustif fait à cette occasion : sur les **93** champs `X=o(...)` des chaînes de spec du port, **trois seulement** sont aussi lus comme liste quelque part — `le`, `invented` et `by` ; les deux premiers étaient déjà traités, le troisième l'est maintenant, la catégorie est fermée.

  **11 sites NON COUVERTS, énumérés plutôt que supposés sûrs.** 36 des 47 sites sont atteints par au moins un scénario (les six `events.json` du dépôt rejoués par le pilote headless, plus sept binaires de test instrumentés) ; les 11 autres ne le sont par rien : `pico8_ft_name` (`pico8_collect.c:53`), `pico8_hy_kt` (`pico8_economy.c:402`), `pico8_cr` (`pico8_menu.c:209` et `:243`), `pico8_ga_kj` (`pico8_planet_family.c:301`), `pico8_nr_gv`/`pico8_nr_hb`/`pico8_nr_cn`×2/`pico8_mx_kf` (`pico8_planet_family_trade.c:90,168,214,241,305`) et `pico8_jc_ch` (`pico8_slipway_display.c:127`). Trois familles : le popup « techs inventées » du menu galactique (aucun fixture n'invente de tech), la famille de planètes `ga`/`nr`/`mx` (aucun fixture ne construit ces classes), et l'effet de particules d'un slipway en construction. Leur classement statique est donné dans le document annexe, mais **il n'est adossé à aucune mesure** — c'est la distinction que l'audit précédent n'avait pas faite, et le point de la story 8. Sur les 36 sites atteints : **0 a reçu autre chose qu'une liste**, et le canal accesseurs n'a signalé **0 incohérence** de tag sur l'ensemble des rejeux.

  **Test, et pourquoi il est honnête sur ce qu'il ne prouve pas.** `tests/test_pico8_ga_export_panel_by.c` construit une vraie planète `ga`, appelle le vrai `pico8_jo_gh()` et lit la ligne « exports: » sur le bouton que `pz()` a construit : « 0/2 » sur une planète neuve, « 2/2 » une fois deux routes d'export dans son `by` — la valeur visible, pas la forme d'une structure. C'est une assertion de contrat sur le producteur, pas une assertion « un garde a été appelé » ; les assertions de comportement qui l'encadrent sont ce à quoi le contrat sert, et ce qui attrapera le jour où `by` contiendra une table non vide. Test volontairement **pas** sous sanitizer, contrairement à son jumeau `test_pico8_planet_gh_row_lq` : cette direction sous-lit et ne peut jamais sortir de l'allocation, il n'y a rien à trouver pour ASan et une cible instrumentée n'affirmerait rien de plus.

Divergence de *représentation*, déjà documentée dans `pico8_entity.c`, sans différence de comportement trouvée — signalée ici parce qu'elle a une conséquence directe pour cet audit : un site de cast qu'aucune méthode ne pourra jamais atteindre tant que la fonction reste morte. Aucune autre divergence vis-à-vis de `pico8/lua.lua` n'a été relevée sur les 47 sites. Par ailleurs, **aucune désambiguïsation heuristique ne reste à supprimer** (story 11) : le seul reniflage `->cls` du port avait déjà été remplacé par le dispatch sur tag lors du correctif `lq`, et un `grep` sur `->cls` ne rend plus que le parcours d'héritage légitime de `pico8_class.c`.

  **Ce que cet audit laisse derrière lui, et qui vaut plus que son résultat.** Le résultat lui-même est modeste et le PRD l'avait anticipé : un seul champ non sûr, aucun affichage faux aujourd'hui. Ce qui change, c'est qu'il est désormais **réfutable**. Chaque ligne nomme sa raison, chaque « sûr » cite un producteur vérifiable, chaque site non atteint est listé comme tel plutôt que dilué dans un total, et `make ref-audit` rejoue la mesure en une commande sur les fixtures du moment — la prochaine phase n'a pas à refaire la passe manuelle, seulement à ajouter ses scénarios au tableau de `tools/ref_audit_report.sh`. La leçon à garder du côté méthode : **chercher les producteurs d'un champ par le nom du champ ne suffit pas** ; dans ce port, un producteur peut être une chaîne de données (`X=o(...)`) que `ob()` transforme en table, et c'est là que se cachait le seul cas de cet audit comme, sous une autre forme, le faux négatif du précédent. `make test` intégral vert (31 cibles `unit` + `replay`).

## Décisions actées

- Cible active : PC via raylib, rendu logiciel uniquement (raylib = fenêtrage/présentation/entrée, jamais de dessin raylib).
- Stratégie : portage littéral fonction par fonction de `pico8/lua.lua`, pas de réécriture depuis la doc de design.
- Noms minifiés conservés + code Lua source en commentaire au-dessus de chaque fonction portée, comme méthode de traçabilité et de vérification principale (Phase 3).
- Mécanisme d'entités/dispatch (`kv:jr`, `hv`/`cv`/`cg`, `dc`/`mv`/`lt`/`he`) porté littéralement, pas réécrit en C idiomatique.
- Arithmétique fixe 16.16 et algorithmes `rnd`/`sin`/`cos` PICO-8 reproduits exactement (pas de flottant natif).
- Pas d'oracle Lua différentiel (investigué et écarté — cf. Stratégie de test) ; tests unitaires C pour l'arithmétique/les primitives pures (Phase 2), comparaison source/port pour le reste (Phase 3), rejeu headless pour l'intégration (Phase 4).
- Backend interchangeable sous une API fixe : software+rejeu JSON+dump texte (Phases 1-4) vs raylib+entrée live (Phase 5), sans jamais modifier `main.c` ni les fonctions portées.
- Le backend raylib enregistre systématiquement chaque session en `events.json` (mode enregistrement) : toute session humaine est rejouable et inspectable en headless par l'agent sans description manuelle du bug.
- Son (`sfx`/`music`) explicitement hors périmètre, pas seulement différé.
- PSX en pause : repris uniquement une fois une version PC pleinement jouable en C obtenue, en repartant de ce C plutôt que de la doc de design.
- Prototype Love2D `game/` supprimé (incarnait l'approche « réécriture » abandonnée).
