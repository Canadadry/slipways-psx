## Implementation Decisions

### Dispatch mechanism this step newly relies on: `dg()`'s per-tick state-method call

`docs/prd/psx-sprites-audio-extraction.md` already traced `_draw()`'s `dc("kj")`/`dc("ev")` double dispatch (`pico8/lua.lua:1188`) in full. This step needs a *third* dispatch path neither prior PRD needed: `_update60()`'s own per-tick loop, `dg()` (`pico8/lua.lua:173-181`):

```
function dg()for _,qc in pairs(hv)do
local fn=qc[qc.me]
if fn then
fn(qc,qc.t)end
if qc.p_ then
he(qc)end
qc.t+=1
end
end
```

Every live entity `qc` in the global entity table `hv` gets `qc[qc.me]` called every tick, i.e. **the entity's current state name (`self.me`) is itself the method name of the function to call**, with `qc.t` (the entity's own age-since-last-`:ks()`-call counter) as the argument. This is how `mz:kz` (item 5 below, called while `self.me=="kz"`) and `nl:ly` (item 3, called while `self.me=="ly"`) run every tick -- not via `dc("kj")`/`dc("ev")`'s draw-pass dispatch at all, but via this separate *update*-pass dispatch, on the entity's *own* update tick counter `t`. This matters for fidelity: `t` here is ticks since the entity's last `self:ks(...)` call (`ke:ks`, `pico8/lua.lua:185-186`, resets `self.t=0`), not frames-since-creation in general -- the same distinction `docs/prd/psx-effects.md` already relied on for `jc:kj`'s `self.nh` counter (also reset by `:ks()`-adjacent logic, not by frame count).

### 1. Spiral particle engine -- `f_`/`ez`/`ei`, `pico8/lua.lua:685-707`

```
function f_(self)self.qy={}
end
function ez(self,n)while rnd()<n do
add(self.qy,self:mm())
n-=1
end
end
function ei(self)
if (self.fa<10 and not gd(self))return
local cx,cy,qo,qg,ro,q_,cs=
self.ra.x,self.ra.y,self.qo,self.qg,self.ro,self.q_,self.k_
for _,p in pairs(self.qy)do
local pv=p.v
p.p+=pv
p.v.x=qo*pv.x+ro*pv.y
p.v.y=qg*pv.x+q_*pv.y
if (p.a)p.v+=p.a
p.l-=0.14
if p.l<=1 then
del(self.qy,p)else
pset(cx+p.p.x,cy+p.p.y,cs[flr(p.l)])
end
end
ez(self,self.fc)end
```

- **`f_(self)`** (`:685-686`): initializes an entity's particle list `self.qy` to empty. Ported as struct initialization, not a function of its own.
- **`ez(self,n)`** (`:687-691`): the spawn-count formula. `while rnd()<n do ... n-=1 end` -- since PICO-8's `rnd()` (no argument) draws uniformly in `[0,1)`, this guarantees exactly `floor(n)` spawns (every iteration up to the integer part always passes, since `rnd()<k` for integer `k>=1` is always true) plus one more with probability `n-floor(n)` (the final iteration, `rnd()<fractional_part`). E.g. `n=3.5` always spawns 3, then a 4th with probability 0.5. This is a distinct formula from `effects.c`'s existing `EFFECTS_FLOW_SPAWN_CHANCE` (a flat `Bernoulli(0.08)` single-particle trial); this one produces a *count*, and its expected value is exactly `n` for any `n>=0`.
- **`ei(self)`** (`:692-707`): the combined per-tick step-and-draw pass (dispatched via `dc("kj")`, since every entity that owns `ei` assigns it to `.kj` -- see item-specific traces below).
  - **Visibility/priority guard** (`:693`): `if self.fa<10 and not gd(self) then return end` -- `gd()` (`pico8/lua.lua:346-348`) is the camera-visibility cull, already established out of scope everywhere in this port (no camera system, `docs/prd/psx-liaison-validity.md`'s Out of Scope). Dropped, matching that precedent exactly: this port's function runs unconditionally (equivalent to always passing the `self.fa>=10` branch).
  - **Per-particle velocity update** (`:698-701`): `p.p+=pv` (position advances by the OLD velocity, read into `pv` before the update, so the position advance uses last tick's velocity, not this tick's -- order matters and is preserved); then the velocity itself is replaced by a fixed 2x2 linear transform of its old value: `v.x' = qo*v.x + ro*v.y`, `v.y' = qg*v.x + q_*v.y`. Four per-type constants (`qo,ro,qg,q_`) parameterize this matrix -- for the wormhole (`g_`, item below) `qo=1.02,ro=-0.0525,qg=0.0525,q_=1.02`, a slight rotation-plus-outward-scale each tick (a `[[1.02,-0.0525],[0.0525,1.02]]` matrix is very close to a rotation by `atan(0.0525/1.02)≈2.95°` combined with a `≈2%` scale-up per tick), producing the spiral-outward look. This is a **general 2x2 linear map**, not literally a rotation matrix (the two diagonal terms aren't required to be equal, nor the off-diagonal terms equal-and-opposite, though for every type this source actually defines they are close to that shape) -- ported as a general 2x2 transform, not hardcoded to a rotation formula, so it's correct for every type's own constants without re-deriving anything.
  - **Optional acceleration** (`:701`): `if(p.a)p.v+=p.a` -- only `ga`'s particles ever set `.a` (`ga:mm`, `pico8/lua.lua:1081-1086`, see "Variants not fully ported" below); the wormhole's own particles never do. Ported as an optional per-particle acceleration field, defaulting to zero, so the one function correctly covers both cases without a second code path.
  - **Aging and death** (`:702-705`): `p.l-=0.14` every tick (a fixed linear decay, independent of any per-type constant); `if p.l<=1 then del(...) else pset(cx+p.p.x,cy+p.p.y,cs[flr(p.l)]) end` -- note the **death threshold is `<=1`, not `<=0`** (unlike `effects.c`'s existing trade-flow particle, which dies at `<=0`) -- a particle that would draw with `cs[0]` (out of `cs`'s 1-indexed range in Lua) is killed one tick early instead. Ported faithfully: `effects_spiral_step_particle` returns "dead" at `life<=1*FX_ONE`, not `life<=0`.
  - **Respawn** (`:707`): `ez(self,self.fc)` -- every tick, re-run the spawn-count formula at rate `self.fc` (a per-type "particles per tick" constant; wormhole `fc=1`, meaning ~1 new particle spawns per tick, maintaining roughly steady-state particle count against the `-0.14`/tick aging and `l<=1` death threshold).
- **`self:mm()`** -- the per-type spawn-particle constructor, called once per new particle by `ez`. The wormhole's own version, `g_:mm` (`pico8/lua.lua:727-730`), is this step's ported reference implementation:
  ```
  function g_:mm()local a=(flr(rnd(self.pn))+rnd(0.5))/self.pn+self.t*0.001
  local p=qm(self.du+rnd(),a)local v=p*self.py
  return {p=p,v=self.pk and v:pa()or v,l=self.ki
  }
  end
  ```
  - **Angle** (`a`): `(flr(rnd(pn))+rnd(0.5))/pn + t*0.001` -- quantizes into `pn` equal sectors (a uniform integer draw in `[0,pn)` via `flr(rnd(pn))`, PICO-8's argumented `rnd(x)` drawing uniformly in `[0,x)`), adds a within-sector jitter centered at the sector's midpoint (`rnd(0.5)`, uniform in `[0,0.5)`, NOT centered -- see caveat below), normalizes to a `[0,1)`-turn fraction (`/pn`), then adds a slow drift term proportional to the entity's own tick age (`t*0.001` turns/tick -- the whole sector pattern rotates slowly over the entity's lifetime). Wormhole: `pn=3` (3 sectors). **Caveat, exact, not glossed over**: `rnd(0.5)` draws uniformly in `[0, 0.5)`, so the "jitter" is not symmetric around the sector's own center the way "midpoint plus symmetric jitter" might suggest -- it biases each sector's spawn angle toward its own upper half. Ported literally (asymmetric, matching source), not smoothed into a symmetric jitter.
  - **Position**: `p = fixed_polar(du+rnd(), a)` -- `du` (a per-type base radius constant, wormhole `du=2`) plus a further `rnd()` (uniform `[0,1)`) jitter, at angle `a`, via `qm()` (`pico8/lua.lua:124-126`, this step's new `fixed_polar` primitive, see below).
  - **Velocity**: `v = p*py` -- radially outward from center, scaled by a per-type constant `py` (wormhole `py=0.06`, small -- particles drift outward slowly); if `self.pk` is true (wormhole `pk=1`), the velocity is instead `v:pa()` (`km:pa()`, the 90-degree-rotation helper `docs/prd/psx-effects.md` already ported reasoning for, applied here to a *velocity* not a unit vector -- rotating `v` by 90 degrees turns "radially outward" into "tangential," i.e. orbital motion around the center instead of drifting away from it). The wormhole uses the tangential branch (`pk=1`), which combined with the `ei()` matrix's own slow rotation is what produces its actual on-screen spiral, not the position-`qm`/velocity-scaling alone.
  - **Lifetime**: `l = self.ki` (a flat per-type constant, wormhole `ki=9` -- no randomness in the initial lifetime itself, unlike position/angle).

**Wormhole's full parameter set** (`g_`, `pico8/lua.lua:708-726`, this step's ported reference instance): `fc=1` (spawn rate), `py=0.06,ki=9` (spawn velocity scale, lifetime), `pn=3,pk=1` (3 angle sectors, tangential velocity), `du=2` (base spawn radius), `qo=1.02,ro=-0.0525,qg=0.0525,q_=1.02` (per-tick velocity matrix), `k_=o(1,1,5,13,6)` (5-entry color ramp, indexed by `flr(l)`, `l` ranging roughly 1-9 down to 1 -- so `cs[flr(l)]` for `l>5` is out-of-Lua-table-range and PICO-8's `nil` color argument to `pset` is treated as "no explicit color" i.e. **the current draw color**, per PICO-8's own documented `nil`-argument convention -- a real, if minor, wrinkle worth a caller-side note, not glossed over: for the first several ticks of a particle's life, `pset` draws with whatever color was last set by an earlier draw call in the same frame, not `k_`'s own ramp; only once `l<=5` does the ramp's own explicit color apply). `g_.kj=ei`, `g_.pq=f_` (init), `g_.mm` is the class's own default -- these four assignments (`pico8/lua.lua:722-726`, `g_.hq=bv` and `g_.ey=d_` are unrelated, non-particle methods) are exactly how the wormhole becomes the generic engine's one live-in-source caller.

- **The tech menu's own concrete anchor/spacing**: `pj.cr = o(hi=v(0,11), gq=v(0,11), ca=10)` (`pico8/lua.lua:827-829`), consumed by `cr()`'s own `pz(pj.cr,bs)` call (`pico8/lua.lua:964`) -- anchor `(0,11)`, each row offset by `(0,11)` from the previous (a vertical list starting near the screen's top edge), in PICO-8's native 128×128 space. **This is the real, live-wireable candidate**: `rules_tech.c`'s `open` boolean (`docs/prd/psx-rules-tech.md`, already real, already read every frame by `game_draw.c`'s existing tech-tile block) is exactly the kind of live open/close edge this animation needs to trigger on -- the only genuine gap between source and this port is that source's menu is a vertical stacked list of variable-content rows and this port's tech menu (per `docs/prd/psx-rules-tech.md`'s own Implementation Decisions) is a fixed horizontal row of 4 known tiles; the *settle-lerp itself* doesn't care about that shape difference (it only needs a per-tile target, which this port's tile loop already computes, and a shared origin, which this step defines as this port's own screen-space equivalent of `pj.cr.hi`, mirroring `screen_map.c`'s own established precedent of rescaling a PICO-8-128-native constant into this port's own resolution rather than reusing the raw number).
- **Every other real call site of `pz()`** (`jo:fe`, colonization-job picker, `pico8/lua.lua:418`; the restart-confirm buttons, `pico8/lua.lua:871-878`; the structure-purchase picker, `pico8/lua.lua:997`; one more at `pico8/lua.lua:1169`) all reuse this exact same settle-lerp mechanism with their own anchor/spacing -- none of them has a live menu-open toggle in this port today (no colonization-commit, no game-over/restart state, no structure-purchase UI exists anywhere yet), so only the tech menu gets an actual live-wiring chunk; the settle-lerp primitive itself is generic and ready for whichever of those lands next.

## Data Model / New Files

No new `.c`/`.h` files: everything in this PRD extends the two existing homes those two categories of primitive already have in this codebase --

- **`psx-slipways/fixed.h`** gains three new general-purpose arithmetic primitives (alongside the existing `fixed_add`/`fixed_sub`/`fixed_mul`/`fixed_sqrt`, none of which is traced game content, all of which are pure math this port's whole fixed-point convention needs):
  - `fixed_t fixed_sin(fixed_t turns)` / `fixed_t fixed_cos(fixed_t turns)` -- PICO-8's built-in `sin()`/`cos()` take their argument as a fraction of one full turn (not radians), and -- a documented, stable PICO-8 API convention, not something to re-derive from decompiled bytecode -- `sin()` is defined with a **flipped sign** relative to the mathematical convention (`sin(x) = -sin(2πx)` in ordinary terms), to keep rotation direction consistent with PICO-8's own y-axis-down screen coordinate system; `cos()` has no such flip (`cos(x) = cos(2πx)`). This sign flip is exactly why `qm()` (below) is `v(cos(lx),sin(lx))*fy` and not some other pairing -- ported faithfully, with an explicit unit test asserting the flip against known values (`fixed_sin(0)==0`, `fixed_sin(0.25*FX_ONE)==-FX_ONE`, `fixed_cos(0)==FX_ONE`, `fixed_cos(0.25*FX_ONE)≈0`), so a future reader can verify the convention was actually applied, not assumed. Implemented as a precomputed lookup table (matching this port's own established "no runtime float, precompute what a real PS1 R3000A without hardware trig would otherwise have to iterate," `docs/plan.md`'s own "la trigo en virgule fixe reste nécessaire" framing) with linear interpolation between entries; exact table size/generation method decided at implementation time (a small build-time Python tool emitting a compiled-in C table, mirroring `tools/gen_psx_sprite_atlas.py`'s/`tools/gen_psx_audio_data.py`'s established "Python tool emits compiled-in C data" pattern from `docs/prd/psx-sprites-audio-extraction.md`, is the most consistent choice, but a hand-written table is also acceptable if the size stays small -- an implementation-time call, not a design fork this PRD needs to pre-commit).
  - `void fixed_polar(fixed_t magnitude, fixed_t turns, fixed_t *out_x, fixed_t *out_y)` -- ports `qm(fy,lx)` (`pico8/lua.lua:124-126`) directly: `*out_x = fixed_mul(magnitude, fixed_cos(turns))`, `*out_y = fixed_mul(magnitude, fixed_sin(turns))`. Every one of this step's angle-based effects (kick wobble, spawn-position jitter, slipway line wobble) is a direct caller of this one function, exactly mirroring `qm()`'s own single-shared-helper role in source.
- **`psx-slipways/effects.c`/`effects.h`** gain this step's seven game-specific primitive families (plus the tech-menu live-wiring addition), alongside the existing `effects_flow_particle_t`/`effects_flow_try_spawn`/`effects_flow_step_particle`:

## Implementation Chunks

Tracer-bullet order: the shared trig primitive first (everything else depends on it), then each effect family as its own small, independently-committable, host-tested chunk, cheapest/most-self-contained first, ending with the one live-wiring chunk:

1. **`fixed_sin`/`fixed_cos`.** Added to `fixed.h`. Host-tested (`host_tests/rng_and_fixed_test.c`) against known turn values (`0, 0.25, 0.5, 0.75`) confirming both the magnitude and PICO-8's flipped-sine sign convention, plus a small tolerance-bounded spot check at an irrational turn value, matching `fixed_sqrt`'s own established testing posture.
2. **`fixed_polar`.** Added to `fixed.h`, built on chunk 1. Host-tested: `fixed_polar(magnitude, 0, ...)` returns `(magnitude, 0)`; `fixed_polar(0, turns, ...)` returns `(0,0)` for any turns; a known non-axis-aligned value matches a hand-computed result within tolerance.
3. **Kick wobble (`effects_kick_t`).** `effects.h`/`effects.c` gain `effects_kick_start`/`_step`/`_offset`, using chunk 2. Host-tested: amplitude starts at `1.25*FX_ONE`; decays by exactly `0.1*FX_ONE` per step, floored at 0; reaches exactly 0 after 13 steps (matching the traced `1.25/0.1=12.5` lifecycle); the offset at a few hand-picked `(amplitude, age_ticks)` pairs matches `fixed_polar(amplitude, age_ticks*0.2, ...)` directly (a thin wrapper, but tested as its own named function per this step's Data Model).
4. **Idle bob (`effects_idle_bob_delta`).** Host-tested against `sin(t*0.005)*0.06` at several hand-picked `t` values, reusing chunk 1's `fixed_sin`.
5. **Slipway reveal ramp (`effects_reveal_ramp_step`).** Pure `int*`-state counter, no dependency on chunks 1-4. Host-tested: the sequence of returned values over 25 calls is `1,2,...,19,20,20,20,20,20`; `EFFECTS_SLIPWAY_REVEAL_RAMP`'s 20 entries match the traced `k_` table exactly.
6. **Probe pulse/sweep radii (`effects_probe_pulse_radius`/`effects_probe_sweep_radius`).** Uses chunk 1 (`fixed_sin`) and the existing `fixed_sqrt`. Host-tested against hand-computed values at `t=0`, `t=15`, `t=40` (both where the ramp-up caps and one full breathing period, since PICO-8's turns-based `sin()` gives `sin(t/40)` a true period of `40` ticks -- see this PRD's own corrected Implementation Decisions note), `t=80` (two full breathing periods) for the pulse; at `t=0`, `t=7.5`, `t=15`, `t=30` for the sweep (confirming the sqrt-ease shape and the cap at `t>=15`).
7. **Spiral particle engine, spawn count (`effects_spiral_spawn_count`).** Depends only on `rng_t`. Host-tested: `rate=0` never spawns; a fixed seed reproduces an identical count sequence (mirroring `planetgen_test.c`'s determinism pattern); a Monte-Carlo regression over many calls at a fixed fractional rate (e.g. `1.5`) confirms the empirical mean lands within a documented tolerance of the rate itself, matching `docs/prd/psx-rules-discovery.md`'s own empty-roll Monte-Carlo precedent.
8. **Spiral particle engine, spawn particle (`effects_spiral_try_spawn_particle`).** Depends on chunks 1-2 and `rng_t`. Host-tested with the wormhole's own reference parameters (`pn=3,pk=1,du=2,py=0.06,ki=9`): a fixed seed reproduces an identical sequence of spawned particles; every spawned particle's initial position lies within the expected radius band; the tangential (`pk=1`) branch produces a velocity perpendicular to the radial spawn vector (dot product near zero, within tolerance); lifetime is always exactly `ki*FX_ONE`.
9. **Spiral particle engine, step particle (`effects_spiral_step_particle`).** Depends on chunk 8's struct. Host-tested with the wormhole's own matrix constants (`qo=1.02,ro=-0.0525,qg=0.0525,q_=1.02`): position advances by the pre-update velocity, not the post-update one (matching source's exact evaluation order); velocity is transformed by the 2x2 matrix exactly; lifetime decrements by `0.14*FX_ONE` per call; a particle survives while `life>1*FX_ONE` and reports dead on the first call that brings it to `<=1*FX_ONE` (not `<=0`, matching the traced threshold precisely -- this is the one place this step's death condition genuinely differs from `effects_flow_step_particle`'s own `<=0`, worth its own explicit regression so the two don't get silently unified incorrectly later); a full spawn-to-death lifecycle test (spawn via chunk 8, step repeatedly until dead) confirms the particle count of steps roughly matches `(ki-1)/0.14` within one tick, mirroring `docs/prd/psx-effects.md`'s own lifecycle-test precedent.
10. **Money-spent/income popup (`effects_popup_t`).** Depends on nothing new. Host-tested: position advances by exactly `(0,-0.34*FX_ONE)` per step; dies once `age>=5*FX_ONE` -- mathematically `5/0.1=50` steps, but since `0.1` truncates to a Q16.16 constant slightly under its true value (`6553`, not the exact `6553.6`), 50 steps only accumulate `age=327650 < 327680`, so the popup is genuinely still alive at step 50 and dies on step 51 (`327650+6553=334203`); the test follows this real, truncated-constant behavior, not the idealized `5/0.1=50` figure; `effects_popup_fade_index` returns `0` at spawn and `4` at the last alive step, monotonically non-decreasing throughout (never re-derives a value outside `[0,4]`).
11. **End-game frame-grow bars (`effects_growbar_t`).** Depends on nothing new. Host-tested: `gz` advances by exactly `0.2*FX_ONE`/call, uncapped -- since `0.2` truncates to a Q16.16 constant slightly under its true value (`13107`, not the exact `13107.2`), `gz` after 16 calls (`209712`) is still below the `3.2*FX_ONE` cap (`209715`), so the cap actually first engages on the 17th call (`222819`), not the idealized `3.2/0.2=16` the mathematical ratio would suggest; the returned height matches `min(gz,3.2)^2` at several hand-picked call counts, including that real 17th-call engagement point, and stays capped afterward.
12. **Menu settle-lerp, pure primitive (`effects_settle_step`).** Depends on nothing new (uses only `fixed_mul`/squared-magnitude comparison, no sqrt -- `#d<=1` is a **squared**-distance test, see Implementation Decisions item 7). Host-tested: a target more than 1 unit (squared) away eases by exactly 40% of the remaining vector per call; a target within the squared-1 threshold snaps exactly to it in one call, never overshoots, never oscillates; repeated calls after snapping leave the position unchanged (idempotent once settled) and report "no longer moving."
13. **Menu settle-lerp, tech-menu live wiring.** A small new stateful wrapper (its own struct, owned either inside `effects.c` as a named singleton accessor or as a tiny new dedicated pair of functions -- exact ownership shape decided at implementation time, mirroring `rules_tech.c`'s own three-layer "pure step / stateful wrapper / real wiring" precedent) holds one `effects_settle_t` per tech tile (`RULES_TECH_ERA1_TILE_COUNT` of them) plus a "was open last frame" flag to detect `rules_tech_get_state().open`'s false→true edge; on that edge, every tile's `ra` is reset to a single shared origin (this port's own screen-space equivalent of `pj.cr.hi=v(0,11)`, rescaled the same way `screen_map.c`'s own established precedent rescales other PICO-8-128-native constants) and its `qf` set to that tile's own already-computed final `x,y` (the existing loop in `game_draw.c` already computes this every frame; this chunk only changes which `x,y` each tile's `SPRT`/`TILE` primitive is drawn at, reading the per-tile `effects_settle_t.ra` instead of the loop's own final position while that tile's settle hasn't finished, and the final position directly once it has -- no change to anything the tile represents or its researched/icon state). Host-testable for the pure per-call math (already covered by chunk 12); the live wiring itself verified via `make psx-slipways-screenshot-pcsx` (Select-press-then-screenshot, confirming the tiles visibly animate in from the shared origin rather than appearing instantly), reusing the exact harness `docs/prd/psx-rules-tech.md`'s own Chunk 4/5 already established, with no new PCSX Lua driver needed unless a specific mid-animation frame needs to be asserted on (decided at implementation time, following `tools/gen_pcsx_slipways_*.py`'s existing pattern if it is).
