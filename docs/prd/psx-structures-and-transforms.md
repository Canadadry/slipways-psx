## Problem Statement

`docs/plan.md` Phase 4 step 15 calls for `rules_planets.c` : "Implémenter les structures spéciales (Slipgate, Infragate, Trading Hub, Synthesizer, Ascension Gate, Laboratory, Food processor) et les actions de transformation de planète (mechanize/terraform/collapse/harvest). Placement : réutilise le mécanisme d'insertion dynamique dans le graphe de voisins (wormhole, Phase 1-2)." `rules_planets.c`/`rules_planets.h` already hold the full, graduated 10-type/24-job colonization roster (`docs/prd/psx-full-planets-and-tech.md`), whose own Further Notes explicitly deferred this step's content and flagged five concrete open questions for whoever picked it up: (1) all 6 structure-shaped `fd` records share the literal empty job name `px=""`, so structures clearly aren't looked up by `px` the way real jobs are -- how they ARE looked up was left unresolved, to be "checked directly against `dr`'s own unstash (9807)"; (2) `docs/plan.md`'s own step-15 wording names **7** structures, but only **6** `fd` records are structure-shaped, with Slipgate/Infragate "named in `dr`/§6 but not present as `fd` job-shaped records at all" -- a discrepancy to resolve from source, not assume; (3) the 4 transform/destroy actions' `ii`/`go`/`cw` fields were "already traced once" by `rules_planets.c`'s original PRD and needed re-verification now that more of the game's data is decoded; (4) the `f+`/`qh`/`qh+` curves (fully decoded in Annexe A but unused until now) are needed by exactly Laboratory/Ascension-Gate/Food-processor/Laboratory-upgrade, per that PRD's own finding; (5) whether this step's "placement" language finally requires live state this port doesn't have, or whether structures/transforms can stay pure, host-testable core logic with zero live wiring, exactly like `rules_planets.c`/`rules_tech.c`'s own precedent -- an open question, not an assumption to carry forward.

This PRD resolves all five directly from source (re-running the project's established `jq`/`unstash()` recipe against `pico8/map.json`, and reading the surrounding `pico8/lua.lua` code that actually consumes the decoded data -- not just the data tables in isolation, which is what actually settles question (1)), rather than re-litigating them from the predecessor PRD's speculation. It also investigates, per this task's own instructions, exactly which of `science`/`energy`/`joy`/the joker (`?`) resources `resource_id_t` needs, and re-confirms the still-`Incertain` 13th resource code `a` stays untouched.

## Solution

Re-run `unstash(8494)` (`fd`, `pico8/lua.lua:1391`) directly against `pico8/map.json` and read it alongside `unstash(9807)` (`dr`, the structures' tooltip-text table) and the structure entity definitions themselves (`pico8/lua.lua:905-1127`, the `qh`/`hj`/`pm`/`mx`/`nl`/`os`/`nr`/`fr` prototype chain) -- not `fd`/`dr` in isolation. This surfaces the concrete answer to question (1): every structure entity carries a literal integer field, `hp` (e.g. `qh`'s own definition sets `hp=1`, `pico8/lua.lua:907`), and `jo:pq()` (`pico8/lua.lua:403-406`) reads `gb[self.hp]` to fetch that structure's production record -- `gb` being the exact same table `hp:pq()`'s `ho(gb,hp.mr,hp.gp)` loop (`pico8/lua.lua:1403`, the mechanism `docs/prd/psx-full-planets-and-tech.md` already traced for real jobs) populates via `add(gb,hp(ri))` in `fd`'s own array order. Since the 6 structure-shaped records are the *first* 6 elements of `fd` (before any of the 8 bare tech-gate strings or the 24 real job records), they land at `gb` positions 1-6 -- exactly matching each entity's own literal `hp=1..6` field. **Structures are addressed by raw 1-based array position, confirmed by two independent, converging pieces of evidence** (their `hp=N` literal field, and their position in the decoded `fd` dump), not by `px` at all -- `px`'s value on a structure record (always `""`) is genuinely never read for lookup purposes; the project's own `px`-tagged display-name field used elsewhere in these same entity definitions (e.g. `qh`'s own separate `px=o("laboratory",c=13)` field, `pico8/lua.lua:907`) is an unrelated, differently-scoped field on the *entity*, not the *job record* -- confirming these are two distinct, same-named fields in two distinct objects, not one field reused.

This same re-read resolves question (2) directly: `dr` (`unstash(9807)`) has exactly 7 tooltip entries (Laboratory, Food processor, Slipgate, Infragate, Trading Hub, Synthesizer, Ascension Gate -- matching `docs/plan.md`'s own step-15 list and `docs/design/slipways-mechanics.md` §6's 7-row table exactly), while `fd` has only 6 structure-shaped records. The 6th `fd` record with no `dr` counterpart is **Protostar** (`pm`), the 8th, non-purchasable entity §6's own footnote already names -- it has *production* data (needs, produces, curve) because it behaves like a live colony once created (by `collapse`), but no purchase tooltip because it can never be bought directly. Slipgate and Infragate, conversely, have **zero production data** (no needs, no produces, no curve -- confirmed directly: neither `nr` nor `fr`'s own entity definition, `pico8/lua.lua:1101-1127`, sets an `hp=` field at all, meaning there is nothing in `gb` for them to link to) because they are pure network connectors with no economic behavior -- so they were never expected to appear among `fd`'s 6 structure records in the first place. Both are still fully real, purchasable, in-scope structures: each has its own literal `od` (cost) and `rr` (tech-gate) field set directly on its entity definition (`nr`: `od=10,rr="slipgates"`, `pico8/lua.lua:1103,1108`; `fr`: `od=25,rr="infraspace"`, `pico8/lua.lua:1126,1125`). The predecessor PRD's flagged discrepancy is resolved precisely: **7 structures is correct** (matching `docs/plan.md`'s own wording and the design doc's §6 table), and the reason 2 of them are absent from `fd` is now a confirmed, source-grounded structural fact (zero production mechanic), not a decode gap -- with Protostar captured as an explicit 8th, non-purchasable data entry alongside them, since `collapse` (this step's own scope) is what creates it and a faithful `collapse` needs to know what it produces.

Question (3) (`ii`/`go`/`cw`) is re-verified byte-for-byte against the current, larger decode and found **unchanged and accurate**: `mechanize`/`terraform` use `go` (a single planet-type code the planet becomes); `collapse`/`harvest` use `cw` (a different *entity* the planet becomes -- Protostar for `collapse`, a plain destroy-marker for `harvest`) plus a previously-uncited `rn` field (a second sound/animation id, structurally parallel to `ii`, with no traced gameplay effect -- left `Incertain`-but-irrelevant, matching the design doc's own `a`-resource precedent, not resolved further). Question (4) is confirmed: `f+` (Ascension Gate, and the Food processor's tech-upgrade target), `qh`/`qh+` (Laboratory, base and tech-upgraded) are exactly and only consumed by these structures, with `hc`'s own already-decoded per-level tables (Annexe A) reused verbatim. Question (5) -- live-wiring -- is answered explicitly below (Implementation Decisions, "Live-wiring verdict"): **no live state is introduced**, confirmed against `docs/prd/psx-galaxy-rendering.md`'s own explicit finding that no dynamic-neighbor-graph-insertion mechanism exists anywhere in this port yet, for the wormhole or for anything else -- `docs/plan.md`'s step-15 "placement" clause names a mechanism that does not yet exist as live code, so this step cannot "reuse" it and does not attempt to invent it.

Extend `rules_planets.h`/`rules_planets.c` in place (the module already housing every other planet-adjacent data table, per its own established convention -- no new file, consistent with the predecessor PRD's explicit "no new module" choice for step 14): `resource_id_t` gains 4 new values (`RESOURCE_SCIENCE`, `RESOURCE_ENERGY`, `RESOURCE_JOY`, `RESOURCE_JOKER` -- the exact 4 resources this step's own data touches, confirmed by exhaustive scan, not guessed); `curve_id_t` gains 4 new values (`CURVE_F_PLUS`, `CURVE_QH`, `CURVE_QH_PLUS`, `CURVE_NONE` -- the last one new infrastructure this step genuinely needs, for Slipgate/Infragate's "no production" case, mirroring `RESOURCE_NONE`'s existing precedent). Two new structs are added: `structure_t` (8 entries: the 7 purchasable structures + Protostar, `STRUCTURE_COUNT`) and `transform_action_t` (4 entries: `TRANSFORM_COUNT`), each with a plain accessor (`rules_planets_structure`/`rules_planets_transform`) and one availability-style helper each (`rules_planets_structure_production`, mirroring `rules_planets_job_production`'s existing shape exactly, since `hp:po()` is confirmed shared between jobs and structures; `rules_planets_transform_applicable_to`, mirroring `rules_planets_job_available_on`'s existing shape). No existing function's signature changes. No new live caller is added anywhere.

## Implementation Decisions

**The 6 structure-shaped `fd` records, re-decoded directly (`unstash(8494)`, `pico8/lua.lua:1391`), in raw array order (positions 1-6, matching each entity's own `hp=N` field):**

```
1: o("","",0,"qh","p?","k","superhuman ai")
2: o("","",0,"f+","p","h")
3: o("","",0,"-","","e")
4: o("","",0,"f-","l","f","xenofoods")
5: o("","",0,"f-","","?")
6: o("","",0,"f-","??","w",f,"?")
```

Field order matches `hp.mr`'s own positional list, already cross-checked by the predecessor PRD (`px,lr,fj,ja,i,o,il,dm`). Every record's `fj` (cost) field is literally `0` -- confirming, by itself, that structures' real purchase cost is **not** read from `fd` at all (see "Cost model" below). Matched against `dr`'s own tooltip text (`unstash(9807)`) and each structure entity's own definition in `pico8/lua.lua:905-1127`:

| # | `hp` | Structure | Needs | Produces | Curve | `il` (curve-upgrade gate) | `dm` (default need) |
|---|---|---|---|---|---|---|---|
| 1 | 1 | Laboratory (`qh`) | people, joker | science | `qh` | `superhuman ai` | -- |
| 2 | 2 | Ascension Gate (`hj`) | people | joy | `f+` | -- | -- |
| 3 | 3 | Protostar (`pm`, non-purchasable) | none | energy | `-` | -- | -- |
| 4 | 4 | Food processor (`os`) | organics | food | `f-` | `xenofoods` | -- |
| 5 | 5 | Synthesizer (`mx`) | none | joker (dynamic) | `f-` | -- | -- |
| 6 | 6 | Trading Hub (`nl`) | joker, joker | luxury | `f-` | -- | joker |

Confirmed by two independent, converging checks per record: (a) `dr`'s own tooltip text (`unstash(9807)`) names the resources in matching prose for Laboratory ("makes",24,"science...","with",19,"...any resource" -- `24`="science", `19`="people", both matching `r`'s own raw codes, Annexe A) and Ascension Gate ("accepts",19,"...turns them","into",25,"happiness" -- `19`="people", `25`="joy"); (b) each entity's own `pico8/lua.lua` definition supplies the fields `fd` deliberately omits (cost, purchase-gate tech, the joker-resolution set) -- see below.

**Cost model: a flat literal on the entity, never `hp:od()`'s job-cost formula.** `hp:od()` (`pico8/lua.lua:1426-1433`, ported already for real jobs as `rules_planets_job_cost`) has exactly one call site in the entire source: `pico8/lua.lua:418`, inside `jo:fe()` (the colonization-job picker), over `bj(self)` -- the same `bj()` filter (`pico8/lua.lua:1391-1398`) that matches a job's `lr` (planet-type code) against the planet being colonized. Structure records all carry `lr=""` (an empty planet-type code, confirmed in the dump above), which can never match a real planet's type code, so structures are structurally excluded from `bj()`/`jo:fe()` entirely -- they are bought through a separate UI flow (the design doc's own itch.io quote: "Buy structures by dragging them from the bottom-right corner," a different panel from the colonization-choice list). Each structure entity instead carries its own literal `od` field, read as a plain integer with **no** tech-multiplier formula applied: Laboratory `od=15` (`pico8/lua.lua:910`), Food processor `od=15` (`:1099`), Slipgate `od=10` (`:1103`), Infragate `od=25` (`:1126`), Trading Hub `od=20` (`:1061`), Synthesizer `od=40` (`:1040`), Ascension Gate `od=60` (`:1003`) -- all 7 matching `docs/design/slipways-mechanics.md` §6's table exactly, no discrepancy. Protostar has no `od` field at all (not purchasable, confirmed). This is ported as a plain `int cost` field on `structure_t`, with **no** cost-formula function added (there is nothing to compute -- `rules_planets_job_cost` is correctly *not* reused here, a deliberate absence, not an oversight).

**Purchase-gate `rr`: an entity-literal field, structurally distinct from real jobs'/transform-actions' `fd`-bare-string `rr`, despite the identical field name.** `docs/prd/psx-full-planets-and-tech.md` already traced the bare-string-loop mechanism (`pico8/lua.lua:1434-1440`) that sets `ri.rr` on real job/transform `fd` records. That loop only ever touches records *within* `fd`'s own array, and the 6 structure records are `fd`'s first 6 elements -- with **zero** bare strings preceding any of them -- so that mechanism assigns no `rr` to any structure record. Structures' actual purchase-gate tech is instead a literal field set directly on the entity's own object definition, a different source location entirely: Ascension Gate `rr="ascension"` (`pico8/lua.lua:1000`), Synthesizer `rr="void synthesis"` (`:1038`), Trading Hub `rr="trade league"` (`:1059`), Slipgate `rr="slipgates"` (`:1108`), Infragate `rr="infraspace"` (`:1125`) -- all 5 matching `docs/design/slipways-mechanics.md` §12's "débloque la structure X" rows exactly. Laboratory and Food processor have **no** `rr=` field on their own definitions at all -- both are purchasable from the start, matching §12's own tech table (no tech is listed as unlocking either). Confirmed structurally distinct from the job/transform mechanism: none of these 5 tech names (`ascension`, `void synthesis`, `trade league`, `slipgates`, `infraspace`) appears among `fd`'s own 8 bare strings (`xenofoods`, `geneseeds`, `drillbots`, `gene rewriting`, `replication`, `biome hacking`, `starbirth`, `geoharvesting` -- every one of which already has exactly one real consumer, 4 in step 14's job roster and 4 in this step's transform roster, with zero orphans either way). Ported as `structure_t.required_tech` (a plain `const char *`, `NULL` when absent), mirroring `colonization_job_t.required_tech`'s existing shape and captured-as-data-only precedent -- no function applies it, for the same reason `colonization_job_t.required_tech` isn't applied: no live colonization-choice/structure-purchase menu exists anywhere in this port (see "Live-wiring verdict" below).

**Curve-upgrade `il`: genuinely shared with `hp:po()`, confirmed reusable as-is.** Laboratory's `il="superhuman ai"` and Food processor's `il="xenofoods"` are the same 7th positional `fd` field real jobs' `il` already occupies, read by the exact same `hp:po()` (`pico8/lua.lua:1422-1425`) that already powers `rules_planets_job_production`. Confirmed by `bb()` (`pico8/lua.lua:1276-1290`), the annual production loop: it calls `pt.hn:po()` uniformly for *every* colonized entity in `cg.jo`, whether `pt.hn` was linked from a real job record (via `bj()`) or from a structure record (via `jo:pq()`'s `self:lz(gb[self.hp])`, `pico8/lua.lua:403-406`) -- one function, two kinds of caller, exactly the "generic, caller-agnostic" shape `rules_planets_curve_value`/`rules_planets_job_production` already have. **No new curve-lookup function is added for structures** -- `rules_planets_curve_value` is reused directly, and a thin structure-specific wrapper (`rules_planets_structure_production`, mirroring `rules_planets_job_production`'s existing "resolve curve + upgraded, then delegate" shape) is added purely for call-site ergonomics and symmetry with the job side, not because the underlying primitive needed to change.

**`hc`'s three newly-needed curve tables, from Annexe A (re-verified, no discrepancy):** `f+ = [0,2,3,4]` (levels 1-4, no `mc` upgrade target); `qh = [0,1,3,5]` (`mc="qh+"`); `qh+ = [0,2,5,8]` (no `mc` target). `CURVE_NONE` (new, this step's own addition, for Slipgate/Infragate's genuine "no production" case) has no per-level table at all -- `rules_planets_curve_value(CURVE_NONE, level, upgraded)` returns `0` unconditionally, for any `level`/`upgraded` combination, mirroring `RESOURCE_NONE`'s existing "real sentinel, not a magic-number-in-disguise" precedent rather than leaving this case as undefined behavior a future caller could trip over.

**Resource-code resolution, joker-resolvable sets (`ba`/`ht`), and the two design-doc corrections this step's research found:**

- Laboratory's joker slot resolves to `ba=o(28,18,20,21,22,48)` (`pico8/lua.lua:914`) = food, bots, organics, ore, tech, goods (6 resources) -- matching `dr`'s own tooltip ("with... and any resource") and the design doc's §6 prose ("any resource") exactly, no discrepancy.
- Trading Hub's 2 joker slots resolve to `ba=o(28,48,18,20,21,22)` (`:1062`) = food, goods, bots, organics, ore, tech (the same 6-resource set, different literal order) -- and Trading Hub's `default_need` (`dm="?"`, the joker itself) is captured as `RESOURCE_JOKER`.
- **Design-doc correction #1 (Trading Hub's produced resource)**: the raw `fd` record (`o("","",0,"f-","??","w",f,"?")`) unambiguously produces `w` = luxury (`r.w=12`, Annexe A -- the exact same code `docs/prd/psx-rules-economy.md` already traced for `db()`'s external-trade bonus and `bf()`'s happiness formula). `docs/design/slipways-mechanics.md` §6's own row for Trading Hub reads "generates [joy]/[énergie?]," a guess the design doc itself never marked with confidence -- this guess does not survive a direct check against `fd`'s own mechanical data (the `dr` tooltip's embedded numeric codes it was based on, `pico8/lua.lua:1062`'s decoded text "generates",25,23,..., are cosmetic UI-text arguments, not resource-letter codes at the same reliability as `fd`'s own game-mechanical fields -- `23` in particular does not correspond to any of `r`'s 13 known resource codes at all, confirming the tooltip text is not a safe source for this value). This step ports Trading Hub as producing **luxury**, per `fd`'s own authoritative mechanical field, and recommends (Further Notes) the design doc's §6 row be corrected.
- **Design-doc correction #2 (Synthesizer's resolvable set)**: `mx`'s own `ht` field (`pico8/lua.lua:1041`, `ht=o(28,20,21,22)`) = food, organics, **ore**, tech. `docs/design/slipways-mechanics.md` §6's own prose reads "can provide food/organics/**bots**/tech" -- `ba`/`ht` never contains code `18` (bots) for Synthesizer; the real 4th resource is `21` (ore). This step ports Synthesizer's dynamic-resolution set from `ht` directly, and recommends the same correction.

Both corrections are captured as static data (`structure_t.resolvable[]`/`resolvable_count`, a new field mirroring `needs[]`/`needs_count`'s existing array-plus-count shape, sized to the real traced maximum of 6 -- `RULES_PLANETS_MAX_RESOLVABLE = 6`). Their dynamic *application* (actually resolving a joker need/produce to a concrete resource at runtime) is out of scope, for the same "no live colony/trade state" reason every other dynamic mechanism in this port is (see Out of Scope).

The `rn` field (collapse `45`, harvest `46`) is a second, previously-uncited numeric id with the same shape as `ii` (a bare integer, no string/table target). ## Testing Decisions

- **What makes a good test here**: assert on observable output (struct field values, formula/accessor results for given inputs) -- never on internal representation (enum integer values, array order, `static` vs. exported), matching every prior PRD's standard in this codebase.
- **Fully host-testable, all 7 chunks** (`gcc`, no PSn00bSDK toolchain): every new struct/function has zero new dependency beyond `fixed.h`/`<stdbool.h>`, already `rules_planets.c`'s existing dependency set. This step **extends** the existing `host_tests/rules_planets_test.c` and `test-rules-planets` Makefile target -- no new target, no new `*_TEST_HOST_SRCS` var, since no new module is created.
- **Regression discipline**: every chunk that adds new data re-asserts the previously-landed chunks' exact values (chunk 1's curve-table regression check; chunk 6's full-roster consolidation), matching the predecessor PRD's own established pattern.
- **Not tested here**: anything requiring the PSn00bSDK toolchain (no new PSX-side behavior is introduced -- see Out of Scope); any live structure-purchase/colonization-choice/planet-transform action (still doesn't exist anywhere in this port); dynamic resolution of any `resolvable[]`/joker slot; `rn`'s dynamic effect (a confirmed sound-effect id read by `jo:hu()`/`rn()`, out of scope only because no audio system exists anywhere in this port); the `a` resource (re-confirmed untouched, not newly investigated further).
