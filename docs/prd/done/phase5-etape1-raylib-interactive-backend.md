## Problem Statement

Phases 1-4 built the entire ported cart (`pico8_cart_load()`/`pico8__init()`/`pico8__update60()`/`pico8__draw()`) and one way to run it: `src/main.c`, a headless driver that reads a fixed `events.json` script frame-by-frame and dumps the final framebuffer as text. No human has ever seen this game move — every verification so far has been an agent reading text. `docs/plan.md`'s Phase 5 is explicit that this is the moment a human actually plays: a real window, live mouse/keyboard input, the same 128x128 framebuffer the software renderer already produces, displayed at a legible scale.

The catch is the plan also says this backend swap happens "sans toucher `main.c` ni aucune fonction portée — seul le backend change" (without touching `main.c` or any ported function — only the backend changes), while `src/main.c` as Phase 4 left it is not, itself, backend-agnostic: it directly calls `pico8_input_load(path)`, `pico8_input_step()`, and `pico8_dump_screen()` — a file-driven replay loop and a text dump, neither of which has any meaning for a live interactive session (there is no fixed frame count to loop over, and nothing to dump to text once a window is drawing every frame). Something has to give: either `main.c` is refactored to hide these specifics behind a swappable interface, or the "sans toucher main.c" promise is read literally (the file itself, never edited again) and a second driver is added alongside it. `docs/plan.md`'s own Phase 4 decision log already leans on `main.c` staying exactly as Phase 4 left it going into Phase 5, and Phase 4's own header comment on `main.c` says it is "reusable as-is by Phase 5's raylib backend" — reusable as it stands, not reusable after edits.

Separately, the plan requires that whatever a human does interactively be reproducible headlessly afterward: every raylib session must record itself to an `events.json` the existing headless driver can replay verbatim, with zero manual steps from the human, so an agent can always reproduce and investigate a reported bug without ever opening a window itself. And before ever asking a human to spend that costly, hard-to-repeat cycle, the agent must have already confirmed the raylib backend at least compiles and links — cheaply, without executing it.

## Solution

Add a second, small driver, `src/main_raylib.c`, that boots the cart exactly the way `src/main.c` already does (load `pico8/gfx.json`/`pico8/map.json`, wire the dispatch context, `pico8_cart_load()` → `pico8__init()` → `pico8_eu()`), but sources its per-frame input from a real raylib window instead of a parsed `events.json`, and presents the framebuffer by uploading it as a texture and drawing it scaled, instead of dumping text. `src/main.c` itself is not modified by this PRD.

This is possible without touching a single ported function because the actual PICO-8 mimicry API — `pico8_gfx_t`, `pico8_mem_t`, and `pico8_input_t` together with `pico8_btn()`/`pico8_stat()` — is already backend-agnostic: none of the three structs or their accessor functions know or care whether `pico8_input_t`'s fields were populated by parsing a JSON file or by polling raylib this frame. What is Backend-1-specific is not that API — it is `main.c`'s own harness code: `pico8_input_load`/`pico8_input_step` (parsing and stepping through a fixed script) and `pico8_dump_screen` (writing a text framebuffer dump). None of that harness code is part of the swappable API the plan describes, and none of it is called by `main_raylib.c`.

A new module, `src/pico8_raylib_backend.h`/`.c`, owns everything that is genuinely raylib-specific: opening/closing the window, uploading the 128x128 framebuffer as a texture and drawing it scaled every frame, polling live mouse position/buttons and the four arrow keys into a `pico8_input_t` for that frame, and maintaining the growing in-memory list of every frame played so it can be written out as a valid `events.json` after every single frame (so a crash loses at most the one frame in flight, never a whole session). The events.json write path itself is added as a small, pure, unit-testable sibling to the existing `pico8_input_load` — `pico8_input_save` — living in `pico8_input.h`/`.c` since it is really just the existing schema's other direction, not raylib-specific at all.

Because raylib is not available as a system package in this project's build/verification environment, it is vendored: a new Makefile target clones a pinned raylib release and builds it as a static library from source, following the exact precedent already established in this repository for PSn00bSDK (`psn00bsdk-toolchain-setup`) — a slow, network-heavy, one-time setup step, kept separate from the fast day-to-day `make`/`make test`. A further target links `main_raylib.c` against that static library; this link step, never an execution of the resulting binary, is the "before calling a human" pre-check the plan's own Phase 5 text requires.

## User Stories

1. As the developer, I want a second driver (`src/main_raylib.c`) that boots the exact same cart the existing headless driver boots, so that the raylib session and every headless replay session start from an identical, already-verified boot sequence.
2. As the developer, I want `src/main.c` left completely unmodified by this work, so that Backend 1 (the scripted headless replay an agent uses to reproduce and investigate reported bugs) keeps behaving exactly as Phase 4 left it, with zero risk of this phase regressing it.
3. As the developer, I want the raylib driver to reuse `pico8_gfx_t`/`pico8_mem_t`/`pico8_input_t`/`pico8_btn`/`pico8_stat` completely unmodified, so that every already-ported function keeps drawing and reading input through the exact code path it was verified against in Phases 1-4.
4. As a human playtester, I want a real window showing the 128x128 framebuffer scaled up to a legible size, so that I can actually see what I'm doing instead of reading a text dump.
5. As a human playtester, I want my mouse position and buttons read live and fed to the game every frame, so that clicking on planets, buttons, and UI panels works the way it does in the original cartridge.
6. As a human playtester, I want the four D-pad directions read from the arrow keys, so that camera panning (`qb:ph()`) responds to my keyboard the way PICO-8's own `btn()` would.
7. As a human playtester, I want the window to close cleanly when I close it or press the platform's usual quit action, so that I don't need special knowledge to end a session.
8. As the developer, I want every raylib session to record itself to an `events.json`-shaped file automatically, with nothing for the human to turn on, so that any session — buggy or not — is available for headless replay afterward.
9. As the developer, I want that recording written to disk after every single frame (not just at clean shutdown), so that a crash or a force-quit loses at most the one frame in flight, never the diagnostic value of the whole session.
10. As the developer, I want each recorded session written to its own timestamped file under `tmp/` rather than overwriting a single shared `events.json`, so that consecutive playtests don't silently clobber each other's recordings and the agent can name "the events.json of the session in question" as the plan describes.
11. As the developer investigating a human-reported bug, I want the recorded file to use exactly the same schema `pico8_input_load` already parses (`mouse_x`/`mouse_y`/`mouse_buttons`/`dpad[4]` per frame), so that I can feed it straight into the existing headless driver with no new tooling.
12. As the developer, I want the events.json write path (`pico8_input_save`) to be a small, pure, independently unit-tested function living next to `pico8_input_load`, so that the recording format's correctness doesn't depend on ever actually opening a raylib window.
13. As the developer, I want the raylib-specific window/texture/input-polling code isolated in its own module (`pico8_raylib_backend`) rather than inlined into `main_raylib.c`, so that `main_raylib.c` stays a thin orchestrator matching `main.c`'s own shape, consistent with this project's one-module-per-concern convention.
14. As the developer, I want any pure, non-window-dependent math this new module needs (e.g. converting a live window pixel coordinate back to the underlying 128x128 PICO-8 coordinate space) extracted into its own testable function, so that at least that piece of the raylib backend has automated coverage despite the window itself being untestable headlessly.
15. As the developer, I want raylib vendored and built from source via a dedicated, clearly slow/network-heavy Makefile target (mirroring `psn00bsdk-toolchain-setup`), so that this project keeps working the same way regardless of what happens to be installed system-wide, and so day-to-day `make`/`make test` stays fast and untouched.
16. As the developer, I want that vendored raylib pinned to a specific released version rather than a floating branch, so that a raylib upstream change can never silently change this project's build out from under it.
17. As the developer, I want a Makefile target that compiles and links `main_raylib.c` against the vendored raylib without ever running the resulting binary, so that I can cheaply confirm the interactive build is sound before ever spending a costly, hard-to-repeat human playtesting cycle on it.
18. As the developer, I want that compile/link check to be the actual, automatable exit criterion for everything this PRD's own chunks can complete, so that whoever runs this PRD (including an unattended autopilot) knows the real phase-closing human playthrough is a separate, later step no chunk here claims to finish.
19. As a future maintainer, I want `main_raylib.c` and `pico8_raylib_backend` to never call raylib drawing primitives to render anything other than the already-computed 128x128 framebuffer texture (no raylib-native UI, no extra HUD), so that raylib stays strictly a windowing/presentation/input layer, matching `docs/plan.md`'s own architecture section.
20. As a future maintainer, I want no `sfx`/`music` playback attempted anywhere in this backend, so that the project's explicit "audio out of scope" guardrail holds for the interactive backend too, not just the headless one.

## Implementation Decisions

**`main.c` vs. a second driver file — settled: a second file, `src/main_raylib.c`; `main.c` is never modified by this PRD.** The tension is real: `main.c` as Phase 4 left it calls `pico8_input_load`/`pico8_input_step`/`pico8_dump_screen`, none of which make sense for a live session, so literally reusing the file unchanged for interactive play is not possible. Resolving that by refactoring `main.c` into a backend-agnostic shape was considered and rejected: `main.c` is not a ported Lua function (this project's literal-port discipline doesn't apply to it), but Phase 4 explicitly built it as a "thin, general-purpose shell, reusable as-is by Phase 5's raylib backend" (its own header comment) — "as-is" meaning unchanged, not meaning-after-refactor. Reading closely, the part of `main.c` that is genuinely swappable is already swappable and needs no change: `pico8_gfx_t`, `pico8_mem_t`, `pico8_input_t`, and their accessor functions (`pico8_btn`, `pico8_stat`, every `pico8_*` drawing call) are the real PICO-8 mimicry API the plan's Architecture section describes, and none of them know or care how `pico8_input_t`'s fields got populated. What is not swappable, and was never claimed to be, is `main.c`'s own harness: `pico8_input_load`/`pico8_input_step` (parsing/stepping a fixed script) and `pico8_dump_screen` (writing a text dump) exist solely to drive and observe Backend 1's own scripted replay, and the plan never lists them as part of the mimicry API. Introducing an abstraction layer to paper over harness code that was never meant to be generic would be exactly the kind of speculative interface this project's own "surgical changes"/"no abstraction for its own sake" discipline argues against, for a driver file on the order of 75 lines. `src/main_raylib.c` therefore duplicates `main.c`'s boot sequence (asset loading, dispatch-context wiring, `pico8_cart_load()`/`pico8__init()`/`pico8_eu()`) verbatim in shape, but its per-frame loop calls into the new raylib backend module for input and presentation instead of `pico8_input_load`/`pico8_dump_screen`, and loops until the window is closed instead of a fixed frame count. `src/main.c` is not opened for writing by any chunk of this PRD.

**The mimicry API needs zero changes.** `pico8_gfx.c`/`.h` depends only on `pico8_mem.h` and contains no raylib references, confirmed by inspection — it was already fully backend-agnostic going into this phase. `pico8_input_t`'s struct shape (an array of `pico8_input_frame_t`, each `{mouse_x, mouse_y, mouse_buttons, dpad[4]}`, plus a `current_frame` cursor) and `pico8_btn`/`pico8_stat` are reused unchanged by the raylib backend: each live frame, the backend fills exactly one `pico8_input_frame_t` from live polling and points a `pico8_input_t` at it (`frame_count = 1`, `current_frame = 0`) before calling `pico8_dispatch_set_input()` — the exact same call the headless driver already makes every frame, just fed from a different source.

**New module: `src/pico8_raylib_backend.h`/`.c`.** Owns every raylib-touching concern as one cohesive, testable-where-possible unit, kept separate from `main_raylib.c` per this project's established one-module-per-concern convention (mirroring how `pico8_gfx`/`pico8_input`/`pico8_dump` are already separate from `main.c`): opening and closing the raylib window at a fixed integer scale of the 128x128 framebuffer (no resizable-window support — not asked for, and out of scope), uploading the framebuffer (read via `pico8_peek`/`pico8_mem_t` at `PICO8_ADDR_SCREEN`, the same region `pico8_dump_screen` already reads) as a texture and drawing it scaled every frame, polling live mouse position/buttons and the four arrow keys into a `pico8_input_frame_t` each frame, appending that frame to a growing in-memory list, and writing that whole list to disk as `events.json`-schema JSON after every frame. If this module's line count approaches the project's own already-twice-flagged oversized-module range (~430-540 lines, per `docs/plan.md`'s Notes de portage), splitting it (e.g. presentation vs. input-capture-and-recording) is a decision for whichever future chunk first crosses that threshold, not a speculative pre-split now.

**Recording: `pico8_input_save`, a new pure function alongside `pico8_input_load`.** Added to `pico8_input.h`/`.c` (not the raylib backend module) since it is purely about the existing `events.json` schema, not about raylib: given an array of `pico8_input_frame_t` and a path, it writes exactly the schema `pico8_input_load` already parses. The raylib backend calls it after every frame with the full accumulated frame list (a full rewrite each time, not an incremental append), guaranteeing the file on disk is always complete, valid JSON — even if the process is killed mid-session, the last successfully written frame's file replays cleanly with no partial-JSON handling needed anywhere. This matches the plan's own explicit wording ("chaque frame de la session... est écrite dans un `events.json`") and needs no new file format, parser, or recovery logic.

**Recording destination: a fresh timestamped file per session under `tmp/`.** `tmp/` is already gitignored and already the project's convention for generated/session output (`tmp/pico8_replay_dump.txt`). Each raylib session writes to its own `tmp/events_recorded_<timestamp>.json` rather than overwriting the single, committed root `events.json` (a Backend-1 fixture the demo/replay targets depend on) or a previous session's recording — matching the plan's own "l'agent reprend directement l'`events.json` de la session concernée" wording, which presumes sessions are individually identifiable.

**Live input mapping.** Mouse: `stat(32)`/`stat(33)` from the live cursor position converted into the 128x128 PICO-8 coordinate space (window pixel position divided by the fixed integer scale, clamped to `[0, 127]`); `stat(34)`'s three bits from the live left/right/middle mouse button state, matching the bit layout `pico8_input.h` already documents. Keyboard: the four arrow keys map directly to `btn(0..3)` (left/right/up/down) — PICO-8's own documented default keyboard binding for player 0, not an invented mapping. No alternate binding (e.g. WASD) is added — not evidenced as needed, and easy to add later without touching anything else.

**Coordinate conversion is a pure, unit-tested function.** The window-pixel-to-PICO8-coordinate conversion (division by the fixed scale factor plus clamping) is written as its own small pure function in `pico8_raylib_backend.c`, taking plain integers rather than any raylib type, so it is testable without a window — the one meaningfully testable piece of the presentation/input-capture concern.

**Vendoring raylib: a new, slow/network-heavy Makefile target, following the `psn00bsdk-toolchain-setup` precedent exactly.** No system package is available for raylib in this project's environment, so a target (e.g. `raylib-vendor-setup`) clones a pinned raylib release tag (not a floating branch) into a vendored directory and builds raylib's own static library from its own build system, exactly mirroring how `psn00bsdk-toolchain-setup` already vendors and builds the PSn00bSDK toolchain from source: documented as slow and network-heavy, invoked once, kept entirely separate from `make`/`make test`. A further target (e.g. `make raylib`) compiles and links `src/main_raylib.c` plus `src/pico8_raylib_backend.c` plus the full engine source list (the same closure `pico8_replay` already links, minus `src/main.c`) against that vendored static library — mirroring `pico8_replay`'s own "full engine closure" Makefile comment. Per this project's execution policy (`CLAUDE.md`, unchanged by this PRD), this target is never invoked in a way that runs the resulting binary; a successful link is the entire automated signal this PRD's own chunks produce.

**No headless/text-dump fallback in `main_raylib.c`.** Unlike `main.c`, `main_raylib.c` never calls `pico8_dump_screen` — its output is the live window, and there is no scripted frame count to run to completion of. This is a deliberate scope boundary, not an oversight: adding a debug text-dump mode to the interactive driver was not asked for by the plan and is left out per this project's simplicity-first discipline.

## Implementation Chunks

1. **Vendor and build raylib from source.** Add the `raylib-vendor-setup` Makefile target (clone a pinned release tag, build the static library), documented as slow/network-heavy like its PSn00bSDK precedent. No project C code depends on this yet; this chunk's own success criterion is that the vendored static library exists and a trivial one-file raylib program can compile and link against it.
2. **`pico8_input_save` + its unit tests.** Add the events.json writer to `pico8_input.h`/`.c`, tested by writing a small set of frames and confirming `pico8_input_load` reads back identical values (a round-trip test), plus a direct string-shape check against the schema `pico8_input.h` already documents. No raylib dependency; buildable and testable immediately as part of the existing `unit` target.
3. **`pico8_raylib_backend` module.** Window open/close, framebuffer texture upload and scaled presentation, live mouse/keyboard polling into a `pico8_input_frame_t`, the pure coordinate-conversion function (unit-tested), and the per-frame call into `pico8_input_save` with the growing frame list. Depends on Chunk 1 (raylib available to link against) and Chunk 2 (the writer it calls).
4. **`src/main_raylib.c`.** The thin driver: duplicate `main.c`'s asset-loading/dispatch-wiring/cart-boot sequence, then loop calling into Chunk 3's module for input and presentation until the window closes. Depends on Chunk 3.
5. **Makefile `raylib` target wiring the whole chain together, link-only.** Compiles and links `main_raylib.c` + the backend module + the full engine source list against the vendored raylib static library. This is the plan's own "avant de faire appel à un humain" pre-check, and the concrete, automatable exit criterion for this PRD's own scope. Depends on Chunks 1 and 4.

## Testing Decisions

- **`pico8_input_save`** (Chunk 2) gets ordinary unit tests, following `tests/test_pico8_input.c`'s existing pattern exactly (construct frames in memory, exercise the function, assert on results) — specifically round-tripping through the existing `pico8_input_load` (write N frames, load them back, assert every `mouse_x`/`mouse_y`/`mouse_buttons`/`dpad` value matches) so the writer and the existing, already-trusted reader are cross-checked against each other rather than against a second hand-written parser.
- **The coordinate-conversion pure function** (Chunk 3) gets its own small unit test: known window-pixel inputs at a known fixed scale map to known 128x128 outputs, including the clamping boundary (a coordinate outside the scaled window clamps into `[0, 127]`, not out of range or negative).
- **Everything else raylib-touching (window lifecycle, texture upload, live input polling, the overall `main_raylib.c` loop) has no automated test in this PRD's scope**, and is not expected to: it requires an actual window, which this project's execution policy forbids opening from an agent at any point, Phase 5 included (the policy only lifts for the human themselves). The only automated signal for this code is Chunk 5's compile/link step. Its real verification is the human playthrough that is this PRD's own explicitly out-of-scope "sortie de phase."
- **No new test binary is added to `make unit`/`make test` by this PRD.** `pico8_input_save`'s tests extend the existing `test_pico8_input` binary (same file, same link line — no new raylib dependency); the coordinate-conversion test can live in a small new raylib-free test file/binary since the function itself takes no raylib types, keeping `make test` exactly as fast and window-free as it is today.

## Out of Scope

- **The actual phase-closing human playthrough** (a human completing probe → wormhole → colonization → slipway → trade → score via the raylib backend without a crash, and confirming the mechanics match their understanding of the original cartridge) is `docs/plan.md`'s own stated Phase 5 exit criterion, and is explicitly **not** something any chunk in this PRD can complete autonomously — it requires a human to actually play an interactive session. Whoever runs this PRD's chunks (including via an unattended autopilot) should treat "the raylib backend compiles and links successfully" (Chunk 5) as the entire scope this document closes; the phase itself stays open until a human plays.
- The pre-Phase-5 REF-representation audit (`docs/plan.md`'s "audit systématique et ponctuel des sites de désambiguïsation REF non gardés") is already done and committed (see `docs/plan.md`'s own Notes de portage entry) — not re-scoped here.
- Any raylib UI/UX polish beyond faithfully presenting the existing 128x128 framebuffer and capturing mouse/keyboard input (resizable windows, alternate key bindings, on-screen debug overlays, fullscreen toggling, etc.) — none of it is asked for by the plan.
- `sfx`/`music` playback of any kind — explicitly out of scope for this entire port, not just the headless backend (`docs/plan.md`'s Garde-fous).
- Any change to `src/main.c`, or to any already-ported function's own logic — this PRD touches only new files and `pico8_input.h`/`.c`'s addition of one new function.
- A general "convert any `pico8_list_t`/positional data to/from JSON" facility, or any generalization of `pico8_input_save` beyond the one schema it already needs to write.
- PSX — untouched, per the plan's standing "PSX paused" decision.

## Further Notes

The recorded-session filename convention (`tmp/events_recorded_<timestamp>.json`) and the fixed integer window-scale factor are both simple, low-risk defaults chosen because no human was available to confirm a preference and neither is load-bearing for the plan's own success criteria; either can be changed later (e.g. if a human playtester wants a different scale) without touching anything else this PRD builds, since both are internal details of `pico8_raylib_backend`, not part of the mimicry API or the recording schema itself.
