## Problem Statement

`docs/plan.md` commits this project to porting `pico8/lua.lua` function-by-function into C (Phase 3), copying its logic verbatim rather than rewriting from the design doc. That literal port is only possible if the ported functions have something fixed to call: the PICO-8 drawing/input/memory primitives (`cls`, `pset`, `spr`, `map`, `mset`, `sget`, `circ`, `circfill`, `rect`, `rectfill`, `line`, `print`, `camera`, `palt`, `fillp`, `btn`, `stat`, `peek`, `poke`, `memcpy`) that `lua.lua` calls directly, including at literal hardware addresses (e.g. `memcpy(0x5f00,0x5000+shl(flr(no),4),16)`, `poke(0x5f2d,1)`, `poke(0x5f80,...)`). None of that API exists yet in this codebase: there is no C code at all beyond the unrelated, paused PSX smoke test (`psx-hello/`), and no `make test` target. Without this layer built first, and without a way to verify it non-interactively (the project's execution policy forbids opening any interactive window before Phase 5), Phase 3 has nothing correct to port onto and no way to catch a wrong primitive early.

## Solution

Build, in plain C with no raylib dependency, a software-rendered implementation of the PICO-8 API surface listed above, backed by a flat byte-addressable memory model that mirrors real PICO-8's address map closely enough that Phase 3's verbatim `peek`/`poke`/`memcpy` calls at literal PICO-8 addresses work unmodified. `main.c` loads the cart's already-extracted sprite and map data at startup, drives frames from a scripted `events.json` replay (mouse + D-pad, no live input), and can dump the framebuffer as plain text (no PNG) for headless inspection by a human or an agent. A demo program exercises at least one call from every category (pixel, shape, sprite, map, text, input, replay-driven frame, dump) and is wired into a new `make test` target whose assertions compare specific framebuffer bytes/`peek` values against hand-computed reference values — not just "the program ran without crashing."

## User Stories

1. As the developer porting `lua.lua` in Phase 3, I want a `cls()`/`pset()`/`spr()`/`map()`/`mset()`/`sget()`/`circ()`/`circfill()`/`rect()`/`rectfill()`/`line()`/`print()`/`camera()`/`palt()`/`fillp()` API with PICO-8's exact call signatures, so that I can paste ported function bodies against it without inventing translation shims.
2. As the developer porting `lua.lua`, I want `peek`/`poke`/`memcpy` to operate on a byte array whose addresses match real PICO-8's memory map (sprite sheet, map, general RAM, hardware/draw-state registers, screen), so that literal hardware-address calls like `memcpy(0x5f00,0x5000+shl(flr(no),4),16)` behave correctly without rewriting them.
3. As the developer, I want the cart's real sprite sheet and map data loaded automatically at startup from the already-extracted `pico8/` assets, so that `spr()`/`map()`/`sget()`/`mset()` calls in later phases render against the actual cart content, not placeholder data.
4. As the developer, I want `btn()` and `stat(32)`/`stat(33)`/`stat(34)` to read from a scripted, versionable `events.json` file instead of live input, so that a game-logic frame can be replayed identically by a human or an agent without opening a window.
5. As the developer, I want a plain-text framebuffer dump (not a PNG), so that I — or an agent with no image-decoding tool — can read the rendered output directly and diff it against a reference.
6. As the developer, I want a demo program that calls every category of the API and asserts precise byte-level results, so that a regression in any primitive is caught by `make test` immediately, without needing a running game to notice.
7. As the developer, I want `make test` to give a clear pass/fail signal (exit code + message), so that this becomes the standard way to verify every subsequent phase's changes, per `CLAUDE.md`'s "never run the project, use `make test`" rule.
8. As the developer, I want the memory model to stay a single flat array covering the addresses actually referenced by `lua.lua`'s scanned `peek`/`poke`/`memcpy` call sites, rather than a fully accurate emulation of every PICO-8 hardware register, so that Phase 1 doesn't spend effort emulating hardware behavior no ported function will ever touch.
9. As the developer, I want `sfx`/`music`/`fget`/`fset`/`mget`/`sset`/`pal`/`cursor`/`color`/`flip`/`btnp`/other unused PICO-8 API surface left unbuilt, matching the plan's explicit scope cut, so that Phase 1 doesn't grow beyond what `lua.lua` actually calls.
10. As the developer, I want `pico8/sprite.png` and `pico8/map.png` left untouched by this phase's code (human-facing previews only) and `pico8/gfx.json`/`pico8/map.json` used as the actual data source, so that asset loading doesn't depend on fragile PNG-to-palette-index decoding when an exact, already-decoded JSON source exists.
11. As a future maintainer, I want each engine module (memory, drawing, input/replay, asset loading, text dump) isolated behind a small, stable interface, so that Phase 5's raylib backend can later be swapped in without touching `main.c` or any ported game-logic function, per the plan's "interchangeable backend under a fixed API" architecture.
12. As the developer, I want the demo/test program's failures to point at exactly which primitive and which byte diverged from the hand-computed reference, so that debugging a broken primitive doesn't require re-deriving the whole expected framebuffer from scratch.

## Implementation Decisions

**Scope boundary.** This PRD covers only Phase 1 as written in `docs/plan.md`: the PICO-8 drawing/input/memory mimicry layer, cart asset loading, scripted replay, text dump, and the demo program wired to `make test`. No function from `pico8/lua.lua` is ported in this phase (that is Phase 3). No raylib code is written in this phase (that is Phase 5). No fixed-point arithmetic type, `rnd`/`sin`/`cos`, or entity/dispatch mechanism is built here (that is Phase 2).

**Module breakdown.** Five modules plus the demo:

- **`pico8_mem`** — the memory core. A single flat byte array covering PICO-8's real address space from `0x0000` up to (and including) the screen region ending at `0x7fff` (32 KiB total). Named offset constants mark the regions this project actually uses: sprite sheet at `0x0000`, map at `0x2000` (with the shared upper sprite-sheet/map region at `0x1000`–`0x1fff` available for the map's extra rows, since `pico8/map.json` reports a 128×64 cell grid — larger than the base 128×32 map region — matching real PICO-8's documented gfx/map memory sharing), and screen/framebuffer at `0x6000`. `peek`, `poke`, and `memcpy` are generic over the whole 32 KiB array — any address Phase 3 code passes (including hardware/draw-state addresses like `0x5f00`, `0x5f2d`, `0x5f80`, or general-purpose RAM like `0x5000`) just reads/writes that byte; no per-address special-casing or hardware-behavior emulation is built for addresses this phase doesn't otherwise use. Out-of-range addresses (outside `0x0000`–`0x7fff`) do not crash: `peek` returns 0, `poke`/`memcpy` are no-ops, matching real PICO-8's tolerant-hardware behavior rather than crashing a literal port that happens to touch an unmapped address. This is the deep module of this phase: a two-function-wide interface (`peek`/`poke`/`memcpy`, plus the named offsets) hiding the entire addressing scheme.
- **`pico8_gfx`** — drawing primitives and draw state. `cls`, `pset`, `circ`, `circfill`, `rect`, `rectfill`, `line`, `print`, `spr`, `map`, `mset`, `sget`, `camera`, `palt`, `fillp`. Holds the draw-state that isn't memory-mapped in this phase (current camera offset, transparency-mask bits, fill pattern) and reads/writes pixels through `pico8_mem`'s screen/sprite/map offsets. Signatures follow the call-site evidence scanned from `lua.lua`: `rectfill(x1,y1,x2,y2,col)`/`rect(x1,y1,x2,y2,col)` (color parameter optional in PICO-8; this port always requires it explicitly — no default-argument emulation, since C has no optional parameters and every scanned call site in scope passes one), `spr(n,x,y,w,h)` with `w`/`h` in sprite-size multiples (a `spr(n,x,y)` convenience wrapper defaulting `w=h=1` is provided since `ui:ev()`/`fn=function(p)...spr(f,p.x,p.y)...` call it with no size), `circ(x,y,r,col)`/`circfill(x,y,r,col)`, `line(x1,y1,x2,y2,col)`, `pset(x,y,col)`, `sget(x,y)` returns the color index at that sprite-sheet pixel, `mset(x,y,val)` writes a map cell, `map(cel_x,cel_y,sx,sy,cel_w,cel_h)`, `camera(x,y)` plus a no-arg `camera()` resetting to `(0,0)`, `fillp(pattern)` plus a no-arg `fillp()` resetting to the solid pattern, `palt(col,transparent)`, `print(str,x,y,col)`. This is the other deep module: a wide but individually simple call surface (matching PICO-8's own documented API, which is why it's stable) hiding pixel math, camera-offset translation, and fill-pattern/transparency handling.
- **`pico8_input`** — `btn(b)` (players beyond 0 are out of scope: no `lua.lua` call site in the drawing/input category needs a player argument for the D-pad path this phase covers) and `stat(n)` restricted to `32`/`33`/`34` (mouse x/y/button-bitmask), both backed by an `events.json` replay loaded once at startup and stepped one frame at a time. This is a deep module: it hides the JSON schema and per-frame bookkeeping behind exactly the two PICO-8 calls that read it.
- **Asset loading** — two small loader functions (not full modules): one parses `pico8/gfx.json`'s `{"width":128,"height":128,"pixels":[...]}` into `pico8_mem`'s sprite-sheet region, one parses `pico8/map.json`'s `{"width":128,"height":64,"cells":[...]}` into the map region (spanning the base map region plus the shared upper region for rows beyond 32). Both are called once from `main.c` at startup. `pico8/sprite.png` and `pico8/map.png` are not read by any C code in this phase — deliberate deviation from the plan text's literal mention of "`sprite.png`": `pico8/gfx.json` is the already-decoded, exact form of the same data (raw 0–15 palette indices), while `pico8/sprite.png` is a 512×512 RGBA render through the palette meant for human preview, and reversing it back to exact indices is unnecessary risk for no benefit when the exact data already exists in `pico8/gfx.json`. This deviation is recorded here and should also get a one-line entry in `docs/plan.md`'s "Notes de portage" journal once this phase starts.
- **Text dump** — one function serializing the screen region of `pico8_mem` to plain text. Format: a first line `128 128` (width height, decimal, space-separated), followed by 128 lines of exactly 128 lowercase hex digits each (one digit per pixel, `0`–`f`, no separators), one line per framebuffer row top-to-bottom. This is fixed-width and grep/diff-friendly, and a byte's screen position is directly recoverable from its line number and column offset — closer in spirit to a plain-text PPM header than to any binary/PNG format, per the plan's "format simple, pas de PNG... proche PPM."
- **Demo program** (`main.c` or a dedicated demo source file) — not a reusable module. Loads assets, loads `events.json`, calls at least one primitive per category (pixel: `pset`; shapes: `line`, `rect`, `circ`; sprite: `spr`; map: `map`; text: `print`), reads `btn`+`stat` once, steps at least one frame driven by `events.json`, and dumps the framebuffer as text. Wired into the new `make test` target.

**Framebuffer pixel format.** One byte per pixel storing a palette index `0`–`15` (unpacked — not PICO-8's real hardware packing of two 4-bit pixels per byte). Resolves the plan text's "128×128/8 couleurs": PICO-8's palette has 16 colors (confirmed by values up to 15 present in `pico8/gfx.json`), so "8 couleurs" is read as a loose/imprecise phrase, not a hard requirement to only support 8 colors — the deciding constraint is instead the plan's own test-methodology requirement that `make test` compare "les octets du framebuffer... à des valeurs de référence calculées à la main," which is far more tractable with one full-index byte per pixel than with hand-computed nibble packing. This is a deliberate divergence from real PICO-8 hardware layout, scoped narrowly: it applies only to the screen region. It does not weaken Phase 3 fidelity because the `lua.lua` call sites found via scanning `peek`/`poke`/`memcpy` do not touch the screen region directly (no `poke2`/`poke4`/raw screen-byte tricks are used, and those opcodes are already out of scope per the plan) — only hardware/general-RAM addresses (`0x5000`, `0x5f00`, `0x5f2d`, `0x5f80`) are touched directly, and those remain generic bytes in `pico8_mem` regardless of the screen's own pixel packing. The sprite sheet is stored the same way (one byte per pixel, matching `pico8/gfx.json`'s already-unpacked form) for the same reason: no scanned call site does a raw packed-nibble `peek`/`poke` on the sprite-sheet region either — all sprite-sheet reads/writes go through `sget`/`mset`/`spr`/`map`.

**`events.json` schema.**
```json
{
  "frames": [
    { "mouse_x": 64, "mouse_y": 64, "mouse_buttons": 1, "dpad": [false, true, false, false] }
  ]
}
```
One object per simulated frame, in order (frame index = array position). `mouse_x`/`mouse_y` feed `stat(32)`/`stat(33)` directly; `mouse_buttons` is the same bitmask PICO-8 exposes via `stat(34)` (bit 0 = left, bit 1 = right, bit 2 = middle); `dpad` is exactly the four booleans `btn(0)`..`btn(3)` read for that frame, in PICO-8's own button-index order (0 = left, 1 = right, 2 = up, 3 = down). Advancing past the last frame in the array is a hard error for this phase (no looping/clamping) — a headless replay running longer than its own script is treated as a test-authoring bug, not a runtime case to paper over.

**JSON parsing.** No general-purpose JSON library dependency is introduced. `pico8/gfx.json`, `pico8/map.json`, and `events.json` each have a fixed, simple, non-nested-beyond-one-level shape (flat integer arrays, one array of small flat objects with numeric/boolean fields, no string escaping needed). Each gets a small hand-written parser scoped to exactly its own shape, consistent with "simplicity first" — not a reusable general JSON module.

**Build.** A new `make test` target (added to the existing root `Makefile`, alongside the untouched `psn00bsdk-*`/`psx-hello*` targets) compiles the demo program and its dependencies with a plain C compiler (C99, no external libraries) and runs it; the demo asserts its own expected values internally (e.g. via `assert()`) and a nonzero exit code or `assert` failure fails the `make test` target. Asset and `events.json` file paths are resolved relative to the repository root (`pico8/gfx.json`, `pico8/map.json`, `events.json`), matching where `make test` is invoked from; no command-line argument handling is added in this phase.

## Implementation Chunks

Dependency-ordered; each chunk is TDD-sized and leaves the tree compiling with `make test` green (once the target exists from Chunk 1 onward, later chunks extend the same demo/test binary rather than starting a parallel one).

1. **`pico8_mem` core** — flat 32 KiB byte array, named region offsets (sprite sheet, map, screen), `peek`/`poke`/`memcpy`, out-of-range no-op/zero behavior. Unit tests: boundary addresses of each named region, an overlapping `memcpy`, an out-of-range `peek`/`poke`.
2. **Cart asset loading** — `pico8/gfx.json` → sprite-sheet region, `pico8/map.json` → map region (including the shared upper region for rows 32–63). Tests assert specific known pixel/cell values (from the JSON source) land at the expected computed memory offsets.
3. **Core framebuffer primitives** — `cls`, `pset`, `camera`, `palt` (the state and pixel-plot plumbing everything else in `pico8_gfx` builds on). Unit tests per primitive, including `camera` offset affecting subsequent `pset` placement and `palt` affecting a subsequent transparent-color draw.
4. **Shape primitives** — `line`, `rect`, `rectfill`, `circ`, `circfill`, `fillp`. Unit tests per primitive (including a `fillp` pattern altering a `rectfill`'s output) plus at least one degenerate case each (zero-length `line`, zero-radius `circ`, single-pixel `rect`).
5. **Sprite/map primitives** — `spr` (with and without explicit `w`/`h`), `map`, `mset`, `sget`. Unit tests reading back sprite pixels and map cells through the drawn framebuffer and through direct `sget`/map-region `peek`.
6. **Text rendering** — `print`. Requires deciding and embedding a fixed bitmap font table for PICO-8's built-in glyphs (not present in any extracted `pico8/` asset — it is part of PICO-8's runtime, not the cart), sized to whatever glyph set the demo exercises. Unit test: `print`ing a known short string and asserting the resulting pixels at known glyph-cell coordinates.
7. **Input/replay** — `events.json` parser + frame stepper, `btn`, `stat(32/33/34)`. Unit tests: multi-frame stepping matches each frame's `dpad`/`mouse_*` fields; a malformed/short `events.json` is treated as a hard error per the schema decision above.
8. **Text dump** — screen-region serializer in the `128 128` header + 128×128-hex-digit-rows format. Unit test: a small hand-drawn pattern (e.g. `cls` to one color then a couple of `pset` calls) dumps to the exact expected text, byte-for-byte.
9. **Demo program + `make test` wiring** — exercises every category per the plan's list, driven by one `events.json`-scripted frame, ending in a text dump; hand-computed assertions on framebuffer bytes/`peek` values after each demo call. This chunk is Phase 1's exit gate.

## Testing Decisions

- **What makes a good test here**: assert on the *output* of each PICO-8 call (specific framebuffer bytes at known `(x,y)` positions, specific `peek`/`sget` return values, specific `stat`/`btn` values for a given replay frame, or the dump's exact text) — never on internal representation details (e.g. never assert on `pico8_gfx`'s internal camera-offset field directly; assert on where a subsequent `pset` actually landed). This matches the plan's own explicit requirement that `make test` "fait des assertions précises... pas juste 'le programme tourne'."
- **Modules getting direct, focused unit-style tests** (beyond the demo's own end-to-end assertions): `pico8_mem` (region boundaries, `memcpy` overlap, out-of-range behavior), the cart asset loaders (`gfx.json`/`map.json` → memory), every `pico8_gfx` primitive individually (including degenerate/edge cases the single demo call per category won't exercise), the `events.json` parser/stepper, and the text-dump serializer. Each of these is a "deep module hides a format or an algorithm" case per the guideline used to resolve this PRD's open questions — isolating their tests means a bug in, say, the dump writer doesn't get misdiagnosed as a drawing bug.
- **What is not separately tested**: the demo program itself has no unit tests beyond being the thing `make test` runs — it *is* the integration/acceptance check the plan asks for. No test doubles/mocks for `pico8_mem` or the file system are introduced; tests run against the real cart assets in `pico8/` and real temporary/fixture `events.json` files, since the whole point of this phase is fidelity to the actual cart, not abstraction over it.
- **Prior art in this codebase**: none — this is the first C code and first test infrastructure in the repository (the removed `game/` prototype was Lua/Love2D; `psx-hello/` has no tests, only a manual boot-and-look verification checklist per `docs/psx-hello-world.md`). This phase establishes the pattern (plain C, `assert()`-based checks, a single `make test` entry point) that Phase 2's unit tests and smoke test will extend, per `docs/plan.md`'s own test strategy.
- **Execution policy**: nothing in this phase's tests opens a window or requires a display, consistent with `CLAUDE.md`'s "never run the project" and the plan's "jamais de fenêtre interactive lancée par l'agent avant la Phase 5." `make test` is the only way this phase's work is verified.

## Out of Scope

- Porting any `pico8/lua.lua` function or game-logic behavior (Phase 3).
- The fixed-point 16.16 numeric type, `rnd`/`sin`/`cos`/`sqrt`/`mid`/`flr`/`abs`/`sgn`/`band`/`bor`/`shl`, vector/geometry helpers, list/string primitives, the `ob()`/`fi()` data-description mini-language, and the entity/dispatch mechanism (`kv:jr`, `hv`/`cv`/`cg`, `dc`/`mv`/`lt`/`he`) — all Phase 2.
- Any raylib code, window, live input, or the recording mode that produces `events.json` from a live session — all Phase 5.
- `sfx`, `music` (explicitly out of scope for the whole project) and any PICO-8 API `lua.lua` never calls: `sspr`, `fget`/`fset`, `mget`, `sset`, `pal`, `cursor`, `color`, `flip`, `btnp`, `peek2`/`peek4`, `poke2`/`poke4`, `cartdata`, `dget`/`dset`, coroutines, `atan2`.
- `btn`/`stat` support for a second player index, or for any `stat` index other than `32`/`33`/`34`.
- Decoding `pico8/sprite.png` or `pico8/map.png`; both remain unread by any code produced in this phase.
- Emulating real PICO-8's packed (2-pixels-per-byte) memory layout for the sprite-sheet or screen regions, or emulating the documented behavior of any hardware/draw-state register this phase's scanned call sites don't touch.
- A command-line interface, configurable asset/replay paths, or any tooling for authoring `events.json` by hand beyond writing plain JSON.

## Further Notes

- The literal-address memory model (`pico8_mem`) is this phase's highest-risk piece to get subtly wrong in a way that only surfaces in Phase 3: if a future ported function touches a hardware address whose real PICO-8 behavior actually matters (not just "store and retrieve a byte"), Phase 1's generic-byte-array model will silently do the wrong thing rather than fail loudly. When Phase 3 hits such a case, per `docs/plan.md`'s "Notes de portage" policy, the resolution should be logged there rather than re-litigated, and `pico8_mem` extended with the specific special-cased behavior needed — not redesigned wholesale.
- The built-in PICO-8 font needed for `print` (Chunk 6) is not present anywhere in the extracted `pico8/` cart assets (it's part of the PICO-8 runtime, not the cart), so it must be sourced or hand-encoded separately when that chunk is implemented; this PRD flags the gap but does not resolve the exact glyph table here.
- `pico8/gff.json`, `pico8/label.json`, `pico8/music.json`, `pico8/sfx.json` are cart assets not touched by this phase (sprite flags, cart label, music, sound — all tied to out-of-scope API surface) and are not loaded by any code this PRD describes.
