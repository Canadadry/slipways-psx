## Problem Statement

Phase 1 built the raylib-free drawing/input/memory mimicry layer (`pico8_gfx`/`pico8_mem`/`pico8_input`/`pico8_assets`/`pico8_dump`). Phase 2 built the numeric/structural foundation on top of it: fixed-point arithmetic, the `km` vector type, the `cl`/`ee`/`be` geometry helpers, the `add`/`del`/`all`/`foreach`/`sub`/`tostr` primitives, the `ob()`/`fi()` data-description mini-language, and the `kv:jr` class system plus its `hv`/`cv`/`cg`/`lt`/`he`/`dc`/`mv` entity-dispatch mechanism (`pico8_fixed`, `pico8_vec`, `pico8_geom`, `pico8_value`, `pico8_list`, `pico8_str`, `pico8_ob`, `pico8_class`, `pico8_entity`). None of the actual game — planets, probes, slipways, trade, the score screen, the mouse/keyboard UI panel dispatcher, the galaxy bootstrap — exists yet: `pico8/lua.lua` still has roughly 140-165 remaining top-level functions and class methods (the plan's own estimate, "~140", is a round number; this PRD's own line-by-line read of the file counts closer to 165 once every one-line class method is counted individually) that are called, directly or transitively, from `_init`, `_update60`, or `_draw`, and none of them are ported. Without them the project cannot reach Phase 4 (headless playability verification), whose entry gate is explicitly "every function reachable from `_init`/`_update60`/`_draw` is ported."

This is also, by the plan's own admission, the phase most likely to regress Phase 1's drawing/memory primitives or Phase 2's entity/dispatch mechanism, since it is the first phase to actually exercise both together at scale (dozens of concrete entity classes, each with several dispatched methods, reading/writing the shared framebuffer and memory-mapped regions) rather than in isolation or through 1-2 fake smoke-test entities.

A second, narrower problem this PRD's own analysis surfaced: Phase 2's `pico8_mv` (the port of `mv(e,rm,...)`) and its underlying `pico8_value_function_t` typedef were deliberately built to take exactly one extra argument, justified at the time by the only two call sites Phase 2's own scope needed (`dc()`'s `entity[nt](entity,entity.ra)` and the placeholder `mo:md(ci[o])`). Reading the rest of `lua.lua`, real `mv()` call sites in Phase 3's scope pass zero, one, or two extra arguments (e.g. `mv(self,"lh")` with none, `mv(held,"ey",nw and nw.kv)` with one, `mv(e,"hd",self.qa,je.ra)` with two) — Phase 2's own single-arg signature cannot serve the UI dispatcher (`ui`, this phase's Chunk 5) without being extended.

## Solution

Port every remaining function/method in `pico8/lua.lua`, keeping its exact minified name and pasting its exact Lua source in a comment directly above the C port, exactly as Phases 1-2 already established and as `docs/plan.md`'s "Garde-fous" require. No rewrite, no renaming, no "improving" a function while porting it. The order is dependency-driven (callee before caller), not feature-driven, per the plan's own explicit rejection of "vertical slice" ordering for a literal monolith port. This PRD's own read of `pico8/lua.lua` (all 1494 lines, read in full) produces the dependency-ordered wave breakdown below — the "real analysis" this step asked for, not a placeholder.

Within each wave (== one lot == one checkpoint, per `docs/plan.md`'s own definition), the same three cheap checks the plan mandates run: (1) grep `src/` for an existing helper — including the two named recurring patterns, `strdup`-like string duplication and doubling-capacity growable arrays — before adding a new private one; (2) compare each touched module's line count against the already-twice-flagged ~430-540 line range and note any crossing in `docs/portage-progress.md`'s "module cible" column; (3) if the wave is the first to exercise `kv:jr`/`hv`/`cv`/`cg`/`dc`/`mv`/`lt`/`he` in a structurally new way relative to Phase 2's smoke test, extend that smoke test with a targeted case. `make test` (Phase 1's demonstration, Phase 2's unit tests and smoke test) must stay green after every wave.

`docs/portage-progress.md` (already scaffolded by Phase 2, currently empty) is the live per-function tracker for this phase — this PRD's wave breakdown (Implementation Chunks, below) is what its `## Vague N` sections should be seeded from as implementation starts, one row per function/method, "restante" until ported.

## Implementation Decisions

**Scope boundary.** This PRD covers only the remaining `pico8/lua.lua` functions/methods reachable from `_init`/`_update60`/`_draw` and not already ported by Phase 1 or Phase 2. It does not cover Phase 4 (headless `events.json` replay verification of the probe→wormhole→colonization→slipway→trade→score loop) or Phase 5 (raylib backend, live interaction) — both explicitly out of scope per the plan's own phase boundaries. `sfx`/`music` remain no-op per the plan's guardrail; this PRD only adds the missing trivial stub *functions* those no-ops need (see Chunk 1), it does not give them real behavior.

**`pico8_mv` / `pico8_value_function_t` arity extension (Chunk 5).** Evidenced from every real `mv()` call site in scope (grepped across the whole file, not just `ui`): the maximum extra-argument count any call site ever needs is **two**. `pico8_value_function_t` is extended from `pico8_value_t (*)(void *self, pico8_value_t arg)` to take a small fixed-size argument list (an argument count plus up to two `pico8_value_t` slots — not a general variadic mechanism, since no evidence anywhere in scope needs more than two), and `pico8_mv`'s signature grows the same way. `dc()`'s own single-argument dispatch (`entity[nt](entity,entity.ra)`) and the placeholder `mo:md(ci[o])` — Phase 2's own two call sites — keep working unchanged by passing an argument count of 1. This is an evidenced, narrowly-scoped extension of a module Phase 2 explicitly built as a starting point (compare the `mo`/`ci` placeholders' own "Phase 3 is expected to give it real content" framing in the Phase 2 PRD's Further Notes) — not a rewrite, not a speculative "make it fully variadic just in case."

**The `pi` table has two independent consumers needing two separate lookup tables (Chunks 2, 4, 8, 15, 17).** `pico8_ob_register_constructor`/`pico8_ob_lookup_constructor` (Phase 2, `char id` key) continue to serve exactly what they were built for: `ob()`'s own single-character `sc`-based nested-constructor branch. Only `'b'` (→ `qz`) and `'v'` (→ `pico8_vec_v`, already built but never registered by Phase 2, per that PRD's own "deliberately does NOT register" note) are ever actually reachable through this path in real spec strings found by this PRD's read of the file; `'s'` (→ `spr`) is registered too for completeness even though no in-scope spec string is confirmed to invoke it via `s(...)` construction syntax. A second, new, small string-keyed lookup table (name → function, e.g. `pico8_pi_dispatch_register(const char *name, ...)` / `pico8_pi_dispatch_lookup(const char *name)`, living in whichever module owns `bl()`) serves `bl()`'s own `oo(pi[e.fn],e)` call, which indexes by the *full* string held in an entity's `.fn` field (`"br"`→`rk`, `"qr"`→`io`, `"rf"`→`eq`, `"ld"`→`lq`'s `ol` method, `"s"`→`spr`) — exactly the keys `pico8_ob.h`'s own comment already flagged as *unreachable through `ob()`'s path* (correctly: `sc` is always one character), which this PRD confirms are fully reachable and load-bearing through `bl()`'s separate path. Each registration happens in the wave that ports the function being registered (`qz`/`v` in Chunk 1/2, `rk`/`eq`/`io` already available from Chunk 1, `lq.ol` in Chunk 3, `spr` already Phase 1) — `bl()` itself (Chunk 2) only needs the lookup mechanism to exist; registrations land progressively as their target functions do.

**Singleton globals ownership (Chunks 4-6, 10, 12).** `mo` (a `qb` instance — camera/scroll), `je` (an `nf` instance — mouse/D-pad reader), `ok` (a `ui` instance — click/panel dispatcher) are constructed by completing `jl()` once `qb`/`nf`/`ui` exist (Chunk 6); `fm` (an `hy` instance — economy state) and `ju` (a `pj` instance — score panel) are constructed by `eu()` (Chunk 22, alongside `dk` — the selected difficulty-option table — and the bootstrap loop building the starting building-slot `ie` entities); `kc` (the currently-open `mh` message-box instance, or none) is a plain mutable global set by `mh:pq()`/read by `pj:ph()`. All of these are module-level C globals declared in the module that owns the class responsible for constructing them (`mo`/`je`/`ok` alongside the completed `jl()`, in whichever module Chunk 6 lands in; `fm`/`ju`/`dk` alongside `eu()`, in whichever module Chunk 22 lands in; `kc` alongside `mh`, Chunk 8) with a small header declaring accessors for any other module that needs to read one — mirroring `pico8_entity.h`'s own `pico8_mo()`-style accessor convention rather than exposing raw `extern` globals across module boundaries.

**`sfx`/`music` stubs (Chunk 1).** `pico8_sfx(int n, int channel)` and `pico8_music(int n)` are added as literal no-ops (matching bodies: do nothing, return nothing) to whichever module already hosts the Phase 1 host-builtin mimicry layer's simplest stubs — this is the first and only place either function is defined; the plan's "son hors périmètre" guardrail means neither ever gets real behavior in this project.

**Module layout is not pre-decided by this PRD.** Following Phase 2's own established practice (small modules per concern, checked against the ~430-540-line disproportionate-size range after every wave, per `docs/plan.md`'s Phase 3 checkpoint rules), the specific `.c`/`.h` files each wave's functions land in are left to be decided during implementation and recorded in `docs/portage-progress.md`'s "module cible" column, not fixed here. A reasonable default (grouping each wave's class(es) and their direct standalone-function dependencies into one or two new modules) is a starting point, not a mandate — if a wave's natural module already exists and isn't near the size threshold, adding to it is fine; if a wave is large enough to threaten the threshold up front (Chunk 13, `jo`), splitting its own module preemptively is a legitimate call for that wave's own implementer to make and log.

**Data-table initialization sequencing (Chunk 11).** The non-function, top-level statements `pico8/lua.lua` runs once at cart-load time to build `r`/`iz`/`df`/`hc`/`fd`/`gb`/`rr`/`dr`/`nb`/`ek` (including the two `foreach(_,ho(...))` field-renaming passes and the `for ri in all(fd) do...add(gb,hp(ri))end` loop) are ported as the body of one explicit C function (this phase's own equivalent of a "module load" step, not folded into `_init()` or `jl()`, neither of which the original source ties this data-building code to — it runs unconditionally at chunk-load time, before either is ever called), called once during process/test startup before anything in Chunks 11+ is exercised.

**Forward references are ported, not deferred.** Every forward reference this PRD's dependency analysis found (`bg:ldown`→`mz`/`g_`; `bv`/`dl`/`d_`→`fm`; `jo:hu`→`kv[hp.cw]`'s runtime-resolved class) is handled the same way: the calling function's exact Lua source is still pasted and ported in its own wave, compiling cleanly against the already-built generic mechanisms (`pico8_class_lookup` for dynamic-by-name instantiation, ordinary field/global access for `fm`/`mo`), simply not meaningfully *exercisable* until its forward-referenced partner's own later wave lands. This is the same treatment Phase 2 already gave the `mo:md()`/`"kj"` dead branch — not a new pattern this phase invents.

**The mutually-recursive trade cluster is not force-ordered.** `jo:cn`, `nr:cn`, `jo:kf`, `mx:kf`, `jo:ib`, `jo:kd`, `trade:kg`, `jc:eb` genuinely call into each other depending on the runtime class of the entity at the other end of a trade route (a planet's `:cn` can invoke another planet's `:cn`, which may be the base `jo:cn` or an override like `nr:cn`, depending on what that specific route connects to). No linear function-before-caller order exists for this cluster; each is ported in its own class's wave (`jo`'s in Chunk 13, `jc`'s `eb` in Chunk 14, `nr`'s/`mx`'s overrides in Chunk 15) relying on the class system's existing dynamic dispatch to resolve the actual call at runtime, exactly as the plan's own "Stratégie de portage" already commits to for the whole entity mechanism.

## Implementation Chunks

Dependency-ordered per this PRD's own read of `pico8/lua.lua`; each is TDD-sized in the sense Phase 3 defines TDD for this phase (no per-function unit test — the exact-Lua-source-comment-above-the-port comparison *is* the test, per `docs/plan.md`'s "Stratégie de test") and leaves `make test` green. Each chunk == one wave == one lot for the plan's own checkpoint (module-size check, duplication-pattern grep, entity/dispatch smoke-test-coverage check). Function/method counts below are this PRD's own count from reading the source, not the plan's round "~140" estimate (which is close, not exact).

1. **Generic pure helpers, list/data glue, and the missing audio stubs** (~27 functions: `ft`, `qj`, `mw`, `gu`, `jp`, `nv`, `la`, `oo`, `ne`, `ij`, `rn` (+ new `pico8_sfx`/`pico8_music` no-op stubs), `jf`, `bu`, `qz`, `gk`, `na`, `ma`, `gd`, `cu`, `dv`, `rk`, `eq`, `io`, `unstash`, `gn`, `ho`; plus the pure data literals `gt`, `er`, `es`, `ct`, `b_`, `co`, `bn`/`bq`, `fb`, and `r`/`iz` via `unstash`). None of these call any other not-yet-ported Phase 3 function — every dependency is a Phase 1/2 primitive (`add`,`all`,`foreach`,`sub`,`peek`,`sqrt`,`sin`,`mid`,`band`,`shl`,`sget`,`poke`,`memcpy`,`rectfill`,`rect`,`spr`,`print`, `qm`/vector ops, `sgn`). Large enough that the implementer may split it into 2-3 sub-lots by sub-concern (table/list helpers vs. drawing-composition helpers vs. misc/data) without changing this wave's own dependency status — none of these sub-splits depend on each other.
2. **`pi`'s dual-registry glue + `bl()`** — the two separate lookup mechanisms decided above; registers `'b'`→`qz`, `'v'`→`pico8_vec_v` into the existing `char`-keyed `pico8_ob` registry, adds the new string-keyed registry for `bl()`'s own `oo(pi[e.fn],e)` path, and ports `bl(rb,nc)` itself.
3. **Root classes with no cross-class dependency** — `ke` (+ `ke.pq=lt`, `ke:ks`), `lq` (`pq`,`ol`,`mn`, plus `pi.ld=lq.ol`'s registration into Chunk 2's string-keyed table), `jb` (`pq`,`ol`), `trade` (`to`,`kg`,`__eq`). None of these four extends or references another not-yet-built class.
4. **`ke`'s shallow subclasses** — `nf` (`pq`,`ph`, using Chunk 1's `bu`), `js` (`pq`,`ph`,`ev`,`kj`,`ldown`, using Chunk 3's `lq`/`jb`, Chunk 1's `rn`/`gk`), `fq` (`ldown`), `qb` (`ph`,`md`, using Chunk 1's `ma`, Phase 1's `btn` — including the documented "`btn(b,1)` always false" decision).
5. **`ui` class** (`lj`,`ev`,`gw`,`bh`,`jz`,`cj`) — depends on Chunk 4's `nf`/`qb` (via `je`/`mo`, not yet real singletons — see Chunk 6), Chunk 1's `gu`/`ft`, and is the wave that forces the `pico8_mv` arity extension decided above (first real 0- and 2-argument `mv()` call sites).
6. **`jl()` completion + `dg()`** — extends Phase 2's `pico8_entity_init()`-based `jl()` with the real `mo=qb()`/`je=nf()`/`ok=ui()` construction and the singleton-ownership decision above; ports `dg()`, the per-tick `hv` dispatch loop. Structurally has no remaining-function dependency of its own beyond Chunk 4/5's classes existing.
7. **`bg` class** (`pq`,`kj`,`ldown`,`rdown`,`hq`) — background/starfield rendering and camera-drag. `bg:ldown` forward-references `mz`/`g_` (Chunks 10/16, not yet ported) — ported as a literal, compiling call, not meaningfully exercisable until both exist (see Implementation Decisions).
8. **`mh`, `iv` classes + `pz()` standalone** (`mh:pq`,`mh:ev`; `iv:pq`,`iv:ph`,`iv:kj`; `pz(p,bs)`) — message-box and floating-notification machinery, needed by many later classes (`jo`, `pj`, `nr`, `bg`'s indirect callers). Depends on Chunk 3's `js`, Chunk 6's `ok`, Chunk 2's `bl`.
9. **Particle-system helpers** `f_`, `ez`, `ei` — used (via direct assignment, not inheritance) by `g_`/`ga`/`hj`'s `pq`/`kj` fields. `ez` calls `self:mm()` polymorphically (resolved once a concrete class defines `mm`, Chunks 10/15) — ported now since `f_`/`ez`/`ei` themselves have no other unported dependency.
10. **`bv`/`dl`/`d_` standalone handlers + `g_` class** (`g_:mm`, plus its `hq=bv`/`ev=dl`/`ey=d_`/`pq=f_`/`kj=ei` field assignments reusing Chunks 8-9's work) — the probe entity. `bv`/`dl`/`d_` forward-reference `fm` (Chunk 12's `hy` instance, not yet real) via `fm:lu()` — same forward-reference treatment as Chunk 7.
11. **Research/tech foundation** — `hp` class (`pq`,`lq`,`jb`,`po`,`od`), the standalone `jo.ex` (used by both `hp:lq` and, later, `jo:hb`), `bj(jo)`, `oj`,`ov`,`gi`,`cb` (economy/tech-gate predicates — `oj`/`gi`/`cb` forward-reference `fm`, same pattern as Chunk 10), and the "game data init" function from Implementation Decisions building `r`/`iz`/`df`/`hc`/`fd`/`gb`/`rr`/`dr`/`nb`/`ek` (including `df`'s and `nb`'s `foreach(_,ho(...))` renaming passes). Depends on Chunk 3's `lq`, Chunk 1's `tostr`(Phase 2)/`ho`/`unstash`.
12. **`hy` class + economy formulas** (`hy:pq`,`nx`,`hk`,`lu`,`lj`,`kt`; standalone `cm`,`bx`,`ck`,`dj`,`bk`,`bd`,`bb`,`dh`,`da`,`cz`,`db`,`ky`,`bf`) — the economy singleton and every pure(-ish) formula over `cg.jo`/`cg.qh`/`cg.hb`/`cg.hk`. Depends on Chunk 11's `oj`/`gi`/`cb`. Forward-references the not-yet-built `jo`/`qh` classes' concrete fields (`.kw`,`.jy`,`.by`,`.mi`, etc.) and collections (`cg.jo`,`cg.qh`) the same way Chunk 7/10 forward-reference their own partners — compiles and is source/port-comparable now, only end-to-end exercisable once Chunk 13 lands.
13. **`jo` class** (`pq`,`hh`,`ldown`,`fe`,`gh`,`gg`,`hu`,`lz`,`kf`,`kd`,`ll`,`gv`,`cn`,`ib`,`hk`,`kj` — 16 methods, this phase's single largest concentration on one class) — the base planet entity. ## Testing Decisions

- **No per-function unit test, for any chunk in this phase** — per `docs/plan.md`'s own explicit "Stratégie de test" for Phase 3: the exact Lua source pasted in a comment directly above each ported C function, compared line by line, *is* the verification. This is not re-litigated here; it is the one testing decision the plan itself already made for this whole phase.
- **`make test` stays green after every wave/chunk** — Phase 1's demonstration program's assertions, Phase 2's unit tests, and Phase 2's entity/dispatch smoke test all keep passing. This is a regression gate, not new test-writing work for this phase's own functions.
- **The entity/dispatch smoke test gets extended, not left alone, when a wave first exercises the mechanism in a structurally new way.** Concretely, at minimum: Chunk 4 (first real multi-level inheritance chain deeper than Phase 2's smoke test used — `js`/`nf`/`fq`/`qb` all extend `ke`, which itself extends `kv`), Chunk 13 (`jo`'s own subclass tree, `qh`→`hj`→`pm`/`mx`, is the deepest chain in the whole cart, and `dc("kj")` gets its first real, non-dead exercise once `mo` is the real `qb` instance rather than Phase 2's empty placeholder), and Chunk 15 (the first wave combining `cv`/`cg` membership across a wide, varied set of sibling/cousin classes) are the most likely candidates; whichever chunk's implementer is first to notice a genuinely new combination not covered by Phase 2's smoke test extends it with a targeted case, per the plan's own third per-lot check.
- **Duplication grep runs every wave, not just once** — before adding any new private helper, grep `src/` for an existing one, and explicitly check whether the new code reimplements the `strdup`-like string-duplication or doubling-capacity growable-array patterns already found independently in `pico8_value.c`/`pico8_ob.c`/`pico8_class.c`/`pico8_entity.c` (Phase 2's own `warn-review` finding) — a grep by function name won't catch either, since each existing occurrence is an inline block, not a named call.
- **Module-size check runs every wave** — compare each touched module's line count to the ~430-540-line range already twice flagged, note any crossing in `docs/portage-progress.md`'s "module cible" column. Chunk 13 (`jo`, 16 methods) is flagged in advance as the single most likely chunk to cross this threshold on its own.
- **No new test framework or convention** — this phase reuses exactly Phase 1/2's `make test`/`unit`/`demo` Makefile targets; nothing here introduces a parallel build or test runner.
