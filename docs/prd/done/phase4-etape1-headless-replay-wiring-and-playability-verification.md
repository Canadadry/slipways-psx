## Problem Statement

Phase 3 finished porting every function reachable from `_init`/`_update60`/`_draw` (`docs/portage-progress.md`'s Vague 22, `src/pico8_cart.c`/`.h`: `pico8_cart_load()`, `pico8__init()`, `pico8_eu()`, `pico8__update60()`, `pico8__draw()`), but that chunk deliberately left all four entry points unwired from `main.c` and the `Makefile` — its own closing note is explicit that this is Phase 4/5's job, not its own. Today there is literally no way to run the ported game: `src/main.c` is still Phase 1's demo program, a flat sequence of `assert()` calls exercising individual PICO-8 primitives (`pset`/`line`/`rect`/`circ`/`spr`/`map`/`print`, one asset check, one `events.json`-driven input step, one framebuffer dump) — it never calls `pico8_cart_load()` or any of the four entry points. Without a real game loop, none of the invariant checks `docs/plan.md` requires for Phase 4's exit gate (planet count staying plausible, credits staying in a sane order of magnitude, no crash) can even be attempted, because there is no code path that plays the game at all.

`docs/plan.md`'s own Phase 4 text also flags a structural fork that has to be resolved before any of that wiring work starts: does `main.c` itself become the headless-replay driver (which would require relocating Phase 1's demo assertions to a dedicated test target, so they don't lose their regression coverage), or does a separate replay binary get added alongside Phase 1's untouched demo `main.c`? The plan is explicit that this must be settled and recorded at the start of Phase 4, not discovered mid-chunk.

## Solution

`main.c` becomes the project's one real headless game driver: it loads the cart assets, wires the dispatch context (gfx/mem/input), calls `pico8_cart_load()` once, drives `pico8__init()`/`pico8_eu()`/`pico8__update60()`/`pico8__draw()` frame-by-frame from a scripted `events.json`, and dumps the final framebuffer as text — never opening a window, matching this project's execution policy at every phase before 5. Phase 1's demo assertions (currently all of `main.c`) are relocated verbatim into a new dedicated test file so they keep running as regression coverage under `make test`, without being entangled with the new driver's own logic.

On top of that driver, a second, dedicated headless test program authors and runs the actual Phase 4 exit-gate scenario: a scripted `events.json` playthrough that exercises the probe → wormhole → colonization → slipway → trade → score chain, calling the same four entry points directly (not by shelling out to the `main.c` binary) so it can also read the live entity/economy state after each stage and assert the plan's two invariants — planet count (`pico8_cg("jo")`'s length) staying in `[0, 90]`, and credits (`pico8_ju()`'s `"nz"` field) staying in a plausible order of magnitude with no overflow-shaped jump — rather than relying on eyeballing a text framebuffer dump for numeric state that was never meant to be read out of pixels.

## User Stories

1. As the developer verifying the ported cart, I want a headless binary that boots the fully-assembled game (`pico8_cart_load()` → `pico8__init()`) and steps it forward frame-by-frame from a scripted `events.json`, so that I have, for the first time in this project, an actual runnable instance of the ported game to observe.
2. As the developer, I want that binary to never open an interactive window, reading all input from `events.json` and writing all output as a text framebuffer dump, so that it respects this project's "no interactive window before Phase 5" execution policy and stays usable in a sandboxed/CI environment.
3. As the developer, I want Phase 1's existing demo assertions (byte-level checks on individual PICO-8 primitives) to keep running exactly as before after this rewiring, so that Phase 1's regression coverage isn't silently lost when `main.c`'s role changes.
4. As the developer, I want the difficulty-select step (`pico8_eu()`, the real first player action in the actual cart) to be a first-class, deliberate part of the driver's boot sequence, so that the replay reflects how the real game actually starts rather than skipping straight into `_update60()`/`_draw()` against a game that was never "selected into."
5. As the developer, I want a scripted playthrough that reaches, in order, probe launch, wormhole traversal, colonization, slipway construction, trade route setup, and a score/credit-affecting tick, so that Phase 4's plan-mandated exit-gate chain is actually exercised end-to-end by one script, not asserted by assumption.
6. As the developer, I want the number of live planet entities (`cg["jo"]`'s count) checked after each of those stages against a plausible range (never negative, never above 90), so that a counting bug (double-registration, a leak in the entity/tag collections) is caught mechanically instead of requiring a human to eyeball a planet count.
7. As the developer, I want the player's credits (`hy`'s `"nz"` field) checked after each stage against a "no aberrant jump" rule rather than a "never negative" rule, so that the check matches the real game's own documented economy behavior (`hy:hk()`'s `self.nz+=self.ge` has no floor) instead of asserting something the real cart doesn't guarantee.
8. As the developer, I want this scripted scenario and its invariant assertions to be a permanent, automated test wired into `make test`/`make unit`, not a disposable verification program, so that Phase 4's exit gate stays enforced as a regression check for the rest of this project (Phase 5 onward), the same way Phase 1/2/3's own dedicated test binaries do.
9. As the developer, I want the new headless driver (`main.c`) to stay a thin, general-purpose "load assets, wire dispatch context, run `events.json`, dump text" shell with no game-specific assertions baked into it, so that Phase 5's raylib backend can later reuse the exact same driver shape (per `docs/plan.md`'s own "same `main.c`, only the backend changes" architecture) instead of needing its own bespoke entry point.
10. As the developer, I want the fork-in-the-road decision (`main.c`-as-driver vs. a separate replay binary) settled and recorded once, here, rather than re-litigated mid-implementation, so that later chunks of this phase build on a fixed foundation.
11. As the developer, I want the new scripted `events.json` fixture for the full playthrough kept separate from the small, already-existing root `events.json` fixture (used by Phase 1's relocated demo test and by `pico8_input`'s own unit tests), so that extending or fixing one script never risks silently breaking the other's unrelated assertions.
12. As the developer, I want any genuinely new bug this phase's own first real full-game exercise uncovers (in the spirit of the several real bugs Phase 3's own chunks found and fixed in already-shipped code) fixed and logged in `docs/portage-progress.md`, not worked around silently, consistent with this project's established practice.
13. As a future maintainer reading `docs/plan.md`'s Phase 5 section, I want Phase 4's output to be a driver that already matches the "backend interchangeable under a fixed API, `main.c` untouched" architecture, so that Phase 5 really can swap in the raylib backend without touching `main.c` or any ported function, as the plan promises.

## Implementation Decisions

**Fork-in-the-road, settled: `main.c` becomes the headless-replay driver.** `docs/plan.md`'s own Phase 5 section states the raylib backend is swapped in "sans toucher `main.c` ni aucune fonction portée — seul le backend change" — that sentence only makes sense if, by the end of Phase 4, `main.c` already *is* the one real game-loop driver sitting on top of the fixed mimicry API, with only the gfx/input backend swapped out from under it in Phase 5. Introducing a second, separate replay binary now would mean Phase 5 either has to introduce a third entry point of its own or retroactively fold the separate binary back into `main.c` — both add churn the plan doesn't ask for. `main.c` becomes the driver; Phase 1's demo assertions move to a new dedicated test file, `tests/test_pico8_demo.c`, containing exactly Phase 1's existing `assert()` sequence (moved, not rewritten) against the same narrow set of Phase 1 modules (`pico8_mem`, `pico8_assets`, `pico8_gfx`, `pico8_input`, `pico8_dump`) it already depended on — no engine-wide link closure for this test, since none of its assertions touch the entity/cart layer.

**New `main.c` responsibilities (thin driver, no game-specific assertions).** In order: load `pico8/gfx.json`/`pico8/map.json` into a `pico8_mem_t` (unchanged from Phase 1), load `events.json` into a `pico8_input_t`, wire `pico8_dispatch_set_gfx`/`pico8_dispatch_set_mem`/`pico8_dispatch_set_input` (`pico8_dispatch_context.h`, built in Phase 3 chunk 4 for exactly this purpose but never yet driven for real), call `pico8_cart_load()` once, call `pico8__init()` once, dispatch one `pico8_eu()` call against a real `js` difficulty-button instance (mirroring the real cart's own "player clicks a difficulty" first action — the same call shape Phase 3 chunk 22's own disposable verification program already used: an instance built from a positional entry of `bo`), then loop over every remaining `events.json` frame calling `pico8_dispatch_set_input()` with that frame, `pico8__update60()`, `pico8__draw()`, `pico8_input_step()`. After the last frame, dump the final framebuffer as text (`pico8_dump_screen`) to a fixed output path (`tmp/pico8_replay_dump.txt`, matching Phase 1's existing `tmp/pico8_demo_dump.txt` convention). No `assert()`-based gameplay checks live in `main.c` itself — it is a general-purpose "run this `events.json` against the real cart, dump the result" shell, reusable by any future script including Phase 5's own recording playback.

**A second, dedicated program owns the actual exit-gate scenario and its invariants.** `main.c`'s dump is pixels, not numbers — it cannot itself assert "the planet count stayed under 90" or "credits didn't jump aberrantly." A new test program (not `main.c`, not a disposable throwaway) drives the same four entry points directly against a full, purpose-authored `events.json` scripting the probe→wormhole→colonization→slipway→trade→score chain, and after each named stage reads live state directly through already-existing generic accessors — no new accessor functions are introduced for this: planet count via `pico8_cg("jo")`'s returned list length, credits via `pico8_instance_get_field(pico8_ju(), "nz", &value)` (the same generic field-read mechanism already used by, e.g., `tests/test_pico8_data_init.c`). This program is wired into the `unit` target (and therefore `make test`), the same way `test_pico8_data_init`/`test_pico8_planet_kj_dispatch` were in Phase 3 — a permanent regression check, not a disposable verification program.

**Module boundary: no new deep module beyond the plumbing that already exists.** The wiring itself needs no new abstraction: `pico8_cart` (bootstrap + entry points), `pico8_input` (events.json parsing/stepping), `pico8_dispatch_context` (gfx/mem/input handoff), and `pico8_dump` (text output) already exist and already have the exact shape this phase needs. `main.c` and the new test program are both thin call sequences over that existing plumbing — consistent with "simplicity first": no new "headless replay engine" module is introduced for a loop that is five function calls per frame.

**Two `events.json` fixtures, kept separate.** The existing root `events.json` (2 frames) stays exactly as-is — it is Phase 1's fixture, still used by the relocated `tests/test_pico8_demo.c` and by `tests/test_pico8_input.c`. The new scripted playthrough gets its own fixture, `tests/fixtures/phase4_playthrough_events.json`, authored specifically to drive the probe→wormhole→colonization→slipway→trade→score chain (mouse coordinates and clicks discovered against the real `pico8_layout`/`pico8_hud`/`pico8_ui` screen geometry, not guessed). `main.c` itself keeps reading its input path from a fixed default (`events.json`, matching Phase 1) unless a command-line argument is given — no new CLI-parsing infrastructure is introduced beyond an optional single positional argument, since the new dedicated test program (not `main.c`) is what actually drives the Phase 4 fixture.

**Makefile changes.** The existing `pico8_demo`/`demo` target is renamed to reflect its new role (`pico8_replay`/`replay`) since it is no longer a "demo" once it runs the real game — its dependency/source list grows to the full engine closure `main.c` now needs (the same list already used by `test_pico8_data_init`/`test_pico8_planet_kj_dispatch`, since `pico8_cart_load()` pulls in essentially the whole engine). A new `$(TMP_DIR)/test_pico8_demo` target builds Phase 1's relocated assertions against their original narrow dependency list, added to `unit`. A new `$(TMP_DIR)/test_pico8_playability` target builds the Phase 4 exit-gate program against the full engine closure, also added to `unit`. `test: unit replay` replaces `test: unit demo` (the new `replay` target is the "does the real game run at all" smoke check; the actual invariant assertions live in `unit`'s new `test_pico8_playability`, not in `replay`).

**Difficulty-select (`pico8_eu()`) is a real, deliberate boot step, not skipped.** The real cart's own `_update60()`/`_draw()` do essentially nothing meaningful before a difficulty button's `my` callback (`eu`) has run (per `pico8_cart.h`'s own documented call-order requirement) — the driver and the playability test both call it explicitly, once, right after `pico8__init()`, before the first `_update60()`.

**Bug handling.** Consistent with `docs/portage-progress.md`'s established practice through all of Phase 3 (`pico8_hy_lu`, `pico8_gn_free`, `pico8_hp_lq`, the dangling `ke` pointer, etc.): any real bug this phase's first full-game exercise surfaces gets a targeted fix plus a one-line journal entry in `docs/portage-progress.md`, not a workaround or a silently-loosened invariant.

## Implementation Chunks

1. **Wiring/plumbing** — relocate Phase 1's demo assertions to `tests/test_pico8_demo.c` (verbatim move); rewrite `main.c` as the thin driver described above; update the `Makefile` (`test_pico8_demo` added to `unit`, `pico8_demo`/`demo` renamed to `pico8_replay`/`replay`, full engine source list). Verified with a trivial 1–2 extra frame smoke run on top of the existing 2-frame `events.json` (extended if needed): the driver calls `pico8_cart_load()` → `pico8__init()` → `pico8_eu()` → a couple of `_update60()`/`_draw()` frames → dumps a framebuffer, with no crash and `make test` fully green (including the relocated `test_pico8_demo`). No gameplay invariants are asserted yet at this chunk — only "the real game boots and runs a couple of frames without crashing," the first time this has ever been true in this project.
2. **Author the scripted probe→wormhole→colonization→slipway→trade→score playthrough** — build `tests/fixtures/phase4_playthrough_events.json` and the skeleton of `tests/test_pico8_playability.c` that drives it through the same four entry points, printing/dumping intermediate framebuffers and raw `cg("jo")` counts / `nz` values at each stage as it goes (no formal pass/fail assertions yet). This is the genuinely exploratory part of the phase — discovering the exact mouse coordinates and click sequence (against `pico8_layout`/`pico8_hud`/`pico8_ui`'s real screen geometry) that trigger each mechanic — and is deliberately kept separate from formal assertions so that fixture-authoring iteration doesn't require a red/green test to keep failing while the sequence is still being found.
3. **Formalize the invariants and close the phase** — turn chunk 2's printed checkpoints into real `assert()`-based checks in `tests/test_pico8_playability.c`: planet count in `[0, 90]` and no aberrant credit jump, at each of the six named stages, wired into `unit`/`make test` as a permanent regression check. This chunk is Phase 4's exit gate per `docs/plan.md`.

## Testing Decisions

- **What makes a good test here**: assert on observable game state reached through the exact same generic accessors any other ported code already uses (`pico8_cg()`'s list length, `pico8_instance_get_field()` on the `hy` singleton returned by `pico8_ju()`) and on process-level outcomes (exit code, no ASan/UBSan report, a framebuffer dump file produced) — never on an internal representation detail of the replay driver itself, which has none worth asserting on (it is a thin loop over already-tested plumbing).
- **`tests/test_pico8_demo.c`** (chunk 1): Phase 1's own existing assertions, moved verbatim — no new test content, just a new home so the driver rewrite doesn't cost this coverage.
- **`main.c` / `make replay`**: covered as a smoke/integration check only — "the real game boots and runs to the end of a scripted replay without crashing, and produces a framebuffer dump" — the same integration-level (not unit-level) treatment Phase 1 gave its own demo program. No gameplay-specific assertions belong here.
- **`tests/test_pico8_playability.c`** (chunks 2–3): the phase's real exit-gate test — a dedicated, permanent test binary in the same spirit as Phase 3's `test_pico8_data_init.c`/`test_pico8_planet_kj_dispatch.c` (both already link the full engine closure for the same structural reason: reaching real game state pulls in essentially everything). Checks planet count and credit-magnitude invariants at each of the six named stages, wired into `unit`.
- **No new tests for `pico8_cart_load`/`pico8__init`/`pico8_eu`/`pico8__update60`/`pico8__draw` themselves** — these were already exercised (unit/smoke-level, function by function) through Phase 3, and Chunk 22's own disposable verification program already confirmed they run clean under ASan/UBSan across multiple `_init()`/`eu()` cycles; that program was never committed, so `tests/test_pico8_playability.c` is also this project's first *permanent, committed* test to exercise the fully-assembled cart end-to-end, closing that specific gap.
- **`pico8_input_load`/`pico8_input_step`'s existing hard-error-on-overrun behavior**: already covered by Phase 1's tests; no new coverage needed, but the new `phase4_playthrough_events.json` fixture must have exactly as many frames as the playability test steps through, per that already-established contract.
- **Prior art in this codebase**: Phase 1's `main.c`+`make demo` (integration-level, assertion-driven) is the direct precedent for the new `replay` target's role; Phase 3's `test_pico8_data_init.c`/`test_pico8_planet_kj_dispatch.c` (dedicated test binaries linking the full engine to reach real, deeply-nested game state) are the direct precedent for `test_pico8_playability.c`.
- **Execution policy**: nothing in this phase opens a window; `replay` and `test_pico8_playability` both run entirely from `events.json` input to text/exit-code output, consistent with `CLAUDE.md`'s "never launch the raylib app interactively... before Phase 5."

## Out of Scope

- Any raylib code, interactive window, or live input — that is Phase 5, explicitly out of bounds here.
- `sfx`/`music` — out of scope for the whole project, not just this phase.
- Fixing the open, previously-logged fidelity gap on `pico8_fixed_rnd`/`sin`/`cos` not being bit-exact with real PICO-8 — already logged in `docs/plan.md`'s Notes de portage as a risk to revisit only if a reliable reference ever becomes available; this phase's invariants (plausible ranges, no aberrant jumps) are deliberately loose enough not to depend on bit-exact reproduction.
- Any module/function-level porting work — Phase 3 is closed; this phase only wires and exercises what Phase 3 already built.
- Extending `docs/plan.md`'s Phase 4 exit criteria beyond what its own text states (the two named invariants, no crash, the six named stages) — no additional invariants (e.g. score formula correctness, UI pixel-perfect layout) are added.
- A general-purpose command-line interface for `main.c` beyond an optional single `events.json` path argument — no flags, no multiple-file batch mode.

## Further Notes

- If chunk 2's fixture-authoring uncovers a stage of the chain that scripted mouse/D-pad input alone cannot reliably reach in a reasonable number of frames (e.g. a UI element whose exact screen coordinates are hard to pin down from `pico8_layout`/`pico8_hud` alone), that is exactly the kind of "not yet exercisable end-to-end" situation `docs/portage-progress.md` already has a documented pattern for (see its Phase 3 entries) — log it there rather than forcing a fragile fixture.
- Should this phase's own first full-game exercise turn up a case matching `docs/portage-progress.md`'s already-flagged open item on `pico8_dg()`'s `pairs(hv)` vs `all(hv)` divergence (two-or-more simultaneous self-removals in one tick), that is explicitly called out there as "a natural candidate for the Phase 4 `events.json` corpus" — worth deliberately trying to trigger if the six-stage script naturally produces such a moment (e.g. two probes returning the same frame), but not worth contorting the fixture to force if it doesn't come up naturally.
- Per `docs/plan.md`'s own Notes de portage journal convention, this phase's own end should add a short entry recording the fork-in-the-road decision made here (already recorded in this PRD, but the plan's journal is the canonical long-lived record other future phases are expected to check).
