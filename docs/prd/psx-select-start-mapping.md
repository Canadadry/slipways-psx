## Problem Statement

`docs/plan.md` Phase 2 step 7 reads: "Select (menu tech) et Start (score courant) : mapping 1:1, disponibles nativement sur la manette PSX, aucune adaptation nécessaire." Steps 5 (✕ mouse-mode toggle) and 6 (○ simulated click, with real press/held/release semantics) are closed, each adding a real new module or extending one (`cursor.c`) with genuinely new, observable, testable behavior. Step 7 names two consumers that don't exist yet in this port — the tech menu is `rules_tech.c` (Phase 3 step 12) and the score/economy display is `rules_economy.c` (Phase 3 step 13) — so, as with step 6's "○ simulates a click" before its consumers existed, the open question is what this step can concretely *build* today, given nothing downstream exists to open or display yet. Unlike step 6, though, Select and Start are not conditioned on cursor-relative anything: they are simple, unconditional button presses. The question this PRD resolves is whether that simplicity means the step reduces to zero new code.

## Solution

Investigated directly (see Implementation Decisions) and confirmed: it does. `psx-slipways/input.c` (Phase 1 step 3) already reads and exposes the PSn00bSDK pad driver's full, unfiltered `PADTYPE::btn` bitmask through `input_get_state().buttons` — every bit, not a subset curated for Cross/D-pad/Circle. Select (bit 0) and Start (bit 3) are present in that value on every frame, today, exactly as unprocessed and exactly as current as every other bit `input.c` already exposes, with no code change required to make that true. There is no cursor-relative position to compute (unlike Circle's click, which needed the cursor's pixel coordinates), no visual acknowledgment to add (unlike Circle's flash, which had a direct, working precedent in `psx-hello/main.c` to reuse — Select/Start have no such precedent there; `psx-hello/main.c` never reads either button), and no mode gating to reason about (Select/Start are not tied to mouse mode, per the plan's own framing and confirmed below). Because nothing consumes these bits yet, and because this codebase's established precedent (`input.c`'s own PRD, echoed by `cursor.c`'s Further Notes) is that edge/press-detection logic belongs to whichever module actually needs it — not pre-built speculatively in a lower layer — the honest, non-inflated scope of this step is: confirm the mapping is already fully present and sufficient, document the bit positions and the non-gating decision for Phase 3 to build on, and add no new module, no new field, and no new test target. This closes out Phase 2's controller-input work.

## Implementation Decisions

**The load-bearing research question, resolved directly: does this step need any new code at all? No.**

- **`input.c`'s existing bitmask is already unfiltered.** Reading `psx-slipways/input.c` (Phase 1 step 3, closed) directly: `g_pad_buttons = g_pad_connected ? pad->btn : 0xffff;` — this assigns the *entire* raw `PADTYPE::btn` register, not a curated subset. `input_get_state().buttons` (`uint16_t`, active-low, same convention documented in `docs/prd/psx-pad-input.md`) already carries Select and Start's bits on every frame, today, with zero code change. Nothing in `input.c`, `cursor.c`, `game_update.c`, or `game_draw.c` masks, filters, or otherwise hides them. This is the direct, current-state confirmation of `docs/prd/psx-pad-input.md`'s own framing: "a single accessor that returns the controller's current button/D-pad state... I don't need to touch PSn00bSDK's raw pad buffer... myself when I add mouse-mode/click/menu logic later" (that PRD's user story 1, written before step 7 existed, already anticipated exactly this step's need and already satisfied it).
- **Bit positions, for Phase 3's benefit**: standard, published PS1 SIO0 digital-button bit layout (the same layout `docs/prd/psx-simulated-click.md` already cited when it added `CURSOR_PAD_CIRCLE`): Select = bit 0 (`PAD_SELECT`, `1<<0`), Start = bit 3 (`PAD_START`, `1<<3`), both from `psxpad.h`'s standard `PAD_*` macros — the same header/macro family every other button in this codebase is already tested against (`input_get_state().buttons & PAD_SELECT`, `& PAD_START`; remember the active-low convention: `0` = pressed).
- **What the plan's "menu tech" (Select) and "current score" (Start) actually are, confirmed against `pico8/lua.lua` directly — real, click-triggered PICO-8 UI actions, remapped onto dedicated buttons.** PICO-8 has no Select/Start-*equivalent input device* at all (it's a 6-button-per-player device: D-pad + two action buttons; the source is, per `docs/design/slipways-mechanics.md` §15, "**pilotée à la souris**" end to end — hover/click, no keyboard/gamepad fallback beyond the inertia-cursor vestige `qb:ph`, which is documented and deliberately not ported, per `psx-mouse-mode-cursor`'s own already-settled finding). But the *actions* the plan assigns to Select and Start — open the tech list, show the current score — are not new-invented PSX-port UX either: both already exist in the source as real, live, click-triggered HUD interactions. Re-reading `pico8/lua.lua` directly, past the automatic end-game path and the inert tech-data table an earlier pass of this PRD stopped at:
  - `ix` (`lua.lua:965-985`) is a table of four fixed-position clickable HUD icons drawn over the play screen. `ix[2].my=cr` (`lua.lua:981`) wires the top-left icon's click handler to `cr()` (`lua.lua:952-964`), which builds a clickable list of the current tier's researchable technologies (`cb(true)`, `lua.lua:956`, itself defined at `lua.lua:1455-1463` as a filter over the `nb` tech table) and opens it live, mid-game, via `pz(pj.cr,bs)` (`lua.lua:964`) — each entry's own click handler (`lua.lua:957`: `my=t.e_ and function()fm:kt(t)end`) researches it directly from the open list. This is a genuine, real, player-triggered, click-to-open tech menu, matching the game's own pitch text quoted in `docs/design/slipways-mechanics.md:11`: "Research technologies from the top-left corner." `pz()` itself (`lua.lua:280-288`) opens the list by populating the shared UI singleton's `le` field (`ok=ui()`, `lua.lua:154-155`); dismissal isn't bespoke code inside `cr()` — it's the general list-menu framework's behavior: every frame `ok:lj()` (called from `_update60`, `lua.lua:1187`) runs `ui:lj()` (`lua.lua:217-224`), whose `if je.l.jn and self.le==le then self:cj() end` (`lua.lua:221-222`) closes whatever list is open the instant a click lands somewhere that isn't one of the list's own buttons. So `pz`'s click-elsewhere-to-dismiss behavior is real and inferable from source, just implemented once for every list menu instead of per-caller.
  - `ix[3]`'s click handler (`lua.lua:984-985`: `function()ju.c_=true fq(de)end`) sets a `c_` flag and spawns `fq(de)` — a small click-catching overlay (`de`, `lua.lua:901-904`) whose own `.my` handler toggles `c_` back off on the next click, anywhere. This same `c_` flag gates the `bz` score/breakdown panel (`lua.lua:797-814` — fields for planets/population/technology/happiness/total, matching exactly what Phase 3 step 13's `rules_economy.c` will need to compute) inside `pj:ph()` (`lua.lua:870-899`, specifically `lua.lua:882`: `if self.c_ and kc~=self.ed then`) — so clicking this second HUD icon genuinely opens the live score panel mid-game, and clicking elsewhere closes it. This matches the pitch text's "Click the heart symbol to check your score."
  - What an earlier pass of this PRD got right: the `nb` tech table itself is inert data with no UI-triggering mechanism of its own — `cb()` (`lua.lua:1455-1463`) just filters it; the *trigger* is `ix[2]`/`cr()`, not the table. And the automatic end-of-game path into the same `bz` panel via `pj:ph()` gated on `fm.hl` (set at `lua.lua:1235`, on reaching the final year or going bankrupt) is real, and exists *in addition to* the live click trigger, as a second route into the same panel. What that earlier pass got wrong was concluding from those two true observations that *no* live, player-triggered mechanism exists at all — it found the inert data table and the automatic end-game path, but missed the two real click-triggered HUD icons (`ix[2]`, `ix[3]`) sitting in the same neighborhood of the source that open the same panels live, mid-game.
  - **Reframing this step's role**: Select and Start's role in this PSX port isn't inventing new UX to fill a gap the mouse-driven original never had — it's re-mapping two existing, click-triggered PICO-8 UI actions (open the tech list, toggle the score panel) onto dedicated buttons, instead of requiring a cursor hover over a fixed-position icon and a click. Read this way, `docs/plan.md` step 7's own "mapping 1:1... aucune adaptation nécessaire" wording (`docs/plan.md:46`) is more literally true than an earlier pass of this PRD gave it credit for: the actions being mapped already exist in the source, just gated behind a mouse click on `ix[2]`/`ix[3]` rather than a controller button.
  - This doesn't change this step's own scope or conclusion: whether the trigger is a mouse click on a HUD icon (original) or a Select/Start press (this port), *wiring* that trigger up to opening `rules_tech.c`'s menu or `rules_economy.c`'s panel is Phase 3's job (steps 12/13), not `input.c`'s. Select and Start's raw bits are already exposed unfiltered today regardless of which framing is correct — there is still no "Reste à trancher" question for *this* step to resolve from `pico8/lua.lua` the way step 6 had one for click semantics; the plan itself already made the only two decisions that exist to make at this level (Select → tech menu, Start → score), and both are phrased as simple, unconditional button mappings, not state machines.
- **`psx-hello/main.c` has no Select/Start precedent** — confirmed by reading the file directly (`psx-hello/main.c:1-141`). It reads and acts on `PAD_CROSS`, `PAD_UP/DOWN/LEFT/RIGHT`, and `PAD_CIRCLE` only; `PAD_SELECT` and `PAD_START` appear nowhere in the file. Unlike Circle's click (which had `click_flash` to directly reuse) and Cross's toggle (which had `mouse_mode`/`cursor_x`/`cursor_y` to directly reuse), this step has no working precedent in this repository to extend or mirror — because, per the point above, there is nothing yet for Select/Start to visibly *do*.
- **Should Select/Start be gated on `cursor.c`'s `mouse_mode`, the way Circle's click is? No — decided, and stated explicitly so Phase 3 doesn't have to re-derive it.** Circle's click is gated on mouse mode because a click is only meaningful relative to a visible cursor position — no cursor, no target to click on. Select and Start have no cursor-relative meaning at all: opening a tech menu or toggling a score panel doesn't depend on where a pixel cursor is or whether it's currently visible — this reasoning applies identically to both buttons on its own, without needing plan wording to support it. For Select specifically, `docs/plan.md` step 12 independently confirms the conclusion in its own words: "menu tech minimal, **accessible en permanence** via Select" (`docs/plan.md:57`) — "en permanence" (at all times) is explicit, stated language ruling out any mode gate. Step 13's wording for Start (`docs/plan.md:58`: "formules réduites... et conditions de fin") says nothing about permanence or gating either way, so Start's no-gating conclusion rests on the cursor-irrelevance argument above, not on step 12's wording, which never mentions Start. `docs/plan.md` step 7's own framing of both as simple, unconditional button presses ("mapping 1:1... aucune adaptation nécessaire", `docs/plan.md:46`) is consistent with this for both. Conclusion: whichever module Phase 3 builds to consume these bits should read them unconditionally, not behind a `cursor_get_state().mouse_mode` check.
- **Where edge detection should live, once Phase 3 actually needs it — not decided here, but a starting opinion recorded for that PRD to pick up, per this codebase's established practice** (`docs/prd/psx-pad-input.md`'s Further Notes did the same for step 5/6; `docs/prd/psx-mouse-mode-cursor.md`'s Further Notes did the same for step 6). The consistent precedent across every prior step (`input.c` deliberately state-only; `cursor.c` owns its own `prev_buttons` for Cross and Circle) is that edge detection belongs to the module that actually consumes the signal, not to `input.c` and not to a module built ahead of its consumer. Following that precedent: `rules_tech.c` (step 12) should keep its own previous-frame Select state to detect a press edge for opening the tech menu, and `rules_economy.c` (step 13) should do the same for Start, independently — see Further Notes for what the original `ix[2]`/`cr()`/`pz()` and `ix[3]`/`fq(de)` click-triggered analogs suggest about each button's likely open/close shape. This PRD deliberately adds neither module nor field for either, so as not to prejudge that choice the same way `input.c`'s PRD deliberately left Cross/Circle's edge semantics for their own later steps to decide.
- **No new module is created.** A module built now, with no consumer, no visual output, and nothing to assert against beyond "the bit is still there" (already proven true and already tested — see below) would be exactly the unobservable, untestable scaffolding this project's guardrails and prior PRDs (`psx-mouse-mode-cursor`'s camera-system investigation, most directly) have consistently rejected.
- **Traceability guardrail, checked explicitly.** No game-design constant, cost, threshold, or formula is introduced or touched by this step; nothing here needs tracing to `docs/design/slipways-mechanics.md`.
- **Interaction-vs-content guardrail, checked explicitly.** This step adds no new capability at all — it confirms an existing one (raw button exposure, already built in Phase 1 step 3) already covers Select and Start. There is no ambiguity to resolve toward "treat as content by default": nothing is being added, so there is nothing to justify.

## Implementation Chunks

None. This PRD's conclusion is that no new code is required: `input.c`'s existing, already-implemented, already-tested raw bitmask accessor already exposes everything Select and Start need, exactly as unprocessed as every other button it exposes. Forcing an artificial chunk (e.g. a no-op module, or renaming `input_get_state()`'s field) would add indirection with no behavioral, testable, or documentation value beyond what this PRD itself already records. The real implementation work — reading Select/Start, deciding their edge/toggle semantics, and building the menu/score screens themselves — belongs entirely to Phase 3 steps 12 and 13, which is where it's scoped in `docs/plan.md`.

## Testing Decisions

- **No new test target is added.** `tools/gen_pcsx_slipways_input_test_lua.py` / `make psx-slipways-input-test-pcsx` (Phase 1 step 3) already exercises `g_pad_buttons` end-to-end under real emulated SIO0 pad injection, reading the *entire* 16-bit bitmask from guest RAM — Select's and Start's bits are already covered by that same mechanism today, by construction (there is no separate "which bits are readable" test per button; the harness proves the whole register round-trips correctly). A new test asserting `PCSX.SIO0.slots[1].pads[1].setOverride(BTN.SELECT)` moves the Select bit would be a legitimate deepening of that existing test's coverage, but this PRD does not add it: it would test the identical mechanism (`input.c`'s bitmask passthrough) the existing D-pad/Cross assertions already prove works for every bit generically, not anything specific to Select/Start.
- **What actually needs a real, dedicated test doesn't exist yet**: whether pressing Select correctly opens/closes a tech menu, and whether pressing Start correctly shows/hides a score panel, are both Phase 3 concerns (step 12/13's own modules and screens). Those PRDs should each add their own headless PCSX-Redux test asserting the real, observable menu/panel state — the same rigor `psx-mouse-mode-cursor-test-pcsx` and its Circle-extension already established for Cross/Circle — once there is a real screen to assert against.
- **`make test`**: unaffected. No new host test is added, since there is no new pure-logic core to extract (this step adds no logic at all).

## Further Notes

- **This closes Phase 2.** After this step, all three named controller-input steps (5: mode toggle, 6: simulated click, 7: Select/Start) are accounted for — step 7 by confirming existing infrastructure already suffices, not by adding new code. Phase 3 (vertical slice) can begin without any open Phase 2 input question remaining.
- **Why this conclusion is not a shortcut**: the same rigor applied to step 6 (real source investigation into `pico8/lua.lua`, explicit citation of line numbers, explicit rejection of an easy-but-wrong shortcut — there, "just fire an instantaneous click"; here, "just build a module because the step needs *something*") was applied here too, and it converged on "nothing new to build" rather than "something to build" only because that's what the evidence (input.c's current source, psx-hello's absence of precedent, pico8/lua.lua's absence of a Select/Start-equivalent trigger) actually supports.
- **Starting opinion for Phase 3 step 12 (`rules_tech.c`)**: now that real precedent exists in the source (see Implementation Decisions), cite it rather than guess from scratch. `ix[2]`/`cr()`/`pz()` (`lua.lua:952-964`, `981`) is a click-to-open list menu whose dismissal isn't "press the same trigger again" — it's the generic list-menu framework's click-elsewhere-closes-it behavior (`ui:lj()`, `lua.lua:217-224`, run every frame via `ok:lj()`/`_update60`, `lua.lua:1187`; `pz()` itself at `lua.lua:280-288`). Re-clicking `ix[2]` while the list is already open doesn't toggle it closed either — `cr()` just closes-then-reopens the same list (a refresh, not a close). Translated to a button: Select most plausibly opens the menu on press, and — because there's no cursor-driven "click elsewhere" equivalent on a gamepad — needs its own explicit close action (a second Select press, a Circle/back press, or similar) rather than literally reproducing "click anywhere else." This is real precedent for *what* Select's original analog does, not a ready-made press-to-toggle-closed mechanism to copy verbatim; step 12's own PRD should decide the concrete close gesture against however the ported menu's controls are actually laid out.
- **Starting opinion for Phase 3 step 13 (`rules_economy.c`)**: real precedent exists here too, and it's more directly reusable than an earlier pass of this PRD assumed. `ix[3]`'s click handler (`lua.lua:984-985`) opens the score panel by setting `c_=true` and spawning a dismiss overlay `fq(de)`; `de`'s own click handler (`lua.lua:901-904`) flips `c_` back off on the next click anywhere. That's a concrete, real, click-to-open / click-elsewhere-to-dismiss toggle overlay — not a hold-to-glance mechanic — gating the same `bz` panel (`pj:ph()`, `lua.lua:882`) this step's automatic end-game path also uses. This is real, stated precedent that Start's interaction shape is closer to a toggle-open overlay (Cross's own toggle shape in `cursor.c` is a reasonable button-side analog) than to Circle's held-level semantics; it is not as fully open a question as an earlier pass of this PRD framed it. Still a starting opinion for step 13's own PRD to confirm, not decided here — translating "click anywhere else closes it" onto a gamepad (second Start press? any-button dismiss?) is a real design choice that PRD still has to make.
- **Why no code was added even though the task description raised the possibility explicitly**: the task's own framing asked this PRD to seriously consider "does this step even need a new module, or does it reduce to nothing" and to say so plainly if the honest answer is "nothing," rather than manufacturing scope. Every piece of evidence gathered — `input.c`'s unfiltered bitmask, `psx-hello/main.c`'s total silence on Select/Start, `pico8/lua.lua`'s total absence of a Select/Start-equivalent trigger, and the plan's own "aucune adaptation nécessaire" wording — points the same direction, so this PRD reports that finding directly instead of building something to have a diff to show.
