## Problem Statement

`psx-slipways/` (Phase 1, steps 1-4, closed) has a glue skeleton, a host-testable galaxy generator, raw per-frame pad-button state (`input.h`/`input.c`, no edge detection by design), and a rendered galaxy — but nothing on the controller does anything yet. `docs/plan.md`'s Phase 2 opens with a deliberate architectural constraint ("un seul mode de curseur, pas de state machine de modes") and its first concrete step: **✕** toggles a "mouse mode" on/off, and while active the D-pad moves a free pixel cursor, with the plan's own wording adding "caméra qui suit" (camera follows). Nothing today computes a button *edge* (press vs. held), nothing tracks a cursor position, and nothing renders one. This is also the first step where anything the player does with the controller becomes observable on screen — Phase 1 was all generation/rendering of static or fixed-seed content, untouched by input.

## Solution

Add a new, PSX-header-free module, `cursor.h`/`cursor.c`, that owns "mouse mode" (on/off) and a pixel-space cursor position `(x, y)`, computed each frame from the previous frame's cursor state plus the previous and current raw pad-button bitmasks (already exposed, unprocessed, by `input.h`). Its core transition function is pure and takes every input as an explicit parameter (no hidden reads of `input.c`'s state, no PSX headers at all), so it — and the thin stateful wrapper around it — are fully host-testable with plain `gcc`, following this project's established convention (`world.c`, `screen_map.c`, `slipway_bench.c`) of keeping logic that *can* run on the host out of the PSX-only code that can't. `game_update()` gains one new call (`cursor_update(input_get_state().buttons)`, mirroring how `input_update()` was already wired in); `game_init()` gains `cursor_init()`. `game_draw()` gains a small `TILE` marker, drawn only while mouse mode is active, reusing the exact GPU-primitive pattern Phase 1 step 4 already established. The already-proven PCSX-Redux headless harness is extended with a new, separate target that injects real SIO0 pad overrides (hold ✕, hold D-pad directions) and reads back the real wired `cursor.c` state from guest RAM, proving the toggle and movement work end-to-end on emulated hardware, not just in a host unit test.

A significant part of this PRD is a research finding, not a design choice: **this step does not build a camera/scroll system**, despite the plan's own "caméra qui suit" wording. See Implementation Decisions for the full investigation and reasoning — the short version is that the current PSX screen mapping already fits the entire galaxy on screen at once, so there is nothing off-screen for a camera to reveal yet; building one now would be untestable, unobservable dead code.

## Implementation Decisions

**The load-bearing research question: does this step need a camera/scroll system? Investigated directly — conclusion: no, not yet, and here's why.**

- **What the original PICO-8 source actually does** (`pico8/lua.lua`): there are *two* separate objects relevant here, not one.
  - `nf` (instantiated as the global `je`, lines ~199-206) is the real mouse tracker: `je.ra = v(stat(32), stat(33))` reads PICO-8's native mouse device position directly, in screen-pixel space (PICO-8's native screen is 128×128). This is what gets rendered as the visible pointer sprite (`ui:ev()`: `spr(..., je.ra.x, je.ra.y)`).
  - `qb` (instantiated as the global `mo`, line ~1128) is a *separate* object driven by `btn(0..3)` (the four D-pad directions) with velocity-based inertia (`qb:ph`, line 1134: accumulate an impulse from held directions, ease velocity toward it at a 0.2 factor, clamp position to `[-64, 320]` on both axes — a range roughly 3× the native 128px screen, because the galaxy's world space is larger than one screen). Its *only* effect is `qb:md` (line 1142): `camera(cp.x, cp.y)` — it directly drives PICO-8's native camera-offset primitive. It has no sprite of its own; nothing renders `mo`'s position as a cursor.
  - The two combine for world-space hit-testing: `ui:lj()` (line 218) computes `self.qa = je.ra + mo.ra` — mouse-relative-to-camera-origin *plus* camera offset — the actual world position under the pointer.
  - Right-mouse-button drag on empty background (`bg:rdown`/`bg:hq`, lines ~378-384) also directly sets `mo.v` (camera velocity) from cursor drag delta — a *second*, independent way the original pans the camera.
- **What `docs/design/slipways-mechanics.md` §15 already concluded** (a prior, independent pass over this same source, read directly for this PRD): it explicitly names `qb:ph` "un vestige de contrôle directionnel... probablement un fallback clavier/manette", and states in the same breath that **the plan deliberately does *not* reuse `qb:ph`'s inertia model for v1**, opting instead for a simple pixel cursor + simulated click. It also states plainly: *"Pas de scroll de zoom : la caméra suit simplement le curseur (`qb:md`)"* — i.e. the design doc itself is the source of the plan's "caméra qui suit" wording, and it's citing `qb:md` (the camera-only object), not `je` (the mouse-position object). This confirms "camera follows the cursor" is a real, sourced concept from the original game, not an invented one — but it also confirms that in the *original*, the D-pad-driven object and the camera-following are the *same* mechanism (`qb`/`mo`), separate from the actual on-screen mouse pointer.
- **Why this doesn't force a camera system into this step anyway**: the reason `qb`/`mo`'s camera-pan exists at all in the original is that PICO-8's native screen (128×128) is *smaller* than the galaxy's world-space extent (position range roughly `[-64, 320]`, i.e. ~2.7-3× one screen per axis) — panning is load-bearing there because most of the galaxy genuinely doesn't fit on screen at once. `psx-slipways/screen_map.c` (Phase 1 step 4, `docs/prd/psx-galaxy-rendering.md`) made a *different*, already-implemented and already-documented choice: it stretches the *entire* generator domain (`[PLANETGEN_PLACEMENT_MIN, PLANETGEN_PLACEMENT_MIN + PLANETGEN_PLACEMENT_SPAN)`, both axes) directly onto the *entire* `SCREEN_XRES`×`SCREEN_YRES` (320×240) drawable area, margin aside. That PRD's own comment in `screen_map.c` already says as much: `SCREEN_MAP_MARGIN`'s comment reads *"Revisitable once a real camera/pan/zoom system exists"*, and its Out of Scope section states outright: *"no camera system exists yet"*. Concretely: **the whole galaxy is always fully visible on screen already, right now, before this step does anything.** There is nothing currently off-screen for a camera to pan into view.
- **Conclusion, stated plainly (per the task's own instruction not to force this in, and not to silently skip it either)**: this step does **not** build a camera/scroll/viewport system. Not because the plan's "caméra qui suit" wording is wrong or being ignored, but because, given the *already-made, already-documented* Phase 1 screen-mapping decision, camera-follow currently has **no observable effect** — a camera that "follows" a cursor when the entire world is already always fully in view is a no-op by construction. Building one now would mean adding a module with literally nothing to verify (no off-screen content ever becomes visible, no clamp is ever exercised, no screenshot could ever show a difference) — untestable, unobservable scaffolding, which this project's own guardrails and prior PRDs (e.g. `psx-galaxy-rendering`'s explicit avoidance of an ordering table "not needed... introducing it speculatively would be exactly the kind of premature complexity" the plan warns against) consistently reject.
- **This is not a permanent closure of the question.** If a *future* rendering step ever changes `screen_map.c`'s strategy — e.g. zooming in on a sub-region for precision, rather than stretching the whole domain to fit, which `screen_map.c`'s own comment already flags as "revisitable" — camera-follow would become meaningful again at that point, and this step's `cursor_get_state()` already hands that future step exactly the pixel-space `(x, y)` target it would need to drive a camera with, at zero cost paid now. This connection is noted in Further Notes so it doesn't need rediscovering.
- **Guardrail check, stated explicitly**: choosing not to build unobservable scaffolding is not "removing content silently" (the Garde-fous rule about not dropping documented rules) — no rule from `slipways-mechanics.md` is being skipped; §15's own text is *about* the interface/controls section, explicitly framed as "points d'attention pour le portage," not a rule with gameplay consequences the way §3/§5 (colonization, slipway validity) are.

**Mouse-mode toggle and cursor movement — pure core + thin stateful wrapper, one new module.**

- **New module `cursor.h`/`cursor.c`**, snake_case/`_t` convention matching `planetgen.h`/`world.h`/`input.h`.
- **Public type and pure core function** (illustrative signature/shape; not literal file contents):
  ```
  typedef struct {
      int mouse_mode; /* 0 = off, 1 = on */
      int x;          /* pixel-space, [0, SCREEN_XRES-1] */
      int y;          /* pixel-space, [0, SCREEN_YRES-1] */
  } cursor_state_t;

  cursor_state_t cursor_step(cursor_state_t prev_state,
                              uint16_t prev_buttons,
                              uint16_t buttons);

  void cursor_init(void);
  void cursor_update(uint16_t buttons);
  cursor_state_t cursor_get_state(void);
  ```
  `cursor_step` is pure: no statics, no I/O, same active-low raw bitmask convention `input.h` already established (`0` = pressed). It computes `pressed = (~buttons) & prev_buttons` (the exact edge-detection idiom `psx-hello/main.c` already uses inline with its local `prev_btn`); if the ✕ bit is set in `pressed`, `mouse_mode` flips. While the *resulting* `mouse_mode` is on, each held D-pad direction (tested against the *current*, not previous, `buttons`, for continuous per-frame movement) nudges `x`/`y` by a fixed per-frame step, all four directions summed before clamping (so diagonal movement isn't double-clamped away), then both axes are clamped to `[0, SCREEN_XRES-1]`/`[0, SCREEN_YRES-1]`. This is a direct, deliberate mirror of `psx-hello/main.c`'s proven cursor demo (`mouse_mode = !mouse_mode` on a Cross edge; `cursor_x`/`cursor_y` adjusted by `CURSOR_SPEED` per held direction; clamped after all adjustments) — not re-derived from scratch.
- **Local button-bit constants, defined inside `cursor.c`, not included from `psxpad.h`.** Since `cursor.c` must stay host-buildable with zero PSX headers, it defines its own small set of mask constants (Cross, Up, Down, Left, Right) matching PSn00bSDK's well-known, published PS1 SIO0 pad-protocol bit positions (the same values this project's own Lua test harness already cross-checks, e.g. `tools/gen_pcsx_slipways_input_test_lua.py`'s comment "`PAD_UP == 1<<4`"). This is a deliberate, documented duplication of five stable hardware-protocol constants — not a re-derivation of behavior — chosen specifically to avoid the alternative (including `psxpad.h`), which would make the whole file, not just part of it, PSX-only.
- **`cursor_update(uint16_t buttons)` takes the current bitmask as an explicit parameter, not by calling `input_get_state()` itself.** This is the key design choice that keeps `cursor.c` host-testable *in full* (pure core and stateful wrapper both), unlike `input.c` (which has no pure core to extract, per its own PRD). The caller, `game_update()`, already has `input_get_state()` in scope, so this costs nothing at the call site: `cursor_update(input_get_state().buttons)`.
- **Internal test-visible state is flat top-level statics** (`g_cursor_mouse_mode`, `g_cursor_x`, `g_cursor_y`, plus `g_cursor_prev_buttons` for edge detection across frames), not one struct static — directly mirroring `docs/prd/psx-pad-input.md`'s already-established rationale for `input.c` (each field gets its own symbol+address in the `.map` file, decoupling the test harness from struct layout/padding).
- **Initial state, decided and justified**: `mouse_mode` starts **off**, cursor position starts at **screen center** (`SCREEN_XRES/2, SCREEN_YRES/2`), `prev_buttons` starts at `0xffff` (nothing held — the same "disconnected/idle" convention `input.c` already uses). Both choices directly mirror `psx-hello/main.c`'s proven precedent (`cursor_x = SCREEN_XRES/2`, `mouse_mode = 0` at boot) rather than inventing new defaults, and "off at boot" keeps the newly-rendered galaxy view (Phase 1 step 4) uncluttered until the player opts in.
- **Movement speed** (`CURSOR_STEP`, pixels/frame): set to the same value `psx-hello/main.c` already uses and proved legible in its own boot/screenshot testing (`CURSOR_SPEED = 2`). **Explicitly labeled a v1 UX/tuning choice, not a `slipways-mechanics.md`-traceable game-design constant** — the plan's traceability guardrail governs costs/thresholds/formulas *from the source game*, and a controller cursor didn't exist in that game at all (it had a real mouse), so there is nothing to trace this value against; stating this distinction explicitly so a reviewer doesn't misapply the guardrail here, per the task framing's own instruction.
- **No inertia/easing.** `docs/design/slipways-mechanics.md` §15 already investigated and explicitly rejected porting `qb:ph`'s velocity-based inertia model for v1 in favor of a simple, direct cursor — this step follows that already-made call, not re-opening it.
- **Wiring**: `game_init()` (in `game_update.c`, the existing simulation-side init dispatch point) gains `cursor_init();` alongside the existing `world_init();`. `game_update()` gains `cursor_update(input_get_state().buttons);` as its second statement, after `input_update();`. `main.c` is untouched — both new calls land at the existing `game_init()`/`game_update()` seams, exactly the pattern `psx-pad-input` and `psx-galaxy-rendering` already established for `input_init()`/`world_init()`.

**Rendering the cursor — decided: yes, in this step.**

- `game_draw.c` gains one new block, after the existing planet/wormhole/slipway drawing: if `cursor_get_state().mouse_mode` is true, draw one small `TILE` centered on `(cursor.x, cursor.y)`, reusing the exact `setTile`/`setXY0`/`setWH`/`setRGB0`/`DrawPrim` sequence Phase 1 step 4 already established for planets (`GAME_DRAW_PLANET_TILE_SIZE`'s sibling constant, e.g. `GAME_DRAW_CURSOR_TILE_SIZE`, similarly arbitrary and undocumented-as-art). Color: plain white (`255, 255, 255`), matching `psx-hello/main.c`'s own cursor precedent and visually distinct from the existing planet (green), wormhole (orange), and slipway (blue) placeholder colors.
- **Justification for rendering now rather than deferring**: (a) `psx-hello/main.c`'s proven demo already renders its cursor — there's a direct, working precedent to reuse, not a new pattern to invent; (b) without a visible marker, this feature has no way to be screenshot-verified, and this project has consistently used `psx-slipways-screenshot-pcsx` as a sanity check for every rendering-affecting step so far; (c) `docs/plan.md`'s own Garde-fous text names "le curseur en mode souris" as a tolerated *interaction-layer addition*, which only makes sense as something the player can actually see.
- **No click-flash/feedback rendering in this step** — that behavior (`psx-hello/main.c`'s `click_flash`, turning the tile yellow briefly) is tied to the ○ click event, which is step 6's scope entirely; this step's cursor is a static white marker with no state beyond position.

**Interaction-vs-content guardrail, checked explicitly.** The toggle flag and pixel position add no game capability, resource, or rule: nothing reads the cursor position except `game_draw.c` (to draw it); no planet/wormhole/slipway state is touched; no cost, no score, no colonization. This matches `docs/plan.md`'s own pre-authorization ("le curseur en mode souris, le bouton ✕ de bascule... sont des ajouts tolérés") exactly, with nothing added beyond what that sentence already scopes.

## Implementation Chunks

Tracer-bullet slices, each independently buildable and testable, cursor-mode-toggle first (simplest, fully host-testable in isolation) through to the real emulated end-to-end proof:

1. **Mode toggle only.** `cursor.h`/`cursor.c` created with the full `cursor_state_t` shape but `cursor_step` implementing only ✕-edge-driven `mouse_mode` flipping (position fields present, initialized, unchanged by this chunk). Host-tested (`host_tests/cursor_test.c`): press-edge flips, held-does-not-reflip, release-does-not-flip, unrelated buttons don't flip it. Wired into `game_init()`/`game_update()`. No rendering yet — purely internal, verified only by the host test.
2. **Cursor movement + clamping.** `cursor_step` extended: D-pad moves `x`/`y` by `CURSOR_STEP` per held direction while `mouse_mode` is on, no movement while off, both axes clamped to screen bounds, diagonal movement summed-then-clamped. Host tests extended: movement while active, no movement while inactive, single-axis and corner (diagonal) clamping, movement resumes correctly after toggling off then back on.
3. **Rendering.** `game_draw.c` gains the gated `TILE` cursor marker. Verified via `make psx-slipways-screenshot-pcsx` (visual check: cursor visible and positioned correctly when mode is toggled on via the existing manual/scripted flows) and the still-unmodified `psx-slipways-boot-test-pcsx`.
4. **Headless PCSX cursor-injection test.** New `tools/gen_pcsx_slipways_cursor_test_lua.py` (mirroring `tools/gen_pcsx_slipways_input_test_lua.py`'s map-symbol-resolution/template approach) resolving `g_cursor_mouse_mode`/`g_cursor_x`/`g_cursor_y`/`test_harness_ready`; new `tools/boot_test_psx_slipways_pcsx_cursor.sh` (mirroring `tools/boot_test_psx_slipways_pcsx_input.sh`'s structure); new Makefile target `psx-slipways-cursor-test-pcsx`. This is the first point the *wired-together* real behavior (input.c → cursor.c → the actual linked binary's static state) is proven under real emulated SIO0 pad injection, not just asserted against the pure function in isolation.

## Testing Decisions

- **What makes a good test here (restated from prior PRDs' established standard)**: assert on observable state through public functions/exported symbols (toggle result, cursor position, clamped bounds), never on internal representation beyond what the flat statics convention already requires for the Lua harness to read them.
- **Host-testable, in full, including the stateful wrapper (unlike `input.c`) — because `cursor_update()` takes its button bitmask as a parameter instead of calling into `input.c`:**
  - New `psx-slipways/host_tests/cursor_test.c`, same shape as `planetgen_test.c`/`world_test.c`/`screen_map_test.c` (hand-built fixtures, `T_CHECK`/`t_run`/`t_report` from `host_tests/t.h`).
  - Cases: Cross-press-edge flips `mouse_mode` from a fixture starting state; holding Cross across two consecutive calls does not re-flip; releasing Cross does not flip; D-pad movement is a no-op while `mouse_mode` is off; each of the four directions moves the correct axis/sign while on; diagonal (two directions held at once) moves both axes in one step; movement clamps at `x=0`/`x=SCREEN_XRES-1`/`y=0`/`y=SCREEN_YRES-1` without overshoot even when the raw unclamped delta would exceed the bound; `cursor_init()` produces the documented initial state (`mouse_mode=0`, centered position); a `cursor_update()`/`cursor_get_state()` round trip through the stateful wrapper reproduces the same result as calling `cursor_step` directly with equivalent arguments (proving the wrapper is a faithful, non-lossy shell around the pure core).
  - New Makefile group `test-cursor` (inline recipe, same shape as `test-planetgen`/`test-galaxy-render`: host `gcc`, `psx-slipways/build-host/` output), and the top-level `test` target updated to depend on it (`test: test-planetgen test-galaxy-render test-cursor`), keeping `CLAUDE.md`'s "`make test` to verify changes" promise complete for this step's code too.
- **Not host-testable, and that's expected**: `game_draw.c`'s new `TILE` block (real `psxgpu.h` primitive calls) and `main.c` (unchanged). Verified instead by:
  - `make psx-slipways-boot-test-pcsx` (existing, unmodified) — confirms boot still doesn't crash with the new per-frame cursor update/draw calls added.
  - `make psx-slipways-screenshot-pcsx` (existing, unmodified target/tooling) — visual sanity check that a toggled-on cursor actually appears and looks like a small distinct marker, not a numeric assertion but a fast way to catch an obviously-wrong tile position or missing gate-on-`mouse_mode` bug.
  - **New `make psx-slipways-cursor-test-pcsx`** (this PRD's own addition, chunk 4): asserts, against the real linked binary under real emulated SIO0 pad injection: (1) `g_cursor_mouse_mode`/`g_cursor_x`/`g_cursor_y` start at their documented initial values after boot; (2) holding ✕ (`PCSX.SIO0.slots[1].pads[1].setOverride(BTN.CROSS)`) for a settle window flips `g_cursor_mouse_mode` to 1, and releasing it does not flip it back; (3) holding D-pad Right (and separately Down) for a fixed number of frames while mode is on moves `g_cursor_x`/`g_cursor_y` by the expected amount (`CURSOR_STEP × frames`, within the settle-frame precision the existing input harness already tolerates); (4) holding a direction for long enough to reach the screen edge leaves the coordinate clamped at the boundary, not wrapped or overshot; (5) toggling ✕ off again and continuing to hold a D-pad direction leaves the cursor position unchanged, proving the gate is real and not just true-by-coincidence in the earlier assertions.

## Out of Scope

- **Click simulation (○) and its press/release-vs-instantaneous semantics** (`docs/plan.md` Phase 2 step 6, and its explicit "Reste à trancher" note) — this step adds no click handling of any kind, and `cursor_state_t` deliberately carries nothing that would prejudge that decision.
- **Select/Start mapping** (`docs/plan.md` Phase 2 step 7) — untouched.
- **Any camera/pan/scroll/viewport system** — investigated at length above; not built in this step, and explicitly not a silent omission (see Implementation Decisions' full reasoning).
- **Any change to `screen_map.c`'s domain-to-screen mapping strategy** — stays exactly as Phase 1 step 4 left it (full-domain stretch, no zoom).
- **Any consumption of the cursor position by game logic** — `pico8/lua.lua`'s hit-testing (`ui:gw`, `mv(e,"hd",...)`), slipway-drag, colonization, and probe-launch logic are all untouched; this step's cursor is visual/positional only, read by nothing but `game_draw.c`.
- **Right-mouse-drag-style camera panning** (`bg:rdown`/`bg:hq` in the original) — not ported; there is no "camera" for it to drive in this step, and no second input mode is being introduced (the plan's "un seul mode de curseur" constraint).
- **`qb:ph`'s inertia/velocity-based movement model** — investigated and explicitly not ported, per `docs/design/slipways-mechanics.md` §15's own prior conclusion; this step's cursor moves at constant per-frame speed instead.
- **Click-flash or any other visual feedback beyond the static cursor marker itself** — tied to the ○ click event (step 6), not introduced here.
- **Any change to `input.h`/`input.c`** — this step's edge detection lives entirely in the new `cursor.c`, per `docs/prd/psx-pad-input.md`'s own explicit guidance; `input.c`'s public API and behavior are unchanged.
- **Any change to `main.c`** — both new `_init`/`_update` calls land at the existing `game_init()`/`game_update()` seams.
- **Modifying `psx-hello/`** in any way — read only, as the proven precedent to mirror.
- **Multi-controller/multitap, analog stick input** — not asked for anywhere in the plan (PS1 standard pad only, as established by `psx-pad-input`).

## Further Notes

- **Why `cursor_update(uint16_t buttons)` takes its input as a parameter rather than reading `input_get_state()` internally**: this is the one design choice in this PRD that most directly determines testability. Had `cursor.c` called into `input.c` directly, the entire file would become link-dependent on PSX-only code (`input.c` includes `psxpad.h`/`psxapi.h`), making even the pure `cursor_step` core's *host test binary* impossible to link, not just harder to write. Passing the bitmask in keeps `cursor.c`'s only dependency `screen.h` (pure `#define`s) — a strictly better position than `input.c` is in, and worth calling out so a future module facing the same shape of problem (pure logic that's driven by, but not itself part of, a hardware-boundary module) copies this pattern rather than `input.c`'s "PADTYPE-typed pointer, single-file-not-testable" one.
- **Why the PAD_* bit constants are duplicated locally in `cursor.c` instead of shared from `psxpad.h`**: the alternative (including `psxpad.h`) would reintroduce exactly the host-testability problem the previous point avoids. The five bit positions duplicated (Cross, Up, Down, Left, Right) are a fixed, published PS1 SIO0 hardware protocol detail, already cross-checked against this project's own Lua test harness (`PAD_UP == 1<<4`) — about as low-drift-risk a piece of "duplicated" knowledge as exists in this codebase, so the duplication is judged an acceptable, explicitly-documented tradeoff rather than the kind of value that should be shared from one source of truth.
- **Where camera-follow logic would plug in, if a future step ever needs it**: per the Implementation Decisions research finding, nothing here is needed today, but if a later rendering step changes `screen_map.c` to a zoomed/cropped viewport instead of stretching the whole domain, that step's natural integration point is `cursor_get_state()`'s already-public `(x, y)` — feed it as a camera's pan target the same way the original's `ui:lj()` combined `je.ra` (mouse) with `mo.ra` (camera offset). No redesign of `cursor.c` would be required; this module's public surface already exposes exactly what such a step would need.
- **Why `mouse_mode` and position live in one struct returned by value, not a pointer to internal storage**: same reasoning `docs/prd/psx-pad-input.md` already gave for `input_get_state()` — the struct is a few scalar `int`s, trivially cheap to copy, and returning by value avoids any question of a caller holding a pointer across an update call.
- **This step is the first to give `cursor.c` (not `input.c`) ownership of previous-frame button state** — `docs/prd/psx-pad-input.md`'s own Further Notes already flagged this as the expected outcome ("the natural place for that logic is whichever module Phase 2 step 5/6 introduces for cursor/click handling"); this PRD is that module, confirming that prediction rather than deviating from it.
