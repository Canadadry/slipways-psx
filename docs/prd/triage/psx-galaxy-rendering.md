## Problem Statement

`psx-slipways/` (Phase 1 steps 1-3) has a glue skeleton, a real host-testable galaxy generator (`planetgen_generate`/`planetgen_build_neighbor_graph`/`planetgen_is_connected`), and raw pad reading — but `game_draw()` is still an empty stub and `game_init()` never calls `planetgen_generate`. Nothing has ever appeared on screen, and `docs/plan.md`'s rendering-approach section leaves an explicit open question un-exercised: whether the R3000A (no hardware FPU) has enough CPU budget left over, after GPU primitive submission, to hit **30 fps against ~30 colonized planets / 40-60 simultaneous slipways** — a feasibility criterion the plan documents as an unverified hypothesis, not a proven target. Phase 1 step 4 (`docs/plan.md` line 38) is the step that both makes the galaxy visible for the first time and is named as the point where the Phase 0 PCSX-Redux headless harness first extends to real game logic. Two of the three things this step must render — the wormhole and the slipway network — have no implemented game mechanic yet (wormhole placement is Phase 4 step 15 content; slipway validity is Phase 3 step 9 content), so this step also has to resolve, without pulling that content forward, what "render a wormhole" and "render slipways" even mean before any of that logic exists.

## Solution

Wire the already-implemented galaxy generator into `game_init()` with a fixed deterministic seed, and render its output on screen for the first time using native PSX GPU primitives: every generated planet as a `TILE` sprite (reusing `psx-hello`'s already-proven sprite path), one designated planet position rendered a second time as a distinct `POLY_F4` flat-shaded polygon standing in for "a wormhole" (explicitly a placeholder marker, not the real click-to-place mechanic), and a capped, deterministic subset of the generation-time neighbor graph's edges (40-60 of them, the same graph `planetgen_build_neighbor_graph` already builds and already tests connectivity over) drawn as `LINE_F2` segments standing in for "slipways" (explicitly synthetic geometry with no cost/validity/game meaning — real slipway logic is Phase 3 step 9's job). The screen-space mapping from the generator's normalized Q16.16 domain to actual `SCREEN_XRES`×`SCREEN_YRES` pixels, and the edge-count-capping logic, are both extracted as small, pure, host-testable modules (no PSX headers), following this project's established pattern of keeping logic that *can* be host-tested out of the PSX-only rendering code that can't. Once real content is on screen, the PCSX-Redux headless harness (`docs/plan.md`'s Phase 0 tooling) is extended with a frame-pacing measurement: a per-loop-iteration counter plus PCSX-Redux's `PCSX.getCPUCycles()` Lua binding (which reads the emulator's cycle-accurate R3000A cycle counter, not host wall-clock time) let a Lua driver compute how many main-loop iterations actually complete per emulated NTSC second under the synthetic 90-planet/1-wormhole/40-60-line load, and assert that figure against the 30fps criterion.

## Implementation Decisions

**Wiring galaxy generation into `game_init()`, at last.**
- A new module, `world.h`/`world.c`, owns the "current generated galaxy" state: a `static galaxy_t g_galaxy`, `static neighbor_graph_t g_neighbor_graph`, and a capped, precomputed synthetic slipway edge list (see below). `world_init(void)` runs the full pipeline once — seed the injected RNG (`rng.h`, already established), `planetgen_generate`, `planetgen_build_neighbor_graph`, then the edge-cap selection — and is called from `game_init()` in `game_update.c` (the existing simulation-side dispatch point), immediately following the pattern `psx-pad-input`'s PRD already established for `input_init()`/`input_update()`: new per-frame or boot-time subsystems get their own `_init`/accessor pair, called from the existing seams, never adding a new call site to `main.c`'s loop body. `world.c` itself has **zero PSX-header dependency** (no `psxgpu.h`/`psxpad.h`) — it only calls `planetgen.h`/`rng.h` functions, all of which are already pure — so, unlike `input.c`, it is fully host-testable (see Testing Decisions).
- **Seed is a literal fixed constant** (`WORLD_RNG_SEED`, e.g. `12345u`), not derived from any hardware entropy source. This is a deliberate continuation of `docs/prd/psx-planet-generation.md`'s explicit deferral ("seeding the injected RNG from a hardware timer at boot" was left for "whichever step first needs to render or verify galaxy state on-console" — that's this step, and the call here is still **no**, for a new, step-specific reason): both the visual output and the FPS measurement need to be exactly reproducible run to run for the headless harness to be a meaningful regression check, so a fixed seed is strictly better for this step's purpose than real entropy would be, not merely an acceptable placeholder. Real seeding remains open for whichever future step implements an actual "new game" flow.
- **`PLANETGEN_PLACEMENT_MIN`/`PLANETGEN_PLACEMENT_SPAN`, currently private `#define`s inside `planetgen.c`, are promoted to public constants declared in `planetgen.h`** (values unchanged, still traced to `pico8/lua.lua:747` per the prior PRD's finding) so the new screen-mapping module (below) can convert against the real generation domain instead of duplicating/re-deriving those two numbers and risking drift. `planetgen.c`'s own internal use is updated to reference the now-public names; no behavior changes.

**Screen-space mapping — a rendering choice, not a game-design constant (stated explicitly per the task framing).**
- New pure module `screen_map.h`/`screen_map.c`: one function, `void screen_map_planet(planet_pos_t p, int *out_x, int *out_y)` (illustrative signature), converting a generated position from its native `[PLANETGEN_PLACEMENT_MIN, PLANETGEN_PLACEMENT_MIN + PLANETGEN_PLACEMENT_SPAN)` Q16.16 domain into integer pixel coordinates within `SCREEN_XRES`(320)×`SCREEN_YRES`(240) (the same constants already defined in `psx-slipways/main.c`, promoted to a small shared header — `screen.h` — so `main.c`, `screen_map.c`, and `game_draw.c` all reference one definition instead of three copies).
- **Formula, fixed-point throughout (no `float`, consistent with this project's established R3000A-no-FPU convention):** for each axis independently, `normalized = (coord - PLACEMENT_MIN) * FX_ONE / PLACEMENT_SPAN` (a Q16.16 value in `[0, FX_ONE)`), then `pixel = MARGIN + (normalized * (AXIS_RES - 2*MARGIN)) / FX_ONE`. `MARGIN` (a small constant, e.g. 8px) keeps planets off the literal screen edge. The domain is stretched independently per axis to fill the full 320×240 drawable area — **not** aspect-corrected into a centered square — because there is no camera/pan/zoom system yet (that's a later concern) and nothing about this step requires preserving the generator's square domain's proportions on screen; this is called out explicitly as an arbitrary, revisitable rendering choice, not a traced value.
- This module is pure C, no PSX dependency, and host-testable (see Testing Decisions): verify the domain's four corners map to the expected margin-adjusted pixel corners, verify the mapping is monotonic per axis, and verify no intermediate product overflows `int32_t`/`int64_t` for the real `SCREEN_XRES`/`SCREEN_YRES` values.

**The wormhole placeholder — deliberately not the real mechanic.**
- Source-fidelity finding, from `docs/design/slipways-mechanics.md` §3 (itself sourced from `pico8/lua.lua:376`, `bg:ldown`): the PICO-8 original has **no placement rule at all** for the wormhole beyond "wherever the player's first click lands" — there is no algorithm to port here, only an interaction (the first click creates it; every click after that launches a probe instead). `docs/plan.md` itself places "the wormhole/dynamic-graph-insertion mechanism" at Phase 4 step 15, and the plan's Phase 1 step 4 wording only ever asks this step to *display* a wormhole, not to place one.
- Decision: `world_init()` designates `g_galaxy.positions[0]` (the first planet `planetgen_generate` happens to place, for the fixed seed above) as the wormhole marker's screen position. This is a **placeholder for the sole purpose of exercising the GPU polygon-primitive path**, not a placement rule, not a game mechanic, and not a claim that "index 0" has any significance — it is documented, in both this PRD and a code comment at the call site, as: *"placeholder position for the wormhole GPU-primitive proof; the real wormhole is placed by the player's first click, Phase 4 step 15 — this is not that."* Reusing a real generated planet position (rather than a hardcoded screen coordinate) was chosen only so the marker always lands inside the actual galaxy's visual footprint instead of at an arbitrary point that might look disconnected from the rest of the scene in a screenshot.
- Rendered as one `POLY_F4` (flat-shaded quad) in a distinct placeholder color, while every other planet renders as a `TILE` sprite (see below) — this means both primitive families the plan names for planets/wormhole ("sprite/polygone") get exercised in this one step, not just one of them, without inventing a second meaning for either.
- **Guardrail check, stated explicitly**: this is an addition of *rendering*, not of interaction or content — no new player-facing capability, state, or rule exists because of this marker (nothing reads or writes its position beyond drawing it; there is no "wormhole entity" struct, no group-`g_`-equivalent, no first-click handling). It does not trip the interaction-vs-content guardrail because it does not add either; it is scaffolding for a GPU-primitive-path proof, exactly as the task framing's suggested resolution described.

**Synthetic slipway lines — reusing real data, with an explicit justification (per the "ambiguous → treat as content, forbidden until justified" rule).**
- **Why this doesn't count as inventing game content**: no cost is computed, no validity rule (range/crossing/planet-on-path from `docs/design/slipways-mechanics.md` §5) is evaluated, no player action creates or removes a line, and nothing about a rendered line is ever read back by any other system. It is pure geometry submitted to the GPU to produce a plausible-shaped, plausible-count load for a performance measurement — the same way a real engineering benchmark exercises a subsystem with realistic-shaped synthetic load before the real subsystem exists. This is the justification the guardrail requires before treating an ambiguous case as acceptable, written down here rather than assumed.
- **Source of the edges**: the generation-time neighbor graph `planetgen_build_neighbor_graph` already builds and `planetgen_is_connected` already BFS-tests, at the same real, traced threshold Phase 1 step 2 already established for probe range (`NEIGHBOR_RANGE_SQ`, squared-`0.19`, `pico8/lua.lua:767-770` — no new threshold is invented). `docs/prd/psx-planet-generation.md`'s own density analysis (mean degree ≈7 at this threshold for N=90) means this graph typically has on the order of 300 edges — far more than the 40-60 the criterion asks for — so a deterministic cap is required, not optional.
- **New pure module `slipway_bench.h`/`slipway_bench.c`**: one function, `int slipway_bench_select_edges(const neighbor_graph_t *g, int planet_count, int max_edges, slipway_edge_t *out)` (illustrative signature; `slipway_edge_t` is a tiny `{int a, b;}` pair of planet indices), which scans `adjacent[i][j]` for `i < j` in a fixed row-major order and appends the first `max_edges` edges found, returning the actual number written (≤ `max_edges`, and less than `max_edges` only if the graph itself has fewer edges than that — which is checked not to happen for the real 90-planet/fixed-seed/0.19 configuration, see Testing Decisions). Row-major scan order is the simplest possible deterministic choice and is called out explicitly as arbitrary — it does not pick "the best" or "the shortest" edges by any game-relevant measure, which would smell like inventing a selection *rule* (content); it just picks *some* fixed, reproducible 40-60 of them.
- **`MAX_SYNTHETIC_SLIPWAYS = 50`** (a `slipway_bench.c`/`world.c` constant, the middle of the plan's stated 40-60 band), chosen once and reused by both the rendering code and the FPS harness so "how many lines are on screen" and "how many lines the benchmark measured against" can never drift apart. This is a benchmark-scaffolding constant, explicitly not a `slipways-mechanics.md`-traceable value (there is no such thing as "50 slipways" in the source game).
- Rendered as `LINE_F2` (two-point flat-shaded line) primitives, per-planet screen coordinates from `screen_map_planet` above, in a placeholder color distinct from both the planet tiles and the wormhole polygon.
- `slipway_bench.c` is pure C, no PSX dependency, host-testable (see Testing Decisions).

**Rendering all 90 generated planets, not a synthetic "30 colonized" subset — an explicit resolution of the criterion's "~30 planètes colonisées" wording.**
- This step has no colonization state at all (job/type assignment happens at probe-discovery time in the source, per `docs/prd/psx-planet-generation.md`'s own finding, and discovery itself is Phase 3 step 10). There is therefore no real basis on which to mark some subset of the 90 generated planets as "colonized" and others not — inventing such a flag here would itself be fabricated game state, exactly the kind of ambiguous addition the guardrail says to treat as forbidden-content-until-justified, and no justification survives scrutiny (a fake colonization flag has no future use; real colonization arrives with real rules in Phase 3).
- Resolution: **render the full generated galaxy — up to 90 planet tiles — every frame**, uniformly, with no colonized/uncolonized visual distinction. This is a strict superset of the criterion's "~30 colonized" in terms of primitive count and CPU-side per-frame construction cost, so the FPS measurement below is, if anything, a **harder** test than the plan's literal criterion, not a weaker approximation of it — documented here explicitly so a reviewer doesn't mistake "we render 90, not 30" for scope creep; it's the conservative direction.

**GPU primitive submission — no ordering table, direct `DrawPrim` per primitive, matching existing precedent.**
- `game_draw()` (in `game_draw.c`, the render-side module `psx-main-skeleton` already established) iterates `world`'s accessors each frame and issues one `TILE`+`DrawPrim` call per planet (≤90), one `POLY_F4`+`DrawPrim` call for the wormhole marker, and one `LINE_F2`+`DrawPrim` call per synthetic slipway edge (50) — ~141 primitives/frame, submitted in the same direct, immediate style `psx-hello/main.c` already uses for its cursor tile (`setTile`/`setXY0`/`setWH`/`setRGB0`/`DrawPrim`), rather than building an ordering table (`GsOT`/`DrawOTag`) — that's genuinely not needed for a flat, non-overlapping, 2D, single-layer scene with no depth sorting, and introducing it speculatively would be exactly the kind of premature complexity `docs/plan.md`'s own framing ("très au-delà du besoin") warns isn't necessary at this scale. If the FPS measurement below ever shows GPU-FIFO stalls from this direct-submission style specifically (distinguishable from genuine per-primitive CPU cost), switching to an ordering table is a known, available fallback for a later step — not pre-built here.
- Colors for all three primitive kinds are arbitrary flat placeholder colors (no real art exists before Phase 5) chosen only to be visually distinct from each other for screenshot verification; not traced to, and not claiming to be, any real Slipways visual.

**FPS measurement — extending the Phase 0 PCSX-Redux harness, and being explicit about what it can and can't measure.**
- **What PCSX-Redux actually exposes, investigated directly in `tools/pcsx-redux/src/core/`:**
  - `PCSX.Events.createEventListener("GPU::Vsync", callback)` (`core/eventslua.cc`) fires once per emulated NTSC VBlank. Tracing `core/psxcounters.cc`'s `Counters::update()`, this event is driven entirely by the emulated R3000A's own instruction-cycle counter (`m_rcnts[3]`'s target is `psxClockSpeed / (FrameRate × HSyncTotal)`, compared against `m_cpu->m_regs.cycle`) — **not** by host wall-clock time or a host-side timer. This is the same mechanism every existing harness in this repo already uses for frame pacing (`waitFrames`, coroutine-yield-per-Vsync in `tools/gen_pcsx_hello_input_test_lua.py`/`tools/gen_pcsx_slipways_input_test_lua.py`).
  - `PCSX.getCPUCycles()` (`core/pcsxlua.cc:37`, `uint64_t getCPUCycles() { return PCSX::g_emulator->m_cpu->m_regs.cycle; }`) directly exposes that same emulated cycle counter to Lua. The PSX's R3000A runs at a fixed, well-known NTSC clock of **33,868,800 Hz** — this is standard, public PS1 hardware documentation, not a value inferred from this codebase.
  - No Lua binding exposes host wall-clock elapsed time tied to emulation progress, and none is needed: `getCPUCycles()` gives a direct, precise, cycle-accurate measure of *emulated* elapsed time, which is exactly what "would this run at 30fps on real hardware" needs — real hardware's own clock is the R3000A's cycle counter, not whatever wall-clock rate a given host happens to emulate at under `--no-ui --run` (which is not throttled to real-time and was already observed, in `docs/psx-hello-world.md`, to take "~336 emulated VBlank frames" to boot without any wall-clock timing claim attached).
  - **Explicit honesty statement (per the task framing's requirement)**: this measurement is **emulated-time FPS**, derived from the same cycle-accurate model a real console's own clock would produce, not host wall-clock FPS and not a measure of PCSX-Redux's own emulation throughput on the machine running the test. It is the correct and only meaningful way to answer "would this hit 30fps on real hardware" from inside this harness, and is documented as such rather than silently presented as literal real-time frames-per-second.
- **Mechanism**: a new `static volatile uint32_t g_frame_count;` in `psx-slipways/main.c`, incremented (with a real store instruction, each iteration — not initialized-once, avoiding the exact dead-store pitfall `docs/psx-hello-world.md` already documented and fixed for `test_harness_ready`) once per main-loop iteration, right alongside the existing `test_harness_ready` marker. This is test-support plumbing at the same layer and for the same reason `test_harness_ready` and pad-input's widened test-visible statics already are (per `docs/prd/psx-pad-input.md`'s precedent) — not business logic, not observable gameplay.
- **New Lua driver** (`tools/gen_pcsx_slipways_fps_test_lua.py`, mirroring `tools/gen_pcsx_slipways_input_test_lua.py`'s map-symbol-resolution/template approach) and **new boot-test script** (`tools/boot_test_psx_slipways_pcsx_fps.sh`, mirroring `tools/boot_test_psx_slipways_pcsx_input.sh`'s structure) plus a new Makefile target `psx-slipways-fps-test-pcsx`:
  1. Wait for `test_harness_ready` (existing boot-readiness pattern, unchanged).
  2. Settle for a short fixed number of Vsync ticks (to clear any startup transient — reused pattern from the input harness's `SETTLE_FRAMES`).
  3. Record `cycles_start = PCSX.getCPUCycles()` and `frames_start = readS32(G_FRAME_COUNT_ADDR)`.
  4. Advance a fixed measurement window of `MEASURE_WINDOW_VSYNCS` (e.g. 180, i.e. 3 emulated NTSC seconds — long enough to average out any single-frame jitter, short enough to keep the test fast) real Vsync ticks via the same `coroutine.yield()`-per-`GPU::Vsync`-event pattern every existing harness already uses.
  5. Record `cycles_end`/`frames_end`, compute `elapsed_emulated_seconds = (cycles_end - cycles_start) / 33868800`, `frames_rendered = frames_end - frames_start`, `achieved_fps = frames_rendered / elapsed_emulated_seconds`.
  6. Assert `achieved_fps >= 30`, with the actual number printed either way (so a passing or failing run both leave a concrete figure in the log, not just a boolean).
- **Scope caveat, stated explicitly per the task framing's instruction to be honest about limits**: this measurement validates the **GPU-primitive-submission and static-scene rendering** portion of the plan's open CPU-budget question, for exactly this step's content (a galaxy generated once at boot, not regenerated per frame; no per-frame liaison-validity recalculation, since that logic doesn't exist yet). It does **not** yet validate the CPU cost of the per-frame trigonometry or live liaison recalculation `docs/plan.md`'s rendering-approach section names as the real open risk — those arrive with later phases (Phase 3 step 9 for liaison recalculation) and get their own measurement then. A pass here is real progress on the feasibility question, not a full closure of it; this PRD does not claim otherwise anywhere else in this document.
- **If the assertion fails during implementation**: per `docs/plan.md`'s own Garde-fous ("points durs, jamais de points bloquants"), the correct response is to record the shortfall as a documented Phase 6 point dur (in `docs/plan.md`), not to silently shrink `MAX_SYNTHETIC_SLIPWAYS`, the rendered planet count, or the 30fps threshold to force the assertion to pass. This is stated here explicitly so a future implementer (or an autopilot) doesn't "fix" a real infeasibility finding by quietly weakening the test.

## Implementation Chunks

Tracer-bullet slices, each independently buildable/boot-testable, anchor behavior (the FPS assertion) reached last:

1. **Screen mapping + galaxy wiring + one planet drawn.** `screen.h` (shared `SCREEN_XRES`/`SCREEN_YRES`), `screen_map.h`/`.c` (pure, host-tested), promote `PLANETGEN_PLACEMENT_MIN`/`SPAN` to `planetgen.h`, `world.h`/`.c` with `world_init()` calling only `planetgen_generate` (no neighbor graph/edges yet), `game_init()` calls `world_init()`, `game_draw()` draws exactly one hardcoded planet (`g_galaxy.positions[0]`) as a single `TILE` primitive. Smallest possible slice proving the GPU-primitive call path end-to-end. Verified via `make psx-slipways-boot-test-pcsx` (still boot-only at this point) plus a manual `make psx-slipways-screenshot-pcsx` look.
2. **All generated planets drawn.** `game_draw()` loops `g_galaxy.positions[0..count)` and draws every one as a `TILE`. No wormhole/slipways yet.
3. **Wormhole placeholder.** `world_init()` designates index 0 as the wormhole marker (documented per Implementation Decisions); `game_draw()` renders it as a `POLY_F4` in a distinct color, and stops drawing it a second time as a plain tile (it's still one of the 90 generated positions, but visually singled out).
4. **Synthetic slipway lines.** `planetgen_build_neighbor_graph` call added to `world_init()` at the traced `0.19` threshold; new `slipway_bench.h`/`.c` (pure, host-tested) selects and caps 50 edges; `world.c` exposes them; `game_draw()` draws each as a `LINE_F2`. This is the first point where the full synthetic scene (90 tiles + 1 polygon + 50 lines) exists — verified visually via `psx-slipways-screenshot-pcsx`.
5. **FPS measurement harness.** `g_frame_count` added to `main.c`; `tools/gen_pcsx_slipways_fps_test_lua.py`, `tools/boot_test_psx_slipways_pcsx_fps.sh`, and the `psx-slipways-fps-test-pcsx` Makefile target added; the plan's literal "mesurer contre le critère de faisabilité" anchor behavior is reached here, exercising the full scene chunk 4 established rather than a partial one.

## Testing Decisions

- **What makes a good test here (restated from prior PRDs' established standard)**: assert on observable output through a module's public functions (mapped pixel coordinates land in range; selected edge count and content are correct; the real 90/50-edge configuration produces the expected counts), never on internal representation.
- **Host-testable, added to `make test` (folded in alongside the existing `test-planetgen` target, matching `docs/prd/psx-planet-generation.md`'s precedent for why `make test` must stay complete per `CLAUDE.md`):**
  - `screen_map.c`: corners of the real `PLACEMENT_MIN`/`PLACEMENT_SPAN` domain map to the expected margin-adjusted pixel corners for the real `SCREEN_XRES`/`SCREEN_YRES`; monotonicity per axis; no overflow.
  - `slipway_bench.c`: small hand-built synthetic `neighbor_graph_t` fixtures (mirroring `planetgen_test.c`'s existing pattern of hand-placed, non-RNG fixtures) verifying the cap is respected, the returned count matches `min(actual_edges, max_edges)`, and the scan order is deterministic (two calls, same input, identical output); plus one check against the **real** configuration (90 planets, fixed `WORLD_RNG_SEED`, real `0.19` threshold) asserting the neighbor graph actually has **more** than `MAX_SYNTHETIC_SLIPWAYS` (50) edges — i.e. confirming the cap is the thing that determines the rendered count for the real scenario, not incidental graph sparseness.
  - `world.c`: an integration-style test (mirroring `planetgen_test.c`'s chunk-5 integration test) asserting that, for the fixed seed, `world_init()` produces exactly 90 planets, exactly 50 synthetic slipway edges, and a wormhole index within range — the concrete numbers this step's rendered scene depends on, checked once as a whole rather than only through each piece in isolation.
  - New Makefile target `test-galaxy-render` (inline recipe, same shape as `test-planetgen`: host `gcc`, no PSn00bSDK toolchain, output under `psx-slipways/build-host/`), and `test` updated to depend on it alongside `test-planetgen`.
- **Not host-testable, and that's expected (same reasoning `psx-pad-input`'s PRD already established for the hardware boundary)**: `game_draw.c` (real `psxgpu.h` primitive calls), `main.c`'s new frame counter (glue/test-plumbing, not logic). Verified instead by:
  - `make psx-slipways-boot-test-pcsx` (existing, unmodified) — still confirms boot doesn't crash with the new, much larger per-frame primitive submission.
  - `make psx-slipways-screenshot-pcsx` (existing, unmodified target/tooling) — a quick visual sanity check per implementation chunk that the scene looks like a galaxy (dots + one differently-shaped/colored marker + connecting lines), not a numeric assertion but a fast way to catch an obviously-wrong screen-mapping or primitive-setup bug well before wiring the FPS harness.
  - The new `make psx-slipways-fps-test-pcsx` (this PRD's own addition) — the real, numeric, pass/fail feasibility assertion described in Implementation Decisions.
- **Prior art reused as-is**: `tools/gen_pcsx_slipways_input_test_lua.py`'s map-symbol-resolution/template-generation approach (for the new FPS driver generator), `tools/boot_test_psx_slipways_pcsx_input.sh`'s script structure (for the new FPS boot-test script), `psx-slipways/host_tests/t.h` and `planetgen_test.c`'s hand-built-fixture-plus-real-configuration testing style (for `screen_map`/`slipway_bench`/`world`'s host tests).

## Out of Scope

- The real wormhole placement mechanic (player's first click creates it; `pico8/lua.lua:376`, `docs/plan.md` Phase 4 step 15) — this step renders a fixed placeholder position only, explicitly documented as not that mechanic.
- Real slipway validity logic: cost (`dj`), range/crossing/planet-on-path checks, `liaison.c` (`docs/plan.md` Phase 3 step 9) — the rendered lines are synthetic geometry with no cost, no validity, and no game meaning.
- Planet type/job/colonization state and the discovery roll (`docs/plan.md` Phase 3 step 10) — all 90 generated planets render identically; there is no "colonized" visual distinction in this step (see Implementation Decisions for why inventing one was rejected).
- Any cursor/click/input-driven interaction with the rendered scene — Phase 2 (steps 5-7), untouched by this step. `game_update()`'s body is unchanged beyond what pad input already added.
- Camera pan/zoom, or any aspect-ratio-preserving projection — the screen mapping stretches the domain to fill 320×240 directly; no camera system exists yet.
- An ordering table / `GsOT`-based draw pipeline — direct `DrawPrim` submission is used throughout; introducing an OT is left as a known fallback for a later step if profiling data ever calls for it.
- Real sprite/polygon art, palette, or any Phase 5 asset-extraction work — all colors are arbitrary flat placeholders.
- Seeding the generator's RNG from real PSX hardware entropy (timer, etc.) — the seed stays a literal fixed constant, continuing the deferral `docs/prd/psx-planet-generation.md` already documented.
- Measuring or validating the CPU cost of per-frame trigonometry, liaison-validity recalculation, or any other dynamic game-logic cost `docs/plan.md`'s rendering-approach section names as the real open risk — this step's FPS measurement covers only this step's own static-scene rendering load; later phases get their own measurement when that logic exists.
- Modifying `psx-hello/` in any way.
- Any change to the existing `psx-slipways-boot-test-pcsx`/`psx-slipways-input-test-pcsx` targets — both are extended-around, not altered.

## Further Notes

- **This is the first use of `LINE_F2` and `POLY_F4` anywhere in this codebase** — `psx-hello/main.c` only ever used `TILE`. Worth flagging for whoever implements chunk 3/4: there is no existing precedent in this repo for these two primitive types' exact field-setting macros, so that part of the implementation should double-check current PSn00bSDK header signatures directly rather than assume they match `TILE`'s shape.
- **Why `world.c` is deliberately kept PSX-header-free even though it's "the thing `game_init()` calls at boot"**: this is the main payoff of splitting it out from `game_draw.c`/`game_update.c` — it's the one place in this step's design that can be integration-tested on the host (exact planet/edge counts for the real fixed-seed configuration) without needing an emulator at all, which is exactly the kind of "deep module" this project's established convention (`planetgen.c`) already favors.
- **The 50-edge cap is intentionally the same number the rendering code and the FPS harness both read from `world.c`'s accessors** — there is deliberately no second, independent "how many lines does the benchmark expect" constant anywhere in the Lua driver; the harness measures whatever the real built game actually renders, not a hardcoded expectation of it, so a future change to `MAX_SYNTHETIC_SLIPWAYS` can't silently desync the two.
- **If a future step needs a *different* synthetic-load shape** (e.g. testing against exactly 40 vs. exactly 60, or against a harder degenerate case like all edges clustered in one screen region), `slipway_bench_select_edges`'s `max_edges` parameter and the row-major scan order are both already generic enough to support that without redesigning the module — noted here so nobody re-derives this from scratch.
- **Recommend, as a small separate follow-up (not part of this PRD, consistent with `docs/prd/psx-planet-generation.md`'s own precedent for flagging but not fixing doc issues)**: once this step lands, `docs/plan.md`'s Phase 1 step 4 line could be annotated with a pointer to the actual measured FPS figure and the caveat above (static-scene-only), the same way step 2's connectivity-rate finding was folded back into the plan's own wording rather than left only in a PRD.
