## Problem Statement

`docs/plan.md` Phase 4 step 14 calls for `rules_planets.c`/`rules_tech.c` : "Étendre... à l'ensemble des 10 types de planètes, spécialisations et 20 technologies documentées." Both modules currently hold deliberately reduced, already-graduated vertical slices: `rules_planets.c` (`docs/prd/psx-rules-planets.md`) ports 3 of 10 planet types (earth-like, forgeworld, mineral) and 5 of ~24 colonization jobs (hiveworld, agroworld, nanotech, bots, mine), chosen to form one closed resource loop; `rules_tech.c` (`docs/prd/psx-rules-tech.md`) ports 4 of 19 technologies (space folding, geneseeds, nanomaterials, drillbots), the real, zero-prerequisite Era-1 slice, live-wired only at the level of a Select-toggled menu open/closed boolean, with **no** per-tech-researched state. Both PRDs explicitly deferred "the rest" to this step, and both left concrete extension points on record (`dm` as traced-but-unapplied data; `nanomaterials_researched`/`job_tech_researched` as generic caller-supplied booleans; the design doc's own tech-table miscount already caught and corrected once).

The plan's own "20 technologies" figure is wrong, and this PRD does not blindly replicate it. `docs/prd/psx-rules-tech.md` already re-decoded the raw `nb` table (`unstash 10457`, `pico8/map.json`) and found **19** tech records, not 20, with era sizes 4/5/5/5, and two techs (`xenofoods`, `autoassemblers`) mis-assigned to the wrong era in the design doc's own §12 prose. This step extends to that already-corrected 19-tech roster, not to a fabricated 20th entry.

Two further things make this step larger than a typical "port a formula" step: (1) the full job table (`fd`, `pico8/lua.lua:1391`, `unstash 8494`) turns out to encode **two distinct tech-gating mechanisms**, not one -- an `il` field (cost surcharge + curve upgrade, already ported for `agroworld`) and a separate, previously-undiscovered `rr` field (job-availability gate, encoded as bare strings interspersed in the raw `fd` array, consumed by a small stateful loop at `pico8/lua.lua:1434-1440`) -- and the existing code only models the first; (2) four jobs (`farm`, `habitat`, `genefarm`, the iceball/gas-giant `excavate`) are available on **two** planet types from a single source record, which the existing `colonization_job_t.planet_type` (a single value, not a set) cannot represent, forcing a small, source-grounded struct change alongside the data growth.

Per `docs/plan.md` Phase 4 step 15's own explicit wording ("les actions de transformation de planète (mechanize/terraform/collapse/harvest)"), the 4 planet-transform/destroy jobs and the 7 non-colonizable structures (§6) remain out of scope for this step -- confirmed structurally distinct in the raw data too (they use `ii`/`go`/`cw` fields instead of the regular `il`/`dm`/`rr` fields real colonization jobs use, and the 6 structure records in `fd` all carry `px=""`, an empty job name, unlike every real job).

## Solution

Re-run the project's established `jq` decode recipe (`docs/design/slipways-mechanics.md` Annexe A) against `unstash(8494)` (`fd`, `pico8/lua.lua:1391`) directly from `pico8/map.json`, rather than trusting the design doc's §8 table's column set as complete -- the same discipline `rules_planets.c`'s and `rules_tech.c`'s own PRDs already applied to `fd`/`nb`. This surfaces the raw array's actual structure (documented in full below) and confirms: **the design doc's §8 table's 24 real-job rows are numerically accurate** (no corrections needed to any cost/needs/produce/curve value, unlike `rules_tech.c`'s PRD's era-assignment correction), but the table is missing two real fields (`il`/`rr`) the raw data has, and missing a `dm` (default-need) value on three more jobs than previously known.

Extend `rules_planets.h`/`rules_planets.c`'s existing enums and static tables in place (append-only, existing entries unchanged): `planet_type_id_t` grows from 3 to 10 entries (`PLANET_TYPE_COUNT`), `colonization_job_id_t` grows from 5 to 24 entries (`JOB_COUNT`), `resource_id_t` gains exactly one new value (`RESOURCE_LUXURY` -- the only resource among the 19 new jobs that isn't already modeled), `curve_id_t` gains exactly one new value (`CURVE_F_MINUS` -- the only curve shape among the 19 new jobs not already modeled; `f+`/`qh`/`qh+` remain structure-exclusive and stay out of scope). `colonization_job_t` gets one shape change (a fixed-size `planet_types[]`/`planet_types_count` in place of the single `planet_type` field, sized to the real traced maximum of 2) and one new optional field (`required_tech`, a `const char *`, mirroring `tech_gate`'s existing shape, for the newly-discovered `rr` availability-gate mechanism). Every existing public function (`rules_planets_type`, `rules_planets_job`, `rules_planets_curve_value`, `rules_planets_job_cost`, `rules_planets_job_production`) needs **zero body changes** -- each is already generic over "whichever job/type the caller asked for" and "whichever tech the caller's boolean represents," a genuine, confirmed finding rather than an assumption (see Implementation Decisions). One new, small accessor is added (`rules_planets_job_available_on`, mirroring source's own `bj()` filter) so the new multi-type representation is independently testable.

Extend `rules_tech.h`/`rules_tech.c`'s existing `tech_id_t`/`tech_t` similarly: `TECH_COUNT` grows from 4 to 19 (append-only, same 4 Era-1 entries first), `tech_t` gains one new field (`era`, an `int` 1-4, meaningful now that more than one era exists). No new function, no new live state: per-tech-researched status stays exactly as unwired as `rules_tech.c`'s own PRD already established (a caller-supplied boolean precedent, never a module-owned "is X researched" global), and era-progression (`ek`'s thresholds, `hy:kt`'s commit) stays exactly as deferred, for the same reason (`rules_economy.c` never wired a live science stockpile either -- confirmed by direct re-read of `docs/prd/psx-rules-economy.md`, see Implementation Decisions). The one real wiring-adjacent change this step makes is **not** to either module's logic: `game_draw.c`'s already-live tech-menu placeholder currently sizes its 4-`TILE` grid off `TECH_COUNT` (`psx-slipways/game_draw.c:209,212`) -- growing `TECH_COUNT` to 19 would silently balloon that already-shipped, screenshot-verified rendering to 19 tiles with no layout redesign. This step decouples that render loop from the data table's size with one new, explicit constant (`RULES_TECH_ERA1_TILE_COUNT = 4`), preserving the exact already-tested visual exactly, rather than letting a data-only step silently change tested PSX-side behavior.

Nothing in this step introduces new live state, a new caller in `game_init`/`game_update`/`game_draw` for `rules_planets.c` (still zero callers, confirmed unchanged), or any change to `rules_tech.c`'s existing live open/closed toggle. This is pure data growth plus the one necessary rendering-compatibility constant -- confirmed explicitly below, not assumed by analogy to the prior two PRDs' unwired precedent.

## Implementation Decisions

**The raw `fd` array's actual structure, re-decoded directly (`pico8/lua.lua:1391`, `unstash(8494)`), not assumed from the design doc.**

Running the project's established `jq` recipe against `unstash(8494)` yields 42 top-level array elements: 6 structure records (`px=""`), 24 real colonization-job records, 4 transform/destroy-action records, and **8 bare strings** interspersed among them. The bare strings are not stray data -- `pico8/lua.lua:1434-1440` is the exact consumer:

```
gb,rr={}
for ri in all(fd)do
if type(ri)=="string" then
rr=ri
else
ri.rr=rr
add(gb,hp(ri))end
end
```

This is a small stateful loop over `fd` in array order: a bare string sets a running `rr` variable (a tech name); every subsequent non-string record gets `ri.rr = rr` (the most recently seen bare string, or `nil` if none has appeared yet) before being wrapped into a job object and added to `gb`. **This is a second, distinct tech-gating field from `il`** (the field `hp.mr`'s positional list already names, `pico8/lua.lua:1400`, `o("px","lr","fj","ja","i","o","il","dm")`, and the one `rules_planets.c`'s existing `tech_gate`/`hp:od()`/`hp:po()` already ports for `agroworld`). `il` (checked via `self.il and oj(self.il)` in both `hp:od()`, `pico8/lua.lua:1426-1433`, and `hp:po()`, `pico8/lua.lua:1422-1425`) gates a **cost surcharge and curve upgrade on an already-available job**; `rr` (checked via `bj(jo)`, `pico8/lua.lua:1391-1398`: `jp(gb,function(b) if oj(b.rr) then ... end end)`) gates **whether the job is offered as a choice at all**. No prior PRD in this codebase had discovered `rr` -- `rules_planets.c`'s own PRD's 5-job subset happens to contain zero jobs with a nonempty `rr` (every bare string in `fd` appears *after* all 5 of those jobs in array order), so this mechanism was invisible to that PRD's own re-decode.

**`resource_id_t`: exactly one new value, `RESOURCE_LUXURY`.** Scanned every one of the 24 jobs' `needs`/`produces` codes: the only resource code among the 19 newly-added jobs not already in `rules_planets.h`'s enum is `w` (`luxury`, `r.w=12` per Annexe A, produced by `tourism`/`luxury`, needed by neither in-scope job -- `luxury` is a genuine terminal sink in this reduced-but-real subset, matching `docs/prd/psx-rules-economy.md`'s own independent finding that `r.w`/"luxury" feeds `db()`'s external-trade bonus and `bf()`'s happiness formula, both outside this module). `science` (`k`), `energy` (`e`), `joy` (`h`), and the joker (`?`) are touched only by structure records (`px=""`) -- confirmed by the same `fd` scan -- so they stay out of scope, per Phase 4 step 15's own structure list.

**`curve_id_t`: exactly one new value, `CURVE_F_MINUS`.** The 19 new jobs' `curve` field is one of `-`, `+`, `f-` only (scanned exhaustively in the table above); `f-` (`tourism`, `luxury`) is the only shape not already in `curve_id_t`. Its per-level table, from `hc` (`pico8/lua.lua`, `unstash 8383`, Annexe A): `f- = [0,1,2,3]` (levels 1-4), with an `mc` upgrade target of `f+` recorded in `hc` itself -- but **neither `tourism` nor `luxury` carries an `il` field** (both are 6-positional-element raw records, `px,lr,fj,ja,i,o` only, no 7th/8th elements), so `hp:po()`'s `self.il and oj(self.il)` condition can never be true for either job regardless of tech state: **this port's `f-`→`f+` upgrade path is never reachable from any in-scope job**, only from the Food processor structure (`il="xenofoods"`, `pico8/lua.lua`'s structure record #4 in `fd`), which is step 15 territory. Resolving the task's key scoping question 3 precisely: `CURVE_F_MINUS` is added (real consumer, `tourism`/`luxury`); `CURVE_F_PLUS`/`CURVE_QH`/`CURVE_QH_PLUS` are **not** added (zero consumers among any of the 24 real jobs -- `qh`/`qh+` are exclusively Laboratory's, `f+` exclusively Ascension Gate's and the Food processor's post-upgrade table, all three structure-only). `rules_planets_curve_value`'s existing upgrade branch (`upgraded && curve == CURVE_MINUS` maps to `CURVE_PLUS`) is left exactly as-is -- no new upgrade branch is added for `CURVE_F_MINUS`, since nothing in scope ever triggers one, mirroring the existing precedent that `CURVE_PLUS` itself already has no upgrade target ported.

**Multi-planet-type jobs: `farm` (xeno, jungle), `habitat`/`genefarm` (barren, iceball), the iceball/gas-giant `excavate` (iceball, gas giant) -- one record each in source, so one enum entry each here, not two.** Source's `lr` field is a *string* of 1 or 2 planet-type codes (e.g. `farm`'s raw record is `o("farm","xj",10,"-","b","f",f,"l")`, `lr="xj"`) -- confirmed by contrast with `colony`/`breed`/`excavate`(mineral variant), each of which appears as **two separate raw records** with different `needs`/`curve` per type (e.g. `colony`(ocean) needs `ore+food` on curve `-`; `colony`(xeno) needs `tech+food` on curve `-` -- same curve, different needs, hence two records) -- source itself only collapses two types into one record when the job's cost/needs/produce/curve are identical across both types. `colonization_job_t.planet_type` (a single value) cannot represent the 4 real two-type cases faithfully without either duplicating data (a drift risk `rules_planets.c`'s own established "single source of truth" style elsewhere doesn't take anywhere else) or dropping one of the two types silently (a guardrail violation). **Resolved**: `planet_type_id_t planet_type` is replaced by `planet_type_id_t planet_types[RULES_PLANETS_MAX_TYPES]` (`RULES_PLANETS_MAX_TYPES = 2`, sized to the real traced maximum -- no job spans 3+ types) plus `int planet_types_count`, mirroring the existing `needs[RULES_PLANETS_MAX_NEEDS]`/`needs_count` shape exactly (same struct-field idiom, same "sized to the real traced max, not padded" convention `rules_planets.c`'s own PRD's Further Notes already established for `RULES_PLANETS_MAX_NEEDS`). A new accessor, `bool rules_planets_job_available_on(colonization_job_id_t id, planet_type_id_t type)`, mirrors source's own `bj()` filter (`pico8/lua.lua:1391-1398`, minus the `oj(b.rr)` tech-researched check, which stays a caller-supplied concern exactly like every other tech-gate in this module) and gives the new multi-type representation a real, independently host-testable surface, not just a struct shape nobody reads.

**Tech-gate threading: confirmed, from source and from the existing signature shape, that zero function changes are needed -- not a new set of named boolean parameters.** `rules_planets_job_cost(colonization_job_id_t id, bool job_tech_researched, bool nanomaterials_researched)` and `rules_planets_job_production(colonization_job_id_t id, int level, bool job_tech_researched)` already take `job_tech_researched` as a single, per-call, job-agnostic boolean -- the caller, not the function, is responsible for knowing which real tech a given job's `il` field names and supplying the correct boolean for *that* tech on *that* call. ## Testing Decisions

- **What makes a good test here**: assert on observable output (table field values, formula/accessor results for given inputs) -- never on internal representation (enum integer values, array order, `static` vs. exported), matching every prior PRD's standard in this codebase, including `rules_planets.c`'s and `rules_tech.c`'s own.
- **Fully host-testable, all 11 chunks** (`gcc`, no PSn00bSDK toolchain): every new/changed function in both modules takes plain parameters and has zero new dependency (`rules_planets.c` still depends only on `fixed.h`; `rules_tech.c` still depends only on `<stdint.h>`). This step **extends** the existing `host_tests/rules_planets_test.c` and `host_tests/rules_tech_test.c` files and the existing `test-rules-planets`/`test-rules-tech` Makefile targets -- no new target, no new `RULES_*_TEST_HOST_SRCS` var, since no new module is created (both targets already compile exactly `psx-slipways/rules_planets.c psx-slipways/host_tests/rules_planets_test.c` / the `rules_tech.c` equivalent, and neither file list needs to change).
- **Regression discipline**: every chunk that adds new data re-runs (not just doesn't-break, but explicitly re-asserts) the previously-landed entries' exact values, per chunk 3's and chunk 11's explicit "existing entries unchanged" test lines above -- this project's established pattern (`rules_tech.c`'s own chunk 1 test list already did this for its 4 Era-1 entries) applied consistently across a much larger extension.
- **Not tested here**: anything requiring the PSn00bSDK toolchain beyond confirming the existing, unmodified `psx-slipways-boot-test-pcsx`/`psx-slipways-rules-tech-test-pcsx`/`psx-slipways-screenshot-pcsx` targets still pass (no new PSX-side behavior is introduced, only a compatibility-preserving constant swap in already-tested code); any live colonization-choice/tech-researched state (still doesn't exist anywhere in this port); `gi()`/`ck()`/`fm.fu`/`hy:kt`/`ek` (still fully out of scope, per `rules_tech.c`'s and `rules_economy.c`'s own PRDs, re-confirmed not re-litigated here); the 7 structures, the 4 transform/destroy actions, or the `ll` empty-planet sentinel (Phase 4 step 15 / Phase 3 step 10 territory, unchanged).

## Further Notes

- **The single highest-value finding**: the raw `fd` array encodes two genuinely distinct tech-gating mechanisms (`il` for cost/curve modification of an already-offered job; `rr`, previously undiscovered, for whether a job is offered at all), consumed by two different pieces of source logic (`hp:od()`/`hp:po()` for `il`; the small stateful `for ri in all(fd)` loop at `pico8/lua.lua:1434-1440` plus `bj()`'s `oj(b.rr)` check for `rr`). The design doc's §8 table's single "Déblocage / effet tech" column, and the fact that `rules_planets.c`'s original 5-job subset happened to contain zero `rr`-gated jobs, meant this distinction was invisible until this step's full-roster re-decode. Recommended, as a small separate follow-up (not part of this PRD, consistent with every prior PSX-side PRD's own practice): `docs/design/slipways-mechanics.md` §8 could split its "Déblocage / effet tech" column into two (a `il`-style "effet une fois recherché" and a `rr`-style "recherche requise pour proposer ce job"), and add the `dm` column `rules_planets.c`'s own PRD already recommended, now with 3 more rows to fill in (`colony`×2, `habitat`).
- **Structures' `px=""` naming quirk, flagged for whoever picks up Phase 4 step 15**: all 6 non-colonizable-structure records in `fd` share the literal empty job name `px=""`. Since `gb[ri.px]=ri` (inside `hp:pq()`'s `ho()` call) would make every structure overwrite the same `gb[""]` dictionary slot, structures clearly aren't looked up by `px` the way real jobs are (`gb["colony"]` would itself only resolve to whichever of the two `colony` records was added last, for the same reason -- array iteration via `bj()`/`jp()` is what actually recovers every record, name collisions and all). Structures are almost certainly addressed by their `dr`-table code (`nr`/`fr`/`nl`/`mx`/`hj`/`qh`/`os`, per §6's own confirmed table) or by raw array position, not by `fd`'s own `px` field -- worth checking directly against `dr`'s own unstash (`9807`) before step 15 assumes structures can be looked up the same way this step's real jobs are.
- **Why the closed-loop test's scope is explicitly *not* extended**: the original 5-job subset's closed-loop property (every need has an in-subset producer, every product has an in-subset consumer) was a deliberate, self-imposed design choice of that PRD's own 5-job selection, not a property of the source game as a whole -- the full 24-job roster genuinely isn't closed (`luxury`, produced by `tourism`/`luxury`, is consumed by no in-scope job; it feeds `docs/prd/psx-rules-economy.md`'s `db()`/`bf()` formulas directly, outside this module entirely). Chunk 10 states this explicitly so a future reader doesn't either (a) assume the extended roster is still closed and get confused when a hypothetical future "closed-loop, full roster" test would necessarily fail, or (b) assume the existing test was weakened by this step (it wasn't touched at all).
