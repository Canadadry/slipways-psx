## Problem Statement

`psx-slipways/` (Phase 1 step 1) is a working glue skeleton — `main.c` dispatches to empty `game_init()`/`game_update()`/`game_draw()` stubs — but it contains zero game logic. The first real logic the porting plan calls for (`docs/plan.md` Phase 1 step 2) is procedural galaxy generation: placing the 90 planets the PICO-8 original places at the start of every game (`bw(n)` defined at `pico8/lua.lua` line 744, called as `bw(90)` at line 1182), rejecting placements that land too close to an already-placed planet, and proving — mechanically, not by eyeballing a screenshot — that the resulting galaxy is never split into pockets a player could never reach. Nothing in the repo does this yet, and nothing in the repo yet establishes what a "host-testable, PSX-independent C module" looks like structurally for this port, even though the plan explicitly asks for this step (and later steps, e.g. Phase 3 step 10's "RNG injectée pour tests déterministes") to be verifiable on the host without the PSn00bSDK toolchain or an emulator.

## Solution

Add a new, self-contained C module to `psx-slipways/` that: (1) places `n` planets on the same bounded 2D domain the PICO-8 source uses, rejecting any placement too close to an existing one (exact threshold and comparison semantics traced to `pico8/lua.lua`, not approximated); (2) builds a distance-based neighbor graph over the placed planets; (3) runs a BFS over that graph to prove every planet is reachable from every other. All three pieces are pure C, buildable and runnable with the host's native `gcc` (no PSn00bSDK headers, no GPU/pad code), following the same "host-testable core logic" spirit `game/lib/t.lua` served for the Love2D prototype. The module uses fixed-point (integer) arithmetic throughout rather than `float`, because it is meant to compile unmodified into the real PSX build later, and the R3000A has no hardware FPU (`docs/plan.md`'s rendering-approach section names "génération procédurale" explicitly as one of the CPU-budget risks this lack of FPU creates). A new host-native test target is added to the build (`make test-planetgen`), and folded into `make test` so the verification command `CLAUDE.md` already directs contributors to use covers this new code too. This step does **not** wire generation into `game_init()`/`game_update()` — see Implementation Decisions for why that's deliberately deferred.

## Implementation Decisions

**Source-fidelity findings (read directly from `pico8/lua.lua`, not inferred from prose):**

- **Placement domain.** `bw(n)` (line 744) places each planet at `p = v(rnd(2.75)+0.125, rnd(2.75)+0.125)` (line 747) — i.e. `x` and `y` are drawn **independently**, each uniformly from `[0.125, 2.875)`. This is *not* the `0..1` square `docs/design/slipways-mechanics.md` §4 describes in passing for the probe-range threshold — that phrasing is the design doc's own approximation and does not match the literal placement code. This PRD ports the literal bounds (`[0.125, 2.875)` per axis, i.e. a span of `2.75` with a `0.125` margin baked into the random range itself — no separate "keep away from the edge" check exists or is needed), not the doc's simplified description. Recommend a follow-up doc correction (not done here — out of scope for a PRD-only pass).
- **Proximity-rejection threshold is on *squared* distance, not linear distance.** `bw` rejects a candidate point until `ij(p, cg.jo) > 0.05` (line 748). `ij(p, j_)` (line 351) returns, as its first value, the minimum of `#(p - o.p)` over all already-placed planets `o` — and `#` on this vector type is overloaded (`km.__len`, line 119: `return self:rg(self)`, where `km:rg` at line 110 is a plain dot product `self.x*v2.x + self.y*v2.y`). So `#v` here is `v.x² + v.y²`, i.e. **squared Euclidean length**, not `sqrt`. `docs/design/slipways-mechanics.md` §3 quotes the comparison verbatim (`ij(p,cg.jo)>0.05`) but its prose ("seuil `0.05` normalisé") reads as a linear-distance threshold; it isn't. The real minimum linear separation the source enforces is `sqrt(0.05) ≈ 0.2236`. This module ports the literal squared-distance comparison (`dx*dx + dy*dy > 0.05`, in the same units as the placement domain above), matching source behavior exactly rather than the doc's paraphrase. (Also flagged as a doc-correction candidate, not fixed in this PRD.)
- **Planet *type* is not assigned at generation time.** `bw` only sets up the type-draw generators (`jo.oc`, `jo.ir`, line 750-751) as closures to be called later; per §3 of the design doc and `jo:hh` (discovery handler, line 407), the actual type (or "empty planet") is drawn when a probe *discovers* the planet, not when the galaxy is generated. This module therefore produces **positions only** — no type/kind field. Type assignment belongs to Phase 3 step 10 (`rules_discovery.c`), not here; this is a scope boundary taken directly from source behavior, not an invented simplification.
- **`game/spot.lua` (the Love2D prototype) is not used as the fidelity reference for this algorithm.** It reimplements placement with a *linear* distance check (`dist(s1, s2) < spot.min_dist`, using real `sqrt`) scaled by an arbitrary `view_size` parameter, not the source's squared-distance check against the fixed `[0.125, 2.875)` domain. It's a reasonable Love2D-era approximation but not a faithful port, so it's read here only for porting *idiom* (module shape, `min_dist`/`border` naming), while `pico8/lua.lua` stays the sole behavioral ground truth, exactly as the task framing for this PRD directs.

**The "graphe de voisins" this step builds is a generation-time validity graph, not the 8-directional D-pad jump-navigation graph.** `game/lib/neighbors.lua` (used by `game/spot.lua`) and `docs/after-v1.md`'s "Mode saut" section describe a *different* neighbor graph: 8 cardinal-direction best-neighbor slots per spot, scored by `distance × (1 + 2 × angular_diff/180)`, built specifically to let a D-pad jump between spots without a free-roaming cursor. `docs/after-v1.md` is explicit that this is "une invention propre au portage manette (absente du PICO-8)" and is deliberately deferred past v1 (Phase 2 chose the mouse-cursor mode instead, per `docs/plan.md`'s "Décisions actées"). Building that graph now would be out-of-plan interaction-layer content shipped early under a different step's name — exactly the kind of thing the plan's own guardrails warn against. Instead, this step's "neighbor graph" is a **generic distance-threshold graph** built purely to give the BFS connectivity check (the plan step's literal, named test) something to traverse: an edge exists between two planets iff the squared distance between them is at most a caller-supplied threshold. This is not a gameplay data structure and nothing later in the game is expected to read it directly.
- **Edge threshold chosen for the real (non-test) connectivity check: base probe launch range, `0.19` (squared units, same convention as above).** Traced to `mz:hq` (line 767-770): a probe's target is rejected as "-too far-" when `nq > ov("space folding", 0.19, 0.27)`, where `nq` is the first return of `ij(...)` — i.e. the same squared-distance function used for placement rejection. `0.19` is the **base** value (no `space folding` tech — no tech state exists yet in Phase 1). Reasoning for using probe range specifically, over slipway range (`0.5`, §5): a slipway can only be built between two already-colonized planets, but a planet can only ever become colonized after a probe reaches it first — so probe range is the actual bottleneck that determines whether a planet is reachable *at all* from a growing empire, making it the right proxy for "can the player ever get here." A back-of-envelope density check confirms this threshold is reasonable for N=90 in the placement domain (mean degree ≈ 7 per planet at this radius, comfortably above the connectivity threshold for a random geometric graph of this size) — this is not a coincidence to rely on blindly, but it explains why the connectivity property is expected to hold reliably rather than by luck.
- This is a deliberate simplification for a **generation-time validation test**, not a claim that "any planet can reach any other" during actual play (real reachability also depends on colonization order, money, and time, none of which exist yet in Phase 1). That distinction is called out explicitly here so a future reader doesn't mistake this graph for a gameplay reachability oracle.

**No `float`/`double` anywhere in this module — fixed-point integers throughout.** `docs/plan.md`'s rendering-approach section states plainly that the R3000A has no hardware FPU, and names "génération procédurale" (this step) alongside trigonometry as one of the CPU-budget risks that fact creates; it also requires this step to be "genuinely reusable unmodified when later compiled into the PSX build." Writing this module in `float` would compile fine on host (gcc has an FPU) but would silently pull in slow software-float emulation the moment it's cross-compiled for PSX, defeating both of those requirements. All coordinates and thresholds are represented as **Q16.16 fixed-point integers** (16 integer bits, 16 fractional bits, stored in a plain `int32_t`), established here as this project's first fixed-point convention (worth reusing, not re-deciding, when step 4's trigonometry work arrives). Squared-distance accumulation (`dx*dx + dy*dy`) is done in `int64_t` to avoid overflow (`Q16.16 * Q16.16` needs a wider intermediate before it's meaningfully compared as `Q32.32`); no `sqrt` is ever needed anywhere in this module, since every comparison in the source (rejection threshold, probe range) is itself against a squared quantity. Concretely, the source constants become:
  ```
  FX_ONE            = 1 << 16                          // Q16.16 unit
  PLACEMENT_MIN     = (int32_t)(0.125 * FX_ONE)         // lua.lua:747
  PLACEMENT_SPAN    = (int32_t)(2.75  * FX_ONE)         // lua.lua:747
  MIN_DIST_SQ       = (int64_t)(0.05  * FX_ONE * FX_ONE) // lua.lua:748 (squared, see finding above)
  NEIGHBOR_RANGE_SQ = (int64_t)(0.19  * FX_ONE * FX_ONE) // lua.lua:768, base value, no tech
  ```
  This snippet is illustrative of the scaling scheme, not literal file contents.
- **RNG is injected, not global, and does not aim for bit-identical output to PICO-8's own RNG.** A small caller-owned RNG state (seed + `next_u32`) is passed into generation, matching the dependency-injection pattern `docs/plan.md` Phase 3 step 10 already commits to ("RNG injecté pour tests déterministes") — this step establishes that pattern rather than inventing a second one later. Reproducing PICO-8's exact internal PRNG sequence is explicitly not a goal anywhere in `docs/plan.md`'s traceability guardrail, which is about constants/formulas/behavior, not bit-identical random sequences; a small, well-known, integer-only PRNG (e.g. xorshift32) is used instead, chosen for being trivially portable and fast on hardware with no FPU. Because the RNG is injected, the "reusable elsewhere" concern (Phase 3 step 10) is satisfied by extracting it as its own tiny module rather than a `planetgen`-private implementation detail.
- **Data structures use fixed-size arrays, no dynamic allocation.** A galaxy is a fixed-capacity array of positions (capacity = 90, the value traced to `bw(90)`) plus a live `count`, sized so a call site can declare it `static`/on the stack with no heap involved — consistent with typical embedded/PSn00bSDK style and the plan's stated small scale (a few dozen entities, nowhere near needing dynamic structures). The neighbor graph is a dense boolean adjacency matrix (90×90 = 8100 bytes) rather than a sparse edge list — simplest to build, test, and BFS over, and trivially small against PSX's RAM budget.
- **Both `count` (planet count) and the neighbor edge threshold are function parameters, not baked-in constants inside the generation/graph functions.** The real values (90, and the traced `0.19`) are supplied by the caller; the functions themselves stay generic. This is what makes the module testable with small, fast synthetic cases (few planets, deliberately picked thresholds) in addition to the real 90-planet/0.19 configuration, without needing two code paths.
- **Generation reports success/failure rather than looping forever or asserting.** The source's `repeat ... until` retry loop has no cap; a generous, purely defensive retry budget is added per point (large enough to never realistically trigger for the real 90-planet/0.05 configuration — the density check above shows placement is comfortably loose) so that a pathological future misuse (too many planets for too tight a threshold) fails observably (a returned status) instead of hanging a test run or, worse, a PSX boot. This changes no observable behavior for any parameter values the game actually uses; it's a safety net, not a game-rule change, and is called out explicitly so it doesn't read as a silent content change.
- **File layout, under `psx-slipways/` (flat directory, `file(GLOB _sources *.c)` in `psx-slipways/CMakeLists.txt` picks up every `.c` file there for the real PSX cross-build):**
  - `fixed.h` — the Q16.16 type and basic ops (add/sub/mul, to/from-float helpers for authoring constants). Header-only, no PSX dependency. New shared convention, expected to be reused by later fixed-point work (trig in step 4).
  - `rng.h` / `rng.c` — the small injectable PRNG (seed, next-u32, next-in-range). Deliberately generic/reusable, not planet-generation-specific, anticipating Phase 3 step 10's stated need.
  - `planetgen.h` / `planetgen.c` — galaxy generation (`planetgen_generate`), neighbor graph construction (`planetgen_build_neighbor_graph`), and BFS connectivity (`planetgen_is_connected`). This is the module the plan step names; one file, one clear responsibility (galaxy topology), reusable unmodified in the real PSX build.
  - `host_tests/t.h` — a tiny, header-only PASS/FAIL/report test harness, named and structured in the spirit of `game/lib/t.lua` (named tests, per-test PASS/FAIL line, a final "`N passed, M failed`" summary, non-zero process exit on any failure) but deliberately not a generalized multi-file suite runner: with exactly one host C test file existing today, `t.lua`'s `find *_test.lua`-based auto-discovery would be solving a problem that doesn't exist yet. `main()` in the test file registers its own tests explicitly; generalizing discovery is left for whichever later step (e.g. Phase 3 step 10) actually adds a second host C test file.
  - `host_tests/planetgen_test.c` — the tests for this step (see Testing Decisions). Lives in a subdirectory specifically so `file(GLOB _sources *.c)` (non-recursive) never sees it — this is the one deliberate deviation from `game/`'s colocated `*_test.lua` convention, and it's a hard requirement, not a style preference: a host-only test file (using the host's `stdio`/`stdlib`, not PSn00bSDK's) included in the PSX cross-build would either fail to compile against the PSn00bSDK toolchain or silently ship dead test code in the retail binary.
- **Not wired into `game_init()`/`game_update()` in this PRD.** The task framing for this PRD explicitly leaves that call open; the call here is **no**, for two reasons: (1) `psx-slipways`'s `game_draw()` is still an empty stub (rendering is step 4) — calling generation from `game_init()` today would produce galaxy state nothing can display or verify on real/emulated hardware, so the richer PCSX-Redux input-driven harness (`docs/plan.md`'s Phase 0 harness, extended "au fur et à mesure des phases suivantes") would have nothing observable to assert against yet; (2) keeping this PRD to "generation logic + host tests" keeps it a clean, independently-mergeable vertical slice, and leaves the actual seeding strategy (e.g. seeding the injected RNG from a hardware timer at boot) as a genuinely separate decision — already flagged as an open follow-up in the prior PRD (`docs/prd/psx-main-skeleton.md`, Further Notes) — for whichever step first has something to render or test on-console. Wiring is therefore explicit **Out of Scope** below, not an oversight.

## Implementation Chunks

Ordered as vertical slices (tracer-bullet style): each chunk is small, independently testable, and the anchor behavior the plan step names (BFS connectivity) is reached by chunk 4, not built up to via a single big untested pass.

1. **Fixed-point + injected RNG foundation** (`fixed.h`, `rng.h`/`rng.c`). Smallest testable unit: Q16.16 conversion/arithmetic round-trips correctly; the RNG is deterministic for a fixed seed and produces values across its declared range. Nothing here is Slipways-specific yet — it's the substrate every later chunk (and later steps) builds on.
2. **Galaxy generation with proximity rejection** (`planetgen_generate`). Places `count` planets in the traced `[0.125, 2.875)` domain, rejecting candidates within the traced squared-`0.05` threshold of any already-placed planet, using the injected RNG from chunk 1. Tests: no two placed planets violate the minimum-distance rule (checked pairwise); exactly `count` planets are produced; two calls with the same seed produce identical output (determinism); a deliberately-impossible configuration (small domain, huge count) reports failure rather than hanging.
3. **Neighbor graph construction** (`planetgen_build_neighbor_graph`). Builds the dense adjacency matrix from a `Galaxy` and a caller-supplied squared-distance threshold. Tests: small, hand-placed synthetic point sets (not RNG-generated) with known expected adjacency, including a threshold chosen to deliberately leave some pairs unconnected.
4. **BFS connectivity** (`planetgen_is_connected`) — the plan step's literal named anchor behavior. Tests: a hand-built connected graph returns true; a hand-built graph with two disjoint clusters (same threshold as chunk 3's disconnected case) returns false; trivial `count` of 0 or 1 returns true.
5. **Integration: the real 90-planet/`0.19` configuration, across many seeds.** Runs the full pipeline (generate → build neighbor graph at the traced probe-range threshold → BFS) for `count = 90` across a large number of distinct seeds (not one hardcoded "lucky" seed), asserting connectivity holds every time. This is the concrete property `docs/plan.md`'s step 2 names ("tout spot atteignable depuis tout autre"), exercised as a real regression test rather than inferred from chunks 2-4 in isolation.

## Testing Decisions

- **What makes a good test here**: assert on the module's observable output (planet positions satisfy the spacing rule; the graph correctly reflects the geometric threshold; BFS correctly reports connected/disconnected), never on internal representation details (retry counts, exact RNG call sequence, matrix storage layout). This mirrors the existing Lua suite's style (`game/panel_test.lua`, `game/lib/neighbors_test.lua`) of testing behavior through a module's public functions.
- **Modules tested**: `fixed.h` (round-trip conversions), `rng.c` (determinism + range), `planetgen.c` (all three public functions, per the chunk breakdown above), plus the chunk-5 integration test tying generation + graph + BFS together at the real N=90/`0.19` configuration.
- **Prior art reused**: `game/lib/t.lua`'s spirit (named tests, PASS/FAIL per line, final pass/fail count, non-zero exit code on failure) is carried into a small C equivalent (`host_tests/t.h`), rather than pulling in an external C test framework — consistent with this repo's existing preference for a tiny in-house harness over a dependency. `game/lib/neighbors_test.lua`'s pattern of hand-placed synthetic fixtures (rather than only RNG-driven cases) for graph-construction tests is reused directly for chunk 3/4's synthetic point sets.
- **Host test invocation.** The top-level `Makefile`'s `test` target today only runs the Lua/Love2D suite (`cd game && lua ../tests/test_all.lua`) — nothing native-C exists yet. This PRD adds:
  - `make test-planetgen`: compiles `psx-slipways/{fixed.h,rng.c,planetgen.c}` and `psx-slipways/host_tests/{t.h,planetgen_test.c}` with the host's native `gcc` (no PSn00bSDK toolchain, no cross-compiler `PATH`/`PSN00BSDK_LIBS` wiring — this is exactly the "gcc natif, sans dépendance PSX" the plan step asks for) into a binary under a new `psx-slipways/build-host/` directory (kept separate from `psx-slipways/build/`, which is the PSn00bSDK cross-build output, to avoid any collision or confusion between the two), then runs it, propagating its exit code.
  - `test` is changed to depend on `test-planetgen` (so `make test` runs the native C tests, then the existing Lua suite) — decided over leaving `test-planetgen` undiscoverable, because `CLAUDE.md` (checked-in project instructions) directs contributors to "Use `make test` to verify changes" generically; if `make test` didn't cover this new code, that instruction would silently stop being true for the PSX C code as of this PRD. `test-planetgen` also stays independently invocable for fast, narrow TDD iteration without paying for the unrelated Lua suite's runtime every cycle.
  - Both are inline `Makefile` recipes (matching the existing `test:` target's own style — a direct command, not a wrapped script), since this is a plain "compile with host gcc and run the binary" step with no orchestration (no `Xvfb`/`xdotool`/emulator) — unlike the PCSX-Redux boot-test targets, which genuinely need a wrapping shell script for that orchestration and so get one.
- **Not tested here**: anything requiring the PSn00bSDK toolchain or PCSX-Redux/Mednafen (this step has no PSX-side behavior to boot-test — `game_init()` isn't touched, per the wiring decision above); planet *type*/kind assignment (not in scope, see Implementation Decisions); the 8-directional D-pad jump-navigation graph (`docs/after-v1.md`, explicitly deferred, not this step's "neighbor graph").

## Further Notes

- The single highest-value finding from re-reading source rather than trusting the design doc's prose: the `0.05` proximity threshold and the `0.19` probe-range threshold are both compared against **squared** distance (`ij()`'s use of the vector type's `__len` metamethod, which is a dot product, not a magnitude). Anyone implementing later steps that reuse `ij()`-style distance checks (slipway range `0.5`/`1.08` in §5, discovery-radius `29`/`35` in §4) should re-verify each one individually against source the same way rather than assuming linear distance from the doc's prose — this PRD only confirmed the two constants it actually needed (`0.05`, `0.19`).
- Recommend, as a small separate follow-up (not part of this PRD), correcting `docs/design/slipways-mechanics.md` §3/§4 to (a) state the real placement domain (`[0.125, 2.875)` per axis, not "`0..1`"), and (b) note explicitly that the `0.05`/`0.19` comparisons are against squared distance. This PRD deliberately doesn't make that edit itself (PRD-only scope), but the finding should not get lost.
- `fixed.h`'s Q16.16 convention is introduced here mainly to serve this step, but it's deliberately named/shaped to be the project's shared fixed-point type going forward — worth reusing rather than re-deriving when Phase 1 step 4 tackles fixed-point trigonometry (`docs/plan.md`'s rendering-approach section already flags that need). No integration with step 4 is assumed or required by this PRD; it's just why the header isn't named `planetgen_fixed.h` or kept private to this module.
- `rng.h`/`rng.c` is similarly factored out (rather than kept private to `planetgen.c`) specifically because `docs/plan.md` Phase 3 step 10 already commits to "RNG injectée pour tests déterministes" for a different system (probe discovery rolls); this step just establishes the pattern and the module first, rather than leaving step 10 to invent its own from scratch.
- The chunk-5 integration test (many seeds, not one) is a deliberate hedge: a single hardcoded seed passing proves nothing about the *algorithm's* reliability, only that one specific draw happened to work.
