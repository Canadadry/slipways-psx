## Problem Statement

`psx-hello/` proved the PSn00bSDK toolchain, build pipeline, and headless boot-test harness end to end, but it is explicitly a throwaway smoke-test project (pad/cursor demo, no game structure). There is no PSX project yet that is meant to grow into the actual Slipways port. Phase 1 (`docs/plan.md`) needs a real game project whose entry point never accumulates game logic over the coming steps (planet generation, pad handling, rendering, rules) the way a naive single-file PSX program tends to — every later PRD needs a stable, logic-free place to plug into.

## Solution

Create a new PSn00bSDK project, parallel to `psx-hello/` and independent of it, whose `main.c` contains only: PSX video/double-buffer bootstrap (the minimum needed to have a VSync-synced frame loop at all), the infinite loop itself, and calls out to `game_init()` / `game_update()` / `game_draw()`. Those three functions are declared in a shared header and defined as empty stub bodies in two small modules split by responsibility (simulation-side vs render-side), so later PRDs (planet gen, pad input, rendering) extend those files instead of ever touching `main.c` again. The build system (`CMakeLists.txt`, `CMakePresets.json`, `iso.xml`, `system.cnf`) mirrors `psx-hello`'s already-proven pattern with only naming changed, and the project gets its own Makefile targets and a boot-test script mirroring the existing PCSX-Redux headless harness, scoped to what this skeleton actually initializes (video, not pad — pad init is step 3).

## User Stories

1. As a developer extending this PSX port, I want `main.c` to contain no business logic, so that game logic added in later steps lives in independently reasoned-about, independently testable modules instead of growing inside the entry point.
2. As a developer extending this PSX port, I want the main loop synchronized on VSync using the same double-buffer pattern already proven in `psx-hello`, so that the frame timing foundation is not re-derived or re-risked for the real game project.
3. As a developer extending this PSX port, I want `main.c` to dispatch to `game_init()`, `game_update()`, and `game_draw()` rather than inlining any of their behavior, so that step 2 (planet generation), step 3 (pad input), and step 4 (rendering) each have an obvious, pre-existing seam to extend without editing `main.c`.
4. As a developer extending this PSX port, I want `game_update()`/`game_init()` and `game_draw()` split into separate files, so that simulation-side and render-side concerns stay in different modules from day one, matching the one-file-one-responsibility convention already used in `game/` (`spot.lua`, `lib/camera.lua`, `panel.lua`, `probe.lua` are each a distinct concern; `game/main.lua` only wires them together).
5. As a developer extending this PSX port, I want the new project's `CMakeLists.txt`/`CMakePresets.json`/`iso.xml`/`system.cnf` to mirror `psx-hello`'s already-validated structure, so that the build/CD-image pipeline isn't reinvented or re-risked for the real game.
6. As a developer extending this PSX port, I want the new project to live in its own top-level directory, so that `psx-hello` keeps working unmodified as a standalone smoke-test/reference project (per its own docs and `Makefile` targets) and this step carries zero risk of breaking it.
7. As a developer extending this PSX port, I want a Makefile target to build the new project, mirroring `psx-hello`'s target exactly (same toolchain `PATH`/`PSN00BSDK_LIBS` wiring), so building it is a one-line, muscle-memory-compatible command.
8. As a developer extending this PSX port, I want a headless boot-test for the new project (reusing the PCSX-Redux/OpenBIOS setup already installed for Phase 0), so "it builds and boots without crashing" is machine-verifiable the same way it already is for `psx-hello`, without requiring a human to launch a GUI emulator.
9. As a developer extending this PSX port, I want the boot-test's success check to only assert on what this skeleton actually initializes (GPU/video setup), not on pad-driver init, so that the test doesn't assert something this step doesn't yet do (pad init is step 3) and doesn't give a false sense of coverage.
10. As a developer extending this PSX port, I want the stub bodies of `game_init()`/`game_update()`/`game_draw()` to do nothing observable (no debug text, no drawing, no placeholder game state), so that this step cannot be mistaken for having shipped any actual game behavior, and later PRDs have a truly blank slate to fill in.
11. As a developer extending this PSX port, I want the executable and CD volume naming to respect the ISO 9660 8.3 filename constraint that `psx-hello` already had to satisfy (`PSXHELLO.EXE`), so the new project's boot files (`SYSTEM.CNF` pointing at the executable) work under the same real constraint without a later rename.
12. As a developer extending this PSX port, I want this PRD to state plainly that there is little to host-test yet, rather than inventing tests that don't fit a glue-only step, so that later PRDs (which do carry real host-testable logic per `docs/plan.md` step 2) aren't held to a testing bar this step can't meaningfully meet.

## Implementation Decisions

- **New top-level directory, not an evolution of `psx-hello/`.** The real game project lives at `psx-slipways/`, parallel to `psx-hello/`. `psx-hello/` is left completely untouched (per task constraints and `CLAUDE.md`: it stays the working smoke-test project with its own two independently-verified boot paths). Rationale: keeping them separate means the smoke-test project's proven state can never be put at risk by real-game-project churn, and the two directories' purposes (throwaway hardware smoke test vs. the actual port) stay unambiguous as the codebase grows.
- **Project/executable naming respects the 8.3 constraint `psx-hello` already worked within.** CMake project name and `psn00bsdk_add_executable` target: `slipways`. Resulting binary: `SLIPWAYS.EXE` (8 characters, exactly at the 8.3 limit, same margin `PSXHELLO.EXE` had). CD volume identifiers: `SLIPWAYS`. `system.cnf`: `BOOT=cdrom:\SLIPWAYS.EXE;1` (same `TCB`/`EVENT`/`STACK` values as `psx-hello/system.cnf` — these are PSn00bSDK boilerplate, not project-specific).
- **Build system files mirror `psx-hello`'s 1:1, renamed only.** `psx-slipways/CMakeLists.txt` mirrors `psx-hello/CMakeLists.txt` (`file(GLOB _sources *.c)`, `psn00bsdk_add_executable`, `psn00bsdk_add_cd_image` with `DEPENDS <target> system.cnf`, `install(... TYPE BIN)`). `psx-slipways/CMakePresets.json` mirrors `psx-hello/CMakePresets.json` verbatim (same toolchain file, same `PSN00BSDK_TARGET`), only `displayName`/`description` text updated. `psx-slipways/iso.xml` mirrors `psx-hello/iso.xml`'s structure (`identifiers`, `directory_tree` with `SYSTEM.CNF` + the executable + the same `1024`-sector dummy padding), renamed to `SLIPWAYS`/`SLIPWAYS.EXE`. No new CMake concepts are introduced.
- **`main.c`'s only non-glue content is the minimum PSX video bootstrap needed to have a VSync-synced loop at all.** This means: `ResetGraph`, a double-buffered `DISPENV`/`DRAWENV` pair, and a per-frame `DrawSync`/`VSync`/buffer-swap step — copied from `psx-hello/main.c`'s already-working `RenderContext`/`init_context`/`display` pattern, since that code is proven and this step's job is not to redesign PSX video bootstrap. This is judged to be platform plumbing intrinsic to "a loop synced on VSync" (the step's own literal requirement), not business/game logic, so it stays inline in `main.c` rather than being extracted into its own module. If/when step 4 (real rendering) makes this grow, extracting it into its own module is that step's call to make, not this one's.
- **No pad init in `main.c`.** `psx-hello/main.c` calls `InitPAD`/`StartPAD`; the new `main.c` does not, because pad reading is step 3 (`docs/plan.md` line 37), out of scope here. Adding it now would be scope creep and would falsely suggest step 3 is already done.
- **Three dispatch functions, not two, even though the plan step literally names only "update/draw".** `game_init()` is added alongside `game_update()`/`game_draw()`, declared together in one shared header (`game.h`) and called once before the loop starts. Rationale: without an init hook living outside `main.c`, step 2 (seeding the 90-planet generation at boot) would have no clean place to hook in except editing `main.c` directly — which defeats the point of this step (a `main.c` later steps never need to touch again). This is still pure dispatch, not behavior: `game_init()` itself does nothing yet.
- **The three functions are split across two files by responsibility, not left as one `game.c`.** `game_update.c` holds `game_init()` and `game_update()` (the simulation/logic side — what step 2's planet generation and step 3's pad-driven state changes will extend). `game_draw.c` holds `game_draw()` (the render side — what step 4 will extend). This mirrors the split already established in `game/main.lua`, which calls into logic-owning modules (`Spot`, `Probe`, `Camera`) separately from `Panel.draw`/`Spot.draw` at draw time, rather than mixing update and draw concerns in one file.
- **Stub bodies are empty — no debug text, no placeholder drawing, no placeholder state.** Unlike `psx-hello/main.c` (which prints pad/cursor debug text every frame because that *is* its entire purpose as a smoke test), the new project's stubs do nothing observable. This keeps the boundary between "step 1 shipped" and "step 2/3/4 shipped" unambiguous, and avoids smuggling any rendering or business logic into a step whose whole point is to have none.
- **New Makefile targets mirror the existing `psx-hello`/`psx-hello-clean` pair exactly**, with `psx-slipways`/`psx-slipways-clean`, using the same `PSN00BSDK_TOOLCHAIN_BIN`/`PSN00BSDK_LIBS_DIR` variables and the same `cmake --preset default` / `cmake --build build` invocation shape, just pointed at `psx-slipways/`.
- **A boot-test script is added for the new project, mirroring `tools/boot_test_psx_hello_pcsx.sh`**, pointed at `psx-slipways/build/slipways.cue` instead of `psx-hello`'s image, reusing the PCSX-Redux/OpenBIOS install from Phase 0 (`make pcsx-redux-setup`) — no new emulator/BIOS setup is needed. Its pass condition greps the run log for the GPU setup line only (e.g. `psxgpu: setup done`), deliberately **not** the pad-driver line `psx-hello`'s script also checks for, since this skeleton never calls `InitPAD`. A corresponding Makefile target (`psx-slipways-boot-test-pcsx`) is added alongside it. This is a boot-only smoke test (log-grep, no assertions on game state), same tier as `psx-hello-boot-test-pcsx` — it is not the richer input-driven harness (`psx-hello-input-test-pcsx`'s Lua/PCSX-Redux bridge reading guest RAM), which has nothing meaningful to assert against yet since there is no game state.
- **Mednafen boot-test path is not duplicated for this project.** `psx-hello`'s Mednafen path exists for ad hoc visual spot-checks and needs a real Sony BIOS a developer supplies locally; it is not part of the automated/headless story. Nothing about this step changes that trade-off, so it's left for a later step (if ever) rather than doubled up speculatively now.

## Implementation Chunks

Not needed. This step is small enough to be a single implementation chunk: build files + `main.c` + two stub modules + Makefile targets + one boot-test script, all added together with no meaningful internal build order (the stubs and the loop that calls them are authored as one unit; nothing here is usable in isolation before the rest exists).

## Testing Decisions

- **There is almost nothing host-testable in this step, and that's expected, not a gap.** `main.c` is glue (a loop + PSX API calls), and `game_init()`/`game_update()`/`game_draw()` are empty stub bodies. None of this is business logic with inputs/outputs worth asserting on host-side (gcc-native) tests — unlike `docs/plan.md` step 2 (planet generation), which is explicitly scoped to be host-testable C in the same spirit as `game/lib/t.lua`. Inventing unit tests for empty functions or for PSX-API glue that can't run off the console would produce tests that assert nothing meaningful; this PRD does not add any.
- **What is realistically checkable: it builds, and it boots without crashing.** Both are already-proven techniques in this repo, reused as-is rather than reinvented:
  - *Build*: `make psx-slipways` (new target, mirrors `make psx-hello`) must succeed — this is the same toolchain already validated by `psx-hello` (`make psn00bsdk-toolchain-setup`), so no new build-tooling risk is introduced.
  - *Boot*: `make psx-slipways-boot-test-pcsx` (new target + script, mirrors `make psx-hello-boot-test-pcsx`) must reach GPU setup and run for the script's timeout window without hanging or crashing, verified headlessly via PCSX-Redux + OpenBIOS (no real Sony BIOS needed, same as the existing harness). This directly exercises the one behavior this step actually adds: a VSync-synced loop that runs.
- **Not added in this step**: the richer input-driven harness (`psx-hello-input-test-pcsx`'s Lua/PCSX-Redux bridge that reads guest RAM and injects pad events) has nothing to assert against yet, since there's no pad reading (step 3) or observable game state (step 2+) in this skeleton. `docs/plan.md` itself places "extend the harness to real game logic" at Phase 1 step 4, not here — this PRD does not pull that forward.
- **Prior art reused as-is**: `tools/boot_test_psx_hello_pcsx.sh` (script structure, Xvfb + timeout + log-grep pattern) and the `psx-hello`/`psx-hello-clean`/`psx-hello-boot-test-pcsx` Makefile targets (target shape, variable names).

## Out of Scope

- Planet generation, neighbor graph, connectivity BFS, or any host-testable C game logic (`docs/plan.md` Phase 1 step 2 — separate PRD).
- Reading the pad via PSn00bSDK's pad API, `InitPAD`/`StartPAD`, or any cursor/click handling (`docs/plan.md` Phase 1 step 3 — separate PRD). No pad code of any kind is added by this PRD, including debug-only pad reads.
- Drawing planets, wormholes, or slipway segments with GPU primitives, or any FPS/faisability measurement against the 30fps/40-60-slipway criterion (`docs/plan.md` Phase 1 step 4 — separate PRD). `game_draw()`'s body stays empty.
- Any game rule, constant, or value from `docs/design/slipways-mechanics.md` — this step is pure infrastructure and references no game-design content, consistent with the plan's traceability guard-rail (nothing here needed tracing back to the design doc).
- Modifying `psx-hello/` in any way (files, Makefile targets, or docs referencing it).
- The richer PCSX-Redux input-driven test harness (Lua bridge reading guest RAM / injecting pad overrides) for the new project — only a boot-only smoke test is added here; the richer harness has no game state to exercise yet.
- The Mednafen boot path for the new project.
- Any decision about how later steps' modules (planet data, pad/cursor state, render commands) are structured internally — this PRD only establishes that `game_init`/`game_update`/`game_draw` are the seams; what goes inside them is each later step's own PRD.

## Further Notes

- `docs/plan.md`'s "Garde-fous" section (traceability of constants, no silently dropped content, no invented juice) is not really engaged by this step, since it introduces no game values or content at all — noted here only to confirm it was checked, not skipped.
- Once step 2 (planet generation, host-testable C) lands, it's worth revisiting whether `game_init()` is the right place to trigger galaxy generation at boot, or whether that belongs behind a later PSX-side RNG-seeding concern (e.g. seeding off a hardware timer) — left to step 2's own PRD rather than pre-decided here.
- The exact PSn00bSDK API calls in `main.c` (`ResetGraph`, `SetDefDispEnv`, `SetDefDrawEnv`, `PutDrawEnv`, `PutDispEnv`, `DrawSync`, `VSync`, `SetDispMask`) are the same ones already in `psx-hello/main.c`; this PRD intentionally does not restate their signatures since they're not new to the codebase and the header docs already cover them via PSn00bSDK itself.
