## Problem Statement

`psx-slipways/cursor.c` (Phase 2 step 5, closed) owns mouse-mode toggle and D-pad cursor movement, but nothing on the controller yet represents a *click*. `docs/plan.md` Phase 2 step 6 calls for Circle (○) to "simulate a click at the cursor's current position... driving directly the logic already present in `pico8/lua.lua` (wormhole placement, colonization, probe launch, slipway drawing), without reinventing a game state machine on top." The plan itself flags an explicit, unresolved question that must be checked against source before this step is coded: does a PICO-8 click have real press/release semantics (held button = drag in progress), or is it purely instantaneous? None of the downstream game logic this step is meant to "drive" exists yet in this port — wormhole placement is Phase 4 step 15, colonization/probe launch (`rules_discovery.c`) is Phase 3 step 10, slipway-drawing validity (`liaison.c`) is Phase 3 step 9 — so this step cannot literally wire into any of it. What it can and must do is resolve the plan's own open question from source and build the correctly-shaped event interface that those future steps will consume, without inventing any placeholder game behavior in the meantime.

## Solution

Read `pico8/lua.lua` directly (see Implementation Decisions for the full citation trail) to settle the "Reste à trancher" question: PICO-8's click is genuinely a press/hold/release gesture, not an instantaneous event — the source computes and dispatches all three (`.jn` press-edge, `.on` held-level, `.hm` release-edge) and every one of the actions the plan names (slipway drawing, probe launch, and the same drag-initiation pattern used elsewhere in the UI) depends on continuous per-frame tracking while held plus a distinct commit/cancel decision at release. A single instantaneous click cannot represent that.

Given that finding, extend `cursor_state_t`/`cursor_step` (not a new module — see Implementation Decisions for why) with three new fields mirroring PICO-8's own `.jn`/`.on`/`.hm` trio for Circle, gated on mouse mode being active, computed from the exact same `prev_buttons`/`buttons` pair `cursor_step` already threads through for the Cross edge (no new statics needed). Add one small, zero-game-logic visual acknowledgment — a click-flash on the existing cursor tile — directly mirroring `psx-hello/main.c`'s already-proven `click_flash` precedent, which is the strongest, most direct evidence in this codebase for what a guardrail-compliant "click happened" signal looks like at this stage: real, visible, and utterly inert with respect to game rules. No wormhole placement, no colonization, no probe launch, no slipway drawing is implemented here — those stay entirely deferred to their named future steps, which this step's event fields (`click_pressed`/`click_held`/`click_released`) are shaped specifically to let them consume without any redesign of `cursor.c`.

## Implementation Decisions

**The load-bearing research question, resolved from source: PICO-8's click has real press/held/release semantics, and every drag-shaped action the plan names depends on all three.**

- **The underlying button-state primitive** (`pico8/lua.lua:204-208`, `bu(qn, oa)`): for each mouse button, PICO-8 computes and stores three fields every frame — `on` (currently held, from `stat(34)`, the native mouse-button bitmask), `jn` (`on and not ia` — just-pressed, a press *edge*), and `hm` (`ia and not on` — just-released, a release *edge*), where `ia` is the previous frame's `on`. This is called for both the left (`je.l`) and right (`je.r`) mouse buttons from `nf:ph()` (line 203). This is structurally identical to the edge-detection idiom `cursor.c` already implements for Cross (`pressed = (~buttons) & prev_buttons`), just computed for all three states instead of one.
- **The dispatcher that consumes it** (`ui:bh(bt)`, `pico8/lua.lua:237-247`): on the press edge (`b.jn`), it calls `<button>down` (e.g. `"ldown"`) on whatever entity is currently hit-tested under the cursor; if that handler's return value is a table, that table becomes the "held" target for the rest of the gesture (`self[bt.."held"]`). Then, **every single frame** while a held target exists (unconditional on press/release — this runs whenever `held` is non-nil), it calls `hq` on that held target with the current world-space cursor position. Finally, on the release edge (`b.hm`), if a held target exists, it hit-tests the entity currently under the cursor and calls `gv` on it (a validity/commit check), then calls `ey` ("end") on the held target with that result, and clears the held reference.
- **Concrete drag-shaped actions built on exactly this pattern, all cited directly**:
  - **Slipway drawing**: `jo:ldown()` (`lua.lua:412-417`, the planet class) — clicking a colonizable ("ly") planet returns `jc({qu=self})`, a new slipway-drag object with the clicked planet as its source. `jc:hq(mp)` (line 622) runs every held frame, re-evaluating the current drag target from whatever's under the cursor (`ok.o_.gv and ok.o_ or {ra=mp, ...}` — snap to a hovered planet, or fall back to the raw cursor position) and recomputing route validity (`self.et=self:ce()`, e.g. `"-too far-"`) live, frame by frame, purely from where the drag currently is. `jc:ey(re)` (line 633) runs once, on release: if the entity under the cursor at release time is nil or the drag fails its own validity check, the slipway is cancelled (`self.p_=true`, a negative sound plays); otherwise the slipway is actually created between source and the release-time target (`self.qu:kf(self); re:kf(self)`). Meanwhile `jo:gv(s)` (line 472) is the "am I a valid drop target for this drag" check hit-tested on whatever planet is under the cursor at release. **Colonization is not a separate click at all** — a planet is colonized by successfully connecting a slipway to it via this same drag, so it inherits the identical requirement.
  - **Probe launch**: `mz:hq(...)` (line 767) and `mz:ey()` (line 774) follow the *identical* shape — probe range/validity (`ov("space folding", 0.19, 0.27)`, the same two thresholds already named in `psx-slipways/world.h`'s `WORLD_NEIGHBOR_RANGE_SQ` comment) is recomputed every held frame as the aim tracks the cursor, and `ey()` decides on release whether the probe actually launches (`self.p_ = self.t<15 or not d_(self)`, i.e. cancelled if released too early or invalid).
  - **A third, independent confirming example**: `ie:ldown(mp)` (line 932, a job/tech-icon UI element) also returns a new held entity on press, following the same dispatcher contract — the pattern isn't specific to slipways or probes, it's the UI's general drag-gesture mechanism.
- **Why an instantaneous click cannot represent any of this**: none of `jc:hq`, `mz:hq`, or the release-time `gv`/`ey` validity-and-commit logic has anywhere to run without (a) a real press edge to *start* tracking, (b) a real per-frame held level to keep *updating* the drag target as the cursor moves, and (c) a real, distinct release edge to *decide* commit-vs-cancel using wherever the cursor ended up. Collapsing this into one instantaneous "click happened" pulse would throw away exactly the information (where did the drag end, relative to where it started, and was the button ever actually released cleanly) every one of these handlers depends on.
- **Conclusion, directly resolving the plan's "Reste à trancher" note**: ○ must expose a real press edge, a real held level, and a real release edge — not just an instantaneous click. This PRD's event shape (`click_pressed`/`click_held`/`click_released`) is a direct, deliberate mirror of PICO-8's own `.jn`/`.on`/`.hm` trio, chosen specifically so a future consumer building the real `jc`/`mz`-style drag logic (Phase 3 step 9, step 10, Phase 4 step 15) can wire into it exactly the way `ui:bh()` already wires into `bu()`'s output, without this step's shape needing to be revisited.

**What this step concretely builds, given that none of the consuming logic exists yet — and why that's a deliberate, guardrail-compliant scope, not scope-dodging.**

- The plan's wording ("driver directement la logique... sans réinventer une state machine de jeu par-dessus") means this step must *not* invent any placeholder version of wormhole placement, colonization, probe launch, or slipway drawing — doing so would be exactly the kind of content-layer invention the guardrails forbid (`docs/plan.md`'s own rule: "en cas de doute... traité comme du contenu par défaut... et doit être justifié explicitement"). There is no doubt here: none of that logic exists in this port (`liaison.c` is Phase 3 step 9, `rules_discovery.c` is Phase 3 step 10, wormhole placement is Phase 4 step 15, all unbuilt), so a placeholder implementation here would be inventing gameplay this port doesn't have anywhere else yet, with no real logic behind it to validate against.
- What *is* left, and squarely in scope: (a) detecting the real press/held/release event shape the source investigation above requires, exposed through a small, stable interface future steps can build on; (b) a real, zero-game-logic visual acknowledgment that the click registered, directly precedented by `psx-hello/main.c`'s own `click_flash` mechanism (see below) — not invented for this step, reused from a mechanism already proven in this exact codebase.
- **This mirrors `psx-mouse-mode-cursor`'s own explicit deferral**: that PRD's Out of Scope section states plainly, "Click simulation (○) and its press/release-vs-instantaneous semantics... this step adds no click handling of any kind, and `cursor_state_t` deliberately carries nothing that would prejudge that decision" — and its Further Notes flagged `cursor.c` as the expected home for exactly this logic. This step is that prediction's fulfillment, not a deviation from it.

**Extend `cursor.c`/`cursor_state_t` — not a new module.**

- **Why here, not a sibling module**: the Circle press/held/release computation needs exactly the same two inputs (`prev_buttons`, `buttons`) `cursor_step` already receives and already uses for the Cross edge — no new statics are needed, since `g_cursor_prev_buttons` already carries the full previous-frame bitmask (not just the Cross bit). A sibling module would either duplicate that same previous-frame-button-state tracking (two owners of "what was pressed last frame," which this codebase has consistently avoided — see `psx-pad-input`'s explicit "no edge detection in `input.c`" rationale) or would need `cursor.c` to expose its internal `prev_buttons` externally, which is worse than just computing the extra fields where that state already lives.
- **New local bit constant**: `CURSOR_PAD_CIRCLE (1 << 13)`, added alongside the existing `CURSOR_PAD_CROSS`/`CURSOR_PAD_UP`/etc. block in `cursor.c` — same standard, published PS1 SIO0 digital-button bit layout those constants already duplicate locally (Select=0, L3=1, R3=2, Start=3, Up=4, Right=5, Down=6, Left=7, L2=8, R2=9, L1=10, R1=11, Triangle=12, **Circle=13**, Cross=14, Square=15), kept local rather than pulled from `psxpad.h` for the exact reason `cursor.c`'s existing constants already are (whole-file host-buildability).
- **`cursor_state_t` gains four new fields**, illustrative shape (not literal file contents):
  ```
  typedef struct {
      int mouse_mode;
      int x;
      int y;
      int click_pressed;      /* edge: Circle press this frame, mouse_mode on */
      int click_held;         /* level: Circle currently held, mouse_mode on */
      int click_released;     /* edge: Circle release this frame, mouse_mode on */
      int click_flash_frames; /* countdown, click-acknowledgment visual only */
  } cursor_state_t;
  ```
- **`cursor_step` logic, added after the existing mouse-mode/movement logic, all gated on the *resulting* `next.mouse_mode`** (matching the existing D-pad-movement precedent, which already tests the post-toggle value for the same frame, not the pre-toggle one — see `test_movement_resumes_after_toggling_off_then_back_on` in the existing host test for the established convention this follows):
  - If `next.mouse_mode` is false: `click_pressed`, `click_held`, `click_released`, and `click_flash_frames` are all forced to `0` — no click state exists at all while the cursor itself is inactive/invisible. This is a deliberate decision: a Circle press or release that happens while mode is off (or the exact frame mode is toggled off mid-hold) produces no event and no lingering flash; a future consumer must not assume a `click_released` is guaranteed to eventually follow every `click_pressed` — it's only guaranteed while `mouse_mode` stays on throughout.
  - If `next.mouse_mode` is true: `pressed_circle = (uint16_t)(~buttons) & prev_buttons & CURSOR_PAD_CIRCLE` (nonzero if the edge is a Circle-press); `click_pressed = pressed_circle != 0`. `click_held = !(buttons & CURSOR_PAD_CIRCLE)` (current level, same active-low convention as everything else in this module). `released_circle = buttons & (uint16_t)(~prev_buttons) & CURSOR_PAD_CIRCLE`; `click_released = released_circle != 0`.
  - `click_flash_frames`: if `click_pressed` this frame, set to `CLICK_FLASH_FRAMES` (restarting the countdown even if a previous flash was still running — a fresh press always resets to full duration, matching `psx-hello/main.c`'s own behavior where `click_flash = CLICK_FLASH_FRAMES` unconditionally overwrites); else if `prev_state.click_flash_frames > 0`, decrement by 1; else stays `0`.
- **New constant**: `CLICK_FLASH_FRAMES 15`, defined in `cursor.h` next to `CURSOR_STEP`, with the same "reused, not re-derived" framing already established for `CURSOR_STEP` — this is `psx-hello/main.c`'s exact, already-legible, already-screenshot-verified value (`#define CLICK_FLASH_FRAMES 15`), not a new tuning decision.
- **Stateful wrapper (`cursor_update`/`cursor_get_state`)**: extended with the matching new flat top-level statics — `g_cursor_click_pressed`, `g_cursor_click_held`, `g_cursor_click_released`, `g_cursor_click_flash_frames` — following the exact convention `docs/prd/psx-mouse-mode-cursor.md` already established (one symbol per field, not one struct static, so the PCSX-Redux Lua harness can address each independently). No change to `cursor_init()`'s existing fields; the four new statics start at `0` (mode starts off, so this is also what `cursor_step` would compute for that initial state).
- **No change to `cursor_update`'s signature** (`uint16_t buttons`, same as today) — the Circle bit is already present in the same bitmask parameter Cross and the D-pad already come through; no new plumbing is needed at the `game_update()` call site (`cursor_update(input_get_state().buttons)` is untouched).

**Rendering the click acknowledgment — decided: yes, directly reusing `psx-hello`'s `click_flash` precedent.**

- `game_draw.c`'s existing cursor-tile block (added by `psx-mouse-mode-cursor`) gains one conditional: color is yellow (`255, 255, 0`, `psx-hello/main.c`'s exact color) when `cursor_get_state().click_flash_frames > 0`, plain white otherwise (the existing color) — no new primitive, no new draw call, just a color choice already present in the same `TILE` block.
- **Justification for reusing this exact precedent, not inventing a new one**: `psx-hello/main.c`'s `click_flash` is a real, working, already-screenshot-verified "click acknowledged" mechanism that has zero game logic behind it — no cost, no resource, no rule, just a color that changes for a fixed number of frames. It is the single closest, most direct piece of prior art in this codebase for exactly the situation this step is in (a click event needs *some* observable effect to be screenshot-verifiable, but must not imply any of the real click-driven mechanics that don't exist yet). Reusing it rather than designing a new visual is also consistent with `psx-mouse-mode-cursor`'s own explicit deferral ("Click-flash or any other visual feedback beyond the static cursor marker itself... tied to the ○ click event, not introduced here" — it named this exact mechanism as this step's to pick up).
- **No other visual changes.** No trace line while held, no ghost slipway, no probe-arc preview — any of those would imply the drag-target logic (`jc:hq`/`mz:hq`'s live validity recompute) that is explicitly Phase 3/4's job, not this step's.

**Interaction-vs-content guardrail, checked explicitly.** `click_pressed`/`click_held`/`click_released` are pure event-detection state, exactly one layer above `input.c`'s raw bitmask and structurally identical to the Cross-edge detection `psx-mouse-mode-cursor` already added — nothing here reads or writes any planet, slipway, wormhole, credit, or score state; nothing is colonized, connected, or spent. `click_flash_frames` is a rendering-only countdown with no gameplay effect, directly reusing a mechanism this codebase has already built and verified. This matches `docs/plan.md`'s own pre-authorization ("...le clic simulé par ○ sont des ajouts tolérés") with nothing added beyond what that sentence scopes.

## Implementation Chunks

Tracer-bullet slices, in dependency order — edge detection first (fully host-testable, no rendering dependency), through the flash visual, to the real emulated end-to-end proof:

1. **Circle press/held/release edges.** `cursor.h`/`cursor.c` gain `CURSOR_PAD_CIRCLE`, the three new `cursor_state_t` fields (`click_pressed`, `click_held`, `click_released` — not `click_flash_frames` yet), and `cursor_step`'s gated edge/level logic. `cursor_update`/`cursor_get_state`/`cursor_init` extended with the matching statics. 2. **Click-flash countdown.** `CLICK_FLASH_FRAMES` constant, `click_flash_frames` field, and its `cursor_step` logic (set-on-press, decrement-otherwise, clamp-at-zero, restart-on-repress-mid-flash). Host tests extended: flash starts at full duration on press, counts down frame by frame to zero and stays there, a second press mid-flash resets to full duration rather than accumulating or being ignored.
3. **Rendering.** `game_draw.c`'s existing cursor `TILE` block gains the yellow-while-flashing / white-otherwise color branch. Verified via `make psx-slipways-screenshot-pcsx` (manual/scripted Circle-hold flow) and the still-unmodified `psx-slipways-boot-test-pcsx`.
4. **Headless PCSX click-injection test.** Extend the existing `tools/gen_pcsx_slipways_cursor_test_lua.py` (add `g_cursor_click_pressed`/`g_cursor_click_held`/`g_cursor_click_released`/`g_cursor_click_flash_frames` to `WANTED`, add a new frame-by-frame pulse-polling helper — see Testing Decisions) and the existing `tools/boot_test_psx_slipways_pcsx_cursor.sh`/`psx-slipways-cursor-test-pcsx` target (same target, not a new one — see Testing Decisions for why) with new assertions proving the real, wired-together behavior under real emulated SIO0 Circle-button injection.

## Testing Decisions

- **What makes a good test here (restated from prior PRDs' established standard)**: assert on observable state through public functions/exported symbols (event fields, flash countdown), never on internal representation beyond what the flat-statics convention already requires for the Lua harness to read them.
- **Host-testable in full** (pure core and stateful wrapper both), same reasoning as the existing cursor tests: `cursor_update` still takes its bitmask as an explicit parameter, so nothing here touches a PSX header.
  - Cases added to the existing `psx-slipways/host_tests/cursor_test.c` (not a new file): Circle-press-edge fires `click_pressed=1` from a fixture starting state with mode already on; holding Circle across two consecutive `cursor_step` calls keeps `click_held=1` but does not re-fire `click_pressed`; releasing Circle fires `click_released=1` on that frame only; unrelated buttons (D-pad, Cross) held simultaneously don't affect the click fields; all three click fields are `0` when `mouse_mode` is off, both when Circle was never pressed and when it's held throughout; toggling mode off (Cross press-edge) while Circle is held forces all three click fields to `0` that same frame, and toggling back on with Circle still physically held does not retroactively fire `click_pressed` (there's no edge in `prev_buttons`→`buttons` for Circle on that frame — only for Cross); `click_flash_frames` is `0` in the documented initial state, becomes `CLICK_FLASH_FRAMES` on a press frame, decrements by exactly `1` per subsequent `cursor_step` call while no new press occurs, reaches and stays at `0` once exhausted, and resets to `CLICK_FLASH_FRAMES` (not `CLICK_FLASH_FRAMES` plus whatever remained) if pressed again while still counting down; a `cursor_update()`/`cursor_get_state()` round trip through the stateful wrapper reproduces `cursor_step`'s result for all four new fields, extending the existing round-trip test rather than adding a new one.
  - Same Makefile group (`test-cursor`), same host `gcc`/`build-host/` shape — no new target, since this is the same module and the same existing target already builds and runs `cursor_test.c` against `cursor.c`.
- **Not host-testable, and that's expected**: `game_draw.c`'s new color-branch (real `psxgpu.h` calls) and `main.c` (unchanged). Verified instead by:
  - `make psx-slipways-boot-test-pcsx` (existing, unmodified) — confirms boot still doesn't crash with the new per-frame click logic added.
  - `make psx-slipways-screenshot-pcsx` (existing, unmodified target/tooling) — visual sanity check that a Circle press actually flashes the cursor tile yellow, not a numeric assertion but a fast way to catch an obviously-wrong gating or color bug.
  - **Extended `make psx-slipways-cursor-test-pcsx`** (this PRD's own addition to chunk 4, same target as `psx-mouse-mode-cursor` introduced): asserts, against the real linked binary under real emulated SIO0 Circle injection: (1) all four new symbols start at `0` after boot (mode starts off); (2) toggling mouse mode on via Cross, then holding Circle for a settle window, brings `g_cursor_click_held` to `1` and keeps it there for the duration of the hold (a **level** assertion, using the same settle-and-check style the existing Cross-toggle assertion already uses — robust to the emulator's per-frame poll timing); (3) releasing Circle brings `g_cursor_click_held` back to `0` after a settle window; (4) `g_cursor_click_flash_frames` is nonzero immediately after a press-plus-settle window and reaches `0` again after waiting comfortably longer than `CLICK_FLASH_FRAMES` frames with no further press (also a level/duration assertion, robust to timing since the countdown spans 15 frames, not 1); (5) holding Circle while mouse mode is off (toggle it off first) leaves all four fields at `0` throughout, proving the gate is real.
  - **New technique this PRD adds to the harness — direct single-frame edge-pulse observation**: `g_cursor_click_pressed`/`g_cursor_click_released` are true for exactly one frame, which the existing test's "wait N frames, then check once" style cannot reliably catch (the pulse can come and go entirely inside a multi-frame `waitFrames` gap). A new helper (illustrative, not literal Lua) samples the target symbol on *every* frame across a short window bracketing the press/release, rather than batching: `local function observePulse(addr, windowFrames) local seen = 0 for i = 1, windowFrames do if readS32(addr) ~= 0 then seen = seen + 1 end coroutine.yield() end return seen end`. The test presses Circle (`setOverride`), calls this once for `click_pressed` across a short window immediately after, and asserts `seen >= 1` (the edge was observed at least once) and a small upper bound (e.g. `seen <= 2`, tolerating the same one-frame override/poll-alignment jitter the existing `assertRange` movement checks already tolerate) rather than exactly `1` — an exact-`1` assertion would be more precise but more timing-fragile than this codebase's existing tests have needed to be elsewhere. The mirror check runs around `clearOverride` for `click_released`.
- **Prior art reused as-is**: the existing `psx-slipways-cursor-test-pcsx` target/generator/script (extended in place, not duplicated) — `readS32`, `waitFrames`, `assertEq`, `assertRange`, `press`, `waitForBoot` all reused unchanged; `host_tests/t.h` and `cursor_test.c`'s existing hand-built-fixture style, extended with new cases in the same file.

## Further Notes

- **Why extending `cursor.c` rather than a new module was judged the right call, restated plainly**: the alternative (a new `click.c` module) would either duplicate `cursor.c`'s existing `prev_buttons` tracking or require exposing it externally — both worse than adding a few gated fields to a pure function that already receives exactly the two inputs (`prev_buttons`, `buttons`) it would need. This keeps one module owning "what did the controller just do, in cursor-relevant terms," matching the single-owner precedent `psx-pad-input`'s PRD already established (edge detection belongs to whichever module needs it, not to `input.c`, and now not fragmented across two cursor-adjacent modules either).
- **Where Phase 3 step 9 (`liaison.c`) should plug in**: per the source investigation above, its natural shape is a small state machine keyed on `click_pressed` (start tracking a drag from whatever planet the cursor was over at press) → `click_held` (recompute route validity every frame as the cursor moves, mirroring `jc:hq`) → `click_released` (commit or cancel based on where the cursor ended up, mirroring `jc:ey`/`jo:gv`). This step deliberately builds no hit-testing or state machine of its own — it only guarantees the three signals that state machine will read are real and correctly timed.
- **Where Phase 3 step 10 (`rules_discovery.c`, probe launch) should plug in**: identical shape to the above, per `mz:hq`/`mz:ey`'s structurally identical pattern — the same three click fields, a different consumer.
- **Where Phase 4 step 15 (wormhole placement) should plug in**: not yet investigated in this PRD (out of scope — `ie:ldown`'s pattern suggests it may be a simpler press-only placement rather than a drag, but that's step 15's own research question to settle against source when it's reached, the same way this step settled its own).
- **Why `click_released` is not guaranteed to eventually follow every `click_pressed`**: this is a real, load-bearing constraint a future consumer must design around, not an oversight — toggling mouse mode off mid-hold (via Cross) zeroes all click state immediately, per this step's explicit gating decision, with no synthetic release event synthesized on the way out. A future drag state machine reading these fields should treat "mode went off while a drag was in progress" as its own distinct cancel path, not assume `click_released` alone covers every way a gesture can end. This is flagged here specifically so it doesn't need rediscovering.
- **Why the flash always restarts to full duration on a fresh press rather than extending or ignoring it**: this exactly matches `psx-hello/main.c`'s own behavior (`click_flash = CLICK_FLASH_FRAMES`, an unconditional overwrite, not `+=`) — reusing the precedent's actual semantics, not just its constant value.
