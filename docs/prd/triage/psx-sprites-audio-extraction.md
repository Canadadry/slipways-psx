## Problem Statement

`docs/plan.md` Phase 5 step 17: "Extraire les sprites et données audio (sfx/musique) de la cartouche PICO-8, remplacer les placeholders de rendu." Unlike every Phase 3/4 PRD in this codebase (pure-formula/data-table ports of `rules_planets.c`/`rules_tech.c`/`rules_economy.c`), this step is asset-extraction plus real GPU-texture rendering: `game_draw.c` currently draws every world element as a flat-color `TILE`/`POLY_F4`/`LINE_F2` primitive (`docs/prd/psx-galaxy-rendering.md`'s own "no real sprite/polygon art... all colors are arbitrary flat placeholders" — still true today, confirmed by direct re-read of the current file), across six call sites: the 90 generated planets, the wormhole marker, the synthetic/live slipway lines, the mouse-mode cursor, the liaison-drag preview line, and the tech-menu tile row. This PRD's governing guardrail, quoted exactly from `docs/plan.md`'s Garde-fous: *"Pas de juice inventé : les seuls effets visuels/sonores ajoutés en Phase 5 sont ceux recensés dans `pico8/lua.lua`. Un effet qui 'améliorerait' le ressenti sans exister dans la source n'est pas ajouté."* — which this PRD treats as a hard boundary: nothing is drawn with a sprite unless a real `spr()`/`sspr()` call site in `pico8/lua.lua` says the original game drew it with one.

That last point turns out to be the single most consequential finding of this PRD's own research (below) — but an earlier pass of this same research got it wrong by tracing only each entity's single most obviously-named draw method. `pico8/lua.lua`'s real per-frame render loop is `function _draw()cls()dv()dc("kj")dc("ev")end` (line 1188): `dc(nt)` (line 188-199) dispatches to `qc[nt](qc,qc.ra)` for every live entity `qc` that was registered under that method name, and an entity registers under **both** `"kj"` and `"ev"` independently, at creation, whenever it defines that method (`lt()`, line 156-162: `for p in all(bm)do if(e[p])ft(cv,p,e)end` with `bm={"kj","ev","hd","hk","hb"}`). So `dc("kj")` and `dc("ev")` **both** fire every frame, for every entity that defines either method — meaning an entity's `:kj` and `:ev` are two independent, both-real draw passes, not "the real one plus a leftover." Re-tracing every `spr`/`sspr`/`sfx`/`music`/`pal`/`fget`/`fset` call site with that corrected picture shows **four of the six currently-wired placeholders have a real, reachable sprite asset somewhere in their actual draw dispatch** — not two. Planets (`jo:kj`) and the cursor (`ui:ev`) were already found correctly. Newly confirmed: the liaison-drag entity `jc` also defines `jc:ev` (line 682-684, `function jc:ev()if(self.qu~=self.re)dl(self)end`), which — since `jc`'s prototype default is `me="kz"` (line 614) — calls `dl()` (line 560-568), and `dl()` draws `spr(31,mp.x-3,mp.y-8)` (line 564) whenever the drag has no valid target with a text reason (an "invalid target" marker). And the tech-menu's per-row resource icon (`t.nk`, `cr()` line 957) is rendered every frame through `js:kj()` (line 271-276, itself dispatched by `dc("kj")`) → `self.lq:ol()` (`lq:ol`, line 295-299) → the closure `lq:mn()` builds for a bare-number label field (line 300-310: `elseif f then fn=function(p)dv(qw)spr(f,p.x,p.y)dv()end`) — a real, reachable `spr()` call, not merely text. Only two placeholders remain genuinely sprite-free after this correction: the wormhole (drawn entirely by `ei()`'s `pset()` particle swirl, `g_:kj`; its separate `g_:ev=dl` assignment is also traced and resolved below — `dl()`'s marker branch is confirmed **unreachable** for a wormhole, since `g_`'s `self.me` is never `"kz"` at runtime) and the synthetic/live slipway-line placeholder (`jc:kj` itself, line 667-681, drawn entirely by `line()`/`pset()`, zero `spr()` calls — `jc`'s *other* draw pass, `jc:ev`, is the one with the real marker, and it maps to this step's separate liaison-drag-preview placeholder, not the slipway-line one). Of the four real, reachable sprites, all four are wired this step (planets, cursor, the liaison-drag marker, and the tech-menu's per-row resource icon — see Implementation Decisions/Chunks). A second review pass corrected an earlier framing of the tech-menu icon as a data-decoding gap: its exact per-tech sprite ids for all 4 Era-1 techs are not undecoded at all — `docs/prd/psx-rules-tech.md` already lists each tech's raw `nk` letter code (space folding=`"t"`, geneseeds=`"l"`, nanomaterials=`"o"`, drillbots=`"b"`), `docs/design/slipways-mechanics.md`'s Annexe A already gives the letter-to-resource-code table (`t=22,l=20,o=21,b=18`), and `nb`'s own load-time transform (`ho()`, `pico8/lua.lua:17-23`, invoked at `:1442`) already resolves each raw `nk` letter to that resource code before the game ever reads `t.nk` — the same resolved-number lookup this PRD already uses elsewhere (the Laboratory tooltip icon, code `24`="science"). The real, narrower gap was that `rules_tech.h`'s own `tech_t` struct simply had no field to hold that already-known value yet (its own comment names `nk` as one of the raw table's five positional fields but excludes it from `tech_t`, "wholly deferred") — a missing struct field plus a small data-population step, not a data-decoding or invention gap, so this step closes it (Implementation Decisions item 5, Implementation Chunks chunk 8). The wormhole's real visual (`pset()` particle swirl) and the slipway line's real visual (color-ramp/thickness line animation) remain step 18's "juice" scope, not this one's.

Six source questions were open going in and are all resolved from direct re-decode below: the real minimal sprite inventory this step needs (a four-sprite wired answer, not the six-call-site answer the placeholder inventory might suggest, and not the two-sprite answer an incomplete single-draw-method trace would suggest either); the concrete PSX-native extraction pipeline/output format (this codebase has **zero** existing CLUT/texture precedent to extend — `game_draw.c` has only ever used flat `TILE`/`POLY_F4`/`LINE_F2`, confirmed by direct grep, and there is no `font.c` or font/glyph/text-rendering code anywhere in `psx-slipways/`, also independently confirmed by `docs/prd/psx-rules-tech.md`); which GPU primitives/PSn00bSDK APIs replace which placeholder (a much smaller list than "all six," per the finding above); and whether PICO-8's SFX/music data is meaningfully "extractable" as pure data without also building a synthesizer (yes, confirmed directly from `sfx.json`'s/`music.json`'s own structure — see below).

## Solution

Re-run this project's established direct-source-trace methodology against `pico8/lua.lua` for every `spr`/`sspr`/`sfx`/`music`/`pal`/`fget`/`fset` call site (not the design doc, and not the six-placeholder list taken at face value, and not any single entity's most obviously-named draw method taken as its *only* draw pass — `_draw()`'s real `dc("kj")dc("ev")` double dispatch, below, means both must be traced), cross-checked against `pico8/gfx.json`'s/`pico8/gff.json`'s/`pico8/sfx.json`'s/`pico8/music.json`'s actual decoded structure. This surfaces the real sprite inventory (four live-reachable sprites wired this step: the default "unknown planet" sprite `43`, the default cursor-pointer sprite `58`, the liaison-drag "invalid target" marker sprite `31`, and the tech-menu's per-tech resource icon — sprites `22`/`20`/`21`/`18` for the 4 Era-1 techs, already traced from two other files in this repo (Implementation Decisions item 5) and newly wired this step by adding the one missing `rules_tech.h` data field; plus a larger traced-but-currently-unreachable roster of 11 planet-type sprites, 4 mood-status icons, and 8 structure-purchase icons, all real and all captured as data for a future step to wire once this port has live discovery/colonization/structure-purchase state) and confirms audio is pure procedural chiptune-synth parameter data (no PCM samples anywhere), extractable as a portable C data table with zero synthesis work.

Two new build-time Python tools (`tools/gen_psx_sprite_atlas.py`, `tools/gen_psx_audio_data.py`, following this project's `tools/gen_pcsx_*.py` naming convention, adapted since no existing tool converts a game asset into a compiled-in C data file rather than a Lua test driver) read `pico8/gfx.json`/`pico8/sfx.json`/`pico8/music.json` directly and emit new, pure, host-testable C modules (`psx-slipways/sprite_atlas.h/.c`, `psx-slipways/audio_data.h/.c`) — static `const` data baked straight into the PSn00bSDK executable (no CD-file loading is introduced; the whole sprite sheet is ~4KB packed 4bpp, trivially small, and this codebase has no `CdRead`/`CdControl` precedent to build on, confirmed by grep). `game_draw.c` then gets exactly four real changes: the planet-tile loop and the mouse-mode-cursor block each swap their flat `TILE` for a real textured GPU primitive (PSn00bSDK's `SPRT`-family primitive over a `LoadImage`-uploaded VRAM texture page, CLUT-indexed), reusing `setRGB0`'s existing tint capability (textured, non-`raw` primitives are still color-modulated on real PS1 hardware) to keep the cursor's already-accepted click-flash yellow tint; the existing liaison-drag preview block gains one addition — the same textured-sprite treatment draws `SPRITE_LIAISON_INVALID_TARGET` on top of its existing green/red `LINE_F2` line whenever `liaison_get_state().live.reason` is a "structural" invalid reason (`LIAISON_ALREADY_CONNECTED`, `LIAISON_BLOCKED_BY_PLANET`, or `LIAISON_CROSSES_ROUTE` — matching exactly which of `jc:ce()`'s outcomes `dl()` draws a marker for, as opposed to `LIAISON_TOO_FAR`'s real source treatment, on-screen text this port still has no font for); and the existing tech-menu tile loop gains the same kind of addition — one textured resource-icon primitive per tile, on top of its existing, unchanged researched/unresearched `TILE`, selected via `rules_tech.h`'s one new `icon` field (Implementation Decisions item 5, Implementation Chunks chunk 8). The wormhole and slipway-line blocks are **not touched** — confirmed, not assumed, that they have no real sprite to swap in.

## Implementation Decisions

### Source data formats, confirmed by direct read (not assumed)

- **`pico8/gfx.json`**: `{"width": 128, "height": 128, "pixels": [...]}` — a flat, row-major array of exactly 16384 integers, each in `[0, 15]` (confirmed: `min`/`max` over the full array are `0`/`15`). This is PICO-8's raw 4bpp indexed sprite-sheet data, already fully decoded to one palette-index integer per pixel — no bit-packing, no base64, no PNG re-decoding needed. Sprite id `N`'s top-left pixel is at `x = (N % 16) * 8, y = (N / 16) * 8` (PICO-8's fixed 16×16-sprite, 8×8-pixel-per-sprite grid), with `pixels[y*128+x]` giving that pixel's palette index.
- **`pico8/sprite.png`** (512×512 RGBA) and **`pico8/original.p8.png`** (160×205 RGBA, the P8PNG cart-label image) are **not needed as extraction sources**, confirmed: `gfx.json` is already fully decoded, structured, indexed pixel data (unlike `pico8/lua.lua`'s own `unstash()`-hidden text tables, which genuinely have no other decoded form in this repo) — `sprite.png` is a human-viewable 4×-upscaled preview render with PICO-8's default palette already baked in as RGBA, redundant with `gfx.json` for extraction purposes, and `original.p8.png` is the cart's own label image (LSB-steganography source for the *other* already-decoded `.json` files), with nothing left to decode from it that `gfx.json`/`sfx.json`/`music.json`/`gff.json`/`map.json` don't already give directly. Neither is read by this step's tooling.
- **`pico8/gff.json`**: an array of exactly 256 entries (one per possible PICO-8 sprite id, `0`-`255`), each `{flag0..flag7: bool}` — PICO-8's per-sprite editor flags (normally consumed by `fget()`/`fset()` for gameplay purposes like tile-collision). **Confirmed unused**: an exhaustive grep of `pico8/lua.lua` for `fget`/`fset` returns **zero matches**. 51 of the 256 entries have at least one flag set (mostly `flag0`), but since the game itself never reads any flag via `fget()`, these are pure PICO-8-editor authoring metadata with **zero gameplay or rendering effect** in the actual running game. This directly resolves this task's own open question about `gff.json` — the opposite of the "gameplay-relevant sprite metadata" hypothesis: it's confirmed dead data. Not extracted.
- **`pico8/sfx.json`**: an array of exactly 64 SFX slots, each `{"notes": [...up to 32 note objects...], "editorMode": int, "speed": int, "loopStart": int, "loopEnd": int}`. Each note is `{"pitch": 0-63, "instrument": 0-15, "volume": 0-7, "effect": "none"|"vibrato"|"drop"|...}`. **No PCM sample data anywhere** — every field is a small integer or enum-string describing PICO-8's built-in procedural waveform synthesizer (instrument id selects a waveform+envelope shape; pitch/volume/effect are per-note synthesis parameters). This directly confirms this task's own key scoping question 4: PICO-8's SFX are genuinely sample-free, procedural chiptune data — "extraction" means capturing this parameter table as portable data, not building a synthesizer (that's step 19's job, if a synthesizer is needed at all for SPU playback — out of scope for this PRD either way).
- **`pico8/music.json`**: an array of exactly 64 pattern slots, each an array of exactly 4 channel entries `{"sfxId": int, "mute": bool, "flag": bool}` — a pattern references up to 4 SFX slots (one per PICO-8 audio channel) to play simultaneously, `mute` silences a channel, `flag` marks pattern-transition behavior (PICO-8's loop/stop-at-end semantics). Also pure small-integer reference data, no samples.

### Draw dispatch: `:kj` AND `:ev` both fire every frame (the methodology correction this revision makes)

An earlier pass of this PRD's research traced only each of the six placeholders' single most obviously-named draw method (`g_.kj`, `jc:kj`, `cr()`'s label-queue build) and concluded from that alone whether a real `spr()` call existed. That undercounts, because `pico8/lua.lua`'s real per-frame render loop is:

```
pico8/lua.lua:1187-1188
function _update60()dg()ok:lj()end
function _draw()cls()dv()dc("kj")dc("ev")end
```

`dc(nt)` (`pico8/lua.lua:188-199`) dispatches `qc[nt](qc,qc.ra)` to every live entity `qc` registered under draw-pass name `nt`. Entity registration (`lt()`, `pico8/lua.lua:156-162`) is: `for p in all(bm)do if(e[p])ft(cv,p,e)end` with `bm=o("kj","ev","hd","hk","hb")` — an entity is added to `cv.kj` if it defines a `:kj` method, and **independently** added to `cv.ev` if it defines an `:ev` method. Since `_draw()` calls `dc("kj")` and then `dc("ev")` **every frame**, any entity that defines both methods gets **both** called every frame — `:kj` is not "the" draw method with `:ev` as a leftover or alternate; they are two independent, both-real, both-live draw passes over the same entity. This is why the wormhole (`g_`) and the liaison-drag entity (`jc`) each needed their `:ev` traced separately from their `:kj`, below, and why the tech-menu's label-queue row (`js`) needed its own `:kj` traced through the indirection of `lq:mn()`'s closures rather than assumed absent just because `cr()` itself contains no literal `spr(` text.

### Real sprite inventory, traced directly from every `spr`/`sspr` call site in `pico8/lua.lua`, across every entity's full `:kj`+`:ev` dispatch

An exhaustive grep for `spr(`/`sspr(`/`sfx(`/`music(`/`pal(`/`fget(`/`fset(` across the whole file finds every call site below (line numbers exact). `sspr()` (scaled/stretched blit) and PICO-8's literal `pal()` (as opposed to this game's own `dv()` wrapper, below) are **never called anywhere** — confirmed, simplifying the inventory to plain, unscaled `spr()` calls only.

**1. Planets — `jo:kj`, `pico8/lua.lua:541-551` — HAS a real sprite.**
```
circfill(p.x,p.y,7,0)dv(self.qw)palt(3,false)palt(0,true)
spr(self.nk and self.nk.s or self.s or 43,p.x-4,p.y-4,2,2)dv()
```

### Palette-swap mechanism (`dv`/`cu`), traced but not needed by any wired sprite

`cu()` (`pico8/lua.lua:134-140`) and `dv()` (`:142`):
```
function cu() local a=0x5000
  for p=0,15 do for c=0,15 do
    poke(a, bor(sget(p,c), c==3 and 0x80))
    a+=1
  end end
end
function dv(no) memcpy(0x5f00, 0x5000+shl(flr(no),4), 16) end
```
`cu()` builds a 256-byte table of 16 sixteen-color palette-remap rows at PICO-8 memory `0x5000`, by **reading the sprite sheet's own top-left 16×16 pixel block as raw data** (`sget(p,c)` for `p,c` in `0..15` — i.e. `gfx.json`'s `pixels[c*128+p]` for `p,c < 16`) rather than from any separate palette-table asset. `dv(no)` then `memcpy`s one 16-byte row from that table into PICO-8's live draw-palette register (`0x5f00`). This is a real, PICO-8-specific data-hiding trick — palette-swap data embedded directly in unused sprite-sheet pixels — worth documenting (Further Notes) even though, per the sprite-inventory trace above, **none of this step's four wired sprites needs any actual CLUT swap**: `df` (planet types) has no `qw` field at all, `ui`'s cursor has no `dv()` call in its draw path, `dl()`'s `spr(31,...)` call for the liaison-drag marker is called bare (no `dv()`/`qw` bracket around it at all), and `lq:mn()`'s number-icon branch (`:309`, the tech-menu icon's `spr()` call) does wrap in `dv(qw)`/`dv()` but `qw` defaults to `0` for a bare-number field like `t.nk` (`local w,qw,qv,fn=6,0`, `:300` — the table-branch that could override `qw` never runs, since `t.nk` isn't wrapped in a table) — row `0` is the same identity-palette row `jo:kj`'s `dv(self.qw)` already loads for every planet (Implementation Decisions item 5). The only confirmed runtime user of `dv()` with an actual non-`0`/non-`nil` `qw`/palette argument is Trading Hub's dynamic recolor (`nl:ly`, already fully traced by `docs/prd/psx-structures-and-transforms.md`'s Further Notes) — not live in this port. This step therefore extracts the sprite atlas's raw pixel data faithfully (including that top-left 16×16 "data, not art" block, left un-special-cased — it isn't drawn by anything this step wires) but does **not** implement any CLUT-swap machinery; a single default identity CLUT is sufficient for every sprite this step wires, including the tech-menu icon.

### Transparency: PS1 hardware convention maps directly onto PICO-8's default

`jo:kj`'s `circfill(...,0) ... palt(3,false) palt(0,true) spr(...)`, `ui:ev`'s plain `spr()` call, `dl()`'s `spr(31,...)` call (`jc:ev`, item 4), and `lq:mn()`'s `spr(f,...)` call for the tech-menu icon (item 5) all rely on PICO-8's *default* sprite-transparency rule (color `0`/black is transparent unless overridden) — `palt(0,true)` in `jo:kj` is a defensive re-assertion of that same default, not a change from it (no other transparency value is ever set for any of these four draw paths — an exhaustive grep for `palt(` across the whole file finds exactly 3 call sites: `jo:kj`'s pair, above, and a `palt(3,...)` bracket inside `ie:kj`'s structure-icon draw, `pico8/lua.lua:937-939`, unrelated to any of this step's four wired sprites). The PS1 GPU has a direct, well-documented hardware equivalent requiring no extra blend-mode setup: a texel (or CLUT-resolved color) of exactly raw `0x0000` is drawn as fully transparent by the GPU itself. Since PICO-8's own color `0` is RGB `(0,0,0)` (black) — the same value either way — this step's CLUT table encodes index `0` as literal `0x0000` deliberately (documented as *why*, not left as an incidental match), giving the same "background shows through" behavior `jo:kj`/`ui:ev`/`dl()`/`lq:mn()` rely on with zero additional per-primitive code.

### Extraction pipeline and output format

- **`tools/gen_psx_sprite_atlas.py`** (new): reads `pico8/gfx.json` directly (no PNG decoding). Packs the full 128×128 indexed sheet into a PSn00bSDK-compatible 4bpp texture blob (2 pixels/byte, row-major, matching the PS1 GPU's native 4bpp CLUT texture format) and emits `psx-slipways/sprite_atlas.h`/`.c`:
  - `static const uint8_t g_sprite_atlas_4bpp[128*128/2];` (8192 bytes — small enough to bake directly into the ELF; no CD-file loading is introduced, matching this codebase's existing "no `CdRead`/`CdControl` anywhere" state, confirmed by grep).
  - `static const uint16_t g_pico8_clut[16];` — PICO-8's fixed, well-known 16-color system palette, converted to PS1 16-bit BGR555, with index `0` deliberately `0x0000` (see above). This is a system/hardware constant, like `SCREEN_XRES`/`SCREEN_YRES` — not a `slipways-mechanics.md`-traceable game-design value, and labeled as such in a code comment (mirroring `docs/prd/psx-galaxy-rendering.md`'s own precedent for labeling rendering/benchmark constants as not game-design values).
  - Named sprite-cell constants for every id traced above with a known numeric value: `SPRITE_PLANET_UNKNOWN = 43` (wired this step), `SPRITE_CURSOR_DEFAULT = 58` (wired this step), `SPRITE_LIAISON_INVALID_TARGET = 31` (wired this step — `dl()`'s marker, `pico8/lua.lua:564`, reachable via `jc:ev` per item 4 above), `SPRITE_RESOURCE_TECH = 22`, `SPRITE_RESOURCE_ORGANICS = 20`, `SPRITE_RESOURCE_ORE = 21`, `SPRITE_RESOURCE_BOTS = 18` (wired this step — the tech-menu's per-tech resource icons, Implementation Decisions item 5, traced from `docs/prd/psx-rules-tech.md`/`docs/design/slipways-mechanics.md`'s Annexe A, not invented; selected per-tech via `rules_tech.h`'s new `icon` field, Implementation Chunks chunk 8), plus the full traced-but-unwired roster: `SPRITE_PLANET_EMPTY = 45`, `SPRITE_PLANET_EARTHLIKE = 160` ... `SPRITE_PLANET_GASGIANT = 96` (all 11 `df` entries), `SPRITE_MOOD_UNHAPPY = 2` ... `SPRITE_MOOD_RICH = 5`, `SPRITE_STRUCTURE_LABORATORY = 174` ... `SPRITE_STRUCTURE_INFRAGATE_0/1/2/3 = 78/78/78/76`, `SPRITE_CURSOR_HELD = 9` (documented dead code, not wired), `SPRITE_CURSOR_HOVER_OVERRIDE = 11` (documented unreachable in this port, not wired).
  - A helper, `void sprite_atlas_cel_rect(int sprite_id, int cel_w, int cel_h, int *out_x, int *out_y, int *out_w, int *out_h)` (illustrative signature) computing a sprite id's pixel rectangle within the atlas (the `x=(id%16)*8, y=(id/16)*8` formula above, generalized to the 2×2-cel case planets use) — pure, host-testable, used by `game_draw.c` to set up `setUVWH`/texture-window parameters without hand-computing coordinates at each call site.
- **`tools/gen_psx_audio_data.py`** (new): reads `pico8/sfx.json`/`pico8/music.json` directly, emits `psx-slipways/audio_data.h`/`.c`:
  - `typedef struct { uint8_t pitch, instrument, volume; sfx_effect_t effect; } sfx_note_t;` (`sfx_effect_t` a small enum matching the JSON's `effect` string values: `none`/`vibrato`/`drop`/etc., re-enumerated exhaustively from the real data, not guessed).
  - `typedef struct { sfx_note_t notes[32]; int note_count; int speed; int loop_start; int loop_end; } sfx_def_t;` and `static const sfx_def_t g_sfx[64];`.
  - `typedef struct { int sfx_id; bool mute; bool flag; } music_channel_t;` and `typedef struct { music_channel_t channels[4]; } music_pattern_t;` and `static const music_pattern_t g_music[64];`.
  - No synthesis, no SPU code, no playback function of any kind — pure data, exactly mirroring `rules_planets.c`'s/`rules_tech.c`'s "pure data + pure function, zero live wiring" precedent, except this module has no functions at all beyond the atlas-rect-style pure helper above (nothing to compute — the data *is* the output).

### GPU primitives / PSn00bSDK APIs — exactly four call sites change

- **Texture upload, once at boot**: a new `sprite_atlas_init(void)` (in `sprite_atlas.c`, PSX-only — the `psxgpu.h`-dependent half of this module, mirroring `world.c`/`screen_map.c`'s existing pure/impure split within one concern) calls `LoadImage` once to upload `g_sprite_atlas_4bpp` to a fixed VRAM texture page, and records that page's `DR_TPAGE` value plus a single uploaded CLUT's VRAM coordinates (from `g_pico8_clut`) for later primitives to reference. Called once from `game_init()`, alongside `world_init()`/`cursor_init()`'s existing boot-time calls.
- **Planet tiles** (`game_draw.c`'s existing loop over `galaxy->positions[]`): each `TILE`+`setTile`/`setXY0`/`setWH`/`setRGB0`/`DrawPrim` sequence becomes a `SPRT` (or `POLY_FT4` with `setUVWH`, whichever PSn00bSDK's current header signature makes the more direct fit — to be confirmed against the live header at implementation time, per this codebase's own established practice of not assuming an exact macro shape without checking, matching `docs/prd/psx-galaxy-rendering.md`'s own explicit "double-check current PSn00bSDK header signatures directly" note for `LINE_F2`/`POLY_F4`) primitive: `setUVWH` selects `SPRITE_PLANET_UNKNOWN`'s 16×16 rectangle (`sprite_atlas_cel_rect`, 2×2 cels) within the uploaded texture page, `setClut` references the uploaded CLUT, `DR_TPAGE` set once (not per-primitive, since every planet uses the same texture page and CLUT). `setRGB0` keeps whatever flat color it currently uses, now acting as a texture modulation tint rather than a flat fill — left at full white (`255,255,255`, i.e. no tint) since the real source draws this sprite untinted.
- **Cursor** (`game_draw.c`'s existing `mouse_mode`-gated block): same primitive-family change, `SPRITE_CURSOR_DEFAULT`'s 8×8 rectangle (1×1 cel), with the existing `setRGB0(255,255,0)`/`setRGB0(255,255,255)` click-flash tint logic kept exactly as-is (now modulating the real cursor texture instead of a flat square).
- **Liaison-drag preview** (`game_draw.c`'s existing `liaison.dragging`-gated block, `psx-liaison-validity.md`'s chunk 5): an **addition**, not a primitive-type swap — the block's existing `LINE_F2` (green/red, driven by `liaison.live.reason`) is left exactly as-is, and one new textured-primitive draw call is added after it, gated on `liaison.live.reason` being `LIAISON_ALREADY_CONNECTED`, `LIAISON_BLOCKED_BY_PLANET`, or `LIAISON_CROSSES_ROUTE` (i.e. not `LIAISON_VALID` and not `LIAISON_TOO_FAR` — see item 4, Implementation Decisions). Same primitive family as the cursor/planet changes, `SPRITE_LIAISON_INVALID_TARGET`'s 8×8 rectangle (1×1 cel), positioned at the drag's live target point (source's `mp.x-3,mp.y-8` offset, `dl()` line 564 — `mp` there is `je.ra`, this port's own `cursor.x`/`cursor.y` equivalent, or the hovered planet's screen position when one is hovered, matching the existing line's own target-point logic immediately above it in the same block). Untinted (`setRGB0(255,255,255)`), since source draws this marker with no color modulation.
- **Wormhole / slipway lines**: **no primitive-type change** — confirmed above, nothing to extract for the wormhole or the slipway lines; `POLY_F4`/`LINE_F2` stay exactly as `docs/prd/psx-galaxy-rendering.md` left them.
- **Tech-menu tiles** (`game_draw.c`'s existing `rules_tech_get_state().open`-gated block, `docs/prd/psx-rules-tech.md`'s chunk 4): an **addition**, not a primitive-type swap — the block's existing flat `TILE` (still carrying the real, if currently-always-false, researched/unresearched tint) is left exactly as-is, and one new textured-primitive draw call is added per tile after it, selecting `SPRITE_RESOURCE_TECH`/`SPRITE_RESOURCE_ORGANICS`/`SPRITE_RESOURCE_ORE`/`SPRITE_RESOURCE_BOTS` (sprite ids `22`/`20`/`21`/`18`, Implementation Decisions item 5) via `rules_tech_get(t)->icon`, the one new field `tech_t` gains this step (Implementation Chunks chunk 8). Untinted (`setRGB0(255,255,255)`), matching `lq:mn()`'s own bare `spr(f,p.x,p.y)` call.

## Testing Decisions

- **What makes a good test here**: decode real data out of the *generated* header/array and assert it against an independently-recomputed value from the real `pico8/gfx.json`/`pico8/sfx.json`/`pico8/music.json` (re-read directly, not hand-copied into test source, mirroring this project's "re-run the decode command at test-authorship time" discipline already established for `unstash()`-sourced data) — never merely "the generated file compiles" or "the array has the right length."
- **Fully host-testable** (`gcc`, no PSn00bSDK toolchain): `sprite_atlas.c`'s data half (the generated `const` arrays) and `sprite_atlas_cel_rect()` — zero PSX-header dependency, same split `world.c`/`screen_map.c` already established between pure-logic and PSX-only halves of one concern. `audio_data.c` is pure data end to end, no PSX-only half at all this step. `rules_tech.c`'s new `icon` field (chunk 8) is likewise plain data, asserted the same way `host_tests/rules_tech_test.c` already asserts `name`/`base_cost`/`era`.
- **Not host-testable, and that's expected** (same PSX-hardware-boundary reasoning every prior PRD in this codebase already gives): `sprite_atlas_init()` (`LoadImage`/`DR_TPAGE`/CLUT-upload calls) and `game_draw.c`'s four changed/added blocks. Verified instead by:
  - `make psx-slipways-boot-test-pcsx` (existing, unmodified) — confirms boot still succeeds with the new texture-upload call and the changed/added primitive draws.
  - `make psx-slipways-screenshot-pcsx` (existing, unmodified target) — the real, source-cited payoff of this step made visible: planets and cursor render as actual PICO-8-derived sprite art instead of flat placeholder shapes, dragging a liaison toward an invalid target shows the real marker sprite alongside the existing red line, and opening the tech menu shows each of the 4 placeholder tiles' real resource icon. This is a spot-check, not a numeric assertion, matching every prior PRD's own established split between host-testable logic and PSX-only rendering.
- **Regression discipline**: chunk 3's roster-constant test re-asserts chunk 1's three already-tested sprites unchanged; chunk 8's tech-icon test (new sprite ids, new `rules_tech.c` field) is independent of chunks 1-6's three sprites but reuses the same pixel-correctness/host-test discipline; chunk 7's audio test is fully independent of chunks 1-6/8 (no shared state); a failure in any one of these never masks the others.
- **New Makefile targets**: `test-sprite-atlas`, `test-audio-data` (inline recipes, same `gcc -std=c11 -Wall -Wextra -I psx-slipways` shape every existing `test-*` target already uses, output under `psx-slipways/build-host/`), both added to `test`'s dependency list.
- **Prior art reused as-is**: `host_tests/t.h`'s PASS/FAIL harness; `docs/prd/psx-galaxy-rendering.md`'s own precedent for "double-check the live PSn00bSDK header signature before assuming a macro's exact shape" (this step is, like that one for `LINE_F2`/`POLY_F4`, the *first* use of a textured/CLUT primitive anywhere in this codebase — no existing call site to copy).

## Further Notes

- **The single highest-value finding of this whole PRD, corrected in this revision**: `pico8/lua.lua`'s real per-frame render loop dispatches **two** draw passes per entity every frame (`_draw()`'s `dc("kj")dc("ev")`, line 1188 — see the "Draw dispatch" subsection above), not one. An earlier pass of this PRD traced only each of the six placeholders' single most obviously-named draw method and concluded only **two** (planets, cursor) have any real sprite asset behind them at all — that conclusion was wrong, because it missed each entity's *second* draw pass. Re-tracing both `:kj` and `:ev` for every placeholder shows **four** of the six currently-wired placeholders have a real, reachable `spr()` call somewhere in their actual draw dispatch: planets (`jo:kj`), cursor (`ui:ev`), the liaison-drag "invalid target" marker (`jc:ev`→`dl()`, newly found), and the tech-menu's resource icon (`js:kj`→`lq:mn()`, newly found). Only **two** placeholders are confirmed to have genuinely no real sprite anywhere in their dispatch: the wormhole (`g_:kj` is a pure `pset()` particle swirl; `g_:ev=dl` is also assigned, but is proven unreachable — `g_`'s `self.me` is never `"kz"` at runtime, see item 3 above, so `dl()`'s `spr()` branch can never fire for a wormhole) and the synthetic/live slipway-line placeholder (`jc:kj` itself is pure `line()`/`pset()` — its sibling `jc:ev` does have the real marker, but that maps to the *separate* liaison-drag-preview placeholder, not this one). Of the four real, reachable sprites, all four are wired this step (planets, cursor, liaison-drag marker, tech-menu resource icon). A second review pass found that an earlier version of this PRD had left the tech-menu icon deferred for a *false* reason — framing its exact per-tech sprite ids as an undecoded, "we'd have to invent it" gap, when in fact those ids (`22`/`20`/`21`/`18` for the 4 Era-1 techs) were already published and decoded across two other files in this repo (`docs/prd/psx-rules-tech.md`, `docs/design/slipways-mechanics.md`'s Annexe A); the real, narrower gap was only a missing `rules_tech.h` struct field, small enough to close this step (Implementation Decisions item 5, Implementation Chunks chunk 8). This reshapes the step from "replace two placeholders that actually have sprites, leave four untouched" to "replace all four placeholders that actually have a real, reachable sprite, and leave only the two genuinely sprite-free placeholders (the wormhole, the slipway line) untouched" — while keeping the guardrail's "nothing invented" boundary fully intact throughout.
- **`self.rheld` is genuinely dead code in the original game** (never assigned, confirmed by exhaustive grep) — a small but real example of "the source itself doesn't do this," worth remembering the next time a `spr()` call site's *other* branches look tempting to wire up for extra polish.
- **The `cu()`/`dv()` palette-swap-table-embedded-in-sprite-sheet-pixels trick** is a neat, PICO-8-specific data-hiding technique — conceptually a cousin of this project's own established `unstash()`-in-PNG-LSB decode recipe for `pico8/lua.lua`'s hidden text tables (Annexe A), just applied to `gfx.json`'s own pixel data instead of `map.json`'s. Worth remembering if a future step needs to trace anything else that reads `sget()` for non-drawing purposes.
- **Recommended follow-up PRDs** (not part of this one, consistent with this project's own established precedent of flagging-but-not-fixing deferred items): (a) font/bitmap-text rendering (would unblock the tech menu's tech-name text, tooltips, and score/HUD text generally — a genuinely separate undertaking from cartridge sprite extraction); (b) the starfield background (`bg`); (c) wiring the 11-type/mood-icon/structure-icon roster once a live discovery-commit/colonization-choice/structure-purchase mechanism exists (still owned by no current plan step, per every Phase 3/4 PRD's own repeated finding — this step doesn't attempt to invent it either). (The per-tech resource-icon id that an earlier pass of this PRD had queued as a follow-up here is no longer one — it's wired directly by this step's own chunk 8, once a second review pass found its blocking "data gap" reasoning was false; see Implementation Decisions item 5.)
- **Cross-reference for step 19**: `audio_data.h`'s `g_sfx[64]`/`g_music[64]` are shaped and ready for whichever future step wires actual SPU playback — `rn()`'s already-traced sound-effect ids (`docs/prd/psx-structures-and-transforms.md`'s own Further Notes: `rn=45`/`46` for collapse/harvest, plus every other `rn(no)` call site in `pico8/lua.lua`) index directly into `g_sfx[]` by the same numeric id PICO-8's own `sfx(no,3)` call uses — no remapping needed between this step's data and step 19's future consumer.
- **This step is a genuine first for this codebase**: no CLUT/texture/`LoadImage` code has existed anywhere in `psx-slipways/` or `psx-hello/` before it (confirmed by grep), the same way `docs/prd/psx-galaxy-rendering.md` flagged `LINE_F2`/`POLY_F4` as a first use in its own step. Whoever implements chunk 4 should double-check the live PSn00bSDK header signatures for the textured-primitive macro (`SPRT` vs. `POLY_FT4` vs. whatever the installed SDK version actually exposes) rather than assume this PRD's illustrative signatures are exact — same caveat that PRD gave for its own two new primitive types.
