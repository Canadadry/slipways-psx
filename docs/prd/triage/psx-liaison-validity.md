## Problem Statement

`docs/plan.md` Phase 3 step 9 calls for `liaison.c` : "calcul de validité des slipways (trop loin / bloqué par une planète / croise une route existante — formules du §5 de la doc de design), branché sur l'événement clic de la Phase 2." Nothing in `psx-slipways/` currently computes slipway validity, and nothing in this port is live-wired to a real player input event yet: Phase 3 step 8 (`rules_planets.c`) deliberately stayed an unwired, pure-data module (no caller), and Phase 2 steps 5-6 (`cursor.c`) deliberately stopped at exposing a stable `click_pressed`/`click_held`/`click_released` event interface without any consumer. This step is explicitly different in kind — it must be the first real gameplay logic in this port that a live click event actually drives, frame by frame, the same way `pico8/lua.lua`'s `jc:hq`/`jc:ey` drive slipway-dragging from the mouse. Two things make this harder than a typical "port a formula" step: (1) the source's own validity function (`jc:ce`, traced below) is only one layer of a larger press→held→release drag mechanic, so "branché sur le clic" requires designing and wiring a small state machine, not just a pure function; (2) the precondition the original game actually requires before any of this math even runs — both endpoint planets must already be colonized — has no equivalent state in this port yet (colonization lands in Phase 3 step 10, not before), so this step must decide, and defend from source, what "wired to the click" concretely means in the meantime without inventing a capability the source game doesn't have.

## Solution

Read `pico8/lua.lua` directly around the `jc` class (the slipway-drag object) and its dispatcher (`ui:bh`, already partially traced by `docs/prd/psx-simulated-click.md`) to extract the exact press/held/release mechanic and the three §5 formulas it evaluates every held frame, then port that mechanic as two layers: a pure, host-testable geometry+state-machine core (`liaison.c`'s "logic" half, mirroring `jc:ce()` exactly, colonization-blind because the source's own `jc:ce()` is colonization-blind — colonization gating lives entirely in `jo:ldown()`/`jo:gv()`, outside `jc:ce()`, in source) and a thin PSX-side wiring layer (a one-line `game_update.c` call plus a `game_draw.c` preview-line block, mirroring `cursor.c`'s own pure-core/stateful-wrapper split). Because Phase 3 step 10 (colonization) hasn't landed, this step treats every planet in the generated galaxy as a valid geometric drag candidate — a deliberate, source-verified interim scope (see Implementation Decisions) — and, just as deliberately, never writes a resulting route into any persistent, still-to-exist "committed slipway network": doing so between two uncolonized planets would be exactly the kind of invented capability the plan's interaction-vs-content guardrail forbids by default. What ships is the full, faithful §5 math, a real press/held/release state machine driven by real controller input under PCSX-Redux, and a live, color-coded preview line — with the actual "become part of the trade network" step withheld until colonization exists to gate it honestly.

## Implementation Decisions

**The three §5 formulas, traced directly from `pico8/lua.lua`'s `jc:ce()` (line 641-653) — the exact function this step ports.**

- **Load-bearing PICO-8 arithmetic fact this whole trace depends on**: PICO-8's `#v` operator on a vector (`km.__len`, line 119-120: `function km:__len() return self:rg(self) end`, where `:rg` is plain dot product, line 110-112) returns the **squared** magnitude, not the magnitude — `#d` is `dot(d,d)`, not `sqrt(dot(d,d))`. This project already relies on exactly this fact for `WORLD_NEIGHBOR_RANGE_SQ` (`world.h`, traced to `mz`'s probe range, `0.19`/`0.27`, explicitly documented there as "squared units"). This step's three formulas depend on the same fact, so every threshold below is a **squared**-distance quantity, not a linear one, whenever it's compared against a `#(...)` expression in source.
- **Range check ("too far")** — `jc:ce()` line 641-644: `if #(sp-dp) > ov("space folding", 0.5, 1.08) then return {qs="-too far-"} end`, where `sp,dp` are the source/target planet positions. This is a **squared**-distance comparison: the real max range is `sqrt(0.5)` in normalized units, not `0.5` as the design doc's prose ("distance normalisée de `0.5`") reads literally — the design doc's number is correct as a squared-units value, imprecise only in calling it "distance" rather than "squared distance" (the same class of prose-vs-source gap this project already found twice, Phase 1 step 2 -- for both §3's placement threshold and §4's probe range -- and Phase 1 step 4, where `world.h`'s `WORLD_NEIGHBOR_RANGE_SQ` comment redocumented the §4 finding as "squared units"). `ov("space folding", 0.5, 1.08)` returns `0.5` unless the "space folding" tech is researched (`oj("space folding")`, always false — no tech system exists yet, `rules_tech.c` is step 12); ported here as `LIAISON_RANGE_SQ = 0.5 * FX_ONE * FX_ONE`, base value only, the `1.08` extension explicitly deferred — the exact same treatment `WORLD_NEIGHBOR_RANGE_SQ` already gave the structurally identical `0.19`/`0.27` probe-range pair. This check runs **first** and short-circuits: if too far, neither of the next two checks is evaluated at all (matches source's early `return`).
- **"Blocked by a planet"** — `be(a,b,c,fh)` (line 1488-1494): `local d=b-a; local l_=d:rg(c-a)/#d; return l_>0.01 and l_<0.99 and #(a+d*l_-c)<fh`. Because `d:rg(c-a)` is a plain dot product and `#d` is the *squared* length of `d`, `l_` is the standard segment-projection parameter `t = dot(d, c-a) / dot(d,d)` — the position along the candidate segment (0 = source, 1 = target) closest to planet `c`. The check requires `t` strictly inside `(0.01, 0.99)` (a margin excluding the immediate neighborhood of either endpoint — a planet essentially coincident with the segment's own source or target must not block it) **and** the squared distance from that closest point to `c` under `fh`. Called from `jc:ce()` (line 648-649) with `fh = 0.0032` — traced here as a **squared**-distance tolerance (real linear tolerance ≈ `sqrt(0.0032) ≈ 0.057` normalized units), for the exact same `#()`-is-squared reason as above; the design doc's "tolérance `0.0032`" is correct as written but, read in isolation, invites the same linear-distance misreading the range check does. Evaluated against **every** planet in the galaxy (`cg.np`, no explicit endpoint exclusion in source — the `t` bounds alone structurally exclude points too close to either endpoint, including the endpoints themselves); the **first** blocking planet found, in galaxy index order, is reported (mirrors `jp(cg.np, ...)`'s list-preserves-source-order behavior).
- **"Crosses an existing route"** — `cl(p1,p2,q1,q2)` (line 1475-1481) plus its `ee` orientation helper (line 1482-1486): a standard four-orientation-test strict segment-intersection check (no square roots, pure sign comparisons of cross products — a good fit for Q16.16 fixed-point, same arithmetic shape as `fixed_mul`). Collinear-with-zero-cross-product cases return "no crossing" (an endpoint touching another segment exactly is not treated as a crossing). Called from `jc:ce()` (line 648-651) filtered to routes of the **same `mt` type** as the candidate (`mt=0`, normal routes) — since infragates (`mt=1`, "can cross other slipways") don't exist in this port yet (Phase 4 step 15), every route this step's route list can ever hold is implicitly `mt=0`, so the type filter is a documented no-op for now, not omitted logic. Evaluated only if the "blocked by planet" scan above found nothing (both scans are concatenated in source as one list via `la(...)`, planets first then routes, and the first item of that combined list — `ds[1]` — is the reported blocker); the **first** crossing route found, in route-list order, is reported.
- **A fourth outcome from the same function, also ported**: **duplicate/already-connected**. Immediately after the range check and before the blocked/crosses scans, `jc:ce()` (line 645-647) walks the source planet's existing outgoing routes (`self.qu.oe`) and, if any of them already terminates at the candidate target, returns that existing route directly (§5's own "Doublon" rule: "si une route existe déjà... reconstruire une seconde est sans effet, le jeu réutilise la route existante"). This step ports it as its own, distinct result reason (not folded into "invalid") so a future consumer can give it different feedback than a genuine geometric failure, matching the richer, message-carrying object shape (`{qs="-too far-"}` vs. an actual route object) source itself returns from `jc:ce()`. Because this step's own route list is never populated (see below), this outcome can never actually fire in this step's *live* wiring — it exists, and is fully host-tested against hand-built fixtures, purely so the pure function is complete and ready for step 10+.
- **Explicitly out of scope from §5, and why**: the cost formula (`dj`/`bk`, line 1259-1264) and the affordability gate (`fm:lu`/`d_`, line 569-576) are both evaluated **outside** `jc:ce()` in source (`d_(self)` checks `not self.et and fm:lu(self.od)` — a separate layer on top of `jc:ce()`'s result), confirming this step's own scope boundary is not an arbitrary cut but the same boundary source itself draws. Both are `rules_economy.c` (Phase 3 step 13) territory — no credit/economy state exists in this port yet. The Slipgate/Infragate 3-connection cap (`#self.oe<3`, line 1110) and the infragate crossing exception are §5/§6 rules about structures that don't exist in this port yet (Phase 4 step 15).

**The colonization-precondition question, resolved from source — not guessed.**

- `jo:ldown()` (line 412-417): a planet in state `"known"` (discovered, uncolonized) opens the colonization menu (`self:fe()`); a planet in state `"ly"` (already colonized — set by `jo:hu`, line 458, after a colonization job is chosen) is what actually starts a drag (`return jc({qu=self})`). **Only a colonized planet can start a slipway drag in source.**
- `jo:gv(s)` (line 472-478), the release-time hit-test-and-validate call on whatever planet is under the cursor when ○ is released: returns `true` (a valid drop target) only `if self.me=="ly"` — an uncolonized planet is never a valid slipway endpoint, on either end.
- **Crucially, neither of these checks lives inside `jc:ce()`** (the function this step ports, traced above) — colonization eligibility is checked entirely by the dispatcher (`ui:bh`, already traced in `docs/prd/psx-simulated-click.md`) and by `jo:ldown`/`jo:gv`, one layer above the pure geometry. `jc:hq`'s own live-preview snapping (line 622: `self.re=ok.o_.gv and ok.o_ or {ra=mp,p=mp/128}`) checks only that a hovered entity *has* a `gv` method (i.e., is a planet at all, any state) — not that `gv()` currently returns true — so even in source, the **held-frame live preview** snaps to and recomputes validity against any hovered planet regardless of colonization state; only the **release-time commit decision** is colonization-gated.
- **Resolution**: this matches the plan's own option (a) exactly, now with direct source evidence rather than a plausibility argument. `liaison.c`'s pure validity core (`liaison_check`, mirroring `jc:ce()`) is colonization-blind by construction, because the source function it ports is colonization-blind by construction — this is not an approximation, it's the same module boundary source itself draws. The **live wiring** (this step) treats every planet in the generated galaxy as a valid geometric drag candidate on both ends, for the same reason source's held-frame preview does: no colonization check gates that path in source either. What source *does* gate — the actual commit, i.e., a new route becoming part of the persistent network (`self.qu:kf(self); re:kf(self)`, line 640) — this step withholds entirely (next decision), so the one thing source colonization-gates is the one thing this step never does anyway. Phase 3 step 10 (colonization) is expected to add the real `jo:gv`-equivalent eligibility check at the commit boundary once colonized-or-not state exists to check; `liaison_check` itself does not change shape when that lands.

**Never persist a committed route — the concrete guardrail resolution.**

- Writing a resulting route into a persistent "real slipway network" between two planets this port cannot yet tell apart from "already colonized" vs. "not" would let a player connect any two raw, uncolonized planets for free — strictly more capability than the source game has (source requires colonization on both ends, traced above). Per the plan's own guardrail ("en cas de doute... traité comme du contenu par défaut... et doit être justifié explicitement"), there is no doubt here: this would be inventing content. This step therefore never writes to any persistent route list on release, regardless of the live validity result.
- What release *does* do: finalizes the live validity computation one more time at the release-time target (mirroring `jc:ey`'s `re`/`d_` decision point structurally, without the `fm:kf` commit call), producing a last known-outcome (valid/reason) for a brief visual conclusion, then returns to idle. No planet, credit, or route-count state changes anywhere.
- **A minimal, currently-always-empty route list is still introduced** (`liaison_route_t { int a; int b; }`, a small fixed-capacity array owned by `liaison.c`, `LIAISON_MAX_ROUTES = 60` — the upper end of `docs/plan.md`'s own stated 40-60-simultaneous-slipway feasibility band, a real forward-looking capacity grounded in the plan's own text, not an arbitrary round number, and deliberately distinct from `slipway_bench.h`'s `MAX_SYNTHETIC_SLIPWAYS = 50`, which belongs to a module explicitly forbidden from growing into real logic). This gives the "crosses an existing route" check a real, live call site today (reading an array that happens to be empty), so Phase 3 step 10 — once it has real colonization state to gate a commit on — only has to start *writing* into this list, not redesign `liaison.c`'s signature or call site. `liaison_check`'s route-list parameter is a fresh type, not a reuse of `slipway_bench.h`'s `slipway_edge_t`, specifically so a real module never structurally depends on a type whose own header says it "must never grow into any" real logic.
- Net effect, concretely observable under PCSX: pressing ○ on any planet starts a live-tracked drag; holding shows a continuously-revalidated preview line, color-coded by the live §5 result; releasing ends the drag with a final one-frame outcome and no permanent change to anything. The full §5 math is genuinely exercised, live, by real controller input — without the port gaining a "build routes without colonizing" capability the source game doesn't have.

**Module shape: pure geometry+state-machine core in `liaison.c`/`liaison.h`, thin PSX-side wiring in `game_update.c`/`game_draw.c` — mirroring `cursor.c`'s established split.**

- **Pure, stateless geometry** (no statics, no PSX headers, Q16.16 only): `liaison_point_blocks_segment` (ports `be()`), `liaison_segments_cross` (ports `cl()`/`ee()`), and the top-level `liaison_check(from_index, from_pos, to_index, to_pos, const galaxy_t *galaxy, const liaison_route_t *routes, int route_count) -> liaison_result_t`, illustrative shape (not literal file contents, decision-encoding only):
  ```
  typedef enum {
      LIAISON_VALID = 0,
      LIAISON_ALREADY_CONNECTED,
      LIAISON_TOO_FAR,
      LIAISON_BLOCKED_BY_PLANET,
      LIAISON_CROSSES_ROUTE,
  } liaison_reason_t;

  typedef struct {
      liaison_reason_t reason;
      int blocking_planet; /* galaxy index, or -1 */
      int blocking_route;  /* index into routes[], or -1 */
  } liaison_result_t;
  ```
  `to_index` is `-1` when the live target is not a hovered planet (raw cursor world position instead, `to_pos` populated via the new screen→world inverse) — this makes "already connected" structurally impossible to fire against a non-planet target (no route endpoint ever equals `-1`), matching source's own object-identity comparison (`w:eb(self.qu)==self.re`) without needing an explicit branch for it.
- **Pure hit test**: `liaison_pick_planet(int screen_x, int screen_y, const galaxy_t *galaxy, int pick_radius_px) -> int` (planet index or `-1`) — operates in **screen-pixel space**, reusing the existing `screen_map_planet` (world→screen, already established) per planet rather than requiring a new inverse for picking itself; `pick_radius_px` is a v1 UX-tuning constant (like `CURSOR_STEP`/`CLICK_FLASH_FRAMES`), not a §5-traceable value. This is new interaction infrastructure this port has needed since `psx-simulated-click` explicitly deferred it ("nothing in this port has planet hit-testing yet") — added here because this is the first step that actually needs to know "which planet is under the cursor."
- **New screen→world inverse**: `screen_map_unproject(int x, int y) -> planet_pos_t`, added to `screen_map.h`/`screen_map.c` as the algebraic inverse of the existing `screen_map_axis` (same `int64_t`-intermediate, `PLANETGEN_PLACEMENT_MIN`/`SPAN`/`SCREEN_MAP_MARGIN` conventions, run in reverse). Needed so the live held-frame validity check has a real world-space position to evaluate when no planet is hovered, mirroring `jc:hq`'s `{ra=mp,p=mp/128}` fallback — without it, the "too far" check could only ever be demonstrated planet-to-planet, not "drag past the max range into empty space," which is real, sourced, live behavior worth keeping.
- **Pure drag-state machine**, mirroring `cursor_step`'s exact shape (a pure function from previous state + inputs to next state):
  ```
  typedef struct {
      int dragging;             /* 0/1 */
      int from_index;           /* source planet, valid only while dragging */
      int hover_index;          /* -1 if not hovering a planet */
      liaison_result_t live;    /* recomputed every held frame */
      liaison_result_t last;    /* final outcome, one frame, after release */
      int last_valid_frames;    /* countdown, visual-only, mirrors click_flash_frames */
  } liaison_drag_state_t;

  liaison_drag_state_t liaison_drag_step(liaison_drag_state_t prev,
                                          cursor_state_t cursor,
                                          const galaxy_t *galaxy,
                                          const liaison_route_t *routes, int route_count);
  ```
  Logic: not dragging + `cursor.click_pressed` + `liaison_pick_planet(cursor.x, cursor.y, ...)` resolves to a real planet → start dragging from it. Dragging + `cursor.click_held` → re-run the hit test and `liaison_check` every call, updating `live` continuously (mirrors `jc:hq` running unconditionally every held frame). Dragging + `cursor.click_released` → one final `liaison_check` at the release-time target, copied into `last`/`last_valid_frames`, `dragging` cleared, **no route ever written anywhere** (previous decision). Dragging + neither `click_held` nor `click_released` this frame (the mode-toggled-off-mid-hold case `cursor.c` already documents as producing no synthesized release) → silently cancel: `dragging` cleared, no `last` outcome shown (there is no meaningful "result" for a gesture that was interrupted, not concluded) — a new, port-specific edge case source itself cannot have (PICO-8 has no mouse-mode toggle), resolved conservatively (cancel, no persisted effect, no spurious feedback) rather than left undefined.
- **Stateful wrapper**, mirroring `cursor_update`/`cursor_get_state`'s flat-statics convention exactly: `liaison_init(void)`, `liaison_update(cursor_state_t cursor)` (calls `world_get_galaxy()` internally and threads the module's own static, currently-always-empty `g_routes`/`g_route_count`), `liaison_get_state(void) -> liaison_drag_state_t`. `game_update.c` gains exactly one line: `liaison_update(cursor_get_state())`, called after `cursor_update`.
- **Rendering**: `game_draw.c` gains one new block, gated on `liaison_get_state().dragging`, drawing a single `LINE_F2` from the source planet's screen position (`screen_map_planet`, already used for every other primitive) to the current live target's screen position (the hovered planet's screen position, or the cursor's own `x`/`y` directly when no planet is hovered — no unprojection needed for rendering the raw-cursor case, only for the validity math), reusing the exact `setLineF2`/`setXY2`/`setRGB0`/`DrawPrim` pattern Phase 1 step 4 already established for synthetic slipway lines. Color: green-ish when `live.reason == LIAISON_VALID` or `LIAISON_ALREADY_CONNECTED`, red-ish otherwise — a v1 UX color choice, not traced art (same framing as the click-flash yellow). No sound (no SPU yet, Phase 5).

**Fixed-point compliance.** All geometry (`liaison_point_blocks_segment`'s dot products and squared-length comparisons, `liaison_segments_cross`'s cross-product orientation tests, `screen_map_unproject`'s inverse) is Q16.16 via `fixed.h`'s existing `fixed_t`/`fixed_add`/`fixed_sub`/`fixed_mul`, with `int64_t` intermediates wherever a product could overflow `int32_t` (mirroring `screen_map_axis`'s already-documented overflow reasoning) — no `float`/`double` at runtime, matching every other module in this codebase.

## Implementation Chunks

Tracer-bullet order, pure logic before wiring before rendering before the real emulated proof:

1. **§5 geometry core.** `liaison.h`/`liaison.c` gain `liaison_point_blocks_segment`, `liaison_segments_cross`, `liaison_check` (all four outcomes: valid, already-connected, too-far, blocked-by-planet, crosses-route, including the too-far short-circuit and the planets-before-routes reporting order), `liaison_route_t`, and the traced constants (`LIAISON_RANGE_SQ`, the `0.0032` block tolerance, the `0.01`/`0.99` margins). Host-tested (`host_tests/liaison_test.c`, new `test-liaison` target) against hand-built galaxy/route fixtures — not Phase 1's synthetic benchmark lines. No wiring, no rendering.
2. **Hit test + screen↔world inverse.** `liaison_pick_planet` (liaison.c) and `screen_map_unproject` (screen_map.c/h). Host-tested: pick returns the correct index within radius and `-1` outside it / with overlapping picks resolved deterministically (nearest wins); unproject round-trips against `screen_map_planet` within a small fixed-point tolerance across a spread of galaxy positions.
3. **Drag state machine.** `liaison_drag_step` and its types. Host-tested with hand-built `cursor_state_t` sequences (mirroring `cursor_test.c`'s press/hold/release sequence style): press-on-planet starts a drag; held recomputes `live` every call as a hand-fed cursor position changes, covering all four `liaison_check` outcomes; release finalizes `last` and clears `dragging`; release never writes to any route list; the interrupted-hold (mode-off-mid-drag) cancel path produces no `last` outcome.
4. **Stateful wrapper + real wiring.** `liaison_init`/`liaison_update`/`liaison_get_state` (still fully host-testable — `liaison_update` takes the already-pure `cursor_state_t`, no PSX header needed); `game_update.c`'s one-line call site. Host tests extended: an `liaison_update`/`liaison_get_state` round trip reproduces `liaison_drag_step`'s result, mirroring `cursor.c`'s own round-trip test.
5. **Rendering.** `game_draw.c`'s new preview-`LINE_F2` block. Verified via `make psx-slipways-screenshot-pcsx` (manual/scripted drag) and the still-unmodified `psx-slipways-boot-test-pcsx`.
6. **Headless PCSX drag-injection test.** New `tools/gen_pcsx_slipways_liaison_test_lua.py` + `tools/boot_test_psx_slipways_pcsx_liaison.sh` + `psx-slipways-liaison-test-pcsx` target (new target, unlike `psx-simulated-click`'s in-place extension — this is a genuinely new module/symbol set, not an extension of `cursor.c`'s existing test binary): injects real Circle press/hold/release plus D-pad movement while held, reads back `liaison.c`'s wired statics (`dragging`, `from_index`, `hover_index`, `live.reason`, `last.reason`) from guest RAM, and asserts the live `reason` field actually changes as the drag target moves across at least one threshold (e.g. dragging far enough to flip from valid to too-far), proving the real, wired, per-frame recomputation — not just that the module compiles and links.

## Testing Decisions

- **What makes a good test here**: assert on observable output through public functions/exported symbols (the `liaison_result_t`/`liaison_drag_state_t` fields, the flat statics the PCSX harness reads), never on internal representation. Same standard every prior PRD in this codebase has used.
- **Fully host-testable** (chunks 1-4, `gcc`, no PSn00bSDK toolchain): `liaison_check` and its two geometry primitives, `liaison_pick_planet`, `screen_map_unproject`, `liaison_drag_step`, and the stateful wrapper (`liaison_update` takes `cursor_state_t` and calls `world_get_galaxy()`, both already host-buildable). New `host_tests/liaison_test.c`, new `RULES_LIAISON_TEST_HOST_SRCS`/`test-liaison` Makefile target, same shape as `test-planetgen`/`test-cursor`/`test-rules-planets`; `test-liaison` added to `test`'s prerequisite list and `.PHONY`, per `CLAUDE.md`'s `make test` promise. `screen_map_unproject`'s round-trip cases are added to the existing `host_tests/screen_map_test.c` rather than a new file (same module).
- **Test fixtures for "crosses an existing route"**: hand-built `liaison_route_t[]` arrays constructed directly in `liaison_test.c` (a segment definitely crossing the candidate, a segment definitely not, a segment sharing an endpoint but not crossing) — the same hand-built-fixture style `planetgen_test.c`/`cursor_test.c` already use, explicitly **not** `world.c`'s synthetic benchmark slipway edges (`slipway_bench.h`), which are fake geometry with no game meaning and a different type (`slipway_edge_t`, not `liaison_route_t`) by design.
- **Not host-testable**: `game_draw.c`'s new `LINE_F2` block (real `psxgpu.h` calls) and the `game_update.c` one-line call site (trivial, covered indirectly by boot-not-crashing). Verified instead by `psx-slipways-boot-test-pcsx` (unmodified — confirms boot survives the new per-frame drag logic) and `psx-slipways-screenshot-pcsx` (visual sanity check of the color-coded preview line).
- **New PCSX headless test** (chunk 6, `psx-slipways-liaison-test-pcsx`): a genuinely new target/generator/script, not an extension of `psx-slipways-cursor-test-pcsx` (unlike `psx-simulated-click`'s in-place extension of `cursor.c`'s own existing test) — justified because this exercises a different module's new symbols end-to-end (drag state, hit-test result, live/last validity reason), not a variation on cursor edge detection. Reuses `readS32`/`waitFrames`/`assertEq`/`press`/`waitForBoot` from the existing PCSX Lua harness conventions unchanged; adds D-pad-hold-while-Circle-held movement (already possible — `cursor.c`'s D-pad movement already works while mouse mode is on, and nothing about this step changes that) to actually move the live drag target across a validity threshold during a single held gesture, which is the one thing a host test cannot prove (real per-frame timing under the real emulated loop).
- **Prior art reused**: `host_tests/t.h`'s PASS/FAIL harness; `planetgen_test.c`/`cursor_test.c`'s hand-built-fixture style; `cursor_test.c`'s press/hold/release sequence-of-`cursor_step`-calls pattern, directly extended to `liaison_drag_step`; `psx-simulated-click`'s PCSX Lua harness conventions (`readS32`, `waitFrames`, `assertRange`, settle-and-check level assertions) for chunk 6.

## Out of Scope

- **Colonization gating of drag-start/drag-end** (`jo:ldown`'s `"ly"` requirement, `jo:gv`'s `"ly"` requirement). No colonization state exists in this port yet (Phase 3 step 10). This step's live wiring treats every planet as a valid geometric candidate on both ends — see Implementation Decisions for the full source-backed justification. Step 10 is expected to add the real eligibility gate at the commit boundary.
- **Ever writing a route into persistent state.** No commit ever happens in this step, regardless of the live validity result — see Implementation Decisions. The introduced route list stays empty throughout this step's own scope.
- **Cost (`dj`/`bk`) and affordability (`fm:lu`/`d_`)** — `jc:ce()` itself doesn't check either; both are layered on top in source and belong to Phase 3 step 13 (`rules_economy.c`). No credit/currency state exists in this port yet.
- **Slipgate/Infragate 3-connection cap and infragate mt=1 crossing exception** (§5/§6) — structures don't exist in this port yet (Phase 4 step 15). This step's route-crossing check is correctly a no-op on the `mt` type filter for now, not a simplification.
- **Any sound/audio feedback** (source's negative sound on an invalid drag, positive sound-adjacent feedback on commit) — no SPU/audio system exists yet (Phase 5 step 19).
- **Trade flow, colony growth, or any economic consequence of a slipway existing** — `effects.c` (step 11) and `rules_economy.c` (step 13); moot anyway since no route ever persists in this step.
- **Right-mouse-button/camera-pan interactions during a drag** — no camera system exists (per `psx-mouse-mode-cursor`'s already-settled finding, unrevisited here).
- **Multi-touch/simultaneous multiple drags** — the source mechanic itself is single-drag (one `held` target per button), and PSX has one Circle button; not applicable.
- **Wormhole-as-endpoint, Slipgate/Infragate-as-endpoint** — those node types don't exist in this port yet (Phase 4 step 15); only the 90 generated planets are ever valid `liaison_pick_planet` results.
- **Changing `cursor.h`/`cursor.c` in any way** — this step is a pure consumer of the existing `cursor_get_state()` interface; no new fields, no signature changes.
- **A `main.c` change beyond `game_update.c`'s new one-line call** — no new `game_init` wiring needed beyond what `liaison_init()` requires alongside the existing `cursor_init()`/`world_init()` calls.

## Further Notes

- **Why this step, not `psx-simulated-click`, adds hit-testing**: `psx-simulated-click`'s Out of Scope explicitly named "world-space hit-testing... nothing in this port has planet hit-testing yet" as deferred, with no owner named. This step is the first (and, per the plan, only Phase-3-scoped) consumer that actually needs to know "which planet is under the cursor," so it's the natural, and only currently-justified, place to add it. A future step needing the same primitive (e.g. probe-launch aiming, `rules_discovery.c`) can reuse `liaison_pick_planet` directly or, if it turns out multiple modules need it, it's a one-file move to promote it — not decided here, since only one real caller exists today.
- **Where Phase 3 step 10 should plug in**: two concrete extension points, both already shaped for it — (1) a colonization-eligibility check at `liaison_drag_step`'s press-to-start-dragging and release-to-finalize decision points (today: any planet; after step 10: only colonized planets, on both ends, matching `jo:ldown`/`jo:gv`), and (2) the actual `liaison_route_t` write on a valid, eligible commit, which today never happens. Neither requires changing `liaison_check`'s or `liaison_pick_planet`'s own signatures — only the state machine's decision logic and the (currently inert) route-list writes.
- **Why `l_>0.01`/`l_<0.99` and `0.0032` are duplicated locally rather than imported from anywhere**: they're literal constants inline in `jc:ce()`/`be()`'s call site in source, not named/exported anywhere in `pico8/lua.lua` itself — this step names them locally in `liaison.h`, following the exact "local, doc-commented, traced-by-citation" convention `cursor.h`'s `CURSOR_PAD_*` constants and `world.h`'s `WORLD_NEIGHBOR_RANGE_SQ`/`WORLD_MIN_DIST_SQ` already established.
- **A genuine new port-specific behavior worth flagging explicitly**: the "mode toggled off mid-drag" cancel path (Implementation Decisions, drag-state machine) has no source equivalent — PICO-8 has no mouse-mode toggle to interrupt a drag with. It's resolved the same conservative way `psx-simulated-click` resolved the structurally identical "mode toggled off mid-hold" case for `click_released` itself: silent cancel, no synthesized outcome, no persisted effect. Anyone touching `liaison_drag_step` later should keep this consistent with that precedent rather than re-deriving a different rule.
- **Recommended, not part of this PRD** (consistent with this project's established practice of flagging design-doc corrections without making them here): `docs/design/slipways-mechanics.md` §5 could gain a one-line note that its `0.5`/`1.08`/`0.0032` figures are squared-distance quantities in source (`#v` = squared magnitude), the same clarification `WORLD_NEIGHBOR_RANGE_SQ`'s own comment already carries for the probe-range pair, so a future reader doesn't have to rediscover the `km.__len` fact this PRD's research surfaced.
