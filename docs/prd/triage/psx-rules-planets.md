## Problem Statement

`docs/plan.md` Phase 3 ("Vertical slice") step 8 calls for `rules_planets.c` : "types de planètes + jobs de colonisation réduits" — the first step of Phase 3 to add real gameplay *rules content* (Phases 1-2 were pure infrastructure: generation, rendering, input). Nothing in `psx-slipways/` currently models a planet's type or what a colonized planet can produce: `planetgen.c` (Phase 1 step 2) deliberately produces positions only, because the PICO-8 source itself doesn't assign a planet's type at generation time — it draws the type later, at probe-discovery time (`jo:hh`, confirmed in `docs/prd/psx-planet-generation.md`'s own findings). The full design doc (`docs/design/slipways-mechanics.md` §8) documents 10 planet types and ~24 colonization jobs (plus 4 planet-transform actions and 7 non-colonizable structures) — porting all of it now would pull Phase 4 step 14's explicitly-scoped work ("Étendre `rules_planets.c`/`rules_tech.c` à l'ensemble des 10 types de planètes, spécialisations et 20 technologies documentées") forward, which the plan's own phrasing treats as intentionally deferred, not an oversight. What's missing is a *deliberately reduced but fully faithful* subset: real types, real jobs, real formulas (cost, production-by-level), traced to source, small enough to review and test completely, but substantial enough that Phase 3's remaining steps (`liaison.c` slipway validity, `rules_discovery.c` probe/type-draw, `effects.c` trade-flow animation, `rules_tech.c` tech gating, `rules_economy.c` trade/maintenance/score) have real, non-trivial data to operate on once they're built.

## Solution

Add `psx-slipways/rules_planets.h`/`rules_planets.c`: a pure, host-testable C module (no PSX headers, no dynamic allocation, Q16.16 fixed-point where any non-integer value is involved — same conventions `planetgen.c`/`fixed.h`/`rng.h` already established) exposing static data tables for **3 of the 10 documented planet types** (earth-like, forgeworld, mineral) and **5 of the ~24 documented colonization jobs** (hiveworld, agroworld on earth-like; nanotech, bots on forgeworld; mine on mineral) plus pure lookup/formula functions (job cost with both traced tech multipliers, production-by-colony-level via the traced growth curves). The 5-job subset is not an arbitrary sample: it is chosen because it forms exactly one closed resource loop (people → ore → tech (+ore) → bots → food → people) — every resource any included job *needs* is produced by another included job, and every resource an included job *produces* is needed by another included job. This gives later Phase 3 steps a genuinely working, self-sufficient miniature economy to connect via slipways and simulate, rather than a a la carte scattering of unconnected jobs. Every constant used (planet rarity, job cost, needs, produce, curve, tech gate) is traced to `pico8/lua.lua`'s `fd`/`df`/`hc` unstash tables (re-decoded directly from `map.json` in this PRD's own research, not taken on faith from the design doc's prose — see Implementation Decisions). Nothing outside this reduced set is invented or approximated: every included job's formula is the real, full source formula (not a simplified stand-in), and everything left out is explicitly logged as deferred to Phase 4 step 14 (types/jobs) or Phase 4 step 15 (the 4 transform/destroy actions and 7 structures), per the plan's "pas de contenu retiré silencieusement" guardrail. Like `planetgen.c` at Phase 1 step 2, this module is **not wired into `game_init`/`game_update`/`game_draw`** — it has no caller yet, and won't until `rules_discovery.c` (step 10) needs to assign a drawn type to a planet and `liaison.c`/`rules_economy.c` (steps 9/13) need to look up job data for a colonized planet.

## Implementation Decisions

**Source-fidelity findings (re-decoded directly from `pico8/lua.lua` + `map.json`, not taken from the design doc's prose alone):**

- **The design doc's §8 job table was independently re-verified against source and found accurate**, but re-decoding surfaced two genuine extra fields the doc's table doesn't show a column for: `il` (a tech-gate name, e.g. `"xenofoods"`) and `dm` (a "default need" resource code). Re-running the project's established decode command (`docs/design/slipways-mechanics.md`'s Annexe A `jq` recipe) against `unstash(8494)` (`fd`, the raw job table) reproduces the doc's rows exactly, plus these extra positional fields, e.g. `o("agroworld","e",5,"-","b","f","xenofoods","l")` — name, planet code, cost, curve, needs, produce, **tech gate `"xenofoods"`, default-need `"l"` (organics)**. Field order was cross-checked against `hp.mr` (`pico8/lua.lua:1400`, `o("px","lr","fj","ja","i","o","il","dm")`), the literal positional-field-name list the source itself uses to parse these records.
- **A single finding not stated anywhere in the design doc's prose**: the job-cost tech surcharge (×1.5) and the job's curve-upgrade (its curve's `mc` target, e.g. "-" → "+") are gated by **the exact same condition** in source — `self.il and oj(self.il)` — read identically in both `hp:od()` (cost, `pico8/lua.lua:1426-1433`) and `hp:po()` (curve, `pico8/lua.lua:1422-1425`). The design doc's §8 table only calls out the cost effect for `colony` (ocean/xeno) and only its §9 closing paragraph calls out the curve effect for `agroworld`/`algae` — nowhere does it state these are the *same trigger*. This module ports that as one shared boolean parameter per job (`job_tech_researched`), not two independently-plausible-but-wrong flags, because that's what the source actually does.
- **Planet-type table (`df`, `pico8/lua.lua:1377-1389`, unstash-free — the type table itself is inline in the minified source, unlike `fd`/`hc`/`dr`/`nb` which are `unstash()`-hidden text)**: fields are `px` (code), `s` (a sprite/palette id — rendering-only, no gameplay meaning, not ported here), `r` (rarity weight), `d` (display name). Rarity values for the 3 included types, read directly: earth-like `r=4.5`, forgeworld `r=6`, mineral `r=4` — matching `docs/design/slipways-mechanics.md` §3's table exactly (no discrepancy found for these three).
- **Curve tables (`hc`, unstash 8383, already fully decoded in the design doc's §9 table and Annexe A, re-verified, no discrepancy)**: `-` = `[1,2,3,3]` (levels 1-4, with an `mc` upgrade target of `+`), `+` = `[2,3,4,4]` (no upgrade target). Both curves used by this step's 5-job subset (mine/nanotech/agroworld use `-`; bots/hiveworld use `+`) — the other 4 documented curve shapes (`f-`, `f+`, `qh`, `qh+`) belong exclusively to structures (Laboratory, Food processor, Ascension Gate — §6, deferred, see Out of Scope) and are not ported here.
- **The job-cost formula's `nanomaterials` discount (×0.85) is global** — traced to `hp:od`'s `if not self.ii and oj("nanomaterials") then od*=0.85 end`, where `self.ii` is only set (truthy) on the 4 transform/destroy actions (`mechanize`/`terraform`/`collapse`/`harvest`, which encode a numeric `ii` sound-effect/flag id instead of the `il` tech-name field regular jobs use — confirmed by the raw `fd` dump, e.g. `o("mechanize","mrsoijx",20,ii=38,go="f")`). Since none of this step's 5 jobs are transform actions, the discount applies uniformly to all 5 when the flag is set.

**Module shape and non-wiring, mirroring `docs/prd/psx-planet-generation.md`'s established precedent for "nothing downstream exists yet":**

- `rules_planets.c` is a **pure data + pure function module**: static `const` tables for the 3 planet types and 5 jobs, plus stateless lookup/formula functions. No `struct` it defines is mutable process-wide state; every function takes its inputs as parameters (including the two tech-researched booleans) and returns a value, exactly the "generic, caller-supplies-the-state" shape `planetgen.c`'s injected-RNG precedent and `world.c`'s "first production caller of a traced constant" precedent both already established.
- **Not wired into `game_init()`/`game_update()`/`game_draw()`.** Same reasoning as `planetgen.c` at Phase 1 step 2: nothing downstream can consume this data yet — no planet in `world.c`'s galaxy has a type field (per `docs/prd/psx-planet-generation.md`'s own finding, type assignment happens at probe-discovery time in source, which is Phase 3 step 10's job, not this step's), no colony/liaison state exists to hold "which job did the player pick for this planet," and no tech state exists to supply real values for the `job_tech_researched`/`nanomaterials_researched` booleans (that's step 12, `rules_tech.c`). Wiring this module's data into live galaxy state is explicit follow-on work for step 10 (assigning a drawn type) and steps 9/13 (looking up a job's formula once a planet is actually colonized) — not this PRD.
- **File layout, `psx-slipways/` (flat, picked up by the existing `file(GLOB _sources *.c)` in `psx-slipways/CMakeLists.txt`, so it compiles into the real PSn00bSDK cross-build unused, exactly like `planetgen.c` did before Phase 1 step 4 wired generation in)**:
  - `rules_planets.h` / `rules_planets.c` — the module itself.
  - `host_tests/rules_planets_test.c` — host tests (see Testing Decisions), following the established `host_tests/` exclusion-from-cross-build convention.

**Data model:**

- `resource_id_t` enum — **only the 7 resources this step's 5 jobs actually touch**: `RESOURCE_PEOPLE`, `RESOURCE_ORE`, `RESOURCE_TECH`, `RESOURCE_BOTS`, `RESOURCE_FOOD`, `RESOURCE_GOODS`, `RESOURCE_ORGANICS`, plus a `RESOURCE_NONE` sentinel (used for "no default need"). The other 4 named resources (`luxury`, `science`, `energy`, `joy`) and the joker resource (`?`) are not represented — every job that touches them is itself part of the deferred subset (see Out of Scope), so adding resource IDs nothing can produce or consume yet would be dead enum values, not real content.
- `planet_type_id_t` enum — `PLANET_TYPE_EARTHLIKE`, `PLANET_TYPE_FORGEWORLD`, `PLANET_TYPE_MINERAL`. A static `const planet_type_t g_planet_types[PLANET_TYPE_COUNT]` table holds each type's traced display name and rarity (`fixed_t`, since `4.5` is not integral — Q16.16, not `float`, per the project's established convention).
- `colonization_job_id_t` enum — `JOB_HIVEWORLD`, `JOB_AGROWORLD`, `JOB_NANOTECH`, `JOB_BOTS`, `JOB_MINE`. A static `const colonization_job_t g_jobs[JOB_COUNT]` table holds, per job: which `planet_type_id_t` it's available on, base cost (plain `int` credits — source costs are always whole numbers), a small fixed-size `needs[]` array (1 or 2 `resource_id_t` entries, in source order) with a count, the single `produces` resource, which `curve_id_t` (`CURVE_MINUS`/`CURVE_PLUS`) governs its production, an optional `tech_gate` (a name string, or `NULL` if the job has none — only `agroworld`'s is set, to `"xenofoods"`), and an optional `default_need` (`RESOURCE_NONE` if the job has none — `hiveworld` → `RESOURCE_GOODS`, `agroworld` → `RESOURCE_ORGANICS`, the other 3 jobs have none).
- **The concrete 5-job data** (all traced above): `mine` (mineral, cost 5, needs `[PEOPLE]`, produces `ORE`, curve `-`, no tech gate, no default need); `nanotech` (forgeworld, cost 8, needs `[ORE]`, produces `TECH`, curve `-`, no tech gate, no default need); `bots` (forgeworld, cost 8, needs `[ORE, TECH]`, produces `BOTS`, curve `+`, no tech gate, no default need); `agroworld` (earth-like, cost 5, needs `[BOTS]`, produces `FOOD`, curve `-`, tech gate `"xenofoods"`, default need `ORGANICS`); `hiveworld` (earth-like, cost 5, needs `[FOOD]`, produces `PEOPLE`, curve `+`, no tech gate, default need `GOODS`).
- **The closed loop this forms**: `mine` needs `PEOPLE` (produced by `hiveworld`) → produces `ORE` (needed by `nanotech` and `bots`) → `nanotech` produces `TECH` (needed by `bots`) → `bots` produces `BOTS` (needed by `agroworld`) → `agroworld` produces `FOOD` (needed by `hiveworld`) → `hiveworld` produces `PEOPLE`, closing the cycle. Every need has a producer within the subset and every product has a consumer within the subset — this is the load-bearing property that makes the 5-job cut a genuine "vertical slice" rather than five disconnected formulas, and it's asserted by a dedicated test (see Testing Decisions / Implementation Chunks).

**Formulas (both fully implemented and tested, not approximated, even though no live caller exists yet for the "researched" flags):**

- `int rules_planets_job_cost(colonization_job_id_t id, bool job_tech_researched, bool nanomaterials_researched)` — ports `hp:od()` exactly: start from the job's base cost; if the job has a `tech_gate` **and** `job_tech_researched` is true, multiply by `1.5`; if `nanomaterials_researched` is true, multiply by `0.85` (unconditionally — all 5 jobs are ordinary colonization jobs, never transform actions, so this always applies); floor to an integer. Computed in Q16.16 fixed-point (`fixed_mul` chained twice, then truncated once at the end via an arithmetic right-shift — matching PICO-8's own internal number representation, which is itself Q16.16, giving this port unusually exact arithmetic fidelity, not just "close enough" integer math), never `float`. The two booleans are ordinary parameters, not hidden global tech state — this step defines and tests the full formula (both flags true, both false, and each individually) so that whichever step first has real tech state (`rules_tech.c`, step 12) only has to supply values, not rederive the formula.
- `int rules_planets_curve_value(curve_id_t curve, int level, bool upgraded)` — the generic curve-lookup primitive: clamps `level` to `[1,4]` (returning `0` for `level < 1`, i.e. an unfounded colony produces nothing, per §9 point 1), looks up the traced per-level table, and if `upgraded` is true **and** `curve == CURVE_MINUS`, looks up `CURVE_PLUS`'s table instead (the `mc` mapping — the only upgrade path any curve in this subset has; `CURVE_PLUS` has no `mc` target to port, and this is not a limitation this step invents, it's what source does for these two curves).
- `int rules_planets_job_production(colonization_job_id_t id, int level, bool job_tech_researched)` — the per-job convenience wrapper mirroring `hp:po()`: resolves the job's `curve_id_t` and whether its `tech_gate` is both present and `job_tech_researched`, then calls `rules_planets_curve_value`. Reuses the exact same "has a tech_gate and it's researched" condition `rules_planets_job_cost` uses, rather than two subtly different gating checks — this is the API surface expressing the shared-trigger finding above as code, not just prose.
- `const planet_type_t *rules_planets_type(planet_type_id_t id)` / `const colonization_job_t *rules_planets_job(colonization_job_id_t id)` — plain accessors into the static tables, for later steps (discovery's type draw will need rarity; liaison/economy will need a colonized planet's job data) to read without duplicating the tables.

**The `default_need` (`dm`) field is captured as static data but its dynamic *application* is out of scope for this step.** Per §8's "repli automatique" rule, a job's `dm` resource is meant to be auto-added to a live colony's requested-needs list at population level 1 — but that requires a live colony/needs-list model that doesn't exist anywhere in the codebase yet (no `liaison.c`, no per-planet colonization state). Storing `dm` on the job table now (rather than omitting the field entirely) means whichever future step models live colony state doesn't have to re-decode `fd` to recover it. Which step actually applies it is intentionally not decided here (see Out of Scope) — most likely `rules_economy.c` (step 13), since applying a default need is tied to the same per-tick colony simulation that step already owns (§9's level-target calculation, `dh`), but this PRD doesn't commit that decision on step 13's behalf.

## Implementation Chunks

Tracer-bullet order — each chunk is independently testable and the anchor property (a genuinely closed vertical-slice economy) is reached by chunk 5, not assumed from the start:

1. **Static data tables** (`planet_type_t`/`colonization_job_t` structs, the 3-type and 5-job `const` tables, plain accessor functions). Tests: every traced field (rarity, cost, needs, produce, curve, tech_gate, default_need) for all 3 types and all 5 jobs matches the source-decoded values in Implementation Decisions exactly — this chunk is pure data-entry correctness, no formulas yet.
2. **Curve lookup primitive** (`rules_planets_curve_value`). Tests: exact per-level values for both curves at levels 1-4 (`[1,2,3,3]` for `-`, `[2,3,4,4]` for `+`); `level < 1` returns `0`; `upgraded=true` on `CURVE_MINUS` returns the `CURVE_PLUS` table's values instead; `upgraded=true` on `CURVE_PLUS` is a no-op (returns the same values as `upgraded=false`, since `+` has no upgrade target in this subset).
3. **Job cost formula** (`rules_planets_job_cost`). Tests: a job with no `tech_gate` (`mine`) is unaffected by `job_tech_researched` in either state; a job with a `tech_gate` (`agroworld`) costs its base value when `job_tech_researched=false` and `1.5×` (floored) when `true`; `nanomaterials_researched=true` applies `0.85×` (floored) independent of the job-tech flag; all four boolean combinations are exercised for `agroworld` (the only in-subset job with both a tech gate and the global discount interacting).
4. **Job production wrapper** (`rules_planets_job_production`). Tests: each of the 5 jobs at levels 0-4 with `job_tech_researched=false`, matching each job's base curve table exactly; `agroworld` specifically re-tested with `job_tech_researched=true`, confirming its output switches to the `+` curve's values (proving the shared cost/curve gating finding above is actually wired correctly, not just documented).
5. **Closed-loop structural regression test.** Walks the 5-job table and asserts: every `resource_id_t` appearing in any job's `needs[]` is `produces` by at least one other job in the table, and every `resource_id_t` appearing as some job's `produces` is needed by at least one other job in the table. This is the concrete "genuine vertical slice, not five disconnected formulas" property this PRD's whole scoping argument depends on, made into an automated check rather than an assertion in prose — a future edit that breaks it (e.g. changing a job's `needs` without checking downstream effects) fails loudly here instead of silently degrading whatever later step first tries to build a live economy on top of this data.

## Testing Decisions

- **What makes a good test here**: assert on this module's observable output (table field values, formula results for given inputs) — never on internal representation details (enum integer values, table array order, whether the tables are `static` vs. exported). This mirrors `planetgen_test.c`'s and `world_test.c`'s existing style of testing behavior through public functions/data, not internals.
- **Modules tested**: `rules_planets.c` (all public data and functions, per the chunk breakdown above). No new shared infrastructure is needed — `fixed.h` (Q16.16 arithmetic) and `host_tests/t.h` (the existing PASS/FAIL harness) are reused as-is, exactly as `world_test.c` and `cursor_test.c` already do.
- **Prior art reused**: `host_tests/planetgen_test.c`'s pattern of testing traced constants against hand-computed expected values (not re-deriving the formula inside the test); `host_tests/world_test.c`'s pattern of a "first production caller" module consuming already-tested primitives without re-testing their internals.
- **Host test invocation**, following `test-planetgen`/`test-galaxy-render`/`test-cursor`'s exact established pattern in the top-level `Makefile`:
  - A new `RULES_PLANETS_TEST_HOST_SRCS` var (`psx-slipways/rules_planets.c psx-slipways/host_tests/rules_planets_test.c`) and `test-rules-planets` target, compiling and running with the host's native `gcc` (`-std=c11 -Wall -Wextra -I psx-slipways`), output under the existing shared `psx-slipways/build-host/` directory.
  - `test`'s prerequisite list gains `test-rules-planets` (alongside the existing `test-planetgen test-galaxy-render test-cursor`), and `test-rules-planets` is added to `.PHONY`, so `CLAUDE.md`'s "use `make test` to verify changes" instruction keeps covering this new code, matching every prior PSX-side PRD's own reasoning for why this is non-optional.
- **Not tested here**: anything requiring the PSn00bSDK toolchain or PCSX-Redux/Mednafen (no PSX-side behavior exists to boot-test — nothing is wired into `game_init`); planet-type *assignment* to a specific galaxy planet (Phase 3 step 10's job); tech-researched state actually flowing from a real tech system (Phase 3 step 12's job); any job/type/structure/transform-action outside this step's 3-type/5-job subset (deferred, see Out of Scope).

## Out of Scope

- **7 of the 10 documented planet types**: ocean, remnant, xeno, jungle, iceball, barren, gas giant — and their full job rosters (`colony` ×2, `strip`, `algae`, `breed` ×2, `hunt`, `dismantle`, `scavenge`, `farm`, `habitat`, `genefarm`, `excavate` ×2). Deferred to `docs/plan.md` Phase 4 step 14 ("Étendre `rules_planets.c`... à l'ensemble des 10 types de planètes"), per the plan's own explicit phrasing.
- **The remaining jobs on the 3 included types**: `goods`, `gadgets`, `uplift` (forgeworld); `luxury`, `tourism` (earth-like). Also deferred to Phase 4 step 14 — these types are included, but not every job available on them is.
- **The 4 planet-transform/destroy actions**: `mechanize`, `terraform`, `collapse`, `harvest`. Explicitly named in `docs/plan.md` Phase 4 step 15 ("les actions de transformation de planète (mechanize/terraform/collapse/harvest)"), so this is a plan-driven exclusion, not one this PRD invents. Confirmed structurally distinct from regular jobs in source too (they use a numeric `ii` field and a `go`/`cw` result-type field instead of the regular `il`/`dm` fields regular colonization jobs use).
- **The 7 non-colonizable structures** (Laboratory, Food processor, Slipgate, Infragate, Trading Hub, Synthesizer, Ascension Gate) and the Protostar. `docs/design/slipways-mechanics.md` §6; also Phase 4 step 15 territory (structures are placed via the dynamic neighbor-graph-insertion mechanism that step reuses from Phase 1-2's wormhole placement, which doesn't exist as a live mechanic yet either).
- **The 4 curve shapes exclusive to structures** (`f-`, `f+`, `qh`, `qh+`) and the Food-processor `f-`→`f+` / Laboratory `qh`→`qh+` tech upgrades (`xenofoods`/`superhuman ai`). Only `-`/`+` are ported, since only those two are used by this step's 5-job subset.
- **4 of the 11 named resources** (`luxury`, `science`, `energy`, `joy`) and the joker resource (`?`), plus the design doc's own flagged-`Incertain` 13th resource key `a`. None of this step's 5 jobs touch them; they arrive with whichever future jobs/structures need them.
- **Dynamic application of the `default_need` (`dm`) field** (auto-adding it to a live colony's requested-needs list at population level 1, §8's "repli automatique" rule). ## Further Notes

- The single highest-value finding from re-decoding `fd` directly (rather than trusting the design doc's §8 table's column set as complete): jobs carry two extra fields the doc's table doesn't show — `il` (tech gate) and `dm` (default need) — and the tech-gate field drives **both** the cost surcharge (§8's row text) **and** the curve upgrade (§9's closing paragraph) off the *same* boolean condition in source, a connection the design doc states in two separate places without ever calling out that they're the same trigger. Anyone extending this module in Phase 4 step 14 to the remaining jobs (several of which — `colony` on ocean/xeno, `algae` — also carry `il`) should reuse this module's `job_tech_researched`-as-single-shared-flag shape rather than re-deriving two independent flags per job.
- The 5-job "closed loop" property (§ Implementation Decisions) is deliberately a stronger bar than the task's minimum ("enough that later steps have real data") — it was chosen because a genuinely self-sufficient miniature economy is strictly more useful to `liaison.c`/`rules_discovery.c`/`rules_economy.c` (steps 9/10/13) than an equally-sized but disconnected job sample would be, at no extra cost in scope (still exactly 3 types / 5 jobs / 2 curves / 7 resources). This is this PRD's own design choice, not something `docs/plan.md` or the design doc mandates — flagged here so a future reader understands *why* these specific 5 jobs were picked over an equally-valid alternative 5.
- Recommend, as a small separate follow-up (not part of this PRD, consistent with `docs/prd/psx-planet-generation.md`'s own precedent of flagging doc corrections without making them): `docs/design/slipways-mechanics.md` §8 could gain two columns (`tech gate` / `default need`) reflecting the `il`/`dm` fields this PRD's research surfaced, and a one-line cross-reference between §8's cost-surcharge text and §9's curve-upgrade text noting they share one trigger.
- `rules_planets.h`'s `resource_id_t`/`planet_type_id_t`/`colonization_job_id_t` enums are deliberately scoped to exactly what this step's subset needs, not pre-sized for the eventual 10-type/full-job roster (e.g. no reserved-but-unused enum values). Phase 4 step 14 is expected to extend these enums (and the corresponding tables) directly rather than this step leaving placeholder gaps for it to fill — consistent with the project's general preference (seen in `planetgen.h`'s `PLANETGEN_MAX_PLANETS`, sized to the real traced `90`, not padded) for real values over speculative headroom.
