## Problem Statement

`docs/plan.md` Phase 3 step 11 calls for `effects.c` : "animation de flux commercial le long des liaisons actives" (trade-flow animation along active liaisons/routes). `docs/design/slipways-mechanics.md` has **no prose about this mechanic at all** -- a `grep` for "flux"/"anima"/"particul"/the relevant PICO-8 symbol names against the design doc returns nothing, so unlike every other Phase 3 step, this one has to be traced entirely from `pico8/lua.lua` directly, with no design-doc cross-check available (flagged as a documentation gap in Further Notes, not fixed here).

Reading `pico8/lua.lua`'s `jc` class (the slipway entity, already the subject of `docs/prd/psx-liaison-validity.md`) surfaces the actual mechanic: `jc:ch(f,t)` (line 657-660) spawns a small traveling dot from planet `f` toward planet `t` with an 8%-per-frame chance, but **only if `self.hg[t.id]` is true** -- `hg` is a per-route, per-target-id set of "is trade currently flowing toward this endpoint" flags, populated once a (simulated) year by `bd()` (line 1265-1275), which walks every colonized planet's actual computed trades (`pt:ib()`) and, for each trade leg, marks the route it travels on (`w.hg[e.lp[i+1].id]=true`). `jc:kj()` (line 667-681) is the per-frame draw/update: it advances every currently-alive particle by its stored velocity, ages it out, and (gated on `gd()`, a screen-visibility/camera-culling test, line 346-348) calls `jc:ch()` again for both directions to maybe spawn a fresh one.

This creates the exact same structural situation `docs/prd/psx-liaison-validity.md` and `docs/prd/psx-rules-discovery.md` already resolved for their own steps, and their own scoping language resolves this one too, checked directly against source rather than assumed by analogy:

- `docs/prd/psx-liaison-validity.md`'s Implementation Decisions ("Never persist a committed route") is explicit and unambiguous: `liaison.c` never writes a resulting route into any real, live route list -- "the introduced route list stays empty throughout this step's own scope," and its Out of Scope names "Trade flow, colony growth, or any economic consequence of a slipway existing" as `effects.c`'s (this step's) and `rules_economy.c`'s territory, "moot anyway since no route ever persists in this step."
- `docs/prd/psx-rules-discovery.md`'s Further Notes independently flags "the colonization-commit gap": no step in `docs/plan.md`'s current Phase 3 list (8 through 13, including this one) owns wiring up `jo:fe`/`jo:hu` (choosing and committing a colonization job). Without a live "which planets are colonized" state, there is no live "founded planet" list, and without that, `bd()`'s trade computation (which is itself what populates `hg`, the very flag this step's spawn condition reads) has nothing real to compute over.

**Conclusion, confirmed from source, not assumed**: as of this step, there is no live "active liaisons" list anywhere in this port for a trade-flow animation to iterate over in a real per-frame game loop -- exactly the situation `rules_planets.c` (Phase 3 step 8) and `rules_discovery.c` (Phase 3 step 10) already found themselves in for structurally identical reasons (no live consumer state exists yet), and both resolved it the same way: port the real, complete, source-traced formulas as pure, host-testable functions with **zero caller in `game_init`/`game_update`/`game_draw`**, rather than either inventing a fake "active" list to iterate (content the source game doesn't have a reason to need yet) or blocking this step on Phase 3 steps this port's plan doesn't actually assign the colonization-commit mechanic to. This step follows that exact precedent.

## Solution

Add `psx-slipways/effects.h`/`effects.c`: a pure, host-testable C module (no PSX headers, no dynamic allocation, Q16.16 fixed-point throughout, matching every other pure module in this codebase) covering exactly the two formulas `jc:ch`/`jc:kj` express for one flow particle traveling along one candidate segment:

1. **Spawn** (`effects_flow_try_spawn`, ports `jc:ch`, line 657-660): given a `from`/`to` screen-space position pair and a caller-supplied `active` flag (standing in for `self.hg[t.id]`, since no live route/trade state exists to compute it), draws one `Bernoulli(0.08)` trial via the project's injected `rng_t`; on success, returns a particle at `from + perp(unit(to - from))` (mirroring `km:pa()`'s exact 90-degree-rotation formula) with velocity `unit(to - from)` (magnitude 1, one screen pixel per frame, mirroring `km:nn()`) and a lifetime equal to `|to - from|` (mirroring `km:qx()`), so the particle travels the correct direction for the correct total distance to functionally reach `to`'s vicinity by the time its lifetime expires -- not, as traced below, an exact arrival at `to` itself.
2. **Step** (`effects_flow_step_particle`, ports the particle-update block inside `jc:kj`, line 673-678): advances a particle's position by its stored velocity and decrements its lifetime by one "engine tick" (`FX_ONE` in this port's fixed-point convention, mirroring the fact that PICO-8's own numbers are natively Q16.16 too, so `t.l-=1` is exactly `lifetime -= FX_ONE` here, not a premature truncation to a plain integer frame count); reports whether the particle is still alive (`lifetime > 0`, matching source's `t.l<=0` deletion test).

Both functions operate purely on caller-supplied screen-space `fixed_t` coordinates and an explicit `active` boolean -- **not** on any galaxy, liaison-route, or trade-simulation state -- because none of that state is live anywhere in this port (see Problem Statement). This is the same shape `docs/prd/psx-rules-discovery.md`'s `rules_discovery_probe_in_range` already uses (a caller-supplied position list standing in for a live "founded planets" state that doesn't exist yet) and the same reasoning: a pure function is fully correct and fully testable today, and gains a real caller only once a future step has something real to pass it.

A third, smaller addition this step needs and no prior module does: `fixed_sqrt`, a new Q16.16 square-root primitive in `fixed.h`. Every prior module in this port that needed a magnitude (`WORLD_NEIGHBOR_RANGE_SQ`, `LIAISON_RANGE_SQ`, `liaison_point_blocks_segment`'s projection-parameter test) stayed in **squared**-distance space specifically to avoid ever needing a real square root (`km:__len`'s squared-magnitude semantics is the load-bearing fact both of those PRDs cite for exactly this reason). `jc:ch`'s `d:nn()` (normalize) and `d:qx()` (linear length, used as the lifetime) are the first place in the traced source that genuinely needs a **linear** magnitude -- a unit-velocity vector cannot be built from a squared distance alone. `fixed_sqrt` is ported as a general arithmetic primitive (like `fixed_mul`), not a traced game-design constant, so it needs no `slipways-mechanics.md` citation, only correctness tests against known values.

**World-space vs. screen-space -- resolved from source, not assumed.** `jc:ch`/`jc:kj` operate on `.ra`, each entity's rendered/screen-scale position (`bw(n)`, line 749: `jo({id=...,p=p,ra=p*128})` -- `.ra` is `.p` linearly rescaled by a constant factor, i.e. a per-axis affine map of the normalized world position, not a second independent quantity). This port's own `screen_map_axis` (`screen_map.c`, line 18-24) is *also*, in its underlying real-valued form, a per-axis affine map (`pixel = MARGIN + (coord - MIN) * usable / SPAN`, a linear-scale-plus-offset in each axis independently, with no clamping or branching) -- though its actual implementation computes that map with two truncating integer divisions (`normalized = (diff*FX_ONE)/SPAN`, then `pixel = MARGIN + (normalized*usable)/FX_ONE`), so it is affine up to integer-rounding error, not bit-for-bit affine. An affine map `f(x) = a*x + b` commutes with linear interpolation: for a world-space point `M = A + t*(B-A)`, `f(M) = f(A) + t*(f(B) - f(A))` exactly, for any `t`, when `f` is evaluated over the reals. So interpolating a point along the world-space segment `A->B` and then applying `screen_map_planet` to it produces the same screen position, up to the same integer-truncation rounding error every other fixed-point computation in this codebase already tolerates, as first projecting `A` and `B` to screen space and interpolating there -- the underlying real-valued map is equivalent either way; the two integer computations can differ by a small rounding error, not zero. Given that near-equivalence, this step follows source's own literal choice (compute directly in already-projected screen-space `fixed_t` coordinates, matching `.ra`'s role 1:1) rather than adding an unnecessary dependency on `planetgen.h`/`world.h`/`screen_map.h` to redo the same computation in world-space first -- `effects_flow_try_spawn`/`effects_flow_step_particle` take plain `fixed_t` screen coordinates, supplied by whichever future caller has already called `screen_map_planet` on both endpoints (mirroring `liaison_pick_planet`'s own precedent of reusing `screen_map_planet`'s existing output rather than re-deriving screen positions).

## Implementation Decisions

**The spawn formula -- traced directly to `jc:ch`, `pico8/lua.lua:657-660`.**

```
function jc:ch(f,t)if rnd()<0.08 and self.hg[t.id]then
local d=t.ra-f.ra
local v=d:nn()add(self.ts,{ra=f.ra+v:pa(),v=v,l=d:qx()})end
end
```

- **Spawn trial**: `rnd()<0.08` (line 657) -- PICO-8's `rnd()` (no argument) returns a uniform draw in `[0,1)`; a plain `Bernoulli(0.08)` trial, independent per call. Ported as `EFFECTS_FLOW_SPAWN_CHANCE = (fixed_t)(0.08 * FX_ONE)`, tested via `rng_next_range(rng, 0, FX_ONE) < EFFECTS_FLOW_SPAWN_CHANCE` -- the exact `rng_next_range`-as-uniform-fixed-draw idiom `docs/prd/psx-rules-discovery.md`'s empty-roll generator already establishes for this codebase (`rng_next_range` treating a `fixed_t` span's raw `int32_t` value directly as the exclusive bound).
- **The "active" gate**: `self.hg[t.id]` (line 657) -- true only when `bd()` (line 1265-1275, itself driven by `pt:ib()`'s live trade computation) has, this simulated year, marked that trade is currently flowing from `f` toward `t` specifically. No live equivalent exists anywhere in this port (see Problem Statement). Ported as an explicit `int active` parameter to `effects_flow_try_spawn` -- the function itself is agnostic to how `active` was determined, exactly mirroring `rules_discovery_probe_in_range`'s caller-supplied-position-list precedent.
- **Direction and offset** (`d=t.ra-f.ra`; `v=d:nn()`; spawn position `f.ra+v:pa()`): `km:nn()` (line 113-114, `self/self:qx()`) normalizes; `km:pa()` (line 115-116, `v(-self.y,self.x)`) is an exact 90-degree rotation of a vector, preserving its magnitude -- since `v` is unit-length, `v:pa()` is also unit-length, so the spawn position is offset from `f` by exactly one screen-space unit perpendicular to the direction of travel. Ported literally: `spawn.x = from_x + (-unit_y)`, `spawn.y = from_y + unit_x` in this port's screen-space `fixed_t` coordinates.
- **Velocity and lifetime**: `v` itself (a unit vector, magnitude 1) becomes the particle's per-tick velocity; `l=d:qx()` (`km:qx()`, line 117-118, `sqrt(#self)` -- the **linear**, not squared, distance from `f` to `t`) becomes its lifetime. `l` is the direct `f`-to-`t` distance, but the particle's real-valued spawn position is already offset from `f` by one unit perpendicular to that line (`f + v:pa()`, see above), and it travels distance `l` in direction `v` from there -- since `f + v*l = f + (t-f) = t`, the particle's real-valued endpoint is `spawn + v*l = t + v:pa()`, i.e. offset from `t` by that same one-unit perpendicular vector, not exactly `t`. This is inherent to the source formula itself (the spawn offset and the direct-distance lifetime are both taken from `f`/`t`, not from the offset spawn point), not a porting bug -- a faithful port reproduces this same near-`t` convergence, which is the load-bearing property `effects_flow_try_spawn`/`effects_flow_step_particle`'s host tests verify directly, within a small, documented fixed-point tolerance (see Testing Decisions), not just assert.
- **Degenerate zero-length segment** (`from == to`): source structurally never calls `jc:ch` with `f==t` (a slipway's two endpoints are always distinct planets, and `jc:ce`'s own logic, `docs/prd/psx-liaison-validity.md`'s trace, never allows a route to itself), so `km:nn()`'s implicit division-by-zero-length case is never exercised in source. This port's function still defines a behavior for it (returns "not spawned," no particle produced) purely as ordinary defensive robustness for a host-tested pure function, exactly the same posture `rules_discovery_probe_in_range`'s `founded_count == 0` branch already takes for an input configuration source itself never produces.
- **Frame-rate assumption**: `0.08` is a per-`_update60`-call probability in source. This port's own Phase 1 step 4 (`docs/prd/psx-galaxy-rendering.md`) already measured and confirmed 60fps on the same class of scene under the PCSX-Redux harness, and no prior PSX-side PRD has needed a frame-rate correction factor for any per-frame formula; this step assumes 1:1 frame correspondence (one call per real engine tick) for the same reason, not a new finding.

**The particle-update formula -- traced directly to the loop inside `jc:kj`, `pico8/lua.lua:673-678`.**

```
self:lg(-1,2,3,bc)self:lg(0,1,1,c)for _,t in pairs(self.ts)do
t.ra+=t.v
t.l-=1
if (t.l<=0)del(self.ts,t)
local x,y=t.ra.x,t.ra.y
rectfill(x,y,x+1,y+1,0)pset(x,y,tc)end
```

- **Position advance**: `t.ra+=t.v` (line 674) -- straight-line addition of the stored unit velocity, once per call. Ported as `x += vx; y += vy` in `fixed_t`.
- **Lifetime and death**: `t.l-=1` then `if (t.l<=0) del(...)` (line 675-676). Because PICO-8's own numbers are natively Q16.16 fixed-point (the same representation `fixed_t` already uses throughout this codebase), `t.l`'s "1" here is one full PICO-8 number-unit, i.e. exactly `FX_ONE` in this port's own convention -- not a plain integer frame counter that would need truncating `l` to an `int` upfront. Ported as `lifetime -= FX_ONE; alive = (lifetime > 0)` (source's `<=0` deletion condition, inverted to "still alive"), keeping `lifetime` a `fixed_t` throughout, matching `l`'s literal fractional-capable representation in source.
- **Drawing** (`rectfill`/`pset`, line 677-678): a 2x2 black-filled square plus a single colored center pixel -- pure rendering, not ported by this step (no `game_draw.c` wiring exists for it; see Out of Scope). Also excluded: the color choice `tc` (`self.mt and 5 or 13`, line 672), tied to the `mt=1` infragate distinction that doesn't exist yet in this port (matching `liaison.c`'s own identical treatment of the same field).
- **The spawn calls inside `jc:kj`** (`self:ch(self.qu,self.re)self:ch(self.re,self.qu)`, line 679) confirm the two-direction pattern: a real caller of `effects_flow_try_spawn` is expected to call it once per direction, each with its own `active` flag (`self.hg[re.id]` vs. `self.hg[qu.id]` in source) -- documented here as the calling convention a future live wiring step should follow, not invented by this step.
- **The `if gd(self.qu) or gd(self.re)` gate** (line 667, `gd()` defined line 346-348: `abs(e.ra.x-mo.ra.x-64)<=76 and abs(e.ra.y-mo.ra.y-64)<=76`) is PICO-8's on-screen/camera-culling test (`mo` is the camera-follow cursor object). `docs/prd/psx-liaison-validity.md`'s own Out of Scope already established "no camera system exists" for this port (the whole galaxy renders on one screen at once, per `docs/prd/psx-galaxy-rendering.md`), so this gate has no equivalent concept here and is not ported -- named explicitly so its absence reads as confirmed non-applicability, not an oversight.

**A new arithmetic primitive: `fixed_sqrt`, added to `fixed.h`.**

- Every prior module needing a magnitude (`WORLD_NEIGHBOR_RANGE_SQ`, `LIAISON_RANGE_SQ`, `liaison_point_blocks_segment`) deliberately stayed in squared-distance space specifically to avoid needing a real square root, citing `km:__len`'s squared-magnitude semantics (`pico8/lua.lua:119-120`) as the reason a squared comparison is always sufficient for a pure distance *threshold* check. `jc:ch`'s `d:nn()` (a **unit** vector) and `d:qx()` (a **linear** length used as a lifetime, which must count down in real frame-equivalent units, not squared ones) cannot be built from a squared distance alone -- this is the first genuinely unavoidable square root in this port.
- Illustrative shape (not literal file contents, decision-encoding only): `fixed_t fixed_sqrt(fixed_t x)` for `x >= 0` (defined as `0` for `x < 0`, a defensive convention, not a traced value), computed as an integer square root of the `int64_t`-widened value `(int64_t)x << 16` (since a `fixed_t` `x` represents the real number `x / FX_ONE`, and `sqrt(x/FX_ONE) * FX_ONE == isqrt(x * FX_ONE)`), using a standard bit-by-bit or Newton-Raphson integer square root -- pure integer arithmetic throughout, no `float`/`double` at runtime, matching every other module in this codebase and `docs/plan.md`'s own "le R3000A n'a pas de FPU matérielle" reasoning.
- Tested against exact perfect squares (`fixed_sqrt(FX_ONE) == FX_ONE`, `fixed_sqrt(4*FX_ONE) == 2*FX_ONE`, etc.) and against known irrational values within a small, documented fixed-point tolerance (e.g. `fixed_sqrt(2*FX_ONE)` close to `1.41421356*FX_ONE`) -- the same "exact where exact, tolerance-bounded where irrational" testing posture `screen_map_test.c`'s round-trip tests and `docs/prd/psx-rules-discovery.md`'s Monte-Carlo tolerance already establish for this codebase.

Combined with the confirmed absence of any live route/trade/colonization state anywhere in this port (Problem Statement), this step follows `rules_planets.c`'s and `rules_discovery.c`'s **unwired pure module** precedent, not `liaison.c`'s live-wired one.

**Data model and function signatures.**

- `typedef struct { fixed_t x, y; fixed_t vx, vy; fixed_t lifetime; } effects_flow_particle_t;` -- all four geometry fields and the lifetime are `fixed_t` (Q16.16 screen-space units), matching `t.ra`/`t.v`/`t.l`'s own literal fractional-capable representation in source (see above).
- `int effects_flow_try_spawn(fixed_t from_x, fixed_t from_y, fixed_t to_x, fixed_t to_y, int active, rng_t *rng, effects_flow_particle_t *out)` -- ports `jc:ch`; returns `1` and populates `*out` on a successful spawn, `0` otherwise (either the Bernoulli trial failed, `active` was false, or `from == to`). `rng` is threaded by the caller, matching every other RNG-injected function in this codebase.
- `int effects_flow_step_particle(effects_flow_particle_t *p)` -- ports the update loop body inside `jc:kj`; mutates `*p` in place (`x/y += vx/vy`, `lifetime -= FX_ONE`) and returns `1` if the particle is still alive (`lifetime > 0`) or `0` if it just died (matching source's `t.l<=0` deletion test -- the caller, not this function, is responsible for removing a dead particle from whatever list it lives in, since this step introduces no such list).
- `fixed_t fixed_sqrt(fixed_t x)` -- added to `fixed.h`, cited above.

## Implementation Chunks

Tracer-bullet order, pure arithmetic primitive first, then geometry decomposition, then the two ported behaviors, then regression coverage -- no wiring chunk, matching `rules_planets.c`'s/`rules_discovery.c`'s own zero-wiring-chunk precedent:

1. **`fixed_sqrt`.** Added to `fixed.h`. Host-tested (extending the existing `host_tests/` fixed-point test coverage, or a new small `host_tests/fixed_test.c` if none currently exists for `fixed.h` in isolation -- confirmed at implementation time against the current `host_tests/` layout) against exact perfect squares and irrational values within a documented tolerance. No wiring, no `effects.c` dependency yet.
2. **Spawn formula.** `effects.h`/`effects.c` gain `effects_flow_particle_t`, `EFFECTS_FLOW_SPAWN_CHANCE`, and `effects_flow_try_spawn`, using `fixed_sqrt` for the unit-vector normalize and the linear-length lifetime. Host-tested (`host_tests/effects_test.c`, new `test-effects` target): `active=0` never spawns regardless of the RNG draw; a fixed RNG seed reproduces an identical spawn/no-spawn sequence (mirroring `planetgen_test.c`'s determinism pattern); a spawned particle's velocity is unit-length (within fixed-point tolerance); the spawn position is offset from `from` by exactly the perpendicular-unit-vector formula; `from == to` never spawns.
3. **Step formula.** `effects_flow_step_particle`. Host-tested: position advances by exactly the stored velocity per call; lifetime decrements by exactly `FX_ONE` per call; a particle survives every call while `lifetime > 0` and reports dead on the first call that brings it to `<= 0`.
4. **Full spawn-to-death lifecycle test.** Spawns a particle via `effects_flow_try_spawn` (forcing `active=1` and a guaranteed-successful RNG draw), then calls `effects_flow_step_particle` repeatedly until it reports dead, asserting: the number of steps to death matches the segment's linear distance (within one tick, per the fixed-point-lifetime-decrement reasoning above); the particle's final position lands within a small, documented fixed-point tolerance of `(to_x, to_y) + perp(unit((to_x,to_y)-(from_x,from_y)))` -- the source formula's actual real-valued endpoint, one perpendicular unit off from `to` itself, per the "Velocity and lifetime" trace above. This is the concrete, automated proof of the "travels the correct direction and distance to converge near `to`" property this whole formula depends on, mirroring `docs/prd/psx-rules-planets.md`'s closed-loop structural regression test's role (turning a design property this PRD's argument leans on into an automated check, not just an assertion in prose).
5. **Spawn-rate statistical regression.** A Monte-Carlo test (many thousands of `effects_flow_try_spawn` calls with `active=1` from a fixed seed), asserting the empirical spawn rate falls within an implementation-chosen tolerance band around `0.08` -- the exact N and tolerance decided empirically at implementation time, mirroring `docs/prd/psx-rules-discovery.md`'s empty-roll Monte-Carlo precedent (itself mirroring `docs/plan.md` Phase 1 step 2's BFS-connectivity-rate precedent) exactly. Guards against a future edit to `EFFECTS_FLOW_SPAWN_CHANCE` silently drifting the animation's visual density without any test noticing.

## Testing Decisions

- **What makes a good test here**: assert on this module's observable output (`effects_flow_particle_t`'s fields, the functions' return values) -- never on internal representation beyond what's already a named, documented struct field. Mirrors every prior pure module's established style in this codebase.
- **Fully host-testable** (all 5 chunks, `gcc`, no PSn00bSDK toolchain): `fixed_sqrt`, `effects_flow_try_spawn`, `effects_flow_step_particle`, and both regression tests. New `EFFECTS_TEST_HOST_SRCS` var (`psx-slipways/rng.c psx-slipways/effects.c psx-slipways/host_tests/effects_test.c`) and `test-effects` target, compiling and running with the host's native `gcc` (`-std=c11 -Wall -Wextra -I psx-slipways`), output under the existing shared `psx-slipways/build-host/` directory -- the exact established pattern `test-planetgen`/`test-cursor`/`test-rules-planets`/`test-liaison`/`test-rules-discovery` already follow. `test`'s prerequisite list gains `test-effects`, and `test-effects` is added to `.PHONY`, keeping `CLAUDE.md`'s "use `make test` to verify changes" promise intact.
- **Not tested here**: anything requiring the PSn00bSDK toolchain or PCSX-Redux/Mednafen (no PSX-side behavior exists to boot-test -- nothing is wired into `game_init`/`game_update`/`game_draw`); `bd()`'s trade computation or any live `hg`-equivalent state (no colonization/trade simulation exists anywhere in this port yet); `jc:lg`'s line rendering, the `nh`/`k_` reveal-color animation, or `ma()`'s generic settle wobble (deferred, see Out of Scope); any real particle-list management or capacity sizing (deferred, see Out of Scope).
- **Prior art reused**: `host_tests/t.h`'s PASS/FAIL harness; `planetgen_test.c`'s/`rules_discovery_test.c`'s `test_same_seed_is_deterministic` pattern, directly reused for the spawn formula's RNG determinism test; `docs/prd/psx-rules-discovery.md`'s Monte-Carlo empty-roll regression pattern, directly reused for the spawn-rate regression; `screen_map_test.c`'s tolerance-bounded round-trip testing style, reused for `fixed_sqrt`'s irrational-value tests and the lifecycle test's "arrives near `to`" tolerance check.

## Further Notes

- **`docs/design/slipways-mechanics.md` has no coverage of this mechanic at all** -- confirmed by direct search, not just an oversight this PRD is guessing at. Recommended, as a small separate follow-up (not part of this PRD, consistent with prior PSX-side PRDs' own practice of flagging design-doc gaps without filling them here): the design doc could gain a short subsection (adjacent to §5 "Slipways") describing `jc:ch`/`jc:kj`'s trade-flow particle mechanic in prose, so a future reader doesn't have to rediscover it purely from `pico8/lua.lua` the way this PRD's own research had to.
- **Why screen-space, not world-space**: checked algebraically in Implementation Decisions (the underlying real-valued affine per-axis projection commutes with linear interpolation; `screen_map_axis`'s actual integer implementation is affine only up to the same truncating-division rounding error every other fixed-point computation in this codebase already tolerates), not assumed by convenience. This means a future caller is free to interpolate in either space with results equivalent up to that small rounding error, not bit-for-bit identical -- this step's choice to operate directly in screen-space (matching source's own `.ra`-space computation 1:1) is the simpler, more source-literal option given that near-equivalence, not the only mathematically valid one, and no downstream test in this PRD needs a coarser tolerance band on that account (the lifecycle test's tolerance is already sized for the spawn formula's own one-unit perpendicular offset, which dominates any rounding difference here).
- **The `0.08` spawn chance and the "1 unit/frame" velocity are both ported as literal, traced constants** -- but their *felt* visual effect (how dense the particle stream looks, how fast a dot visibly crosses the screen) is inherently resolution-dependent: source's `.ra` space is scaled to PICO-8's native 128x128 pixel grid, while this port's `screen_map_planet` targets a different screen resolution entirely. This is the same category of already-precedented "v1 rendering-scale constant, revisitable" issue `screen_map.c`'s `SCREEN_MAP_MARGIN` and `liaison.h`'s `LIAISON_PICK_RADIUS_PX` already document for their own resolution-dependent pixel constants -- not a new kind of imprecision this step introduces, and not something this step resolves differently from those precedents (the formula's *structure* is ported exactly; only its felt scale on a different screen size is inherently unfixed by a pure per-segment port).
- **No "Incertain" item was needed for this step's core formulas** -- every constant (`0.08`, the unit-velocity magnitude, the perpendicular-offset rotation, the distance-as-lifetime relationship) traces to an unambiguous source expression. The one open question the task framing raised (world-space vs. screen-space) was resolved algebraically to a documented near-equivalence (exact in the real-valued math, rounding-bounded in the actual integer implementation), not left ambiguous.
- **`fixed_sqrt` is this port's first real (non-squared) magnitude primitive** -- worth keeping in mind for any future module (e.g. a live probe-reveal-sweep radius, if ever ported, or genuine trigonometry per `docs/plan.md`'s own "la trigo en virgule fixe reste nécessaire" line) that also needs a linear distance or a normalized direction rather than a squared-distance threshold comparison; those should reuse this primitive rather than each defining their own.
- **Where a future live trade-flow step should plug in**: three concrete, already-shaped extension points -- (1) a real `bd()`-equivalent trade computation (most plausibly `rules_economy.c`, step 13, once colonization/trade state exists) to produce a real `active` boolean per direction per route; (2) a real per-route particle list (capacity to be sized against this port's actual screen resolution and `LIAISON_RANGE_SQ`-derived maximum segment length, not source's PICO-8-128px-native figures, since the felt-scale caveat above means a source-literal capacity wouldn't transfer directly); (3) a `game_draw.c` call site drawing each live particle (reusing whatever primitive renders a committed slipway's own line, itself not yet built -- see Out of Scope). None of `effects_flow_try_spawn`'s or `effects_flow_step_particle`'s signatures need to change when that step lands.
