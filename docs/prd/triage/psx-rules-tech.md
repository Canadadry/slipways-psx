## Problem Statement

`docs/plan.md` Phase 3 step 12 calls for `rules_tech.c` : "menu tech minimal, accessible en permanence via Select" (a minimal tech menu, accessible at all times via Select). Unlike steps 10/11 (`rules_discovery.c`/`effects.c`, both deliberately unwired pure modules -- their plan wording carries no live-wiring language), step 12's "accessible en permanence" is explicit, stated wiring language, directly mirroring step 9's "branché sur l'événement clic" that made `liaison.c` this port's first genuinely live-wired gameplay module. Two things make this step harder than a "port a table" step: (1) `docs/plan.md` Phase 4 step 14 ("Étendre `rules_planets.c`/`rules_tech.c` à l'ensemble des 10 types de planètes, spécialisations et 20 technologies documentées") explicitly defers the full tech tree, so this step must pick a genuinely reduced, internally-coherent subset -- following `rules_planets.c`'s own already-established "reduced vertical slice, full roster deferred" precedent (`docs/prd/psx-rules-planets.md`), not an arbitrary N of the documented techs; (2) the source's actual "research a tech" commit action (`fm:kt`, more precisely `hy:kt`, traced below) spends a science resource (`fm.jk`) that no economy system in this port produces yet (`rules_economy.c` is Phase 3 step 13, not committed), so this step must decide, and defend from source, what "a live tech menu" concretely means when the one thing a real tech menu is *for* -- researching a tech -- cannot honestly be committed yet.

## Solution

Read `pico8/lua.lua` directly (the `nb`/`ek`/`cb`/`gi`/`hy:kt`/`ix[2]`/`cr`/`pz`/`ui:lj` cluster, all traced with line numbers below) and re-decode `nb` (unstash 10457, `pico8/map.json`) rather than trusting the design doc's §12 table/prose at face value -- the same "verify against raw unstash data, don't take the doc's prose on faith" discipline `rules_planets.c`'s PRD already applied to `fd`. That re-decode surfaces a load-bearing correction: **the raw `nb` table has exactly 19 tech records, not 20, and Era 1 (`lv==1`) has exactly 4 techs, not 5** -- `xenofoods` and `autoassemblers`, which the design doc's own §12 table lists under Era 1/Era 2 respectively, carry raw `lv` values of `2`/`3` in the actual unstash data. This resolves this PRD's central scoping question directly from source, without guessing: the real, zero-prerequisite, always-available tier is **space folding, geneseeds, nanomaterials, drillbots** (4 techs), not the 5 the design doc's prose implies. This is ported as a pure static-data module (name/era/base-cost/resource-code fields, each traced to the raw dump), plus a genuinely live, wired piece: a menu **open/closed** boolean, toggled by Select's press edge, following `cursor.c`'s own already-established Cross-toggle idiom (a fresh port-specific gesture -- source's own dismissal is "click elsewhere," which has no gamepad equivalent, so this step adopts the one toggle idiom this codebase already uses for exactly this class of problem, rather than inventing a second gesture family). What this step does **not** introduce is a live "which techs are researched" state or a real research-commit action: `hy:kt` (the function the plan's own framing implicitly points to) spends `fm.jk` (a science stockpile no economy module in this port produces) and advances `fm.ew` (era) -- both are genuinely out of reach until `rules_economy.c` (step 13) and Phase 4 step 14 exist, mirroring `liaison.c`'s own "never persist a committed route" resolution for the structurally identical problem (a real, live mechanic whose commit step needs economy state this port doesn't have yet). Rendering reuses the established "colored placeholder primitive" convention (`TILE`s, one per Era-1 slot, positioned top-left -- the source pitch text's own words, "Research technologies from the top-left corner," and `ix[2]`'s own `ra=v(0,0)` position, both point at the same screen corner) since no font/glyph rendering exists anywhere in `psx-slipways/` yet (confirmed by direct search -- zero hits for font/glyph/text-draw code).

## Implementation Decisions

**The central scoping finding, re-derived from raw `nb` data, not the design doc's prose: 19 techs, not 20; Era 1 is 4 techs, not 5.**

- Re-running the project's established decode command (`docs/design/slipways-mechanics.md` Annexe A's `jq` recipe) against `unstash(10457)` (`nb`, `pico8/map.json`) reproduces 19 raw tech records, each of the shape `o(px, lv, nk, od, oy)` -- field names cross-checked against `hp.mr`-style positional parsing at `pico8/lua.lua:1442` (`foreach(nb,ho(nb,ob([["px","lv","nk","od","oy",]]),{"nk"})))`; the `{"nk"}` third argument to `ho()` (`pico8/lua.lua:17-23`) means each tech's raw `nk` field is looked up through the resource-code table `r` (`pico8/lua.lua:1377`, `unstash 8192`) rather than kept as a literal value.
- **The 19 raw records, in table order, with their real `lv`/`od` values** (name, lv, nk-raw-code, od): `space folding`(1,"t",4), `geneseeds`(1,"l",5), `nanomaterials`(1,"o",6), `drillbots`(1,"b",7), `xenofoods`(**2**,"l",10), `slipgates`(2,"t",12), `geoharvesting`(2,"o",14), `trade league`(2,"t",16), `replication`(2,"b",18), `autoassemblers`(**3**,"b",19), `skill implants`(3,"b",22), `starbirth`(3,"o",25), `biome hacking`(3,"l",28), `infraspace`(3,"t",31), `superhuman ai`(4,"t",34), `void synthesis`(4,"o",38), `gene rewriting`(4,"l",42), `time compression`(4,"b",46), `ascension`(4,"a",50). Era sizes by raw `lv`: **4/5/5/5 = 19**, not the "5 par niveau" the design doc's own §12 prose (`docs/design/slipways-mechanics.md:235`) states.
- **The design doc's own §12 *table* (not just its prose) already reflects this discrepancy silently**: counting its rows directly gives 19, matching raw data exactly, and its Era 3 column already only lists 4 rows (skill implants, starbirth, biome hacking, infraspace) -- but its era *assignment* for two specific techs is wrong relative to raw `lv`: the doc lists `xenofoods` under Era 1 (doc row, `docs/design/slipways-mechanics.md:243`) where raw `lv` is 2, and `autoassemblers` under Era 2 (`docs/design/slipways-mechanics.md:248`) where raw `lv` is 3. This PRD treats the raw `nb.lv` field, not the doc's era column, as ground truth -- per the project's own traceability guardrail ("toute constante codée doit être retrouvable... une valeur ambiguë se résout en relisant `pico8/lua.lua`"), and consistent with `rules_planets.c`'s own precedent of re-verifying the design doc's §8 table against raw `fd` data rather than trusting it uncritically.
- **Resolution**: the real, zero-prerequisite, always-available Era-1 slice (`fm.ew` starts at `1`, `hy:pq()`, `pico8/lua.lua:1198-1203`; `cb()`'s filter is `t.lv==fm.ew`, `pico8/lua.lua:1458`) is **space folding, geneseeds, nanomaterials, drillbots** -- 4 techs, not 5. This is smaller than the 5 a naive reading of the design doc's table suggests, but it is the raw-data-accurate answer, and it remains the same kind of "natural, self-contained, no era-progression-logic-needed" slice the task's own framing anticipated -- it's just 4 techs wide, not 5, because `xenofoods` genuinely isn't one of them in the shipped game.

**Downstream live-consumer check, done directly against `rules_planets.h`/`.c`: no live consumer exists for any Era-1 tech, regardless of subset chosen.**

- `rules_planets_job_cost(colonization_job_id_t id, bool job_tech_researched, bool nanomaterials_researched)` (`rules_planets.h:108`, `rules_planets.c:111-127`) already carries a **named** `nanomaterials_researched` boolean parameter -- the one Era-1 tech with a matching, already-shaped hook in this codebase. But `rules_planets.c` itself is **not called anywhere** in `game_update.c`/`game_draw.c` (confirmed by direct read of both files -- neither references any `rules_planets_*` symbol), per that module's own PRD ("Not wired into `game_init()`/`game_update()`/`game_draw()`... no caller yet"). So even though the parameter's *name* already anticipates `nanomaterials`, there is no live call site today for this step to feed a real value into -- the same "nothing downstream exists yet regardless of which subset is chosen" finding the task anticipated for `rules_discovery.c`/`effects.c`'s own precedent. `agroworld`'s `tech_gate = "xenofoods"` (`rules_planets.c:61`) is the only other named tech-gate string in this codebase, and it now provably belongs to Era 2 (`xenofoods` raw `lv=2`), not this step's Era-1 slice -- so it isn't a connection point for this step either.
- `world.h`'s `WORLD_NEIGHBOR_RANGE_SQ` (`world.h:24-30`) and `liaison.h`'s `LIAISON_RANGE_SQ` (`liaison.h:16-21`) both already name-and-defer "space folding"'s range extension (`0.19`→`0.27`, `0.5`→`1.08`) in their own comments -- real, already-existing forward references to this exact tech, both still hardcoded to their base (un-researched) value, both explicitly *not* touched by this step (see Out of Scope) since there is no live tech-researched state to flip them with.

**Is a real "researched" state introduced? Resolved: yes for the menu's own open/closed state; no for per-tech researched status.**

- `rules_planets_job_cost`/`rules_planets_job_production` already establish this codebase's precedent for tech-gate state: plain, caller-supplied `bool` parameters, never a module-owned global "is X researched" singleton. This step follows that precedent for per-tech researched status: it is never tracked as live state anywhere in `rules_tech.c`. The reason is the same one `liaison.c` used for never persisting a committed route: the one thing a real research action does in source (`hy:kt`, traced next) needs live economy state (`fm.jk`, a science stockpile) this port has no producer for yet (`rules_economy.c`, Phase 3 step 13, not committed). Introducing a `g_tech_researched[TECH_COUNT]` global that this step can only ever set to `false` would be exactly the unobservable, purposeless scaffolding this project's guardrails (and `psx-select-start-mapping`'s own "no module built with no consumer" reasoning) already reject.
- The menu's **open/closed** boolean is different: it is directly, immediately observable (the menu is drawn or it isn't) and is exactly what "accessible en permanence via Select" requires to be real. This is introduced as genuine, live, wired state -- a `rules_tech.c`-owned static, updated every frame from real Select input, exactly mirroring `cursor.c`'s `g_cursor_mouse_mode` in shape (a single toggled boolean, owned by the module whose job it is).

**`hy:kt` (the "research a tech" commit action), traced in full -- confirmed out of scope, mirroring `liaison.c`'s cost/affordability deferral.**

- `hy:kt(t)` (`pico8/lua.lua:1446-1454`; `fm` is the live singleton instance of the `hy` class, `fm=hy()`, `pico8/lua.lua:1182`, so `fm:kt(t)` and `hy:kt(t)` refer to the same method -- this PRD uses `hy:kt` for precision, matching how the method is actually defined in source): `self.jk-=gi(t)` (debits the tech's cost from the player's science stockpile `jk`), `add(self.invented,t.px)` (marks the tech researched by name), then, if `self.ew<4 and #self.invented>=ek[self.ew]`, `self.ew+=1` (advances the current era once enough total techs are invented -- `ek`, traced next), finally `self:lj()` (a full economic recompute, `pico8/lua.lua:1226-1238`, itself dependent on live colony/trade state this port doesn't have).
- **`fm.jk` (the science stockpile)** is initialized to `0` (`hy:pq()`, `pico8/lua.lua:1198-1203`) and incremented annually by `self.po[r.k]+1` (`hy:hk()`, `pico8/lua.lua:1212` -- `r.k` is the science resource code, `unstash 8192`: `k=24`, confirmed against `iz`'s `24="science"`). No module in this port produces or tracks any resource stockpile yet -- this is squarely `rules_economy.c` (Phase 3 step 13) territory, the same boundary `liaison.c`'s PRD already drew for `dj`/`fm:lu` (the slipway cost/affordability formulas).
- **Conclusion**: this step never calls anything resembling `hy:kt`. No science is ever debited, no tech is ever marked researched, no era ever advances. This is a deliberate, source-backed scoping decision, not a silently dropped rule -- `hy:kt`'s full mechanism is documented here precisely so whichever step first has a real science economy (most likely a continuation of Phase 4 step 14, once `rules_economy.c` exists) can port it directly rather than re-deriving it.

**`gi()` (per-tech cost) and `ek` (era-unlock thresholds), traced and recorded, both genuinely undetermined/unwireable this step.**

- `gi(t)` (`pico8/lua.lua:1471-1474`): `return flr(t.od*max(0.55,fm.fu[t.nk]))` -- floor of the tech's static base cost (`t.od`, stored per-tech in the `nb` table, listed above) multiplied by `max(0.55, fm.fu[t.nk])`, a **minimum-floored** discount factor. `fm.fu` is assigned by `hy:lj()`'s annual recompute (`pico8/lua.lua:1227-1228`: `self.po,self.fu=bx(),ck()`) from `ck()` (`pico8/lua.lua:1252-1256`): a per-resource-code table starting at `1` for every resource, decremented by `0.15` for each `"qh"`-tagged entity (a structure category -- Laboratories, per the design doc's own vocabulary) whose last production resource matches that code. `t.nk` (the raw per-tech code, translated through `r[...]` per the `ho()` field-mapping confirmed above) indexes into this table. **This formula is fully traced but genuinely unwireable this step**: it depends on live per-resource production totals (`bx()`), a live structure count (`cg.qh`), and the live science stockpile `fm.jk` it would debit -- none of which exist in this port. Only the static `od` field (the tech's authored base cost, independent of any live economy) is captured as informational data on this step's table, mirroring `rules_planets.c`'s own precedent of storing a traced-but-not-yet-applicable field (`dm`) as static data for a future step to pick up without re-decoding. The design doc's own §12 prose already flags `fu` as "non détaillé" -- this PRD's research confirms that characterization is accurate (it is a real, traced, but currently un-computable formula) rather than resolving it further, since nothing in this port needs its output yet.
- `ek` (`pico8/lua.lua:1445`): `ob([[2,4,7,12,]])` -- cumulative-invented-tech thresholds `{2,4,7,12}` to unlock Eras 2/3/4, confirmed unchanged from the design doc's §12 citation. **Not wired this step**: era progression only matters once a live `fm.invented`/`fm.ew` exists (it doesn't -- see `hy:kt` above), and this step's entire subset is Era 1 by construction, so no era-transition logic has anything to operate on yet regardless.

**Open/close gesture for Select: resolved as a press-edge toggle, following `cursor.c`'s own Cross-toggle idiom -- not a second dedicated close input.**

- Source's own dismissal (`ui:lj()`, `pico8/lua.lua:217-224`, run every frame via `_update60`'s `ok:lj()` at `pico8/lua.lua:1187`) is "a fresh left click lands anywhere and the currently-open list wasn't just replaced by this same click" (`if je.l.jn and self.le==le then self:cj()end`, line 221-222) -- a mouse-native "click elsewhere closes it" mechanic with no literal gamepad equivalent (`docs/prd/psx-select-start-mapping.md`'s own Further Notes already flagged this precisely, offering "a second Select press, or a Circle/back press" as a starting, not binding, opinion for this PRD to resolve).
- **Resolved: Select's press edge toggles the menu's open boolean** (open→closed, closed→open, on the same button, every press), exactly mirroring `cursor.c`'s already-shipped `CURSOR_PAD_CROSS` toggle idiom for `mouse_mode` (`cursor.c:28-30`). This is chosen over a second dedicated close input (e.g. Circle) for three concrete reasons: (1) it reuses an idiom this codebase has already built, tested, and shipped once, rather than introducing a second, subtly different toggle-vs-hold-vs-second-button gesture family; (2) Circle is already claimed by `liaison.c`'s drag mechanic (mode-gated on `mouse_mode`) -- overloading it to also close the tech menu would require deciding whether that Circle press is "close the menu" or "start a drag" whenever both are momentarily plausible, a real ambiguity a same-button toggle sidesteps entirely; (3) `docs/plan.md` step 7's own framing of Select as a "mapping 1:1... aucune adaptation nécessaire" simple, unconditional button press is most literally satisfied by "press it, get the opposite state," not by a press-to-open/different-input-to-close split.
- This is a genuine, new, port-specific gesture with no PICO-8 equivalent (source has no toggle-close mechanic at all -- clicking `ix[2]` again while its list is open just closes-then-reopens the same list, per `docs/prd/psx-select-start-mapping.md`'s own already-cited finding, which is a refresh, not a close). Flagged explicitly here, the same way `liaison.c`'s PRD flagged its own "mode toggled off mid-drag cancels the drag" as a genuine new port-specific behavior with no source equivalent, resolved conservatively and documented rather than left implicit.

**Selection cursor / D-pad navigation inside the open menu: deliberately not added this step.**

- The task's own framing raises a real conflict: `cursor.c`'s D-pad already unconditionally moves the mouse-mode pixel cursor whenever `mouse_mode` is on (`cursor.c:32-47`), with no awareness of any other module; if `rules_tech.c` also consumed D-pad edges for its own in-menu slot navigation while the menu is open, both systems would react to the same D-pad press simultaneously (the pixel cursor moving *and* a menu highlight moving), a real, user-visible interaction conflict this codebase has not had to resolve before (Circle's drag and D-pad's cursor movement coexist cleanly in `liaison.c` specifically because both are meant to happen together -- aiming a drag while moving the cursor -- which is not true of "move the pixel cursor" vs. "move a menu highlight").
- **Resolved: no selection cursor, no D-pad consumption, this step.** The reasoning is not primarily about avoiding the D-pad conflict (real, but secondary) -- it's that a selection highlight would have **nothing to confirm**: this step introduces no research-commit action (see `hy:kt` above), so a highlight that can move among 4 tile slots but can never trigger anything meaningful would be exactly the purposeless-scaffolding-for-its-own-sake this project's guardrails already reject (`docs/prd/psx-select-start-mapping.md`'s own "no module built with no consumer" reasoning, applied here to "no selection cursor with nothing to select toward"). The menu's open/closed state alone is the real, live, observable thing this step's own scope actually needs and can meaningfully test.
- **Left for Phase 4 step 14**: once a real 20(19)-tech tree and a real science economy exist, a real "pick a tech, spend science" flow becomes meaningful, and *that* is when the D-pad-ownership question (a genuinely new state machine in `rules_tech.c` reading raw D-pad edges itself, per this codebase's per-module edge-detection-ownership precedent, likely needing to suppress or coexist with `cursor.c`'s own D-pad handling while the menu is open) needs a real answer. Recorded here as the concrete extension point, not resolved.

**Select's edge detection and gating, confirmed against `docs/prd/psx-select-start-mapping.md`'s already-settled findings.**

- Edge detection lives in `rules_tech.c` itself: a module-owned `uint16_t g_rules_tech_prev_buttons` (initialized `0xffff`, matching `cursor.c`'s own `g_cursor_prev_buttons` convention exactly), diffed against the current frame's raw `input_get_state().buttons` to compute Select's press edge (`PAD_SELECT`, bit 0, `1<<0`, active-low -- same bit position `docs/prd/psx-select-start-mapping.md` already cited from `psxpad.h`'s standard macros).
- Select is read **unconditionally** -- never gated on `cursor_get_state().mouse_mode`. This isn't re-derived from scratch: `docs/prd/psx-select-start-mapping.md`'s Implementation Decisions already settled this exact question for this exact step, citing step 12's own "accessible en permanence" wording as the reason no mode gate can apply. This step's `rules_tech_update` reads `input_get_state().buttons` directly (the same raw accessor `cursor_update` itself consumes), not `cursor_get_state()` at all -- `rules_tech.c` has no dependency on `cursor.c` whatsoever.

**Rendering: confirmed no font/glyph system exists; placeholder colored `TILE`s, top-left, following the established convention.**

- Direct search of `psx-slipways/` for font/glyph/text-rendering code (`grep -rli "font\|glyph\|text_draw\|draw_text\|char_"`) returns zero matches. No text-rendering capability exists in this port at all yet -- confirmed, not assumed. Readable tech names/costs cannot be displayed this step (matches Phase 5's own scoping: sprite/text extraction is step 17).
- **Placeholder**: 4 `TILE` primitives (one per Era-1 tech slot), arranged in a small fixed grid anchored at the screen's top-left corner -- not an arbitrary choice: both the pitch text ("Research technologies from the top-left corner," `docs/design/slipways-mechanics.md:11`) and `ix[2]`'s own source position (`ra=v(0,0)`, `pico8/lua.lua:970`) independently point at the same screen corner, so even a fully-placeholder rendering choice traces back to something real. Each tile's color reflects a **caller-local**, not module-owned, placeholder "researched" array declared directly in `game_draw.c` (`const bool tech_researched[RULES_TECH_COUNT] = { false, false, false, false };`, commented as "no live science economy exists yet to populate this -- Phase 3 step 13 / Phase 4 step 14") -- this keeps the render call site genuinely reading real (if currently constant) parameters passed into a primitive-drawing loop, the same shape `liaison.c`'s `live.reason`-driven line color already established, without `rules_tech.c` itself owning a fake "is researched" singleton the module has no way to ever set to `true`. Tile size/spacing/colors are v1 UX/rendering choices, not traced art (same framing as `GAME_DRAW_CURSOR_TILE_SIZE`/the click-flash yellow).

**Traceability and interaction-vs-content guardrails, checked explicitly.**

- Every constant this step actually wires (Select's bit position, the Era-1 tech subset's `px`/`lv`/`nk`/`od` fields) is traced to an exact `pico8/lua.lua` line or `unstash` address above. Every constant this step traces but does *not* wire (`gi`, `ek`, `hy:kt`'s debit/mark/era-advance) is explicitly named as traced-but-deferred, not silently dropped.
- Interaction-vs-content: the menu's open/closed toggle mirrors a real, existing source mechanic (`ix[2]`/`cr()`/`pz()` opening a real, live, click-triggered tech list, mid-game) remapped onto a dedicated button -- not a new capability invented for this port, the same conclusion `docs/prd/psx-select-start-mapping.md` already reached for Select's role in general. The one genuinely new thing this step adds -- the press-to-toggle-closed gesture itself -- is interaction-layer only (how the menu is dismissed), never content (no resource, action, or rule this port's source doesn't already have), and is justified explicitly above per the guardrail's own "in case of doubt, justify explicitly" requirement.

## Implementation Chunks

Tracer-bullet order, pure logic before wiring before rendering before the real emulated proof -- mirroring `liaison.c`'s live-wired chunk shape, not `rules_planets.c`'s/`rules_discovery.c`'s/`effects.c`'s unwired shape, per step 12's own "accessible en permanence" language:

1. **Static Era-1 tech data table.** `rules_tech.h`/`rules_tech.c` gain a `tech_id_t` enum (`TECH_SPACE_FOLDING`, `TECH_GENESEEDS`, `TECH_NANOMATERIALS`, `TECH_DRILLBOTS`, `TECH_COUNT`) and a `tech_t { const char *name; int base_cost; }` static table (name and the traced `od` field only -- `lv`/`nk` are documented in this PRD but not stored as struct fields, since nothing in this step's own scope reads them: `lv` is implicitly "1" for every entry by construction, and `nk`/`fu`/`gi` are wholly deferred, per Implementation Decisions), plus a plain accessor `const tech_t *rules_tech_get(tech_id_t id)`. Host-tested (`host_tests/rules_tech_test.c`, new `test-rules-tech` target): all 4 entries' `name`/`base_cost` match the raw-decoded values above exactly.
2. **Pure open/close toggle step.** `int rules_tech_step(int prev_open, uint16_t prev_buttons, uint16_t buttons)` -- computes Select's press edge (`(~buttons)&prev_buttons&RULES_TECH_PAD_SELECT`, mirroring `cursor_step`'s own idiom exactly) and flips `prev_open` on that edge; a held or released Select does nothing further (this is a pure edge-triggered toggle, no held-state semantics, unlike Circle's press/held/release trio -- Select's job here is simpler by design, matching its "simple, unconditional button press" framing in `docs/plan.md` step 7). No statics, no PSX headers. Host-tested: press toggles open→closed and closed→open; holding Select across multiple frames toggles only once (on the edge, not every frame); a frame with no edge leaves the state unchanged.
3. **Stateful wrapper + real wiring.** `rules_tech_init(void)`, `rules_tech_update(uint16_t buttons)` (threads the module's own static `g_rules_tech_open`/`g_rules_tech_prev_buttons`, calling `rules_tech_step` internally), `rules_tech_get_state(void) -> rules_tech_state_t { int open; }`. `game_update.c` gains exactly one new line, `rules_tech_update(input_get_state().buttons)` (reading the raw accessor directly, not through `cursor_get_state()` -- see Implementation Decisions), alongside `game_init()`'s existing `cursor_init()`/`liaison_init()` calls gaining `rules_tech_init()`. Host-tested: an `rules_tech_update`/`rules_tech_get_state` round trip reproduces `rules_tech_step`'s result across a hand-fed press/release sequence, mirroring `cursor.c`'s own round-trip test style.
4. **Rendering.** `game_draw.c` gains one new block, gated on `rules_tech_get_state().open`, drawing the 4 placeholder `TILE`s top-left as described in Implementation Decisions. Verified via `make psx-slipways-screenshot-pcsx` (manual/scripted Select press) and the still-unmodified `psx-slipways-boot-test-pcsx`.
5. **Headless PCSX test.** New `tools/gen_pcsx_slipways_rules_tech_test_lua.py` + `tools/boot_test_psx_slipways_pcsx_rules_tech.sh` + `psx-slipways-rules-tech-test-pcsx` Makefile target (a genuinely new target, not an extension of `psx-slipways-cursor-test-pcsx`/`-liaison-test-pcsx`, since this exercises a new module's new symbol, mirroring `liaison.c`'s own "new module gets a new target" precedent): injects a real Select press, waits, reads back `rules_tech.c`'s wired `g_rules_tech_open` static from guest RAM, asserts it flips to `1`; injects a second Select press, asserts it flips back to `0` -- proving the real, wired, per-frame toggle under actual emulated SIO0 pad injection, not just that the module compiles and links.

## Testing Decisions

- **What makes a good test here**: assert on observable output through public functions/exported symbols (`tech_t` field values, `rules_tech_state_t.open`, the flat static the PCSX harness reads), never on internal representation -- the same standard every prior PRD in this codebase has used.
- **Fully host-testable** (chunks 1-3, `gcc`, no PSn00bSDK toolchain): the tech data table, `rules_tech_step`, and the stateful wrapper (`rules_tech_update` takes a plain `uint16_t`, no PSX header needed, no dependency on `world.c`/`cursor.c`/`liaison.c` at all -- this module is a leaf, simpler than `liaison.c`'s own host-test dependency chain). New `host_tests/rules_tech_test.c`, new `RULES_TECH_TEST_HOST_SRCS`/`test-rules-tech` Makefile target (`psx-slipways/rules_tech.c psx-slipways/host_tests/rules_tech_test.c` -- no other `.c` files needed, matching `test-cursor`'s own minimal-dependency shape), added to `test`'s prerequisite list and `.PHONY`, per `CLAUDE.md`'s `make test` promise.
- **Not host-testable**: `game_draw.c`'s new `TILE` block (real `psxgpu.h` calls) and the `game_update.c`/`game_init()` wiring lines (trivial, covered indirectly by boot-not-crashing).
