## Problem Statement

`psx-slipways/` (Phase 1 steps 1-2) has a working glue skeleton (`main.c` dispatching to `game_init()`/`game_update()`/`game_draw()`) and host-testable galaxy generation, but it never touches the controller. `docs/plan.md` Phase 1 step 3 calls for reading the pad via PSn00bSDK's own API directly (no cross-runtime abstraction needed). Every later Phase 2 step (✕ toggles mouse mode, ○ simulates a click, Select/Start map to menu/score) needs *something* in `psx-slipways` that already knows the controller's current button state each frame — today nothing does, and `game_update()` has no seam to read it from.

## Solution

Add a small `input` module to `psx-slipways/` that owns the PSn00bSDK pad driver end to end: buffer setup, `InitPAD`/`StartPAD`/`ChangeClearPAD` bootstrap, and a per-frame snapshot of the raw button/D-pad bitmask and pad-connected flag, exposed through one read-only accessor. `main.c` gains exactly one new call (`input_init()`, placed the same way `psx-hello/main.c` places its own `InitPAD`/`StartPAD`, right after video bootstrap and before the game loop starts) and stays otherwise untouched — the per-frame read is triggered from `game_update()` (simulation side) instead of adding a fourth call site to `main.c`'s loop body. No cursor, mode toggle, click, or menu logic is added: this step only makes "what is the pad doing right now" available to code that will consume it starting in Phase 2. Because this touches real PSn00bSDK headers unavailable on the host, correctness is verified by extending the existing PCSX-Redux headless input harness (already proven on `psx-hello`) rather than by a host-gcc unit test.

## Implementation Decisions

- **New module: `input.h` / `input.c`, flat inside `psx-slipways/`** (picked up automatically by `psx-slipways/CMakeLists.txt`'s `file(GLOB _sources *.c)`, same as every other module there). Naming follows the project's established snake_case/`_t` convention (`planet_pos_t`, `galaxy_t`, `rng_t` in `planetgen.h`/`rng.h`), not the PascalCase style used ad hoc in `psx-hello`.
- **Public API** (`input.h`):
  ```
  typedef struct {
      int      connected;  /* 1 if PADTYPE::stat == 0 for port 1, else 0 */
      uint16_t buttons;    /* raw PADTYPE::btn bitmask, active-low, port 1;
                               0xffff (nothing pressed) when disconnected --
                               same convention psx-hello/main.c already uses.
                               Test with the PAD_* macros from psxpad.h. */
  } input_state_t;

  void input_init(void);
  void input_update(void);
  input_state_t input_get_state(void);
  ```
  `input_get_state()` returns by value (the struct is 4-6 bytes with padding — trivially cheap to copy, and returning by value avoids handing out a pointer to module-internal storage that a caller could mistakenly hold across an `input_update()` call). This snippet is illustrative of field names/types, not literal file contents.
- **Raw, active-low bitmask, not a translated/inverted convention.** `buttons` is passed through exactly as PSn00bSDK's `PADTYPE::btn` presents it (0 = pressed, matching the hardware protocol), so callers test it with the same `PAD_CROSS`/`PAD_UP`/etc. macros `psx-hello/main.c` already uses (e.g. `!(state.buttons & PAD_CROSS)`). Inventing a second, active-high convention here would mean every later Phase 2 step re-learns/converts a polarity that doesn't exist in the hardware or in the one proven precedent (`psx-hello`) already in this repo — added indirection with no benefit.
- **No edge/press-release detection in this module.** `input_get_state()` reports only "what is held right now." `psx-hello/main.c` computes its own `pressed = (~btn) & prev_btn` edge entirely inside `main()` using a local `prev_btn` — i.e. even the one existing precedent in this codebase treats edge detection as a *caller* concern, not something the pad-reading layer itself provides. `docs/plan.md`'s own "Reste à trancher" note leaves open whether ○'s click should be edge-triggered, held-duration-triggered, or both (press-and-release pair for drag) — baking any specific edge semantics into this step's API would prejudge that undecided question. Phase 2 step 5/6's own module keeps whatever previous-frame state it needs to compute edges, exactly the way `psx-hello/main.c` already does inline.
- **Buffer setup and driver bootstrap mirror `psx-hello/main.c` exactly**, moved into `input_init()`: `static char pad_buff[2][34];` (module-private, `input.c`-only), `InitPAD(pad_buff[0], 34, pad_buff[1], 34)`, `StartPAD()`, `ChangeClearPAD(0)`. Only port 1 (`pad_buff[0]`) is ever read; the port-2 buffer exists only because `InitPAD`'s signature requires it, matching `psx-hello`'s scope (single standard PS1 pad, no multitap).
- **`main.c` gets exactly one new line: `input_init();`**, called after video bootstrap (`init_context`) and before `game_init()` — the same relative ordering `psx-hello/main.c` uses (video setup, then `InitPAD`/`StartPAD`, then the loop). This is judged the same category of "platform bootstrap, not business logic" that `psx-main-skeleton`'s PRD already used to justify keeping video init inline in `main.c`, and that PRD's own "no pad init in `main.c`" call explicitly named this exact step (step 3) as the one expected to add it — so this isn't scope creep on that decision, it's that decision's anticipated follow-through. `main.c`'s loop body (`game_update(); game_draw();`) is **not** modified.
- **The per-frame read (`input_update()`) is called from `game_update()` (in `game_update.c`), as its first statement**, not from `main.c`'s loop. This keeps `main.c` at exactly the three dispatch seams `psx-main-skeleton` established (plus the one bootstrap call above), rather than adding a fourth per-frame call site there; every future per-frame subsystem this port adds can follow the same pattern (its own `_update()` called from `game_update()`, not from `main.c`) without ever re-opening `main.c` again. `game_update()`'s body becomes exactly `input_update();` — no button state is read or acted on yet; that starts in Phase 2.
- **Internal test-visible state is two flat top-level statics in `input.c`, not one struct symbol.** Mirroring `psx-hello/main.c`'s own approach (`cursor_x`, `cursor_y`, `mouse_mode`, etc. as separate top-level `static` scalars, each independently visible as its own symbol+address in the linker `.map` file), `input.c` keeps:
  ```
  static int     g_pad_connected;
  static int32_t g_pad_buttons; /* widened from the real uint16_t on purpose, see below */
  ```
  `input_get_state()` composes the public `input_state_t` (with its real `uint16_t buttons` field) from these on each call. Decoupling the public struct shape from this internal representation means a later step could change the internal storage (e.g. if per-button edge tracking eventually moves into this module after all) without breaking the public API or the test harness's symbol names.
- **`g_pad_buttons` is deliberately widened to `int32_t` in its test-visible backing storage, even though the real hardware field is 16 bits.** This lets the boot-test harness (below) reuse the existing `readS32` helper in `tools/gen_pcsx_hello_input_test_lua.py`'s generated Lua unmodified, instead of adding a new 16-bit memory-read helper for one field. No information is lost: PSn00bSDK's pad button bitmask never uses more than its 16 real bits, so the widen/narrow round-trip through `int32_t` is exact and unambiguous. The *public* `input_state_t.buttons` stays `uint16_t` regardless — this widening is purely an internal test-visibility convenience, not a change to the type callers see.
- **No constant or game-design value is introduced by this step.** Nothing here needs tracing to `docs/design/slipways-mechanics.md` — button *meaning* (mouse-mode toggle, click, menu) is entirely Phase 2's concern; this step only reads raw hardware state. Checked explicitly against the plan's traceability guardrail.
- **Interaction-vs-content guardrail, checked explicitly.** Reading raw pad state adds no player-facing capability at all (no cursor, no input event, nothing observable in `game_draw()`, which stays untouched) — it's pure infrastructure one layer below where the plan's interaction-layer allowance (cursor/toggle/click) even starts. Nothing here required the "ambiguous → treat as content, forbidden until justified" fallback; there is no ambiguity to resolve.

## Implementation Chunks

1. **`input` module + wiring.** `input.h`/`input.c` (bootstrap + per-frame snapshot + accessor), one new line in `main.c` (`input_init()`), one new line in `game_update.c` (`input_update()`). Buildable via the existing `make psx-slipways` (PSn00bSDK cross-build) target with no other changes. Nothing consumes `input_get_state()` yet — this chunk's own boot-test extension (chunk 2) is what proves it works.
2. **PCSX-Redux input-driven boot-test extension**, reusing chunk 1's build output. New `tools/gen_pcsx_slipways_input_test_lua.py` (map-symbol lookup + Lua driver generation, mirroring `tools/gen_pcsx_hello_input_test_lua.py`), new `tools/boot_test_psx_slipways_pcsx_input.sh` (Xvfb + timeout + pcsx-redux invocation, mirroring `tools/boot_test_psx_hello_pcsx_input.sh`), and a new Makefile target `psx-slipways-input-test-pcsx`. Depends on chunk 1 only for the symbols it reads (`g_pad_connected`, `g_pad_buttons`, plus a `test_harness_ready` boot marker — see Testing Decisions).

## Testing Decisions

- **Not host-gcc-testable, and that's expected, not a gap** — same situation `psx-main-skeleton`'s PRD already documented for `main.c`'s video bootstrap, now applying to pad bootstrap for the same reason: `input.c` calls real PSn00bSDK APIs (`InitPAD`, `StartPAD`, `ChangeClearPAD`, the `PADTYPE`/`PAD_*` types from `psxpad.h`) that don't exist as headers on the host and can't be meaningfully stubbed without testing a fake instead of the real driver contract. Unlike `planetgen.c` (Phase 1 step 2), there is no pure-logic core here to extract and unit-test in isolation — the entire module *is* the hardware boundary. `make test-planetgen`'s pattern is deliberately not reused for this reason, per user story 15.
- **What is realistically checkable: the exposed state actually reflects real (emulated) controller input**, verified headlessly by extending the already-proven PCSX-Redux input harness (`tools/boot_test_psx_hello_pcsx_input.sh` / `tools/gen_pcsx_hello_input_test_lua.py`) rather than inventing a new testing technique:
  - `tools/gen_pcsx_slipways_input_test_lua.py` reads `psx-slipways/build/slipways.map`, resolves `g_pad_connected`, `g_pad_buttons`, and `test_harness_ready` to addresses (same `WANTED`-list/regex approach as the `psx-hello` generator), and emits a Lua driver.
  - The generated driver waits for boot (`test_harness_ready == 0x1eadbeef`, same marker convention — see below), then asserts `g_pad_connected == 1` (a pad is present under PCSX-Redux's default SIO0 setup, same as the existing `psx-hello` harness already relies on implicitly), then uses `PCSX.SIO0.slots[1].pads[1].setOverride(BTN.UP)` to hold D-pad Up and asserts `g_pad_buttons & PAD_UP == 0` (bit clear = pressed, active-low) via `readS32(G_PAD_BUTTONS_ADDR)`, then `clearOverride` and asserts the bit sets again (`& PAD_UP ~= 0`). This directly exercises "the pad read works and reflects real input" (the task's own success criterion) without touching anything Phase 2 owns — no cursor position, no mode flag, no click event exists to assert on, because this step doesn't create any.
  - `tools/boot_test_psx_slipways_pcsx_input.sh` mirrors `tools/boot_test_psx_hello_pcsx_input.sh`'s structure exactly (prerequisite checks, `Xvfb`, `--dofile`, exit-code propagation) pointed at `psx-slipways/build/slipways.cue`/`.map`.
  - New Makefile target `psx-slipways-input-test-pcsx`, added to the existing `.PHONY` list alongside `psx-slipways-boot-test-pcsx`.
- **A `test_harness_ready` boot marker is added to `main.c`, mirroring `psx-hello/main.c`'s own `static volatile int test_harness_ready` pattern exactly** (declared and set to `0x1eadbeef` right after `input_init()`, before the loop starts). This is test-support plumbing already established as acceptable at this exact layer by the one existing precedent in this repo — it's not game logic and not "debug text," just a boot-reached signal the headless harness polls for instead of guessing a fixed frame count.
- **Not extended in this step**: `psx-slipways-boot-test-pcsx` (the existing boot-only smoke test, log-grep on `psxgpu: setup done`) stays as-is — this PRD adds a second, separate, input-driven target rather than folding pad assertions into the boot-only one, matching how `psx-hello` itself keeps `psx-hello-boot-test-pcsx` (boot-only) and `psx-hello-input-test-pcsx` (input-driven) as two distinct targets rather than merging them.
- **Prior art reused as-is**: `tools/gen_pcsx_hello_input_test_lua.py` (symbol-resolution approach, `readS32` helper, `waitFrames`/`press`/`assertEq`/`assertRange` helper shape, `test_harness_ready` polling pattern) and `tools/boot_test_psx_hello_pcsx_input.sh` (script structure). `PCSX.SIO0.slots[...].pads[...].setOverride`/`clearOverride` is the same real SIO0-protocol injection mechanism already validated end-to-end for `psx-hello`.

## Out of Scope

- Cursor position, movement, or any pixel-space state (`docs/plan.md` Phase 2 step 5) — this step exposes only the raw button/D-pad bitmask, nothing derived from it.
- Mouse-mode toggle logic (✕ bascule on/off) — Phase 2 step 5.
- Click simulation (○) or the still-undecided press/release-pair-vs-instantaneous-click semantics flagged in `docs/plan.md`'s "Reste à trancher" note — Phase 2 step 6. This step deliberately adds no edge/press-release detection that step 6 would then have to work around or reuse incorrectly.
- Select/Start menu/score mapping — Phase 2 step 7.
- Any consumption of `input_get_state()`'s value beyond calling it once per frame to keep the snapshot fresh — `game_update()` does not branch on any button in this step.
- Any change to `game_draw()` — nothing here is observable on screen.
- Multi-controller / multitap support, analog stick reading — not asked for anywhere in `docs/plan.md` (PS1 standard pad only, no stick used, per the plan's own opening line).
- A host-gcc unit test target for this module (see Testing Decisions for why one isn't meaningful here).
- Any change to `psx-hello/` (left untouched, per `CLAUDE.md` and prior PRDs).
- Folding this step's assertions into the existing boot-only `psx-slipways-boot-test-pcsx` target — kept as a separate, additional target instead (see Testing Decisions).

## Further Notes

- **Where edge/press-release detection should probably live, for step 6's benefit later**: given this step deliberately keeps `input.c` state-only (no previous-frame comparison), the natural place for that logic is whichever module Phase 2 step 5/6 introduces for cursor/click handling — it would keep its own `prev_buttons` (obtained by comparing two consecutive `input_get_state()` calls) exactly the way `psx-hello/main.c` already does inline with `prev_btn`. This PRD doesn't create that module or pre-decide its name; it's flagged here only so step 6's own PRD has a documented starting opinion instead of re-deriving it.
- **Why `input_get_state()` returns by value instead of a `const input_state_t *`**: the struct is a couple of scalar fields (no arrays, no large buffers, unlike `galaxy_t`/`neighbor_graph_t` in `planetgen.h`, which are correctly passed by pointer because they're genuinely large). Returning by value avoids any question of whether a caller may hold onto the pointer across an `input_update()` call sequencing hazard — there is none to reason about if there's no pointer.
- This step's `int32_t`-widening trick for `g_pad_buttons` is a narrow, explicitly-scoped convenience for this one field in this one test harness; it isn't proposed as a general pattern for future PSX modules exposing 16-bit hardware state to tests, and a later step should re-decide it case by case rather than assume it's now "the way."
