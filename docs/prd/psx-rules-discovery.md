## Problem Statement

`docs/plan.md` Phase 3 step 10 calls for `rules_discovery.c` : "coût (3 crédits, 3 mois), portée de sonde (seuil 0.19, étendu à 0.27 avec *space folding*), tirage planète vide (~45%) — RNG injecté pour tests déterministes." Nothing in `psx-slipways/` currently models probing or discovery: `world.c`'s `galaxy_t` (Phase 1 step 2) is positions only, with no per-planet discovered/colonized/type state of any kind, and `rules_planets.c` (Phase 3 step 8, `docs/prd/psx-rules-planets.md`) deliberately stayed an unwired, pure-data module covering only 3 of the 10 documented planet types. Re-reading `pico8/lua.lua`'s `mz` class (the probe entity) directly surfaces a genuine discrepancy the plan's own one-line spec inherited from `docs/design/slipways-mechanics.md` §4: the source's probe entity (`mz`, `pico8/lua.lua:752-761`) sets `fp=1`, and `fp` is the literal months-argument passed to the game clock (`fm:nx(self.fp or 0)`, the commit function `d_()`, line 571; `hy:nx(hx)` accepts `hx` in months, lines 1204-1209) — the probe costs **3 credits and 1 month**, not 3 months. Both the design doc's prose ("et 3 mois de temps") and the plan's own one-liner ("3 crédits, 3 mois") state 3 months; the source data disagrees. Per this project's traceability guardrail ("une valeur manquante ou ambiguë se documente... et se résout en relisant `pico8/lua.lua` — jamais par une valeur 'raisonnable' inventée"), source wins: this PRD ports 1 month, not 3, and flags the correction rather than silently matching the plan's wrong number.

A second, structural question the task framing raises: is this step's "portée de sonde" (0.19/0.27) the same underlying source value as `world.h`'s existing `WORLD_NEIGHBOR_RANGE_SQ`, or a distinct constant needing its own definition? And does this step introduce the first per-planet "discovered" state in the codebase, or does it stay a pure, unwired formula module like `rules_planets.c`? Both are resolved from source in this PRD (see Implementation Decisions), not assumed.

## Solution

Add `psx-slipways/rules_discovery.h`/`rules_discovery.c`: a pure, host-testable C module (no PSX headers, no dynamic allocation, Q16.16 fixed-point, RNG injected via the project's existing `rng_t`, exactly the conventions `rules_planets.c`/`planetgen.c` already established) covering **only the three things `docs/plan.md`'s step 10 one-liner actually names**: the probe's cost (as two named integer constants, source-corrected), the probe's launch-range gate (a pure function reusing `world.h`'s existing `WORLD_NEIGHBOR_RANGE_SQ` directly — confirmed below to be the literal same traced source value and even the same source expression `world.h`'s own comment already cites, not a coincidentally-equal number), and the empty-planet roll (`jo:hh`'s `jo.ir()<0.45` test, faithfully porting `jo.ir`'s actual generator — a stateful, mean-reverting random walk, `jf(0.8,0.5)`, not a plain uniform `Bernoulli(0.45)` draw — with its mutable bias state threaded explicitly by the caller alongside an injected `rng_t`, so a test can reproduce an exact sequence deterministically).

Everything else `jo:hh`/`mz` touch is explicitly out of scope, for reasons traced to source, not convenience: the *type* actually drawn when a probe isn't empty (`jo.oc()`, `gn(df,2,...)`) needs rarity data for all 10 documented planet types plus a stateful, depleting, anti-repeat weighted pool — `rules_planets.c` only has 3 of those 10 types today, so a faithful type draw is structurally impossible until Phase 4 step 14 extends it; the plan's own step 10 wording itself only says "tirage **planète vide**" (the empty/non-empty roll), never "tirage de type," which lines up exactly with what's actually portable right now. The probe's reveal-sweep radius (`mz:pr`/`mz:kz`, `oi=ov("space folding",29,35)`) is a visually-scaled *pixel* radius for an on-screen circle animation — a different quantity from the *normalized-world, squared-distance* launch-range gate this step ports, and the design doc's own §4 text warns explicitly against confusing the two ("à ne pas confondre"). And, following the exact reasoning `docs/prd/psx-rules-planets.md` and `docs/prd/psx-liaison-validity.md` already established for their own out-of-scope boundaries, no live per-planet "discovered" state, no probe entity/animation, and no wiring into `game_init`/`game_update`/`game_draw` are added here: `docs/plan.md`'s step 10 wording has none of step 9's ("branché sur l'événement clic de la Phase 2") live-wiring language — it reads exactly like step 8's formula-only phrasing — and no live "founded/colonized planets" list exists anywhere in this port yet (colonization's actual commit mechanic, `jo:hu`/`jo:fe`, has no assigned step at all — flagged in Further Notes, not invented here). This module is therefore, like `rules_planets.c`, **not wired into `game_init`/`game_update`/`game_draw`** — it compiles into the real PSn00bSDK cross-build via the flat `file(GLOB _sources *.c)` glob with zero caller, exactly matching that precedent.

## Implementation Decisions

**Probe cost — corrected from the plan's own stated value, traced directly to source.**

- `mz`'s data table (`pico8/lua.lua:752-761`): `od=3,fp=1,` (line 758) — `od` is the generic cost field (`fm:lu(self.od)` debits it, the same field `rules_planets.c`'s job costs use); `fp` is the generic months-cost field.
- The generic action-commit function `d_(self)` (`pico8/lua.lua:569-576`): `if not self.et and fm:lu(self.od) then self:ks(self.dq or "ph") fm:nx(self.fp or 0) rn(self.ik or 54) return true ...`. This is called from `mz:ey()` (`pico8/lua.lua:774-775`, `self.p_ = self.t<15 or not d_(self)`) — the probe's real cost/time commit happens exactly once, ~15 frames after the target is chosen (giving the too-far check in `mz:hq`, line 767-771, time to set `self.et` first).
- `fm:nx(hx)` is `hy:nx(hx)` (`fm`/`hy` share the same interface/fields — `nz`, `ge`, `jk`, `lo`, `yr`, cross-checked against `pj:hb`'s score-screen read of `fm.nz`/`fm.ge`/etc., `pico8/lua.lua:847`): `pico8/lua.lua:1204-1209`, `self.lo+=hx ... if self.lo>kx then ... self:hk() end` — `hx` is unambiguously a **months** argument (the design doc's own §2 confirms this: "`hy:nx(hx)` avance l'horloge de `hx` mois").
- **Conclusion**: the probe costs `od=3` credits and `fp=1` month — not the "3 crédits, 3 mois" both `docs/design/slipways-mechanics.md` §4 and `docs/plan.md`'s step-10 one-liner state. Ported as `RULES_DISCOVERY_PROBE_COST_CREDITS = 3` and `RULES_DISCOVERY_PROBE_COST_MONTHS = 1`, plain `#define`s (no formula, no tech multiplier touches either field — `hy:nx`'s "time compression" tech changes the year-tick *threshold* `kx`, not the incoming `hx` value itself, an unrelated global time-system rule already out of scope here), each citing this exact source trail. This is this PRD's single highest-value finding — see Further Notes for the recommended (not-in-scope) design-doc/plan correction.

**Probe launch-range gate — confirmed to be the literal same source value `world.h`'s `WORLD_NEIGHBOR_RANGE_SQ` already cites, reused directly.**

- `mz:hq(...)` (`pico8/lua.lua:767-771`): `nq,self.ij=ij(self.p,self.ox) if nq>ov("space folding",0.19,0.27) then self.et=mz.jj end` — `self.p` is the probe's target position, `self.ox` is the list of "founded" (colonized) planets (set in `mz:pq()`, line 764-766: `self.ox=jp(hv,function(p) return p.fx end)`, filtering the global live-entity list `hv` — lines 153/156/163 — to planets whose `fx` flag is true; `fx` is set in the colonization-commit path, `pico8/lua.lua:458`).
- `ij(p,j_)` (`pico8/lua.lua:351-358`): returns the **minimum squared distance** (`d=#(p-o.p)`, using `km:__len`'s squared-magnitude semantics, `pico8/lua.lua:119-120` calling `km:rg`'s dot product, lines 110-112 — the exact same "`#v` is squared, not linear" fact this project already relied on for `WORLD_NEIGHBOR_RANGE_SQ` itself and for `liaison.c`'s `LIAISON_RANGE_SQ`) from `p` to the nearest point in list `j_`.
- **This is the literal same traced call `world.h`'s own existing comment already cites**: `world.h:22-29` reads "*Squared neighbor-probe-range threshold, traced to `pico8/lua.lua:767-770` (`mz:hq`'s base probe range -- 0.19 squared units -- before any 'space folding' tech...)*" — i.e. `WORLD_NEIGHBOR_RANGE_SQ` was **already** defined by tracing this exact probe-range mechanic, reused by `world.c` for its own (rendering-only) neighbor graph. This step's probe-range gate is not a coincidentally-equal number; it is the same traced constant, at its own original, intended use. **Resolution: this step reuses `WORLD_NEIGHBOR_RANGE_SQ` directly (`#include "world.h"`), not a second `RULES_DISCOVERY_*` constant** — defining a duplicate would create exactly the drift risk a single source of truth exists to prevent.
- The "space folding" extension (`0.19`→`0.27`) is left unmodeled, matching `WORLD_NEIGHBOR_RANGE_SQ`'s own existing scope (no tech system exists yet, `rules_tech.c` is step 12) and `LIAISON_RANGE_SQ`'s identical treatment of its own `0.5`→`1.08` extension (`docs/prd/psx-liaison-validity.md`).
- **Function shape, decoupled from any live global state**: `bool rules_discovery_probe_in_range(planet_pos_t target, const planet_pos_t *founded_positions, int founded_count)` — computes the minimum squared distance from `target` to every position in `founded_positions` (mirroring `ij()`'s own loop shape, and `planetgen_fits`'s/`liaison_pick_planet`'s existing squared-distance loop idiom in this codebase) and returns `min_dist_sq <= WORLD_NEIGHBOR_RANGE_SQ` (source's own comparison is `nq > threshold` → too far, so in-range is `<=`, matching `liaison.c`'s identical boundary convention for its own range check). `founded_count == 0` always returns `false` (no founded planet exists to be "in range" of — mirrors `ij`'s own `32767` sentinel-minimum behavior when its input list is empty, and matches that this situation cannot actually arise in source anyway, since `bg:ldown` special-cases the very first click into placing the wormhole rather than launching a probe). This is a **caller-supplied position list**, not a read of any live galaxy/colonization singleton — see "Module shape" below for why.

**Empty-planet roll — the actual stateful generator, RNG-injected, not a simplified coin flip.**

- `jo:hh()` (`pico8/lua.lua:407-411`): `self.nk = jo.ir()<0.45 and df.ll or jo.oc() ...` — the empty/non-empty branch this step ports is exactly `jo.ir()<0.45`.
- `jo.ir` is assigned **once**, at galaxy-generation time (`bw(n)`, `pico8/lua.lua:749-751`: `jo.oc,jo.ir = gn(df,2,jf(0.5,dk.en)), jf(0.8,0.5)`) — a single closure instance reused for **every** discovery for the rest of that game session, not re-created per probe.
- `jf(n_,b)` (`pico8/lua.lua:333-338`): returns a closure over a mutable `b`. Each call: `v = rnd(1-abs(b)) + max(b,0)`; then `b += (0.5-v)*n_`; returns `v`. This is a **mean-reverting random walk** (design doc §3's own description, confirmed accurate), not `rnd(1)`. For `jo.ir = jf(0.8, 0.5)`: `n_=0.8`, initial `b=0.5` — both literal, not randomized or difficulty-dependent (design doc's "indépendante de la difficulté" is confirmed: `jf(0.8,0.5)` takes no `dk.en` argument, unlike `jo.oc`'s `jf(0.5,dk.en)`).
- **Ported as**: `typedef struct { fixed_t bias; } rules_discovery_empty_roll_t;` with `void rules_discovery_empty_roll_init(rules_discovery_empty_roll_t *state)` (sets `bias = FX_ONE/2`, i.e. `0.5`, the literal initial `b`) and `bool rules_discovery_roll_empty(rules_discovery_empty_roll_t *state, rng_t *rng)`, which: draws a fixed-point uniform value in `[0, FX_ONE - |bias|)` via `rng_next_range` reused exactly as `planetgen_generate` already does (treating a `fixed_t` span's raw `int32_t` value directly as `rng_next_range`'s exclusive bound — the established idiom, `planetgen.c:33-34`), adds `max(bias, 0)` to get `v`; updates `bias += fixed_mul(fixed_sub(FX_ONE/2, v), FX_ONE_POINT_8_CONST)` (`n_=0.8` in Q16.16); returns `v < FX_ONE*45/100` (`0.45`). The state is explicitly threaded by the caller across repeated calls (not reset per call), matching `jo.ir`'s own one-time-created, session-long closure shape — a direct mirror of `rng_t` itself being threaded through `planetgen_generate`, satisfying `docs/plan.md`'s own "RNG injecté pour tests déterministes" phrasing for this step.
- **A Monte-Carlo regression test** (many rolls from a fixed seed, asserting the empirical empty-rate lands within a documented tolerance band of `0.45`) is included specifically because this generator's stationary distribution isn't something to re-derive by inspection — the exact tolerance band is an empirical, implementation-time choice (same posture `docs/plan.md`'s own Phase 1 step 2 already takes for `planetgen`'s BFS-connectivity rate, "un taux de déconnexion attendu" bounded empirically, not analytically), not a "reasonable" number invented here.

**Module shape and non-wiring — resolved from the plan's own wording, not assumed by analogy.**

- `docs/plan.md`'s step 10 one-liner has **no live-wiring language** — no "branché sur..." phrase, unlike step 9's (`liaison.c`) explicit "branché sur l'événement clic de la Phase 2." It reads exactly like step 8's (`rules_planets.c`) formula-listing phrasing. Combined with the fact that a faithful *type* draw is currently impossible (needs all 10 planet types; `rules_planets.c` has 3), and that no live "founded planets" or "probe entity" state exists anywhere in this port, this step follows `rules_planets.c`'s **unwired pure module** precedent, not `liaison.c`'s live-wired one.
- **No new per-planet persistent state is introduced.** `world.c`'s `galaxy_t` gains no "discovered" field, no "founded" field, no type field. `rules_discovery_probe_in_range` takes a caller-supplied `planet_pos_t` array for "founded planets" rather than reading any live galaxy/colonization singleton, for the same reason `rules_planets.c`'s functions take booleans as parameters rather than reading tech state: no real, live source of that data exists yet anywhere in this port, and inventing a placeholder one (e.g. an always-empty "founded" list baked into `world.c`) would be exactly the kind of "reasonable invented" state the traceability guardrail forbids for game-rule state, not just game-rule constants.
- **A genuine gap this research surfaced, flagged but not filled here**: `jo:hu`/`jo:fe` (the actual "choose a colonization job, commit a planet to `"ly"` state" mechanic) has no assigned step anywhere in `docs/plan.md`'s Phase 3 list — step 8 ports job *data* only, step 10 (this step) ports discovery-adjacent *formulas* only, and no step explicitly says "wire up choosing and committing a colonization job." Per the "pas de contenu retiré silencieusement" guardrail this is worth surfacing, not silently working around — see Further Notes. It does not block this step, since this step's three formulas (cost, range, empty-roll) are all colonization-state-blind in source too (`mz:hq`'s range check only needs `self.ox`, a plain position list; `jo:hh`'s empty-roll needs nothing about colonization at all).
- **File layout, `psx-slipways/` (flat, picked up by the existing `file(GLOB _sources *.c)` in `psx-slipways/CMakeLists.txt`, compiling into the real PSn00bSDK cross-build unused, exactly like `rules_planets.c`/`planetgen.c` before their own consumers existed)**:
  - `rules_discovery.h` / `rules_discovery.c` — the module itself.
  - `host_tests/rules_discovery_test.c` — host tests (see Testing Decisions).

**Data model and function signatures.**

- `RULES_DISCOVERY_PROBE_COST_CREDITS` / `RULES_DISCOVERY_PROBE_COST_MONTHS` — plain `int` `#define`s, cited above.
- `bool rules_discovery_probe_in_range(planet_pos_t target, const planet_pos_t *founded_positions, int founded_count)` — cited above; `#include "world.h"` for `WORLD_NEIGHBOR_RANGE_SQ` and `planetgen.h` (via `world.h`) for `planet_pos_t`; no dependency on any function `world.c` defines, no link-time dependency on `world.c` itself (the macro is header-only).
- `rules_discovery_empty_roll_t` / `rules_discovery_empty_roll_init` / `rules_discovery_roll_empty` — cited above; depends on `fixed.h` and `rng.h` only.
- No `resource_id_t`/`planet_type_id_t` dependency at all — this module never resolves *which* type a non-empty discovery becomes, so it has no reason to depend on `rules_planets.h`.

## Implementation Chunks

Tracer-bullet order, pure formulas only, no wiring:

1. **Probe cost constants.** `RULES_DISCOVERY_PROBE_COST_CREDITS`/`RULES_DISCOVERY_PROBE_COST_MONTHS` in `rules_discovery.h`, each with the full source citation from Implementation Decisions in its comment. Tests: both constants equal their traced values (`3`, `1`) — including a test whose name/comment explicitly documents that this is `1`, not the `3` the plan/design-doc text states, so the correction is asserted, not just narrated in the PRD.
2. **Probe launch-range gate.** `rules_discovery_probe_in_range`, reusing `WORLD_NEIGHBOR_RANGE_SQ`. Tests: a founded planet at exactly the threshold distance is in-range (`<=`); one epsilon beyond it is out of range; the nearest of several founded planets is the one that governs the result (a far founded planet doesn't wrongly report "too far" when a near one is actually in range); `founded_count == 0` always returns `false`.
3. **Empty-roll generator.** `rules_discovery_empty_roll_t`/`_init`/`rules_discovery_roll_empty`, porting `jf(0.8,0.5)` plus the `<0.45` test. Tests: same-seed-and-same-initial-state produces an identical roll sequence (mirroring `planetgen_test.c`'s `test_same_seed_is_deterministic`); the generator's `bias` field visibly evolves across calls (not a stateless/constant-probability stand-in); a hand-computed first few rolls from a fixed seed match values derived by manually stepping `jf`'s formula.
4. **Empty-roll statistical regression.** A Monte-Carlo test: many thousands of rolls from a fixed seed, asserting the empirical empty rate falls within an implementation-chosen tolerance band around `0.45` (the exact N and tolerance are decided during implementation, empirically, matching Phase 1 step 2's own BFS-connectivity-rate precedent — not invented here). Guards against a future edit to `jf`'s constants (`0.8`, `0.5`, `0.45`) silently drifting the game's discovery odds without any test noticing.

## Testing Decisions

- **What makes a good test here**: assert on this module's observable output (constant values, function return values, the roll generator's externally-visible `bias` field and its returned booleans) — never on internal representation beyond what's already a named, documented struct field. Mirrors `rules_planets_test.c`'s and `planetgen_test.c`'s existing style.
- **Modules tested**: `rules_discovery.c` (all public data and functions, per the chunk breakdown above). Reuses `fixed.h` (Q16.16), `rng.h` (`rng_t`/`rng_next_range`), and `host_tests/t.h` (the existing PASS/FAIL harness) as-is.
- **Prior art reused**: `host_tests/planetgen_test.c`'s `test_same_seed_is_deterministic` pattern, directly extended to the empty-roll generator; `host_tests/rules_planets_test.c`'s pattern of testing traced constants against hand-computed source-derived values; `docs/plan.md` Phase 1 step 2's own precedent for an empirically-bounded statistical test (the BFS-connectivity rate over ~2000 seeds), reused here for the Monte-Carlo empty-rate check.

## Further Notes

- **The single highest-value finding**: the probe's real cost is **3 credits, 1 month**, not the "3 crédits, 3 mois" both `docs/design/slipways-mechanics.md` §4 and `docs/plan.md`'s own step-10 one-liner state — traced unambiguously to `mz`'s `od=3,fp=1` (`pico8/lua.lua:758`) flowing through `d_()`'s `fm:nx(self.fp or 0)` (line 571) into `hy:nx(hx)`'s months semantics (lines 1204-1209, itself confirmed by the design doc's own §2 prose describing `hy:nx`). Recommended, as a small separate follow-up (not part of this PRD, consistent with prior PSX-side PRDs' own practice of flagging design-doc corrections without making them): both `docs/design/slipways-mechanics.md` §4 ("et 3 mois de temps") and `docs/plan.md`'s Phase 3 step 10 line should be corrected to "1 mois."
- **A second, smaller finding worth a reader's attention**: `jo.ir` (the empty-roll generator) is created **once per game session**, not once per probe — a future step wiring a live probe entity must hold a single, persistent `rules_discovery_empty_roll_t` for the whole game (analogous to how `world.c` holds one `rng_t`-seeded galaxy for the whole session today), not re-initialize it per probe launch. Re-initializing per probe would silently change the game's actual discovery odds, since the mean-reverting walk's bias carries information across calls by design.
- **The colonization-commit gap**: no step in `docs/plan.md`'s current Phase 3 list (8: `rules_planets.c` data, 9: `liaison.c` slipway validity, 10: this step, 11: `effects.c`, 12: `rules_tech.c`, 13: `rules_economy.c`) explicitly owns wiring up "choose a colonization job for a discovered planet, commit it to colonized state" (`jo:fe`/`jo:hu`). This is a genuine content-tracking gap this PRD's research surfaced, not one it resolves — flagged per the "pas de contenu retiré silencieusement" guardrail, most plausibly `rules_economy.c`'s territory (it already owns "conditions de fin" and the closest existing per-colony state discussion) or a Phase-3-step-10-adjacent follow-up, but this PRD doesn't bind any future step to that placement.
- **Where a future live probe step should plug in**: three independent, already-composable primitives — cost constants (read directly), `rules_discovery_probe_in_range` (call with the live cursor/target position and whatever "founded planets" list that future step maintains), and `rules_discovery_empty_roll_t` (create once per game session, call `rules_discovery_roll_empty` once per successful discovery). None of their signatures need to change when that step lands; only real call sites need to be added.
- `rules_discovery.h`'s functions are deliberately scoped to exactly the three things `docs/plan.md`'s step 10 names, not pre-sized for the eventual live probe mechanic (e.g. no placeholder "probe state" struct, no reserved "planet type" output field) — consistent with this project's established preference (`rules_planets.h`'s enums, `planetgen.h`'s `PLANETGEN_MAX_PLANETS`) for real, traced values over speculative headroom.
